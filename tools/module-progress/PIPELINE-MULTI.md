# 双机并行车道协议（Mac A 调度 + Mac B 执行）

> 本文是 `PIPELINE.md` 的**双机扩展**，不是替代。
> 单机流程、硬性要求、组批协议、验证层级全部沿用 `PIPELINE.md`，本文只补充
> 「两台机器如何分工、冲突如何在结构上被消除、跨机车道怎么流转」。
>
> **机器相关的运行参数（配额、load 阈值、节流阈值）不进本文件**，
> 各自放在本机 gitignored 的 `.dev-agent/PIPELINE.local.md`。
> 本文只放协议与可复用原理。

---

## 0. 一句话架构

```
        ┌──────────────────────────────────────────────────────┐
        │  Mac A —— 调度者（唯一写集成头）                       │
        │  cron: 0 8-20 * * *      每小时 1 轮                  │
        │  持有：lanes.json · 集成头 · Flyway 版本号分配权         │
        │  职责：plan → 签发票据 → 收割 → 并入 → L2 → push        │
        └───────────────────┬──────────────────────────────────┘
                            │  git push 车道分支（分支即票据）
                            ▼
        ┌──────────────────────────────────────────────────────┐
        │  Mac B —— 执行者（只干活，不合并）                      │
        │  cron: */5 8-20 * * *    每 5 分钟轮询（空转零成本）    │
        │  持有：自己的 remote-claims.json（gitignored）          │
        │  职责：领票 → 建 worktree → 跑 worker → L1 → push       │
        └──────────────────────────────────────────────────────┘
```

**一句话原则：只让一台机器写共享状态。** 所有跨机冲突都源于「两个写者」，
把写者收敛到一个，冲突就**在结构上消失**，而不是靠分区表去赌。

## 1. 四条不变式（这套设计成立的全部理由）

| # | 不变式 | 谁持有 | 消除了哪类冲突 |
| - | --- | --- | --- |
| I1 | 集成头 `integration/module-dev` **只有 Mac A 能写** | Mac A | 两机 push 同一分支的竞态、合并冲突 |
| I2 | Flyway 版本号**只有 Mac A 分配** | Mac A | 两机扫本地树 → 分配出同一个 V 号 |
| I3 | 在途车道表 `lanes.json` **只有 Mac A 写** | Mac A | 同 L3 兄弟模块被两机同时开工 |
| I4 | 台账 `module-progress.md` **只有 Mac A 写** | Mac A | 465 行版本化表的双写冲突 |

> **I2 为什么会撞**：`lane.mjs` 的 `allocateVersions()` 扫的是**本机工作树**里
> `backend/services/*/src/main/resources/db/migration` 下已存在的 `V\d+__`，
> 再加上 `lanes.json` 里已预分配的号。两台机器的工作树各自独立 →
> 各自算出「下一个可用号」→ **必然重合**。
> 车道刚排出来时文件还没落盘，所以连「扫磁盘」都救不了，只有单点分配能根治。
>
> **I3 为什么会撞**：`pickModules()` 里的 `usedL3` 是**函数内局部 Set**，
> 每次 `plan` 调用从空开始。它能防同一次调用内撞，**防不住**「上一批还在跑 + 这一批又排」。
> 单机时这是已知缺陷；双机时它变成「两机同时排同一 L3」——共表、共端点前缀、共前端路由。
> 收敛到单一调度者后，调度者能看见**两台机器**的全部在途车道，I3 才真正成立。

## 2. 冲突面矩阵：双机同构 vs 单调度

| 冲突面 | 单机如何解决 | 双机同构会怎样 | 本方案 |
| --- | --- | --- | --- |
| Flyway 版本号 | `plan` 预分配并写 `lanes.json` | 两机各扫本地树 → **同号** → 合并后 Flyway 报 *Found more than one migration* | I2 结构性消除 |
| 同 L3 兄弟模块 | `usedL3` 调用内去重 | 跨调用 + 跨机双重失效 → **同表同路由** | I3 结构性消除 |
| 累积白名单 `apps/web/src/lib/api-proxy.ts` | 协议规定「求并不是二选一」 | 两机各改 → 硬冲突；**取错一侧会静默删掉已交付路由**（页面 404 且 typecheck/lint/vitest 全绿） | 只有 A 合并，A 按协议求并 |
| 集成头 push | 单一分支单一写者 | 两机 push 同一分支 → **非快进拒绝 + 竞态** | I1 结构性消除 |
| 台账 `module-progress.md` | `contract-union` 驱动器求并 | 两机各改行 → 行级冲突 | I4 结构性消除 |
| 契约 `packages/api-contracts/src/**` | `contract-union` 驱动器 | 求并本身没问题，但两机各自 codegen 的产物基线不同 | A 合并时求并 ✓ |
| 调度闸 `lane.mjs gate` | 仓库内文件锁 | 两把互不相干的锁 → **双闸同时开** | 只有 A 取闸 |
| `lock.mjs` 开发锁 | 仓库内文件锁（TTL 90 分钟） | 同上 | B 不需要该锁 |
| 心跳/失联判定 | `lanes.json.heartbeatAt` | 两机各写一份 `lanes.json` → **A 看不见 B 的心跳** | B 把心跳写进车道分支，A 读远端 |

### 2.1 仍然存在的真实共享面（**必须人工/协议处理，不假装没有**）

1. **`apps/web/src/lib/api-proxy.ts`** —— 它**不在** `contract-union` 驱动器的覆盖范围内
   （`.gitattributes` 只覆盖 `packages/api-contracts/src/**` 与台账）。
   Mac B 的车道改了它，Mac A 并入时**必须按协议求并**：
   内层 `inventory/` 组与外层仓库级段**两层 alternation 都要并**，只并内层会静默丢路由。
   验证方式是**跑真 proxy 断言 HTTP 状态码**（放行=转发，拦截=404）并同时断言反向用例。

2. **同服务的迁移落点** —— I2 已经保证版本号不撞；但 A 合并 B 的车道后，
   同一服务目录里会同时出现两机写的迁移，**执行顺序由版本号决定**。
   这不是冲突，是设计。

3. **契约 codegen 产物** —— `packages/api-contracts/src/catalog.ts` 是 codegen 产物，**禁止手改**。
   A 合并时若发现 B 的车道改了契约，必须重新跑一次 codegen，而不是手改合并结果。

## 3. 跨机车道的生命周期

```
① 签发   Mac A: plan → 生成车道(分支+worktree+版本号) → 写任务书 → commit 进车道分支 → push
② 领取   Mac B: fetch → 看到分支上有 .lane-tickets/<id>.md → 本地 claim → 建 worktree
③ 执行   Mac B: 读任务书 → 派 worker 子任务 → 实现 → L1 验证 → commit(不 push)
④ 交付   Mac B: 删除 .lane-tickets/<id>.md → 写交付报告进 commit message → push 车道分支
⑤ 收割   Mac A: fetch → 发现票据已消失且 tip != base → 收编为 ready
⑥ 并入   Mac A: merge-ready → 合并进集成头 → sync → L2 → push 集成头
```

### 3.1 票据即分支（为什么不用共享队列文件）

票据写在**车道分支自己的文件** `.lane-tickets/<模块ID>.md` 里，随该分支 push。

- **没有共享可变文件** → 没有「两机同时写队列文件」的竞态
- 每个分支只被一条车道用 → 分支之间互不干扰
- 票据的删除即「完成信号」：worker 在交付时删掉它，A 看到文件消失 = 这条车道做完了
- 票据文件**不进最终集成头**：worker 删了它，合并时两侧都不存在该文件 → 不会进树

> ⚠️ `.dev-agent/` 整个被 `.gitignore` 忽略（`.gitignore:104`），
> **票据不能放在 `.dev-agent/` 下** —— 放进去 git 根本不会跟踪，push 上去的是空分支。
> 票据目录用仓库根的 `.lane-tickets/`。

### 3.2 完成判据（A 侧收割的硬条件）

一条远端车道**同时满足**以下两条才算完成：

1. 远端分支 tip 上 **`.lane-tickets/<id>.md` 不存在**（worker 删了）
2. 远端分支 tip **不等于** `lanes.json` 里记的 `baseSha`（确实有新提交）

只满足 1 不够：worker 可能删了票据但没提交任何代码。
只满足 2 不够：代码提交了但票据还在 = worker 没走完交付流程。

### 3.3 心跳与失联

Mac B 的心跳**不写 `lanes.json`**（那是 A 的），而是 push 一个**带注释的 tag** `hb/<模块ID>`：

```bash
git tag -f -a hb/11-2-3-2 -m "lane heartbeat $(date -Iseconds)" HEAD
git push --force upstream refs/tags/hb/11-2-3-2
```

**心跳时间 = tag 的 tagger 时间**，A 侧用 `git for-each-ref --format='%(taggerdate:iso-strict)'` 读。

- **不用文件、不用 commit** —— 每 25 分钟一条心跳 commit 会把车道分支历史冲垮
- **不用自定义 ref 命名空间**（`refs/hb/*`）—— GitHub 只保证放行
  `refs/heads/*` / `refs/tags/*` / `refs/notes/*`，自定义命名空间会被拒
- **每个车道一个独立 tag 名** → 不会互相覆盖 → 没有推送竞态

A 侧拉心跳 tag：

```bash
git fetch upstream '+refs/tags/hb/*:refs/tags/hb/*'
```

失联判定沿用单机口径：**90 分钟没有任何新推送** 即视为失联，由 A 回收重派。

## 4. 定时任务分配

### 4.1 Mac A —— 调度者

| 项 | 值 |
| --- | --- |
| cron | `0 8-20 * * *`（整点，仅 08:00–20:00） |
| 现有 cron_id | `fcf14c15-6744-4ec2-b733-fc31d5babf44` |
| 触发频率 | 每小时 1 次（节流闸 55 分钟，配 60 分钟栅格留 5 分钟余量） |
| 本机车道配额 | 6（`RUNNING_QUOTA`，A 自己的 `.dev-agent/PIPELINE.local.md`） |
| 一轮做什么 | sync → gate → 容量闸 → plan → **签发票据** → 本机派 task → **收割** → merge-ready → L2 → push |

**A 不做的事**：不去 B 上跑测试、不读 B 的工作区、不合并 B 的本地分支。
A 看到 B 的**全部**信息都来自远端 git。

### 4.2 Mac B —— 执行者

| 项 | 值 |
| --- | --- |
| cron | `*/5 8-20 * * *`（每 5 分钟，仅 08:00–20:00） |
| 触发频率 | 每 5 分钟轮询 |
| 本机车道配额 | 6（**B 自己的** `RUNNING_QUOTA`，按 B 的硬件另测） |
| 一轮做什么 | gate → fetch → 扫票据 → 领票 → 建 worktree → 派 worker → L1 → 交付(push) |
| **不做** | plan / merge-ready / L2 / sync / 改台账 / push 集成头 / 取调度闸以外的状态写 |

**为什么 B 轮询 5 分钟而 A 是 60 分钟**：

- A 的节流是**时间闸**（55 分钟），因为 A 每一轮都要跑 L2 全量验证 —— 那是发热大头。
- B 的节流是**有没有票**：空转只做一次 `git fetch` + 扫分支列表（< 2 秒），
  **不起容器、不编译、不写工作区 → 零发热**。
- 所以 B 可以高频轮询，B 的发热完全来自真实工作。
- 票据从签发到领取：平均 2.5 分钟、最坏 5 分钟。相对 A 的 60 分钟批次节奏，
  这是 ~4–8% 的吞吐损耗，换来的是 B 的 CPU 常年空转等待。

**B 的静默窗口**与 A 相同：`20:30 → 次日 08:00` 不发起新任务（已在跑的车道允许跑完）。
`cron` 的 `8-20` 已经结构性地保证夜间不触发，tick 内自检是兜底。

### 4.3 两机的负载闸各自独立

`RUNNING_QUOTA` / `LOAD_MAX` / PG 容器数闸**都是本机参数**，各自实测各自填：

| 参数 | Mac A | Mac B |
| --- | --- | --- |
| `RUNNING_QUOTA` | 6 | 6（**按 B 的核数/风扇另测**） |
| `LOAD_MAX` | 12 | B 实测后填（空载基线不同，不能照抄 A 的 12） |
| PG 容器降噪闸 | >= 6 停止派发 | >= 6 停止派发 |

> ⚠️ **B 的 `LOAD_MAX` 不能照抄 A 的 12**：load 阈值的下限是**本机空载基线**，
> A 的基线是 4–8（WeChat + Docker VM + IDE）。B 上跑什么、基线多少，**必须实测**。
> 把阈值设到基线以下 = 把流水线整个锁死（这个坑 A 踩过一次：设成 6 → 连空载 7.04 都超）。

## 5. 车道分配策略

Mac A 每轮 `plan` 出 N 条车道后，按**序号奇偶**切给两台机器：

- 奇数序号 → Mac A 本机执行
- 偶数序号 → Mac B 远程执行（签发票据）

默认奇偶切分保证两机负载均衡。特殊情况下（某机在跑长任务、某机被抢占）
由调度者临时改成「全给 A」或「全给 B」，**不需要改代码**。

> **切分的依据是「车道的编号」，不是「模块的归属」** ——
> 这与双机同构方案的「按卷静态分区」有本质区别：
> 静态分区要求人先验判断哪些卷能并行（会踩到多服务卷的坑，
> 比如卷 09 = `trade + channel`、卷 10 = `channel + trade + warehouse`，
> 主责服务只是 README 里的**第一项**，实际落库可能跨服务）。
> 奇偶切分不预判任何模块属性，**冲突由 I1–I4 在结构上兜住**。

## 6. 故障处理

| 情况 | 判据 | 动作 |
| --- | --- | --- |
| B 掉线 | 90 分钟无新推送 / tag | A 回收该车道（`abandon`）→ 下一轮重派（可能改派给 A） |
| B 交了但 A 收不到 | 远端 tip 有提交、票据已消失 | A 重跑 `remote-lane.mjs adopt` |
| 票据推不上去 | `git push` 被拒（非快进） | **远端已有同名分支且内容不同** = 陈旧车道，人工确认后 `abandon` 再重发 |
| B 的车道 L1 红 | worker 报告 | B **不重派**，回报 A；A 决定 abandon 还是等上游 |
| A 的 L2 红 | 集成头全量验证 | 可能是**并发资源争抢造成的假红**（多套 Testcontainers PG 互饿）→ **先隔离复跑最大那一堆**，不要直接 bisect |
| 两机同时写台账 | 不可能 | I4 保证 |

## 7. 分阶段落地（不要一次全开）

| 阶段 | 做什么 | 通过标准 |
| --- | --- | --- |
| **P0** | B 装环境、`lane.mjs init`、克隆仓库、跑一次 `sync.mjs` | B 上 `sync.mjs` 输出的计数与 A **完全一致** |
| **P1** | B 建 cron 但**只轮询不领票**（A 还没签发） | B 的空转轮次连续 3 轮无报错、无发热 |
| **P2** | A 签发 **1 条**车道给 B，B 完整走完 ①→⑥ | 该模块在集成头里、迁移生效、L2 绿 |
| **P3** | A 签发**一半**车道给 B，观察 3 个批次 | 无版本号冲突、无 L3 兄弟并发、无台账冲突 |
| **P4** | 按需调两机的 `--lanes` | 两机 load/PG 容器数都在闸内 |

> **P0 的「计数完全一致」是一道硬检查**：它一次性验证了 B 的仓库状态、
> 台账解析、蓝图解析与 A 对齐。这一步不过，后面全不用做。

## 8. 已知代价（说清楚，不粉饰）

1. **A 会为 B 的车道也建本地 worktree**（`plan` 现在的行为）→ 多一次 `pnpm install`（约 20–40 秒）+ 磁盘占用。
   根治办法是给 `plan` 加 `--executor` 参数（B 的车道只建分支不建 worktree），
   这是**后续优化**，不阻塞 P2。过渡期 A 的 worktree 由 `gc` 回收。

2. **票据 commit 会留在车道分支的历史里**（合并后文件本身不在树里）。
   审计友好，代价是分支历史多两个 commit。

3. **A 是单点**。A 挂了整条流水线停摆（B 仍可把已领的车道做完并 push，
   但没人收割、没人合并）。**A 的恢复比 B 重要**：
   A 挂了就直接在本机重跑 A 角色的 cron，不要把角色对调。

4. **两机各跑一次 L2 会浪费**。本方案里 **L2 只在 A 上跑一次**（在集成头上），
   B 只跑 L1（本模块 + allowlist 反向回归）。这是吞吐能翻倍而发热不翻倍的关键。

## 10. 集成测试抓到的两个坑（已修，留作判据）

`remote-lane.itest.mjs` 在隔离沙箱里真跑一遍 签发→领取→心跳→交付→收割→并入。
它抓到的两个 bug 都是**协议级**的，不是打字错：

### 10.1 收割时用陈旧的本地分支判票据 ⇒ 已交付的车道永远收编不了

`lanes.json` 里的车道分支引用（`refs/heads/feat/x`）**不会自动跟着远端走**。
A 侧若直接用本地引用判「票据还在不在」，读到的是**签发那一刻的快照** ——
票据当然还在，于是判定为「未交付」，跳过。下一轮还是跳过，**交付物烂在远端**。

⇒ 判据：**完成与否只能看远端 tip**。收割前必须
`git fetch upstream +<branch>:refs/remotes/upstream/<branch>` 刷新远端跟踪引用，
再在**远端跟踪引用**上判票据。

（远端跟踪引用能随时更新，是因为它永远不会被检出；
而本地分支被 A 的车道 worktree 检出着，`git fetch remote branch:branch` 会被拒。）

### 10.2 `ls-tree` 不带 `-r` ⇒ 列的是目录项本身，永远拿不到里面的票据

`git ls-tree <ref> .lane-tickets`（不带 `-r`）列出的是 **`.lane-tickets` 这个目录项**，
不是它的内容。B 侧 `poll` 因此永远返回空数组 —— 而且**不报错**。

⇒ 判据：列目录内容必须 `git ls-tree -r --name-only <ref> <dir>`。

**这两个坑的共性**：都是「静默地返回了错误的空结果」，
和 `plan --help` 那类坑同族 —— **不报错 ≠ 做对了**。
所以跨机脚本必须有端到端测试，而不是靠肉眼看输出。
