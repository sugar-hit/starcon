# 数据模型与数据访问选型调研

日期：2026-09-27。性质：调研，配合 [数据模型设计](../../db/schemas/README.md) 产出。技术栈已由 [ADR-0003](../decisions/0003-backend-runtime-kotlin-spring-boot.md) 锁定，本记录的是**为什么**，以及设计过程中每个取舍的备选方案。

## 直接回答两个问题

### DB：PostgreSQL 16

已定。理由按重要性排：

| 需求                               | PG 的表现                                                              |
| ---------------------------------- | ---------------------------------------------------------------------- |
| 跨租户运营查询、计费汇总、平台对账 | 一条 SQL 跨全部租户，共享 schema 下天然可行                            |
| 租户隔离                           | RLS 是数据库一等公民，绕过应用层也越不了权                             |
| 金额精度                           | `NUMERIC` 原生任意精度，**MySQL `DECIMAL` 在中间结果里容易退化成浮点** |
| 行锁 / 条件更新                    | `SELECT ... FOR UPDATE`、条件 `UPDATE`，库存扣减直接可用               |
| 生成列                             | `GENERATED ALWAYS AS ... STORED` 让 `available` 不可能与源列漂移       |
| 约束触发器                         | `DEFERRABLE INITIALLY DEFERRED` 让借贷平衡在提交时校验                 |

**为什么不选 MySQL**：星云 ERP / 订单聚合场景 PG 是事实标准，jOOQ 对 PG 的支持最好，`NUMERIC` 与生成列是本设计的地基。唯一实质缺点是 RLS 生态资料少于 MySQL，但 [PostgreSQL RLS 官方文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) 完全够用。

**为什么不选 CockroachDB**：分布式确实解决单点，但本项目第一期没有单点问题，而 RLS、约束、部分索引这些我们重度依赖的特性在 CRDB 上语义有差异。多租户共享 schema 的收益（跨租户分析）反而会因分布式事务而变贵。

### ORM：jOOQ —— 准确说，**故意不用 ORM**

这是本次选型里最需要说清的一点：**starcon 的后端不引入 ORM。**

jOOQ 的定位是「从数据库 schema 生成类型安全的查询类」，SQL 由人写、由编译器检查字段与类型是否存在。它替代的是 JPA 的**查询构造**部分，不替代持久化语义管理。

| 方案             | 优点                                                                            | 缺点                                                                                    | 结论    |
| ---------------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------- |
| **jOOQ**         | SQL 完整可见可审阅；编译期发现字段改名；与 Flyway schema 天然对齐；无隐式 flush | 没有对象图持久化，映射代码手写                                                          | ✅ 采用 |
| Hibernate / JPA  | 对象图映射省代码；生态最熟                                                      | **隐式 flush 时机不可预测**；懒加载让「先读后写」变成隐式 SQL；关键扣减逻辑无法逐行审阅 | ❌      |
| Exposed          | Kotlin 原生，DSL 友好                                                           | 仍以 DSL 抽象 SQL，审阅时看不到真实 SQL；社区规模小于 jOOQ                              | ❌      |
| MyBatis          | SQL 可控                                                                        | 映射靠 XML，无编译期校验                                                                | ❌      |
| Spring Data JDBC | 比 JPA 简单                                                                     | 仍有隐式行为；无类型安全查询                                                            | ❌      |
| 裸 JDBC          | 完全可控                                                                        | 样板代码多，易写错                                                                      | ❌      |

**决定性理由**：starcon 最不能出错的是库存扣减与财务过账。Hibernate 的隐式 flush 与懒加载会把「我读了库存，然后写回去」变成一串隐式 SQL —— 一旦实体上有其他关联被意外触碰，flush 时机就变了。这种 bug 在代码评审里看不出来、在测试里偶发、上线后表现为**超卖或账不平**，是最难排查的一类问题。

[ADR-0003](../decisions/0003-backend-runtime-kotlin-spring-boot.md) 已经明确「不用 JPA/Hibernate 做主路径」。jOOQ 生成的代码在 `build/generated` 下，**永不手改**。

## 数据模型的关键取舍

以下每条都是「A 还是 B」的真实选择，记录备选方案与判据。

### 1. 主键 UUIDv7 而非自增 bigint

| 方案                     | 优点                                                                                      | 缺点                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **UUIDv7（应用层生成）** | 可在写库前生成（事件关联、幂等键需要）；多写入源无序列争用；不泄露业务量；B-tree 局部性好 | 16 字节，索引略大；**PG 16 没有内置 `uuidv7()`**（PG 18 才有），必须应用层实现   |
| `bigserial`              | 索引最小，顺序写入最快                                                                    | 多写入源时序列成瓶颈；**外部同步必须先拿 ID 才能建单**，被迫两段式；业务量可推断 |
| `uuid` v4                | 无顺序争用                                                                                | 随机分布导致 B-tree 页分裂严重，写入密集表性能明显下降                           |

选 UUIDv7。**「PG 16 没有 uuidv7()」是必须应用层生成的硬原因**，不是风格偏好。

### 2. 状态用 `TEXT + CHECK` 而非 PG 原生 `ENUM`

| 方案           | 加值                                                | 删值 / 改名                        | 评估 |
| -------------- | --------------------------------------------------- | ---------------------------------- | ---- |
| `TEXT + CHECK` | 改一条迁移                                          | 改一条迁移                         | ✅   |
| PG `ENUM`      | `ALTER TYPE ... ADD VALUE`（PG 12+ 不能在事务里跑） | **需重建整个类型**，是公认运维痛点 | ❌   |

订单状态一定会演进（`CREATED → CONFIRMED → ALLOCATED → SHIPPED → DELIVERED` 之后大概率还要加 `ON_HOLD`、`RETURN_REQUESTED`）。让演进的成本是一行迁移，比让 DDL 看起来更「严谨」重要。

### 3. 不做软删除（三个明确例外）

| 方案                     | 优点                                                         | 缺点                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| **不用软删除**（本设计） | 唯一约束不被占用；统计口径一致；与「事实表 append-only」一致 | 误删无法恢复                                                                                                                           |
| 全表 `deleted_at`        | 可恢复                                                       | **软删除行仍然占着唯一编码** → 租户「删了再新建同编码」失败；`COUNT(*)` 到底含不含全靠每处记得加条件；RLS 之外的第二套过滤条件，极易漏 |

例外仅三处，理由都是「外部可能重推，丢了就断链」：`listing`、`listing_sku_mapping`、`outbox_event` / `idempotency_record`（本身 append-only）。

### 4. 库存余额权威在仓库级，不在库位级

这是全设计里最重要的一条。详见 [04-inventory.md](../../db/schemas/04-inventory.md)。

| 方案                                | 原子预占                             | 风险                                   |
| ----------------------------------- | ------------------------------------ | -------------------------------------- |
| **余额键 = (sku, warehouse)**       | 单行条件更新                         | 需另建 `location_balance` 支持货位拣货 |
| 余额键 = (sku, warehouse, location) | 需要 `SUM` 后更新 → **重新引入竞态** | 要修得对多行加锁并规定加锁顺序         |

履约流程里可用量的决策单位是**仓库**（订单从某仓发货，不是从某个货架格）。把权威放在仓库级，原子预占就是一条 SQL：

```sql
UPDATE inventory_balance SET reserved = reserved + :qty
 WHERE tenant_id=:t AND sku_id=:s AND warehouse_id=:w AND available >= :qty
```

配合 `available` 是生成列 + `CHECK (available >= 0)`，**超卖在 DB 层就存不进去**，不依赖应用层记得判断。

### 5. 库存流水 + 余额双表（投影模式）

| 方案                                       | 优点                               | 缺点                                                                   |
| ------------------------------------------ | ---------------------------------- | ---------------------------------------------------------------------- |
| **ledger（append-only）+ balance（投影）** | 余额可审计、可重算；扣减原因可追溯 | 两者必须同事务写，写错会漂移                                           |
| 只有余额表                                 | 简单，少一次写                     | **只知道数字变成了多少，不知道为什么**。盘亏、错扣、平台漏发全查不出来 |

ERP 的库存纠纷（「我这批货去哪了」）靠的就是流水。漂移风险由「同事务写入」这条纪律 + 集成测试断言 `SUM(ledger) == balance` 控制。

### 6. SPU/SKU 变型用两张关联表，不用多态

`spu_attribute` 和 `sku_attribute` 结构相同，只是外键不同。**不合并成一张带 `product_type` 多态外键的表** —— 多态外键拿不到引用完整性，而这里错了会直接导致「同一 SPU 下生成重复 SKU 组合」，是静默的数据损坏。

属性值用 `value_id`（枚举型）与 `value_text`（自由文本型）二选一，`CHECK (num_nonnulls(value_id, value_text) <= 1)` 保证。

### 7. `listing_sku_mapping` 刻意冗余 `shop_id`

业务规则的真实键是 `(tenant, platform, shop, external_id) → 内部 SKU`。如果只对 `(tenant, listing_id, external_sku)` 加唯一，就**阻止不了**「同一店铺同一 external_sku 映射到两个内部 SKU」→ 订单会路由到错误 SKU。

冗余一列 `shop_id` 换取这条唯一约束可表达，是刻意的反范式。

### 8. 状态机数据驱动

`order_status_transition` 存合法迁移，而不是散在代码里的 `when` 分支。运营要加「发货后 7 天自动确认收货」这类规则时，改数据不改代码。

### 9. 借贷平衡用延迟约束触发器

`CHECK` 只能看单行，做不到「所有分录合计借 = 合计贷」。`DEFERRABLE INITIALLY DEFERRED` 的约束触发器在 `COMMIT` 时检查，**不平的凭证在数据库层面就存不进去**。详见 [07-finance.md](../../db/schemas/07-finance.md)。

### 10. 弱引用 vs 空壳父表

`journal_entry.source_id`（来源跨 5 张表）和 `attachment.resource_type/resource_id` 用弱引用，**不建外键**。

代价：失去外键完整性，需要定期巡检 SQL 查孤儿。收益：避免为「让外键好看」而建一张空壳 `business_document` 表 —— 那会污染整个模型，且所有业务表都要多一个 `document_id`。

对比：如果接受「只能指向一张表」，就必须建父表。这是**用一处弱引用换掉全模型污染**，并且这两个场景的孤儿（孤儿凭证附件）只占资源、不影响账目正确性 —— 而账目正确性是 finance 的硬要求，孤儿凭证则不是。

### 11. 角色按租户隔离，权限码表全局

`role` 带 `tenant_id`（允许每租户自定义角色），`permission` 是全局静态码表。建租户时自动种下 `is_system = TRUE` 的系统角色。

角色与权限是多对多，因为「运营主管在 A 租户能退款、B 租户不能」是正常业务。

### 12. `membership` 唯一 `(tenant_id, user_id)`

这条约束让租户上下文解析退化成**一次唯一查找**。[ADR-0002](../decisions/0002-multi-tenancy-strategy.md) 要求「租户 ID 由已认证用户的成员关系解析」—— 如果一个用户在一个租户内可能有多条成员关系，解析就需要额外规则（挑哪条？取并集？），那正是租户解析漏洞的常见来源。

代价：一个租户内不支持多组织。已记入 backlog。
