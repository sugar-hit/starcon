## 结论与前提

基于当前仓库以 Next.js / TypeScript 前端为主、apps/api 与 packages/database 尚为骨架，~~建议采用 **TypeScript + NestJS（Fastify adapter）+ PostgreSQL 的模块化单体**~~ → **本文此建议已作废，实际采用 Kotlin + Spring Boot 3 + PostgreSQL（见 [ADR-0003](../decisions/0003-backend-runtime-kotlin-spring-boot.md)）**。API 与后台 worker 分进程部署，共用领域代码。四个业务系统是工作界面与权限视角，不应直接划成四套数据库。

沿用 ADR-0001 的模块化方向，但不要把“以后拆服务只改 deployment”理解为保证：拆分还涉及事务边界、数据迁移、失败恢复和接口版本。现有 overview 中 Kafka、ClickHouse、三套 K8s 等是目标蓝图，不代表已经实现或第一期必需。团队技能、日订单量、峰值同步量、部署地区、可用性目标与运维预算尚未核实；这些会影响部署规模，不妨碍先统一业务模型。

## 形态比较

| 方案           | 数据一致性 / 交付影响                                              | 本项目建议                           |
| -------------- | ------------------------------------------------------------------ | ------------------------------------ |
| 模块化单体     | 模块有明确归属，关键操作可在一个数据库事务完成；部署与排障简单     | 现在采用                             |
| 微服务         | 可独立扩缩容与发布，但跨服务一致性、消息重复、网络失败都要额外处理 | 出现实测瓶颈或独立团队需求时局部拆分 |
| 无边界的大单体 | 初期快，但任意跨表写入会让库存与财务规则失控                       | 避免                                 |

微软架构资料明确列出微服务的复杂性及跨服务数据一致性成本：[微服务架构](https://learn.microsoft.com/en-us/azure/architecture/microservices/)、[数据考虑](https://learn.microsoft.com/en-us/azure/architecture/microservices/design/data-considerations)。因此，数据互通本身不构成采用微服务的理由。

## 服务端语言

| 语言 / 框架         | 适用判断                                                                | 取舍                                                                     |
| ------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| TypeScript / NestJS | 与现有团队代码和严格 TS 规范最一致，适合订单、库存、平台 API 等业务编排 | 推荐主后端；运行时仍需输入校验，不能把 TS 类型当鉴权或校验               |
| Java / Spring Boot  | 若核心团队已有成熟 Java ERP 经验，可优先考虑                            | 需要调整现有全栈 TS 规范、增加契约生成及双语言维护；无团队依据不主动引入 |
| Go                  | 独立高吞吐连接器或 CPU/资源瓶颈模块                                     | 有测量依据再引入，第一期不为假设的性能问题拆语言                         |
| Python              | OCR、预测、数据科学等专项任务                                           | 作为独立服务候选，主交易链路保持单一语言                                 |

NestJS 的 [modules](https://docs.nestjs.com/modules) 支持显式导出服务，适合约束领域接口；[Fastify adapter](https://docs.nestjs.com/techniques/performance) 是官方支持路径，但 Express 专用中间件不能直接照搬。选择它主要为模块组织和与当前 TS 栈一致，框架基准不能预测 ERP 的真实容量。

## 第一期基础设施

- PostgreSQL：唯一交易事实源，主数据、订单、库存流水、履约及结算均按领域分表/分 schema；API 不能绕过领域服务。
- REST + OpenAPI：前后端契约生成，移动端与外部集成都可复用；不直接暴露 ORM 表模型。
- 数据访问：优先验证 Drizzle + 明确 SQL 迁移，先做 RLS、事务连接、复合外键的小型验证后定 ADR；关键库存 SQL 必须可审阅。此处为候选，非已验证选型。
- 后台任务：先用 PostgreSQL outbox + worker 承接可靠同步；若任务调度/限流需要 Redis 队列，可再加入。缓存与消息队列均不作为库存事实源。
- 对象存储：文件、标签、票据；数据库只存受权限约束的元数据。
- 部署：一个 API + 一个 worker + 托管 PostgreSQL，按实际 SLA 配置备份、恢复演练与监控。Kafka、ClickHouse、Kubernetes 待流量与团队条件证明需要再引入。

## “底层打通”具体意味着什么

同一租户内共享统一身份、统一业务编码、明确数据归属与可追踪业务关系。不同租户仍严格隔离；互通不等于所有人都能看到全部数据，也不等于所有模块都能写任意表。

| 数据                              | 唯一维护方                   | 跨模块使用方式                                       |
| --------------------------------- | ---------------------------- | ---------------------------------------------------- |
| 租户、组织、成员、角色            | identity / tenancy           | 服务端授权、成员关系与租户上下文                     |
| 商品 SPU / SKU、属性、单位        | catalog                      | 所有订单、采购、库存引用内部 SKU ID                  |
| 店铺、平台 listing、外部 SKU 映射 | channel                      | (tenant, platform, shop, external ID) 映射到内部 SKU |
| 仓库、库位、库存流水与预占        | inventory                    | 通过库存服务预占/释放/扣减，其他领域不直接改数量     |
| 供应商、客户、承运商              | 对应 partner / shipping 领域 | 统一 ID，地址与名称在业务单据保留历史快照            |
| 订单、订单行、状态                | order                        | 引用 SKU / 店铺 / 客户，支付、履约、退款状态分开     |
| 出库单、包裹、运单                | fulfillment / shipment       | 关联订单行与库存流水                                 |
| 结算、币种、汇率快照              | finance                      | 引用业务单据及原币金额，不能拿实时汇率重算历史账     |

同款商品可对应多个平台 listing；平台 SKU 字符串不能充当全局主键。订单保存当时的名称、价格、税费与汇率快照，主数据变更不覆盖历史单据。金额用数据库 NUMERIC 与服务端 decimal/金额库，禁止用浮点运算直接记账。

跨模块读取使用公开 service 或经设计的只读共享视图；报表可建立只读投影。每张事实表只有一个写入所有者。数据库可同库，但这些边界必须在代码审查中执行。

## 一致性与隔离先做对

1. 租户上下文由已认证用户的成员关系确定，通过 @starcon/tenancy 传播；不能信任客户端任意 tenant header。
2. 每张业务表携带 tenant_id，业务唯一约束与关联外键带租户维度，例如 (tenant_id, sku_id)；RLS 启用 USING / WITH CHECK，运行角色不得为 superuser、BYPASSRLS 或绕过策略的 owner。
3. 连接池内用事务级租户上下文，禁止连接归还后残留租户；后台任务同样恢复并校验上下文。RLS 是纵深防御，模块权限仍需校验。[PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
4. “订单落库 + 库存预占 + outbox 事件”由应用用例协调各领域服务，在同一个 DB 事务连接中完成；库存使用条件更新或行锁，不用先读余量再无锁写回。
5. 第三方网络调用放到提交后的后台任务，设置超时、重试、幂等、失败待处理与人工重放；外部副作用不能假装可被本地事务回滚。
6. outbox 与业务数据同事务提交，worker 至少一次投递，消费者按事件 ID 去重，记录版本以处理乱序。解决的是可靠交付，不承诺 exactly-once。[AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
7. 按店铺/外部订单 ID 去重，保留同步游标、来源、更新时间、失败原因和审计记录；定期核对平台订单与本地记录。

## 从哪里开始

按验收结果推进，不按月份强制拆服务：

1. **主数据与闭环设计**：选一个真实店铺/平台、一个仓库、少量 SKU，画出实体关系、映射、订单状态与权限矩阵。明确库存可用量口径、取消释放与失败补偿。
2. **可运行后端底座**：建立 apps/api、database、tenancy、auth、money 的最小实现、迁移、OpenAPI、日志与测试。先证明两个租户互不可见、伪造租户无效、连接池不串租户。
3. **SKU / 店铺 / 仓库**：实现真实持久化和导入，验证重复编码、外部映射冲突、跨租户外键拦截，再让前端读取真实列表。
4. **第一条纵向闭环**：一个平台订单接入 → SKU 映射 → 原子预占 → 出库 → 库存扣减 → 形成待结算记录。没有真实物流接口时明确标记人工出库，不伪造回传成功。
5. **失败路径先验收**：重复 webhook 不重复扣库；并发最后一件只能成功一单；取消可释放；事务回滚不丢库存；worker 重启可续跑；乱序事件不回退状态；历史金额不随汇率变化。
6. **扩第二个平台**：检验统一模型是否成立，再补采购、调拨、退货、对账与运营报表。

第一个里程碑应是“一家店的真实订单能安全走完库存与履约”，而不是先把所有页面的 CRUD 做完。调研不等于本轮实施后端。

## 何时拆服务

出现某模块独立扩容的持续瓶颈、独立团队发布冲突或明确隔离 SLA 时再拆。优先考虑连接器同步、OCR、报表；订单/库存先保持同事务边界。拆前必须有幂等契约、可观测性、数据归属、补偿策略和回放验证，不能只依据项目运行时长或“企业级”标签。
