# ERP SaaS 身份与组织管理调研

调研日期：2026-09-28。针对本项目商品中心承载登录和组织管理的问题。

| 官方资料                                                                                                                                                                                       | 可采用的产品原则                                             | Starcon 的边界                                                       |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| [Odoo 用户](https://www.odoo.com/documentation/saas-18.2/applications/general/users.html)、[多公司](https://www.odoo.com/documentation/17.0/applications/general/companies/multi_company.html) | 用户可以获得多个公司的访问资格，当前公司是工作上下文         | 租户是独立数据边界，不照搬共享数据库的多公司规则                     |
| [Shopify 角色](https://help.shopify.com/en/manual/your-account/users/roles)、[组织权限](https://help.shopify.com/en/manual/your-account/users/roles/permissions/organization-permissions)      | 用户、组织访问和业务角色分别管理；组织管理权限与店铺权限不同 | IAM 不属于商品；同一角色分配满足操作与数据范围，不做跨角色拼接       |
| [ERPNext 用户与权限](https://docs.frappe.io/erpnext/adding-users)                                                                                                                              | 用户管理、角色权限、用户限制、密码及账号停用属于统一系统能力 | 成员停用与全局用户停用必须区分；先接入真实能力，再分阶段扩展认证方式 |

结论：登录是应用入口；账户代表人；membership 代表人在某租户内的身份；角色分配负责该身份的权限。租户、部门、店铺不可混为一种组织节点。ERP 业务功能还包括商品、渠道、采购、订单、库存、仓储、物流、财务与分析；这些功能共同消费 IAM，不拥有 IAM。

现状：identity 已提供认证、会话、多租户成员、部门、角色、子租户与所有权转移。错误集中在应用层：CatalogWorkspace 同时实现登录和组织管理，组织入口仍是占位页，顶栏账户仍允许切换演示角色。应复用现有已测试的后端隔离规则，重建应用级边界。
