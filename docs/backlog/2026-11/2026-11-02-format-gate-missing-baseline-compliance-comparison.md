# 增量格式闸缺「基线合规性对比」—— 触碰既有债文件会把存量债算成本批红

> 发现时间：2026-11-02 01:24（流水线 round-153 的 L2 收尾阶段，由 tick 记录、**未擅自改闸**）
> 严重度：**中** —— 只在「本批触碰了一个本来就不合 prettier 的文件」时发作；
> 但发作时闸会红，**挡住整批 push**，且修法容易被误当成「全仓 prettier --write」（巨量 diff 风险）
> 归属：`tools/module-progress/format-gate.mjs`（调度器自有的判分工具）
> 触发方：2026-11-01 的两次调度者协议提交（`f8f1fcc1` 重写 §0.0 嵌套列表、`6b8ae806` 加 §3.3.1 表格）
> —— 两者破坏了 `tools/module-progress/PIPELINE_CRON_PROMPT.md` 的 prettier 排版

---

## 现象

round-153 的 L2 八步里，七步绿，**只有增量格式闸红**：

```
### format-gate :: node tools/module-progress/format-gate.mjs
{
  "ok": false,
  "batch": { "base": "00658d46087f", "head": "b28382dc5764", "mergeCount": 6 },
  "changedFiles": 70,
  "checkedFiles": 42,
  "violations": [ "tools/module-progress/PIPELINE_CRON_PROMPT.md" ]
}
```

**同一个文件在批次基线 `00658d46` 上是合规的** ⇒ 这次是**本批引入**，不是存量债 ⇒ 修掉即可。

## 缺口本身

闸现在的判据是：「**本批触碰过的文件，现在是否合规**」。

它**不比对**「该文件在批次基线上是否本来就合规」。于是出现这个不对称：

| 情形 | 现状（闸） | 应该是 |
| --- | --- | --- |
| 基线合规 → 本批改成不合规 | 🔴 红（本批引入，拦得对） | 🔴 红 |
| **基线就不合规 → 本批只是改了内容** | 🔴 红（**误判成「本批引入」**） | ⚪ 不红（存量债不该阻塞） |
| 基线不合规 → 本批顺手改对了 | 🟢 绿 | 🟢 绿 |

协议里写的是「**存量债不得让闸打红**（本批新增必须拦、存量不阻塞）」——
第二行与实现不一致。

## 为什么这次是「本批引入」而不是缺口发作

运气成分不小：出问题的文件恰好在基线上是**合规**的（`PIPELINE_CRON_PROMPT.md` 之前一直合规，
是本批的两次编辑把它弄坏的）。若当时那个文件本来就带着排版债，tick 就会误判成「本批引入」，
去改一个**不该由本批负责**的文件 —— 或者更糟：为了让它绿而顺手重排，产生无关 diff。

## 建议的修法（**未实施**）

给闸补一步基线比对：对每个 `violations` 里的文件，

1. 取批次基线上的那份内容（`git show <base>:<path>`）；
2. 判定它在基线上是否也不合规；
3. **基线不合规 且 违规集合相同** ⇒ 归类「存量债」，不计入本批违规；
   **基线合规** ⇒ 本批引入，保持拦。

⚠️ 实现要点：prettier 的判定依赖**文件路径**（`.prettierignore`、`.prettierrc`、按扩展名推断 parser），
所以比对时必须把基线内容写到**同相对路径**下再跑 prettier，不能扔到 `/tmp`（那样 config 解析不到、结论会错）。

⚠️ 改闸就是**在同一轮里动裁判** —— round-153 没有擅自改是对的。
应当作为独立批次做，并给 `tools/module-progress/format-gate.itest.mjs` 补三个用例：
「基线合规 + 本批改坏 ⇒ 红」「基线不合规 + 本批只改内容 ⇒ 不红」「基线不合规 + 本批改对 ⇒ 绿」。

## 现在的处置（round-153 实际做法，可复用）

违规文件属于**调度者自己拥有**、本批无车道触碰的协议文件 ⇒
**在集成头就地只修这一个文件**（`pnpm exec prettier --write <该文件>`），
**不做全仓 `--write`**，改动量 11 insertions / 11 deletions，
修完**只重跑 format-gate 这一步**（其余六步结论继续成立），并在说明里写清归属与取证。
