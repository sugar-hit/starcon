# 夹具的「写死日期」会随日历自己红 —— 测试脆弱性的一类系统性来源

> 登记时间：2026-10-26（batch-104 调度者）。
> 触发事件：L2 批次闸在 **channel** 模块红了一处，隔离复跑**仍红**（不是机器拖慢型假红），
> 排查后发现是**夹具把「昨天」写成了绝对日期**，到点自己跨过阈值 ⇒ 断言自己变红。
> 详见 `docs/sessions/2026-10/2026-10-26-batch-104-l2-supplement-and-dispatch.md` 第六节。

## 一、已确认的一例（本轮已修）

`backend/services/channel/src/test/java/com/starcon/channel/LogisticsExceptionIntegrationTest.java`

```java
static final OffsetDateTime RECENT_AT = OffsetDateTime.parse("2026-10-19T08:00:00Z");  // 写死
```

它的语义是「**未命中票**：最后一次轨迹是**昨天**」，
而被测规则是「停滞超过 **7** 天」（threshold = 7 × 24 × 60 分钟）。

⇒ 相对「现在」才是「昨天」；写死之后，这张票在
**2026-10-26T08:00:00Z（= 北京时间 16:00）** 就攒够了 7 天，
从那一刻起它变成命中票 ⇒ `candidateCount` 由 1 变 2 ⇒
「只有满足阈值的票进候选池」这条断言**从那天起每天都会红**。

**实测时间线（可复核）**：

| 时刻 | 谁跑的 | 结果 |
| --- | --- | --- |
| 2026-10-26 14:13 CST（= 06:13 UTC） | round-104 的 L2，channel 全量 2344 例 | ✅ 全绿（**尚未到 08:00 UTC**） |
| 2026-10-26 16:00 CST（= 08:00 UTC） | —— | 🔴 夹具跨过阈值，**红灯自此打开** |
| 2026-10-26 19:03 CST（= 11:03 UTC） | 本轮 L2，channel 全量 2344 例 | 🔴 `Tests run: 2344, Failures: 2` |
| 2026-10-26 20:05 CST（= 12:05 UTC） | 隔离复跑（机器空闲、容器峰值 1） | 🔴 仍红 ⇒ **不是机器拖慢型假红，是真红** |

⇒ **与本轮并入的车道无关**（本批 `backend/services/channel/` 一行未改），
也**与被测业务逻辑无关**（业务代码一行未改）—— 红的只有夹具。

**修法**（已落）：把绝对日期换成相对当前时刻
`OffsetDateTime.now(ZoneOffset.UTC).minusDays(1)`，并在代码注释里写明为什么不能写死。

## 二、同类问题的**判定形状**（怎么认出它）

> **夹具里写死的日期** ＋ **被测逻辑拿它跟「现在」比一个相对阈值** ⇒ 这条断言会随日历自己变红。

三个必要特征，缺一不可：

1. 夹具常量是**绝对日期**（`OffsetDateTime.parse("2026-xx-xx...")` / `LocalDate.parse(...)`）；
2. 被测逻辑的判据含**相对阈值**（「停滞超过 N 天」「N 分钟内」「最近 N 天」）；
3. 夹具日期的**语义随日历漂移**（「昨天」「最近」「当前」这类相对语义被写成了绝对值）。

⚠️ **不是所有写死日期都是 bug**：
- 「过去很久」（`2026-01-01`、`2026-03-01`）用于「老数据」语义 ⇒ **安全**（只会越来越老）；
- 「未来」（`2099-01-01`）用于「未到期」语义 ⇒ **安全**。

**危险的是「贴近当下」的那批** —— 它们会在某个确定时刻跨过阈值。

## 三、扫描口径与规模（2026-10-26 实测）

```bash
grep -rnoE '(OffsetDateTime|LocalDate|Instant)\.parse\("2026-[0-9]{2}-[0-9]{2}' \
  backend/services/*/src/test/java/ | sed -E 's/.*parse\("2026-([0-9]{2})-([0-9]{2}).*/2026-\1-\2/' | sort | uniq -c
```

命中里**最贴近当下**的一批（其余是「过去很久」或「未来」，安全）：

| 日期 | 命中数 | 备注 |
| --- | --- | --- |
| `2026-10-19` | **9** | 🔴 **本轮已红的那一个就在这里**（另外 8 处在 channel `StockForecastIntegrationTest` / `StubComplianceCatalogServer` 与 warehouse `AllocationResultIntegrationTest` / `StockoutAlertIntegrationTest`） |
| `2026-10-15` | 9 | 🟡 待核 |
| `2026-10-05` / `2026-10-03` / `2026-10-02` | 11 / 8 / 20 | 🟡 待核 |

⚠️ **这个计数不等于缺陷数** —— 每处都要按上面「三个必要特征」逐条判，
**大部分「过去很久」的写死日期是安全的**（而且**故意写死**才有可复现性）。
**不要批量替换** —— 把「老数据」夹具改成相对时间反而会破坏确定性。

## 四、处置方案（**本轮只做了第 ① 项**）

1. ✅ **本轮已修**：确认在红的这一处（`LogisticsExceptionIntegrationTest.RECENT_AT`）
   —— 改成相对当前时刻 + 写明理由。**只修这一处，因为只有它挡住了 L2**。
2. 🟡 **待做（专门巡检任务）**：按「三个必要特征」逐个核 2026-10-02 / 10-03 / 10-05 / 10-15 / 10-19 这几批夹具，
   确认哪些真的与「相对阈值」比较。
   - 核出来的每一处要么改相对、要么**在注释里写明为什么这个绝对日期是安全的**。
   - **这属于「跨模块巡检」而不是某一个模块的开发** ⇒ 建议单独派一个巡检任务，不塞进模块车道。
3. 🟡 **根治方向（值得单独决策）**：给测试夹具加一个**统一的时间基准**（例如一个 `TestClock` 夹具 / 一个 `TODAY` 常量），
   让「相对语义」只有一个入口；顺带在 CI 里加一道**日历漂移防线**（例如把关键夹具的日期算成相对量并断言
   「距今 X 天」），从根上消掉「某天突然自己红」这一类事故。
   ⇒ 这一条涉及多个服务的测试写法，**属于架构级决策**，本轮不擅自开工，留给人工拍板。
