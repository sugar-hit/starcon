# 2026-10-24 CI 闸工具在 run 仍在进行时给出「可以合并」的假绿灯

创建：2026-10-24。发现人：main 同步任务（并入 `main` 的闸门，第 64 轮）。
影响范围：`tools/module-progress/ci-gate.mjs` —— **并入 `main` 的放行闸本身**。

本条不是功能缺陷，是**闸门的判据缺陷**。它的危险在于：它放行的那一刻，红色还没出现。

## 现象

本轮对同一个 PR #65、同一份代码，两次调用闸工具得到**相反**的结论：

| 调用时刻                                 | run 状态                            | 闸工具输出                                                                                                    | 退出码 |
| ---------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------ |
| run 刚开始（6 个作业全部 `in_progress`） | `in_progress`                       | `PR #65（run #40011998322）：（无失败作业）` / `新增失败作业：无` / `新增失败用例：无` / **`结论：可以合并`** | 0      |
| run 收尾后                               | `completed`（`conclusion=failure`） | 同一条 run，判出**新增失败用例 2 条** / **`结论：阻塞`**                                                      | 1      |

**同一份代码、同一轮 run，两次结论相反。**

## 根因：把「还没有结论」当成了「没有失败」

run 还在进行时，所有作业的 `conclusion` 都是 `null`。
闸工具统计失败作业时，若把 `conclusion == null` 一律计入「非失败」，就会得到「无失败作业」，
而基线侧那些**将要失败**的作业此刻也还没结论 ⇒

> 「PR 的失败集合 ⊆ 基线的失败集合」这条判据会**空洞地成立**。

这就是它比「全部没结论」更难察觉的原因：输出里列不出任何失败作业，
看上去像一份干净的、认真做过的比较，而不是一份空清单。

## 为什么必须单独记

`main` 的基线本身就是红的，所以合并闸走的是**基线相对判据**（PR 的失败不得比基线更多）。
在这种判据下，**「看不见失败」与「没有失败」在结果上无法区分** ——
闸门的「可以合并」只有在 run 真正收尾后才有意义。

同样的道理适用于任何「比较两个集合的失败项」的工具：
**在飞作业必须被显式识别出来，而不是默认归入「通过」。**

## 处置口径

- **工具侧**：`ci-gate.mjs` 取 run 状态时，若 `status != completed`，
  应按「状态取不到」处理（退出码 2，提示下轮再试），**不得**给出「可以合并」。
- **工具侧**：打印被判读的 run 的 `status` / `conclusion` / `head_sha`，
  让读结论的人能一眼看出这份结论是不是基于一个收尾后的 run。
- **调用侧**：拿到「可以合并」后、执行 `gh pr merge` 之前，
  **先确认该 run 的 `status` 是 `completed`** —— 不要用「大部分作业都跑完了」代替「跑完了」。
- **本任务口径**：run 收尾前，闸工具的结论一律不采信；自己下钻作业日志比对失败用例集合。

## 影响面

- 并入 `main` 的放行闸：假绿灯会让一个带新增失败的 PR 提前进 `main`。
- `main` 基线本身是红的 ⇒ 这类假绿灯**不会**因为「基线也红」而被兜住。

## 完成标准

- 对一个仍在进行中的 run 调用闸工具，退出码为 2，输出不含「可以合并」。
- 对一个已收尾的 run，结论与手工比对的失败用例集合一致。

## 修复记录（2026-10-24 第 65 轮，main 同步任务）

工具侧已修，`tools/module-progress/ci-gate.mjs`：

1. **新增 `runIsSettled(run)`**：只有 `status === 'completed'` 的 run 才算判据可用。
   `prRun()` 在取到未收尾的 run 时**抛错** ⇒ `main()` 走「取不到 CI 状态」分支 ⇒ 退出码 2。
2. **基线选取不再兜底取 `runs[0]`**。原来 `runs.find(r => r.conclusion !== null) ?? runs[0]`，
   在 main 上一个收尾 run 都没有时会把**在飞 run** 当基线（失败集合被低估 ⇒ 同样的假绿灯）。
   现在取不到合格基线就抛错。
3. **判据从 `conclusion !== null` 改成 `status === 'completed'`**。
   排队中（尚未开始）的 run，其 `conclusion` 同样是 `null`，旧判据会把它当成已收尾。
4. **被取消（`conclusion === 'cancelled'`）的 run 一律拒绝当判据** ——
   它的大量作业停在 `cancelled`/`skipped`，没有可用结论。
5. **显式按 `createdAt` 倒序取最新 run**，不再依赖 `gh run list` 的返回顺序。
6. **输出补上 run 标识**：`status` / `conclusion` / `head_sha`（短），
   读结论的人能一眼看出这份结论是不是基于一个收尾后的 run。

回归测试补在 `tools/module-progress/ci-gate.itest.mjs`（断言 26 条，全绿）：

- 在飞 run / 排队中 run / 状态缺失 ⇒ 一律不算收尾；
- **反向锁定假绿灯的形态**：在飞作业被当成「非失败」时，`compareRuns` 确实会给出「不阻塞」
  —— 这条断言把「为什么必须在取 run 处拦住」写成可执行的证据，而不是只写结论。

实测对照（同一份代码、两个场景）：

| 场景                                 | 修复前             | 修复后               |
| ------------------------------------ | ------------------ | -------------------- |
| run 还在跑（全部作业 `in_progress`） | 「可以合并」（错） | 退出码 2，状态取不到 |
| run 已收尾且失败                     | 阻塞               | 阻塞（判定不变）     |

⚠️ **本条只修工具侧，调用侧纪律仍然要守**：
工具已经不会再给假绿灯，但「拿到『可以合并』后先确认 run 收尾」这条纪律仍应保留 ——
万一工具被回退或绕过，纪律是最后一道防线。
