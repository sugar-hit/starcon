## 现象

worker 子会话在干活途中被网络层掐断（`net::ERR_HTTP2_PING_FAILED` / `ERR_CONNECTION_CLOSED`），
**车道的成果全部停留在工作区未提交状态**，0 个 commit。
下一轮 tick 重派该车道时，worker 从「读懂半成品」重新起步，
而且**上一任留下的未提交改动仍在工作区里**，两任 worker 在同一堆文件上叠加，归属边界越来越糊。

## 为什么这是流水线级问题（不是 worker 的锅）

1. **worker 侧网络熔断不在仓内可控范围**，但**「掐断即全损」是编排层可以消除的**。
2. 协议要求 worker「全部验证跑绿、commit 完之后」才 `land`，隐含假设是会话会活到最后。
   一旦这条假设不成立，代价 = 整条车道的工时归零，而流水线**没有降级路径**：只有重派，没有「捞回半成品」。
3. 与既有 backlog 的区别：
   - `2026-10-30-orphan-keepalive-daemon-gate-deadlock-round133.md` 记的是**持闸 tick 猝死 ⇒ 闸成孤儿**；
   - 本条记的是 **worker 猝死 ⇒ 成果无版本库留存**，两者触发条件相似但后果与修法完全不同，不能合并归档。

## 建议处置（按代价从低到高）

1. **【已在本轮临时启用】任务书写死「分阶段 commit」**：后端 → 契约 → 前端 → 格式修复，每阶段自绿即 commit。
   代价：零；收益：会话再被掐断时，最多丢「最后一个未 commit 的阶段」，
   而不再丢整条车道。**建议固化为协议条款**，写进 `PIPELINE.md` 的子任务模板第 8 条。
2. **【建议】`lane.mjs heartbeat` 记录工作区指纹**（脏文件数 + `git diff` 摘要哈希），
   让调度者能区分「worker 正在推进」与「worker 已死但工作区还有货」，
   并在 worker 猝死后立刻知道「这里有 N 项可复用的半成品」。
3. **【建议】`plan` 重派时把「上一任的未提交成果清单」写进任务书**，
   并明确标注「前任自陈未经核实」—— 本轮 18.1.2.2 的前任笔记就误判了耦合红点（详见 round-139 会话日志），
   若不标注，下一任 worker 会照着错的结论走。
4. **【待评估】worker 会话的心跳/保活**：当前只有 25 分钟一次的人工心跳，
   网络层掐断后 90 分钟 TTL 才判崩，**空窗期长达 65 分钟**，期间车道占着 `LANES` 名额不干活
   （本轮 `plan` 实测：两条僵尸车道占满 `LANES=2`，`newlyPlanned` 为空、`serviceBlocked` 为空 ——
   即「有活没人干」的典型形态）。是否能把判崩依据从「心跳年龄」改为「心跳年龄 + 工作区指纹无变化」？
