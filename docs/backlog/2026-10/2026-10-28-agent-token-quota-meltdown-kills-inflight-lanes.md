## 实测事实

2026-10-28 **19:03 前后**，四个会话在**同一时刻**死于**同一个错误**：

| 会话 | 角色 | 错误 |

| `mvs_7cb9160e7252420aabb24aa88693c0c8` | worker · Lane 13.4.2.1 成本结构 | `已达到 Token Plan 用量上限 (2056)` |

⇒ 这是**额度侧的统一熔断**，不是 worker 自身崩溃、不是代码问题、不是机器资源问题。

## 为什么它比代码问题更严重

1. **它杀掉的是「已经写了一半」的进度**。13.4.2.1 在被杀死前已经写完
   232 行迁移 + 2400 行后端 + 1032 行测试 + 1100 行前端 —— **只差验证和 commit**。
   这些成果**全部靠 worktree 幸存**才没丢。
2. **它会杀掉调度者本身**。第 122 轮调度者死于同一原因，导致它的「追加动作」只做了一半
   （13.4.1.1 落地并入做了，identity 修复车道的完整任务书交付质量打了折扣）。
3. **它直接放大了 push 积压**。调度者一旦死，`收尾三件套`（写说明 → commit → push）
   可能整轮不执行 —— 而那正是用户明确要求「每次开发完成都要」的三件事。

## 流水线的既有应对（已生效）

- **worktree 隔离**：车道代码写在各自 worktree，worker 被杀不会污染集成头。
- **orphan 回收机制**：`lane.mjs` 依据心跳（TTL 90 分钟 / 宽限 60 分钟）判活，
  被杀的车道下一轮 `plan` 自动列入 `toDispatch` 重派。
- **任务书落盘**：`.dev-agent/taskbooks/r<批次>-<模块>.md` 存的是**完整可重放**的任务书，
  重派时直接复用 ⇒ **取证成果不会随 worker 一起消失**。

## 待办

- [ ] **观察额度水位**：熔断前是否有可观测的信号（用量面板 / 报错前的额度告警）。
      若有，流水线可以在熔断前**主动少派一条车道**，而不是被动全灭。
- [ ] **额度恢复窗口优先回收「有半成品」的车道** —— 第 123 轮已按此处理：
      `plan` 把两条 orphan 车道列入 `toDispatch`，`reDispatched: 1`。
- [ ] **把「接手半成品」写进任务书第一节** —— 第 123 轮已做
      （`.dev-agent/taskbooks/r123-13.4.2.1.md` 第一节 = 摸清现状 + 跑 L0 编译闸看哪里断了）。
- [ ] **收尾三件套尽早做**：L2 一绿就先 push，**不要攒着** —— 攒着就可能被熔断打断。

## 建议（需要用户决定，流水线无权自行调整）

- 额度水位偏低时，**人工补额度**或在熔断窗口期**主动暂停派发**，
  让在途车道跑完再恢复 —— 而不是让熔断随机收割在途进度。
- 注意 `TOKEN_HORIZON=2026-10-25T00:00:00+0800` 已经过期（当前为降档模式：
  `LANES=4/2=2`、节流闸 50→100 分钟）。降档已经降低了消耗速率，但**没能挡住这次熔断** ——
  说明当时的消耗不是由车道数决定的，而是由**单个长任务**（写完 2400 行后端 + 1100 行前端）
  的 token 消耗决定的。**降档对这种熔断基本无效。**

### 对既有机制的两条修正

1. **「worker 全灭」不等于「调度者也死」** —— 判活要分两个主体看：
   调度者会话可能活着（还在跑 L2），worker 却是全灭的。
   2026-10-28 的「孤儿回收机制」依赖 worker 续心跳；这次心跳也停在 04:50/04:32，
   靠 TTL(90 min) 兜底判 stale —— **能兜住，但要等 90 分钟**，这正是本轮调度闸被占满一轮的直接原因。
2. **`plan` 的派发前冲突预检会拦住 18.3.1.2** —— 它的 worktree 里躺着 1596 行未跟踪文件。
   协议规定「worktree 已存在且含未跟踪文件 ⇒ 立刻停止派这条，零改动退出」。
   ⇒ **重派前必须先决定接管还是弃掉**，否则要么卡住、要么把半成品再丢一次。
