## 为什么它比代码问题更严重

1. **它杀掉的是「已经写了一半」的进度**。13.4.2.1 在被杀死前已经写完
   232 行迁移 + 2400 行后端 + 1032 行测试 + 1100 行前端 —— **只差验证和 commit**。
   这些成果**全部靠 worktree 幸存**才没丢。
2. **它会杀掉调度者本身**。第 122 轮调度者死于同一原因，导致它的「追加动作」只做了一半
   （13.4.1.1 落地并入做了，identity 修复车道的完整任务书交付质量打了折扣）。
3. **它直接放大了 push 积压**。调度者一旦死，`收尾三件套`（写说明 → commit → push）
   可能整轮不执行 —— 而那正是用户明确要求「每次开发完成都要」的三件事。

## 流水线的既有应对（已生效）

- **worktree 隔离**：车道代码写在各自 worktree，worker 被杀不会污染集成头。
- **orphan 回收机制**：`lane.mjs` 依据心跳（TTL 90 分钟 / 宽限 60 分钟）判活，
  被杀的车道下一轮 `plan` 自动列入 `toDispatch` 重派。
- **任务书落盘**：`.dev-agent/taskbooks/r<批次>-<模块>.md` 存的是**完整可重放**的任务书，
  重派时直接复用 ⇒ **取证成果不会随 worker 一起消失**。

  让在途车道跑完再恢复 —— 而不是让熔断随机收割在途进度。
