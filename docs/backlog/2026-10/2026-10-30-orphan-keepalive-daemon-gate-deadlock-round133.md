## 三、round-133 的接管（复用 batch-107 的原子路径）

```bash
# ① 停掉孤儿守护（该脚本没有 STOP-KEEPALIVE 机制，只有循环上界 ⇒ 只能结束进程）
kill 79126 79124

# ② 走 lane.mjs 自己的陈旧闸接管分支（单 node 进程，窗口 < 1ms）：
#    把闸目录 mtime 拨回「持闸者真实死亡时刻」（owner 文件里的时间戳，不是「现在 - 71 分」）
#    ⇒ mtime 反映事实，不是伪造新鲜度
#    然后执行与 lane.mjs gateAcquire() 逐行等价的逻辑
node .dev-agent/takeover-r133.mjs
# ⇒ age=18161s > TTL=4200s ⇒ 走陈旧闸接管分支 ⇒ 写入新 owner
```

**与「清闸硬闯」的区别**（这三点是本轮刻意守住的）：

1. **不调用 `gate release`**（它是无条件 `rm -rf` 整个闸目录）⇒ 不制造 release→acquire 的竞速窗口；
2. **mtime 拨回的是持闸者真实死亡时刻**，不是「现在 - 71 分」⇒ 闸龄判据仍如实反映「死了 5 小时」；
3. **全程在同一个 node 进程里完成**（重建闸目录 + 写 owner 之间无间隙）。

## 四、真正的修法：把续期守护本身改成「有界 + 可自终止」

前三次复发都暴露同一个根因：**续期守护是「崩溃即孤儿」的形态**——
它不知道自己的持有者已经死了，于是无限刷新闸目录 mtime，把协议的 TTL 自愈路径彻底堵死。

round-133 起用的 `.dev-agent/keepalive-r133.sh` 有**三重退出条件**（任一满足即退出）：

| # | 退出条件 | 覆盖的场景 |
| --- | --- | --- |
| 1 | **闸目录被删**（= 本轮正常收尾的 `gate release`） | 正常结束 ⇒ 无需人工干预，守护自己消失 |
| 2 | **停止标记** `.dev-agent/STOP-KEEPALIVE-R133` 存在 | 人工或下一轮 tick 立即停 |
| 3 | **墙钟上界** 10800 秒（3 小时） | **调度者崩溃** ⇒ 守护也会自己死，绝不变成「能无限续命的孤儿」 |

另：上界用**墙钟判据**而不是**循环计数判据** ——
机器有停顿时 `sleep` 会被拉长，「有界循环」在有停顿的机器上不等于「有界」
（batch-107 的取证原文）。

**这三条同时消掉了两个老问题**：母文档待办「守护应带持有者 PID 存活检测，持有者一死就自杀」
由「墙钟上界 + 闸目录消失」近似满足；而「tick 崩在闸里，最多挡住下一轮」的自愈路径**重新可用**。

## 五、仍未修（交人工 / 后续车道）

- [ ] **`lane.mjs` 的闸龄判据仍应从「闸目录 mtime」改成「最新 keepalive 文件的 mtime」**
      （母文档原有待办，未做）。即便守护有界，只要它还在跑，闸龄判据仍被刷新；
      改成「最新 keepalive 文件的 mtime」后，守护停 ⇒ 闸龄立刻开始计。
- [ ] **`gate release` 应只删自己持有的闸**（母文档原有待办，未做）。
      本轮之所以不用 release+acquire，正是因为 release 是无条件删整个闸目录。
- [ ] **`lane.mjs` 应提供一个受管的「等待并接管」入口**（带 owner 存活检查 + 单进程原子），
      不要让每个 tick 各自写临时接管脚本。本轮的 `.dev-agent/takeover-r133.mjs` 就是临时脚本，
      **应该沉淀进 `lane.mjs`**（例如 `lane.mjs gate reclaim`）。
- [ ] **续期守护应随 tick 一起结束**（`finally` 里终止），并把「守护 PID」写进
      `dispatch.gate/` 里，让下一轮 tick 能一眼看出「上一个 tick 的守护还活着」。

      ⇒ **「owner PID 不存在」本身不能作为「持闸者已死」的独立证据** ——
      本文件第二节取证清单的第 1 条（round-133 记的「PID 73961 不存在」）正属这一类，

## 六、流程教训

**「撞闸 ⇒ 零派发」这条规则的前提是「持闸者是活体 tick」。**
当持闸者已死（四重以上证据）时，一味照搬「零派发 + 汇报」会变成
**把一个可自愈的故障固化成长期停机**——round-130/131/132 连做三次，
每次都点名要人工解，但人工没介入，流水线就多停了 3 轮。

⇒ 母文档里已经写好的「**先取证再决定**」纪律，应该在**第一次**取证就执行，
而不是连续三轮只取证不处置。
