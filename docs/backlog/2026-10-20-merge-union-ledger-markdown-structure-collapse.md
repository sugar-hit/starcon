# merge-union 台账分支：按整行文本去重，把台账的 markdown 多表结构压塌

> 发现时间：2026-10-20 批次 33 交付轮（`merge-ready` 合并 4 条车道时）
> 严重度：**中** —— 数据不丢、解析不坏，但**渲染坏**，且**每一次并入都会发生**
> 归属：`tools/module-progress/merge-union.mjs`（台账合并分支）

---

## 现象

`docs/product/capability-blueprint/module-progress.md` 是**四张 markdown 表**拼成的文档
（总览 / 分阶段进度 / 分系统进度 / 465 行主台账），各表自带 `| --- |` 分隔行。
每次 `merge-ready` 合并车道后，该文件会变成：

| | 空行数 | `\| --- \|` 分隔行数 | 台账行数 | 唯一模块 ID |
| --- | --- | --- | --- | --- |
| 并入前（车道分支 / 正常提交） | **17** | **4** | 465 | 465 |
| 并入后（`merge(...)` 提交） | **1** | **3** | 465 | 465 |

⇒ **并入一次，少 16 个空行、少 1 张表的分隔行。**

## 根因

`merge-union.mjs` 的台账分支（`.gitattributes` 里
`docs/product/capability-blueprint/module-progress.md merge=contract-union`）走的是
**行级兜底并集**：把 `ours` 与 `theirs` 的行拼起来，**非台账行按整行文本去重**：

```js
if (!m) {                       // 不是台账行（模块 ID 行）
  if (seen.has(line)) continue; // ← 整行文本相同就丢
  seen.add(line);
  outLines.push(line);
}
```

问题在于**空行和重复的分隔行文本完全相同**：

- 17 个空行 ⇒ 文本都是 `''` ⇒ 只留 1 个；
- 5 列分隔行 `| --- | --- | --- | --- | --- |` 在「分阶段进度」与「分系统进度」两张表里
  各出现一次 ⇒ 文本相同 ⇒ 只留 1 个 ⇒ **「分系统进度」表失去分隔行**。

⇒ 该表在 GitHub / IDE 里**不再渲染成表格**，退化成普通文本行；
段落之间的空行也被吃掉 ⇒ 段落粘连成一大坨。

## 为什么一直没被发现

**它被调度者每轮的例行 `sync.mjs` 悄悄修回去了。**
`sync.mjs` 是**重新生成**整个台账文件（不是打补丁），生成物天然带完整结构（17/4）。
于是每一批的节奏变成：

```
merge(...) 提交   → 1/3   ← 结构塌了
下一轮 sync.mjs   → 17/4  ← 顺手修好
```

⇒ 从台账的**最终状态**看永远正常，只有翻历史才能看见这个来回。
本条是靠**逐个 merge 提交比对空行/分隔行数**才暴露出来的（2026-10-20 第一次系统性扫）。

## 影响评估

- ❌ **不丢数据**：465 行台账行、465 个唯一模块 ID 全在；`sync --check` 绿；
  合并后的台账里 batch-33 四行的「已交付」状态与证据完整（`betterRow` 规则：证据非 `—` 优先 → 状态 已交付>进行中>未开发 → 证据长度）。
- ⚠️ **渲染坏**：「分系统进度」表失去分隔行 ⇒ 不再是表格。
- ⚠️ **观感坏**：段落粘连。
- ⚠️ **流程脆弱**：**依赖「下一轮一定会跑 sync.mjs」来兜底**。
  任何一轮若在 `merge-ready` 之后、`sync` 之前就把台账提交出去（或者干脆不跑 sync），
  塌陷的版本就会进版本库。
- ⚠️ **闸外可见**：`SYNC-MAIN.md` 的 main→集成头同步任务也用同一个驱动合台账，
  它提交的那一刻**不会**跑 `sync.mjs` ⇒ 那条路径产出的台账**就是塌的**。

## 建议修法

改 `merge-union.mjs` 的台账分支，**不要对非台账行按整行文本去重**。可选：

1. **推荐：以 ours 为主干，只追加 theirs 里 ours 没有的整行**，
   并**跳过空行与 `| --- |` 分隔行的去重**（这两类行应按出现次序保留）。
   台账的非台账行（表头、分隔行、统计行）本身是**脚本生成**的，
   ours 与 theirs 的差异只会在统计数字上 —— 真正的并集语义仍然只对模块 ID 行生效。
2. 或者：台账分支**整体交给 `sync.mjs` 重新生成** —— 驱动在台账上只做「不报错」，
   实际内容由 `sync.mjs` 依据蓝图重算（状态与证据按模块 ID 继承）。
   这最符合台账文件头「本文件由 `sync.mjs` 生成，请勿手工增删行」的定位。
3. 最小改动：把 `seen.has(line)` 的判断加上 `line.trim() === '' || line.startsWith('| --- |')` 的例外。

## 验收判据

- 合并一次后：空行数与分隔行数与并入前**完全一致**（17 / 4）。
- 台账行数 465、唯一模块 ID 465。
- 批次 33 四行（4.4.1.3 / 9.2.1.1 / 9.2.2.1 / 4.5.2.2）状态为「已交付」且证据完整。
- `node tools/module-progress/sync.mjs --check` 输出「台账与蓝图一致」。

> ⚠️ 修这个驱动要**同时**考虑 `SYNC-MAIN.md` 那条路径 —— 它也依赖同一个驱动，
> 不能只按「调度者会跑 sync」来设计。
> 改驱动属于**工具链**改动，不属任何业务车道 ⇒ 应单独派一条修复车道，
> 不要塞进正在跑的批次。
