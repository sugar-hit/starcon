## 一、本轮最关键的一件事：r154 的后端结论无效，因为它跳过了 5 个模块

r154 的 `mvnw verify` 在 `warehouse` 失败后**默认跳过了 `trade` / `crm` / `finance` / `reporting` / `platform`**：

```
[INFO] warehouse .......................................... FAILURE [13:42 min]
[INFO] trade .............................................. SKIPPED
[INFO] crm ................................................ SKIPPED
[INFO] finance ............................................ SKIPPED
[INFO] reporting .......................................... SKIPPED
[INFO] platform ........................................... SKIPPED
```

而 batch-128 交付的四个模块**全部落在 `platform` 服务**（16648 行新代码）⇒
**r154 从头到尾没有跑过本批交付的任何一行新代码**。

⇒ r154 的 `mvn-verify exit=1` **不是本批引入的回归**，它是「warehouse 先炸 ⇒ 后面根本没跑」。
拿它当「本批红了」的证据是**误判**：真正的全量结论从未产生过。

**修法**：本轮 L2 脚本改用 `./mvnw verify -fae`（fail at end）——
单个模块失败**不再跳过后续模块**，一次跑完就能拿到**全量**失败集，
而不是只看到第一个失败模块就以为「后面都没问题」。

> 这一条已写进 `.dev-agent/l2-r155.sh` 的脚本注释，作为后续每轮的默认做法。

## 二、本批新增失败的真实归因：1 条，是**断言写在错误的层**

### 2.1 前端：`ai-forecast-allowlist.test.ts` 的「兄弟车道互不误吃」用例

**红在哪**：`platform/ai/usage/capabilities` 期望 404，实际 200。

**根因**：那条断言用 **HTTP 状态码**表达「本车道的 `ai/forecast` 条目没有吃掉兄弟车道的形状」。
但这条语义在 HTTP 层**根本不可表达**：

| 时点 | `platform/ai/usage/capabilities` 的 proxy 结果 | 原因 |
| --- | --- | --- |
| 兄弟车道（18.4.3.1）**并入之前** | **404** | 没有任何条目放行它 |
| 兄弟车道**并入之后** | **200** | 被**兄弟自己那一条**放行 |

同一个语义，并入前后 HTTP 状态码**含义相反** ⇒
拿状态码写这条断言 = 把断言绑死在「兄弟还没并入」这个分支拓扑上，**并入的那一刻它必红**，
而红的原因与本车道无关。

**修法**：断言挪到**正则层** —— 本车道的 pattern 对兄弟的形状必须**不匹配**。
这条性质与「兄弟是否已并入」无关 ⇒ 恒成立、恒有意义。
另加一条「兄弟形状恰好被兄弟自己那一条放行」的正向断言，钉住「求并，不是二选一」。

**顺带消掉重复**：把 api-proxy 条目的 AST 解析抽成 `apps/web/src/lib/api-proxy-entries.ts`（测试侧共用）。
`notification-template-allowlist.test.ts` 里原本已有一份**逐字重复**的实现 ——
两条车道都在 `/platform/ai/…` 命名空间下、白名单是累积型共享文件，
判定口径必须一致，否则两个车道会得出互相矛盾的结论。

**验证**：`ai-forecast` 6 + `ai-usage` 5 + `notification-template` 3 = **14 例全绿**；
`pnpm --filter @starcon/web typecheck` 通过；增量格式闸 `ok:true`（94 个改动文件 / 0 违规）。

### 2.2 后端：`SafetyStockIntegrationTest#同一个SKU的自有仓档与平台仓档可以并存`

**红在哪**：`expected: 2L but was: 1L`（`page.total()` 只查到 1 档，实际建了 2 档）。

**归因取证**（这是本轮做实的一步，不是推测）：

| 证据 | 结论 |
| --- | --- |
| `git diff 6b8ae806 b4a6deef -- backend/services/warehouse backend/libraries` | **空** ⇒ warehouse 代码与库**一个字节没变** |
| r153（`6b8ae806`）warehouse 模块 | **SUCCESS**，同样 **1674** 例，0 失败 |
| r154（`b4a6deef`）warehouse 模块 | FAILURE，同样 **1674** 例，**1** 失败 |
| 本批改动的后端文件 | **只有 `platform` 服务 + 4 个 identity 权限迁移**，warehouse 一行没碰 |

⇒ 同一份 warehouse 代码，r153 跑同样的 1674 例全绿、r154 跑同样的 1674 例红 1 条，
而本批**没有碰过 warehouse 的任何一行** ⇒ **这不是本批引入的回归**。

**判定**：这是 warehouse 侧一条**存量**的、与本批无关的墙钟敏感失败
（本仓已有同类先例：`723cee8f` 寄售结算跨钟域、`7c15c64c` 渠道夹具相对锚点、
`694ac30d` 银行对账夹具相对锚点 —— 都是「测试依赖挂钟边界 ⇒ 某个时段必红」）。
r154 的墙钟落在 `02:13`（仓库历史上「本地 00:00–08:00 必红」的窗口内），
r153 的墙钟落在 `00:49`（同一窗口）⇒ 两次都撞在窗口里，**但只有一次红** ⇒ 典型的边界竞态。

⇒ 按覆盖规则第 4 条，它**不落在**本批新增清单里，**不构成本批回归**；
本轮把它记进存量基线（`.dev-agent/l2-baseline.txt`），让后续轮次能正确判「存量红 vs 本批新增」。
