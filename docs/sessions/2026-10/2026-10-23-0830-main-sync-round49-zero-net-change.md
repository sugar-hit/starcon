# 2026-10-23: 集成分支并入 main（第 49 轮 · 零净变更复核）

## 摘要

本轮把 `integration/module-dev` 同步进 `main`。起手体检显示两分支的**树差异非空**（73 个文件），
按协议不能直接判定「无新内容」，于是进入真实合并取证。

合并形态是「真合并 + 57 个 add/add 冲突」。逐文件取证后确认：**这 57 个冲突全部是排版差异，
不存在任何内容分歧，而且主分支侧已经是仓库规范排版、集成分支侧不是**。
据此 57 个冲突全部取主分支侧，解完冲突后**落地树哈希与 `main` 的树哈希逐字节相同**
（两侧同为 `89ad580a`），即集成分支**没有任何主分支尚未包含的内容**。

结论：**零净变更，本轮无待合入的新交付。**

## 决策 / 结论

### 1. 「有没有新内容」以落地树哈希为准，本轮为零净变更

- `upstream/main` tip = `c6e73834`（树 `89ad580a`），`upstream/integration/module-dev` tip = `3a0dbe33`。
- 两侧树差异报 **73 个文件**（863 增 / 2764 删），看上去像一次实增量。逐文件核对后全部不是内容差异：

| 类别                     | 文件数 | 核对结论                                                                   |
| ------------------------ | ------ | -------------------------------------------------------------------------- |
| 两侧都存在，差异只在排版 | 57     | 经仓库规范排版归一化后**逐字节相同**（57/57）；主分支侧已是规范态（57/57） |
| 只在主分支侧存在         | 16     | 主分支独有内容，合并动作不改变它                                           |
| 只在集成分支侧存在       | 0      | **空集** —— 集成分支没有任何主分支缺的内容                                 |

- 冲突面 **57 个文件全部是 add/add**（相对共同祖先 `4ab1d8d`，两侧各自新增同一批文件）。
- 在专用 worktree 里真实合并、解完 57 个冲突后 `git write-tree` = `89ad580a…`，
  与 `git rev-parse upstream/main^{tree}` **完全相同**。

⇒ **主分支没有任何集成分支尚未包含的内容。** 判定依据是落地树哈希，不是树差异：
树差异是双向的，既含「集成分支有、主分支没有」，也含「主分支有、集成分支没有」，
后一部分不该被合入动作改变。

### 2. 冲突解法：取主分支侧，零内容丢失、不增加格式债

两条互相独立的取证合起来支撑「取主分支侧」：

- **规范化取证**：用仓库自身的排版器（3.9.9 + 仓库配置 + tailwind 插件）分别归一化两侧的 blob。
  主分支侧 **57 个文件里 0 个发生变化**，集成分支侧 **57 个文件全部发生变化**，
  归一化之后两侧逐字节相同 ⇒ 差异只在排版，且主分支侧就是规范形态。
- **阴性对照**：为证明上面这条判据有区分力，向集成分支侧注入 4 类已知语义改动
  （改字符串字面量 / 新增导出常量 / 改数字字面量 / 改标题文字），
  在 4 个样本文件上共 12 次有效注入，**12 / 12 全部被检出**；
  另有对照实验证明归一化通道本身是活的（故意写坏的代码喂进去，输出 ≠ 输入）。

- **取主分支侧 ⇒ 语义零损失**：既然归一化之后两侧内容逐字节相同，
  那么「取主分支侧」得到的就是「两侧的并集按规范排版之后的结果」，不可能丢内容。
- **取集成分支侧反而会加重存量失败**：那 57 个文件会变成未格式化状态，
  `format:check` 的失败文件数凭空多 57 个，直接抬高 `Lint` 作业的失败量。
  本轮落地结果实测 **57 / 57 个已解冲突文件全部规范合规** ⇒ **零新增格式债**。

⚠️ `merge-resolve.mjs` 把这 57 个文件**全部**判成「并入（人工）」——
它比对的是文件的**原始字节**，而主分支侧是**排版归一化之后**的字节，
原始字节必然对不上 ⇒ **该工具在纯排版场景会全量误报**，
它的结论必须与格式归一化取证**交叉验证**后才能采信。

### 3. 白名单文件本轮不在冲突面内

`apps/web/src/lib/api-proxy.ts` 两侧**逐字节相同**，未进冲突面 ⇒
累积型白名单「两层 alternation 求并」的陷阱本轮不触发。
白名单代理路由守卫测试仍然照跑（见第 5 节）。

### 4. 后端与契约产物完全未受影响

- `backend/` 整树两侧**完全相同**，零差异。
- 迁移脚本集两侧文件名集合**差集为空**。
- `packages/api-contracts`、`packages/sdk` 契约产物**零差异**。
- 功能台账 `docs/product/capability-blueprint/module-progress.md` 两侧**逐字节相同**。

⇒ 本轮合入动作**不可能**引入后端回归或契约漂移。

### 5. 定向验证全绿

- 台账行数 **465**、模块 ID **无重复**；台账与功能蓝图一致性自检**通过**。
- 静态预检（后端迁移里的危险形状）：迁移脚本集两侧内容哈希相同（`8394a0be…`），
  存量计数 **88 / 42 / 21**（`ADD COLUMN` 无默认值 / `SET NOT NULL` / `CHECK` 约束）
  属既有存量，本轮**未新增、未触碰任何迁移脚本**。
- 冲突面专项验证：**9 个测试文件 / 338 例全通过**
  （访问安全、买家黑名单、评价回复白名单守卫，访问安全 / 关怀提醒 / 消息发送 / PII 管理模型，
  以及白名单代理路由守卫两组）。

### 6. 没有跑本地全量 L2

协议第 5.1 节的三个例外条件**均不成立**（未动后端业务代码与迁移脚本、
台账自检是绿的、定向测试全绿）。更重要的是：本轮**落地树与 `main` 的树逐字节相同**，
重跑全量 L2 只会复现 `main` 的既有状态，**没有信息增量**；
且本地全量属发热高峰，全量闸由 CI 的远端 runner 承担。

## 关键 trade-off / 讨论

- **「取主分支侧」与「取集成分支侧」的方向不随意切换。**
  判据始终是同一条：「归一化之后两侧是否逐字节相同，以及哪一侧已经是规范形态」。
  本轮主分支侧是规范形态 ⇒ 取主分支侧。
- **树差异不是「有没有新内容」的判据。** 本轮树差异报 73 个文件，
  落地树哈希却证明净增量为零；若只看树差异，就会每轮都以为有大增量、每轮都开一个空 PR。
- **归一化相等这类结论必须配阴性对照。** 只有对照实验（通道是活的）不够 ——
  通道可能是「活的但无区分力」的。本轮注入 12 次已知语义改动全部被检出，
  才敢采信「57 / 57 逐字节相同 ⇒ 内容等价」这个结论。
- **闸工具的结论不能直接采信。** 上一轮已记录：它选基线 run 时不检查该 run 的作业是否收完，
  会把「基线没有失败作业」虚读出来从而假阻塞。本轮若开同步 PR，须先确认基线 run 收完。
