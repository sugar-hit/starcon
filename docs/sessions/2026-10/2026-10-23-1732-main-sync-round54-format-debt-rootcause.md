## 决策摘要

本轮 `origin/main` 仍领先集成头 **20 个提交**（`merge-base = 4ab1d8d1`），与第 53 轮**同一个 tip、同一个 merge-base、同一批 20 个提交**。
`git merge --no-ff origin/main` 再次失败：**58 个文件冲突**（57 个 add/add + 1 个 content），与第 53 轮**逐个文件名完全一致**。

按协议「冲突不自行解决」，已 `git merge --abort` 并取证上报。

**但本轮没有停在「又一次冲突」**：第 53 轮的结论是「冲突面 100% 是 Prettier 格式漂移，根因是集成头这 58 个文件本身没跑过 Prettier」，
它把修法列为待办却**没有验证修法是否成立**。本轮用纯 git plumbing 做了两次模拟，把「修完长什么样」量化了出来：

> **先把集成头这 58 个文件按仓库自己的 `.prettierrc` 格式化，再合并 ⇒ 冲突从 58 个降到 1 个**，
> 且**净内容变化是 0 行业务代码**（只多出 18 个 main 侧的文档 + 台账的纯空行差异）。

也就是说：**第 53 轮判断的根因是对的，而且这个根因是可以在集成头侧单方面消除的，不需要动 main、不需要改发布侧。**

## 关键 trade-off

- **为什么不自己解冲突**：协议第 3 步明令「冲突不自行解决」，`git merge --abort` 后上报。
  本轮遵守了协议，**没有把模拟结果落成任何提交或分支**（模拟全部走 `git merge-tree` + 临时 index + 临时 tree/commit 对象，
  **未改任何 ref、未改工作区、未改真实 index**）。
- **为什么这次值得多花力气做模拟**：连续两轮撞同一堵墙，而第 53 轮的待办第 2 条写着
  「建议二选一：流水线 L2 增加一道 `prettier --check` 闸；或同步任务改用『先对 ours 跑 Prettier 再三方合并』的策略（**需要改协议，本任务不擅自改**）」。
  ⇒ **模拟正好是替「需要改协议」这条待办做前置验证**：如果模拟证明该策略可行，下一轮改协议就有据可依；
  如果证明不可行，就该止损改别的方向。**本轮只验证、不擅自改协议。**
- **为什么不顺手把格式债清掉**：`format:check` 当前基线是 **762 个文件不合规**，其中大量是**本轮不该动的历史文件**
  （`packages/ui/**`、`tools/module-progress/**`、几十篇旧会话日志）。一次性全量格式化会让集成头产生一个
  上千文件的巨型 diff，**远超「同步」这一职责边界**，且会与流水线正在跑的批次打架（并发同 worktree 构建）。
  ⇒ 属于「需要改协议 + 需要人拍板范围」的事，本任务不擅自做。

### ② 格式归一化取证：`prettier(ours) == theirs` **57 / 58**

⚠️ **本轮修正了第 53 轮取证方法里的一个坑**：归一化**必须带仓库自己的 `.prettierrc`**。
用 Prettier 默认配置（`printWidth` 80）跑，只有 **44 / 58** 相等，会**误判成「14 个文件有实质内容差异」**；
带 `--config .prettierrc`（`printWidth: 100` + `prettier-plugin-tailwindcss`）跑，才是 **57 / 58** 相等。

> 这个坑很关键：`.prettierrc` 里的 `printWidth: 100` 与尾随逗号 `trailingComma: "all"` 正是两侧排版分叉的来源，
> 归一化时不用仓库配置 = 用错误的度量衡去量排版差异。
