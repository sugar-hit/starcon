# 2026-10-22 12:00：集成分支零变更复核与取证配方失效陷阱

## 摘要

本轮是同一个零变更窗口的第三轮复核（11:00 那轮开出 PR #34，11:30 那轮做了独立复核）。
本轮**没有新交付要合入**：集成分支 `integration/module-dev` 自 08:30 起未再推进，
`main` 侧自上一轮起也没有新提交，因此合入结果对 `main` 零影响。

本轮的实际产出有两项：

1. **独立复核了零变更结论**，并比上一轮多做了一次「归一化空白」的口径校正 ——
   发现上一轮记录的「集成侧独有 4 行」在未归一化口径下其实是 6 行，
   差在 Markdown 表格的分隔行与列宽上。结论方向不变，但口径需要写进协议。
2. **发现并修正了协议 4.6 节取证配方的一个真实缺陷** ——
   `git show :2:` / `git show :3:` 在 `git add` 解冲突文件之后就不再可用，
   而 4.6 节没有写明这个顺序约束，agent 很容易先 add 再取证、然后卡在
   `fatal: path ... is in the index, but not at stage 2`。

## 决策 / 结论

### 1. 零变更结论可复现：落地树 == main 树

在专用 worktree 里从 `upstream/main` 重新做了一次完整合并并逐块解冲突：

| 检验项                 | 实测值                                                     |
| ---------------------- | ---------------------------------------------------------- |
| 树差异                 | 39 个文件，`+137636 / −143293`                             |
| 提交数口径             | `rev-list --left-right --count` 报 31 / 464（虚的）        |
| 合并预演的冲突文件     | **1 个**（协议文件本身）                                   |
| 契约文件自动求并       | 10 个契约文件全部自动求并，无未解冲突                      |
| **解完冲突后的落地树** | `ac76155e3123a8ae562fd04fa394376944603b76`                 |
| **main 树哈希**        | `ac76155e3123a8ae562fd04fa394376944603b76`（**完全相同**） |

独立验证：解完冲突后 `git diff --stat upstream/main --cached` 为空
⇒ index 与 `main` 树逐字节相同。

⇒ **合入后 `main` 一个字节都不会变 ⇒ 本轮不开功能合入 PR。**

### 2. 树差异 39 个文件全部是 main 侧独有，与集成分支无关

逐文件核对了 39 个差异文件的方向：

- **25 个是 `D`（main 有、集成分支没有）** —— 全是 `main` 侧独有的会话记录、
  `tools/progress-site/` 看板工具、`docs/backlog/` 条目。
  这些是历次同步 PR 与其它 PR 留在 `main` 上的产物，集成分支从来没有过。
  真合并时 git 会自动保留 `main` 侧，所以它们**不该**被合入动作改变。
- **13 个是 `M`（两侧都改过）** —— 10 个契约文件 + `.gitignore` + 协议文件。
  其中 `.gitignore` 的差异是 `main` 侧多了两行（进度看板构建产物的忽略规则），
  同样是 main 侧独有。
- **0 个是 `A`（集成分支有、main 没有）** ⇒ 集成分支侧没有任何新文件。

⇒ 树差异非空**完全由「main 侧独有」造成**，与「集成分支有新内容」无关。
这与 2026-10-22 早先各轮记录的结论一致。

### 3. 协议文件的冲突：取 main 侧，零丢失

`merge-resolve.mjs` 给出 `[并入（人工）]`，理由是「main 侧的文件版本不在集成分支的历史里」。
按 4.6 节的精神自行取证后，判定为**取 main 侧**：

| 口径                      | 集成分支侧独有 | main 侧独有 |
| ------------------------- | -------------- | ----------- |
| 未归一化空白（`sort -u`） | 6 行           | 128 行      |
| **归一化空白后**          | **4 行**       | 124 行      |

集成分支侧那 4 行逐条核验，**全部是旧措辞被 main 侧新版替换**：

| 集成侧独有的行                          | main 侧对应的新版形态                |
| --------------------------------------- | ------------------------------------ |
| `&& echo "无新内容"                     |                                      | echo "有新增内容"` | 已换成落地树判据的 `&& echo "零变更：本轮不开 PR" |     | ...` |
| `\| 没有开着的 PR **且** 有新内容 \|`   | 已换成 `落地树 != main 树`           |
| `\| 没有开着的 PR **且** 没有新内容 \|` | 已换成 `落地树 == main 树（零变更）` |
| 表格分隔行（列宽不同）                  | 只是列宽差异，同一张表               |

⇒ 取 main 侧零丢失，解冲突后文件与 main 侧逐字节相同（`b280bc636ba84650`）。

### 4. 发现协议 4.6 节取证配方的真实缺陷并已修正

4.6 节给的配方是：

```bash
git show :2:<file> | sort -u > /tmp/side_main.txt   # stage 2 = main 侧
git show :3:<file> | sort -u > /tmp/side_head.txt   # stage 3 = 集成分支侧
```

**缺陷**：`git add` 一执行，stage 2 / stage 3 就被清掉。
本轮第一次跑这套配方就撞上了：

```
fatal: path 'tools/module-progress/MAIN_MERGE_CRON_PROMPT.md' is in the index, but not at stage 2
hint: Did you mean ':0:tools/module-progress/MAIN_MERGE_CRON_PROMPT.md'?
```

而 4.6 节没有写明顺序约束 ⇒ agent 很容易按「先解冲突 add、再看证据」的顺序做，
然后卡住并误以为是自己操作错了。

**修正内容**（已写回协议 4.6 节）：

1. 明确**取证必须早于 `git add`**，
2. 给出已 add 之后的等价替代写法（`git show upstream/main:<file>` /
   `git show upstream/integration/module-dev:<file>`），
3. 补上**两侧必须用同一条命令归一化空白**的要求 ——
   否则 Markdown 表格的分隔行与列宽会被算成「集成侧独有内容」，
   差集结论失真（未归一化 6 行 vs 归一化 4 行）。

## 关键 trade-off / 讨论

**为什么不因为「树差异 39 个文件」就开 PR？**

树差异是双向的，它回答的是「两个分支的内容是否不同」，
而要回答的问题是「合入后 `main` 会不会变」。这两件事不等价。
判据是落地树哈希，本轮实测落地树与 `main` 树完全相同 ⇒ 不开 PR。

**为什么本轮还是要动一次 main？**

零变更本身不产生交付，但本轮有两项**新东西**：

1. 协议 4.6 节的取证配方缺陷是**真实会让下一轮 agent 卡住**的问题；
2. 归一化口径的差异会让「集成侧独有行数」在不同轮次报出不同数字，
   后续复核者会误以为是新变化。

按仓库的沟通上下文规范（有结论的会话要落 `docs/sessions/`），
这两项都需要落到仓库里，所以本轮只提交**协议修正 + 本会话记录**，
不带任何功能代码。

**为什么契约文件不用再单独做语义比对？**

落地树哈希与 `main` 树相同，这已经蕴含了「合并结果里每个契约文件的字节
与 main 侧完全一致」⇒ 契约无漂移。上一轮（11:30）已用 JSON 归一化做过更细的
语义等价复核（paths 键集合、schemas 键集合、规范化整篇文档全等），
本轮不需要重复。
