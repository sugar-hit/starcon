## 摘要

本轮把 `integration/module-dev` 并入 `main` 的动作完整走了一遍（建 worktree → 真合并 → 解冲突 → 核落地树），
结论是**合入后 `main` 一个字节都不会变**，因此**本轮没有开同步 PR**。

真正产出的不是一次合并，而是**把上一轮遗留的一个结构性缺陷查清楚了**：
第 32 轮把那份会话纪要的表格分隔行规范化后落到了 `main` 上，但这份规范化**从未回流到集成分支**，
于是同一处 add/add 冲突在下一轮原样复现。

本轮还踩到并定位了一个**会让冲突裁决得出相反结论的取证陷阱**（详见「决策 / 结论」第 3 条）。

## 决策 / 结论

### 1. 零变更结论成立，且必须做两次判定

树差异与落地树哈希的实测值：

| 检验项             | 实测值                                                     |
| ------------------ | ---------------------------------------------------------- |
| 树差异             | 2 个文件（`+66 / −146`）                                   |
| 提交数口径         | 虚高，不可作为判据                                         |
| 合并预演的冲突文件 | **1 个**（会话纪要副本，add/add）                          |
| 解完冲突后的落地树 | `5298ea7b28276e007be11d7b289f8f4283051da8`                 |
| **`main` 树哈希**  | `5298ea7b28276e007be11d7b289f8f4283051da8`（**完全相同**） |

真合并后 `git write-tree` 与 `git rev-parse upstream/main^{tree}` 逐字节相等，
`git diff upstream/main <落地树>` 为空 ⇒ **零变更**。

台账复核：`module-progress.md` 仍为 **465** 行 L4 记录，无重复 ID（`sort | uniq -d` 为空）。

### 2. 同一处 add/add 冲突连续两轮复现，根因是规范化结果没有回流

冲突文件：`docs/sessions/2026-10/2026-10-22-batch-64-dispatch-crm-compliance-lanes.md`。

两侧的行级差集**只有 Markdown 表格分隔行**（分隔行的破折号个数不同），其余内容逐字节相同。
更强的判据是格式化等价性：

| 检验                                | 结果             |
| ----------------------------------- | ---------------- |
| `prettier(集成分支侧)` vs `main` 侧 | **逐字节相同**   |
| `prettier --check` 主分支侧         | exit 0（合规）   |
| `prettier --check` 集成分支侧       | exit 1（不合规） |

⇒ 两份文件是**同一份文档的两种排版形态**，主分支侧已是规范形态。

第 32 轮的裁决是「取集成分支侧 + 落地前格式化」，本轮的裁决是「**取主分支侧**」。
两者结论相反，但依据是同一条规则：**取已经合规的那一侧**，这样落地的格式闸失败文件数相对基线零增长。
第 32 轮之所以取集成分支侧，是因为当时主分支侧还没有这份文档。

**真正的缺陷在别处**：第 32 轮把规范形态落到了 `main`，但集成分支侧**始终没有被回流更新**，
所以下一轮三方合并又在同一处撞上 add/add。**只要主分支 → 集成分支的反向同步不做一次，
这个冲突就会每轮复现一次**，每一轮都要重新做一次同样的取证。
⇒ 结构性修法是做一次主分支 → 集成分支的反向同步，把规范形态带回集成分支。

### 3. 取证陷阱：worktree 里 `prettier` 不可用，失败输出会被当成「内容不同」

在 git worktree 里跑 `pnpm exec prettier` 会直接失败 —— worktree 没有 `node_modules`：

```
undefined
 ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL  Command "prettier" not found
```

危险之处不在报错本身，而在**失败时 prettier 把这段错误文本写进了输出文件**（本次 80 字节），
再用 `cmp` 去比对输出与主分支侧的文件时，`cmp` 读到的是错误文本与文档内容，
自然得出「**两者不一致**」的结论 —— 而正确结论是「格式化后逐字节相同」。

本轮第一次取证就撞上了它，若照抄这个结论，会把「取主分支侧」误判成「必须人工求并」。
⇒ **worktree 里做格式化取证，要么把根级 `node_modules` 软链进去，要么直接用主工作区的工具链跑**。

### 4. `main` 在本轮中途前进，判定必须重做

第 33 轮开工时的 `main` 是 `08a2947c`；取证期间一个并发会话把第 32 轮的会话记录 PR 合了进来，
`main` 前进到 `36b2c51e`。树差异因此从 1 个文件变成 2 个文件（多出来的那份是**主分支独有**的会话记录，
集成分支从来没有过），但**落地树依然与 `main` 逐字节相同** ⇒ 结论不变。

⇒ 冲突裁决与落地树判定都必须在**最新的 `main`** 上重做一遍，不能沿用上一轮取到的证据。

## 关键 trade-off / 讨论

- **为什么本轮不开同步 PR**：落地树与 `main` 相同，同步 PR 会是一条无内容的合并提交，
  只会给 `main` 添噪音。本轮改为单独提交本篇会话记录。

- **为什么冲突取边不靠行级差集单独定案**：行级差集在本例里给出的结论是「两侧各有独有行」，
  但那些「独有行」全是表格分隔行的列宽噪声。若只到差集这一步就停下，会误判成「必须人工求并」。
  格式化等价性是更强的一层判据，它直接回答了「两份是不是同一份文档」。

- **零变更轮要不要顺手修集成分支侧的格式**：不要。
  主分支侧已经是规范形态，取它即可；集成分支侧修不修不由本任务决定（那是流水线的地盘），
  也不影响落地结果。
