# 2026-10-23: 集成分支并入 main（第 50 轮 · 零净变更复核）

## 摘要

本轮把 `integration/module-dev` 同步进 `main`。起手体检显示两分支的**树差异非空**（74 个文件），
按协议不能直接判定「无新内容」，于是进入真实合并取证。

合并形态是「真合并 + 57 个 add/add 冲突」。逐文件取证后确认：**这 57 个冲突全部是排版差异，
不存在任何内容分歧，而且主分支侧已经是仓库规范排版、集成分支侧不是**。
据此 57 个冲突全部取主分支侧，解完冲突后**落地树哈希与 `main` 的树哈希逐字节相同**
（两侧同为 `f41d60c4`），即集成分支**没有任何主分支尚未包含的内容**。

结论：**零净变更，本轮无待合入的新交付。**

## 决策 / 结论

### 1. 「有没有新内容」以落地树哈希为准，本轮为零净变更

- `upstream/main` tip = `4f52a417`（树 `f41d60c4`），`upstream/integration/module-dev` tip = `3a0dbe33`。
- 两侧树差异报 **74 个文件**（863 增 / 2891 删），看上去像一次实增量。逐文件核对后全部不是内容差异：

| 类别                     | 文件数 | 核对结论                                                                   |
| ------------------------ | ------ | -------------------------------------------------------------------------- |
| 两侧都存在，差异只在排版 | 57     | 经仓库规范排版归一化后**逐字节相同**（57/57）；主分支侧已是规范态（57/57） |
| 只在主分支侧存在         | 17     | 主分支独有内容，合并动作不改变它                                           |
| 只在集成分支侧存在       | 0      | **空集** —— 集成分支没有任何主分支缺的内容                                 |

- 冲突面 **57 个文件全部是 add/add**（相对共同祖先 `4ab1d8d`，两侧各自新增同一批文件）。
- 在专用 worktree 里真实合并、解完 57 个冲突后 `git write-tree` = `f41d60c4…`，
  与 `git rev-parse upstream/main^{tree}` **完全相同**。

⇒ **主分支没有任何集成分支尚未包含的内容。** 判定依据是落地树哈希，不是树差异：
树差异是双向的，既含「集成分支有、主分支没有」，也含「主分支有、集成分支没有」，
后一部分不该被合入动作改变。

### 2. 集成分支本轮未移动，上一轮同步的成果仍然成立

`upstream/integration/module-dev` 的 tip 仍是 `3a0dbe33`（最后一次提交 07:48），
与第 49 轮同步时记录的 tip **完全相同**。也就是说，自第 49 轮同步（08:46 合入）以来，
集成分支没有新提交，冲突面也仍是同一批 57 个文件。

⇒ 本轮是同一同步点的重复复核，不是新交付。协议要求「每轮从仓库现状重新取证」，
所以结论仍然重跑了一遍完整取证链，而不是沿用上一轮的判断。

### 3. 冲突解法：取主分支侧，零内容丢失、不增加格式债

三条互相独立的证据通道合起来支撑「取主分支侧」：

- **通道① 字节级 Prettier 收敛**：用仓库自身的排版器（3.9.9 + 仓库配置 + tailwind 插件）
  分别归一化两侧的 blob。**57 / 57 个文件归一化后逐字节相同**；
  主分支侧 **57 / 57 个文件归一化后零变化**（已是规范态），集成分支侧 **0 / 57**。
- **通道② 独立指纹复核**：TypeScript AST 指纹 **33 / 33** 相同；
  Markdown 规范化行序列 **24 / 24** 相同。这条通道与通道①的工具不同，结论一致。
- **通道③ 阴性对照**：向集成分支侧注入已知语义改动（改字符串字面量 / 新增导出常量 /
  改数字字面量 / 改标题文字），共 **123 次有效注入，123 / 123 全部被检出**；
  另有对照实验证明归一化通道本身是活的（故意写坏的代码喂进去，输出 ≠ 输入）。

- **取主分支侧 ⇒ 语义零损失**：既然归一化之后两侧内容逐字节相同，
  那么「取主分支侧」得到的就是「两侧的并集按规范排版之后的结果」，不可能丢内容。
- **取集成分支侧反而会加重存量失败**：那 57 个文件会变成未格式化状态，
  `format:check` 的失败文件数凭空多 57 个，直接抬高 `Lint` 作业的失败量。
  本轮落地结果实测 **57 / 57 个已解冲突文件全部规范合规** ⇒ **零新增格式债**。

⚠️ `merge-resolve.mjs` 把这 57 个文件**全部**判成「并入（人工）」，并把类型标成 `content` ——
这是工具缺陷：它用 `git rev-parse <ref>:<path>` 判断路径是否存在，
而该命令在路径不存在时会把**参数原样回显到 stdout**（退出码 128），
于是「共同祖先里没有这个文件」（add/add）被误读成「两侧都改过」。
本轮 57 个文件全部打印 `fatal: path ... does not exist`，
证明它们在共同祖先里**都不存在**，即**全部是 add/add**，不是 content。

### 4. 通道② 的两个归一化盲区（先暴露、再修、再复跑）

第一版指纹实现报 TS/TSX 22 / 33、Markdown 15 / 24，逐个诊断后确认**两处都是归一化方法的缺陷，
不是内容差异**，修正后 33 / 33、24 / 24 全部一致：

- **JSX 空白**：`{' '}`（JsxExpression 包一个空白字符串字面量）与裸空白 JSX 文本。
  集成分支侧写的是裸空白，主分支侧写的是 `{' '}`。
  实测 Prettier 会把裸空白改写成 `{' '}`（集成分支侧格式化后 `{' '}` 由 1 处变 6 处，
  与主分支侧的 6 处一致），两边格式化结果逐字节相同 ⇒ 渲染行为一致。
  ⚠️ 但**不能**直接把二者当成同一个记号：裸空白在跨行时会被 React 整体丢弃，
  与 `{' '}` 并不总是等价。归一化只能「两侧都跳过」，等价的判定要交回通道①的字节级比对。
- **Markdown 表格**：主分支侧的表格是**按列宽对齐**的（各列补空格），
  集成分支侧是紧凑写法；表格分隔行的破折号数量也随之不同。
  归一化要处理：列表符号（`-` / `+` / `*`）、有序列表序号、引用块前缀与引用块内空行、
  竖线两侧空白、连续空白折叠。

## 关键 trade-off / 讨论

- **「取主分支侧」与「取集成分支侧」的方向不随意切换。**
  判据始终是同一条：「归一化之后两侧是否逐字节相同，以及哪一侧已经是规范形态」。
  本轮主分支侧是规范形态 ⇒ 取主分支侧。
- **树差异不是「有没有新内容」的判据。** 本轮树差异报 74 个文件，
  落地树哈希却证明净增量为零；若只看树差异，就会每轮都以为有大增量。
- **归一化相等这类结论必须配阴性对照。** 只有对照实验（通道是活的）不够 ——
  通道可能是「活的但无区分力」的。本轮注入 123 次已知语义改动全部被检出，
  才敢采信「57 / 57 逐字节相同 ⇒ 内容等价」这个结论。
- **指纹通道报不一致时，先怀疑指纹。** 本轮通道②的 11 处不一致全部来自归一化方法的盲区，
  逐个诊断后确认无内容差异；但**不能**因为「大概率是盲区」就跳过诊断 ——
  每一处都定位到了具体的原始行差异才判定。
- **闸工具的结论不能直接采信。** 第 47 轮已记录：它选基线 run 时不检查该 run 的作业是否收完，
  会把「基线没有失败作业」虚读出来从而假阻塞。本轮开同步 PR 前后都确认基线 run 已收完。
