# 2026-10-22 11:30：集成分支并入主分支的独立复核与流水线基线平价取证

## 摘要

本轮是同一个零变更窗口的后续一轮（11:00 那轮已开出同步 PR #34）。本轮**没有重新开 PR**，
而是对上一轮的合并结果做了一次**完全独立的复核**：

1. 在一份全新工作区里，从主分支重新做了一次合并并逐块解冲突，
   算出的落地树与主分支树**逐字节相同**（与上一轮记录里的哈希一致）——
   说明上一轮的解法可复现，不是碰巧。
2. 补齐了上一轮**没做完**的一项取证：流水线里有三个作业闸工具只能比作业粒度，
   这轮把它们逐个做了**明细级**比对，结论仍是平价。
3. 收尾时发现上一轮遗留了一个**带未提交改动**的工作区，
   且该工作区还占着同步分支 —— 会阻塞下一轮的 `checkout -B`。
   已把那 26 行结论补回会话记录后清理掉。

复核通过后刷新了同步分支并合入主分支。

## 决策 / 结论

### 1. 合并结果可独立复现：落地树 == 主分支树

在一份全新工作区里从主分支重新合并集成分支：

| 检验项                 | 实测值                                                     |
| ---------------------- | ---------------------------------------------------------- |
| 树差异                 | 37 个文件，`+137636 / −143046`                             |
| 提交数口径             | `rev-list --left-right --count` 报 30 / 464（虚的）        |
| 合并预演的冲突文件     | **1 个**（协议文件）                                       |
| **解完冲突后的落地树** | `eca743b45d32a30ddc228c46e67d1dca65d66d99`                 |
| 主分支树哈希           | `eca743b45d32a30ddc228c46e67d1dca65d66d99`（**完全相同**） |

⇒ 与上一轮记录里的落地树哈希**逐字符相同**，冲突解法可复现。

### 2. 冲突的四个区块逐块看过，集成侧没有独有内容

协议文件共 4 处冲突块，逐块核对：

| 区块 | 集成侧内容                                   | 判定                 |
| ---- | -------------------------------------------- | -------------------- |
| 1    | 旧判据的一行 echo 写法                       | 已被主分支侧新版替换 |
| 2    | **空**（主分支侧是整段新增的落地树判据章节） | 主分支侧是纯新增     |
| 3    | 旧决策表的两行                               | 已被主分支侧新版替换 |
| 4    | **空**（主分支侧是整段新增的基线章节）       | 主分支侧是纯新增     |

行级集合差集（两侧归一化空白后 `sort -u` 再 `comm`）：
**集成侧独有 4 行 / 主分支侧独有 124 行**，
集成侧那 4 行逐条都是被新版替换掉的旧措辞
⇒ **取主分支侧零丢失**（与上一轮结论一致）。

⚠️ 这也再次说明：**工具报「必须人工并入」只是保守警报，不是判决**。
它只证明「不能机械取一边」，不证明「必须两侧都留」。
取证后若证明并集等于一侧，就该只留那一侧。

### 3. 契约文件语义等价的复核方法可复用

上一轮只说了「契约漂移是纯序列化漂移」。这轮换了个更硬的判据：
**把 JSON 解析出来，数值统一归一化（`1.0` / `1` / `1e-06` / `0.000001` 视为同一个值），
再比对整篇文档**。

结果：5 个 OpenAPI 契约文件的 **paths 键集合、schemas 键集合、规范化后的整篇文档**，
三者全部相等；5 个 TypeScript 契约文件行级完全一致。

⇒ 契约两侧只有数值字面量写法不同，**语义完全等价**，驱动求和落在主分支侧既有字节上。

### 4. 流水线平价不能只看闸工具的作业粒度

闸工具结论是「可以合并，新增失败作业：无，新增失败用例：无」，
但它同时标注了三个**明细不可比的作业**（浏览器端到端、代码风格、安全审计）——
这几个作业只比了粒度，**作业内部多出来的失败它看不见**。这轮逐个补了明细比对：

| 作业             | 明细比对方法                         | 结果                                                                                            |
| ---------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------- |
| 代码风格检查     | 比对失败**文件集合**（不是只比数量） | 两侧各 600 个文件，**双向差集为空**；本轮新增文件不在失败列表内                                 |
| 安全审计         | 漏洞数 + 严重度分布 + 锁文件字节     | 两侧均 10 项、严重度 `1 low / 7 moderate / 2 high`；依赖锁文件 blob 两侧相同                    |
| 浏览器端到端用例 | 异常类型集合 + 根因链路              | 两侧**完全一致**（`UnsatisfiedDependencyException` → … → `AccessDeniedException: /app/target`） |
| Java 集成测试    | 失败用例逐条比对                     | 两侧**同一个**失败用例（`ApprovalRecordIntegrationTest` 驳回后重新发起…，9 跑 1 败）            |

⇒ **确实是平价**，可以合。

### 5. 抽流水线日志时踩到的三个 shell 陷阱（已解决）

这轮补做明细比对时连续踩了三个坑，**都不是流水线的问题，是抽日志的方法问题**：

1. **BSD 的 `sed` 不认 `\x1b`** —— 去 ANSI 颜色码的 `sed 's/\x1b\[[0-9;]*m//g'` 在 macOS 上
   **不报错也不生效**。改用 `perl -pe 's/\e\[[0-9;]*m//g'`。
2. **BSD 的 `sed` 把方括号里的 `\t` 当字面量** —— POSIX 规定方括号表达式内反斜杠是字面量，
   所以 `s/^[^\t]*\t[^\t]*\t//` 在 macOS 上匹配不到 tab。
   抽日志要**用 `awk -F'\t'` 切字段**，不要用 `sed` 切 tab。
3. **流水线日志的行格式是 3 段不是 4 段**（作业名 / 步骤名 / 消息）——
   `cut -f4-` 会得到空。用 `cut -f3-`。

另外：**日志里的汇总计数行不是文件名**。
`Code style issues found in 600 files` 这一行也以 `[warn] ` 开头，
不剔除它，文件数会算成 601 —— 上一轮就是被这个 +1 咬过一次。

### 6. 收尾自检要加一条：固定分支是否还被某个工作区占着

上一轮遗留的工作区带着**未提交改动**（26 行结论），并且**还占着同步分支**。
后果：下一轮执行 `checkout -B <同步分支>` 会被 git 直接拒绝，
**整轮空转**，而且那 26 行结论会永久丢失。

⇒ 收尾自检除了「自己的工作区删了吗」「闸放了吗」，
还要加一条：**协议指定的固定分支是不是还被某个工作区占着**
（`git worktree list | grep <分支名>`）。
命中的是本任务自己的遗留 ⇒ 先把有价值的内容取回来，再清掉工作区。

⚠️ 只删本任务自己的：流水线的工作区是按模块号命名的（`2.4.2.3` 之类），
本任务的是 `main-merge-*` / `sync-*`，两者名字不重叠。

## 关键 trade-off / 讨论

**「直接合已验证的 PR」还是「刷新分支再合」？**

刷新分支要多等一轮流水线（约 10 分钟），而且会让 PR 头提交变化、旧流水线结果作废；
好处是上一轮遗留的那 26 行结论能入库，本轮的复核也能留痕。

选**刷新**：那 26 行是一个已验证过的真实教训（闸工具的粒度盲区），
直接合就等于永久丢弃；同时遗留工作区占着固定分支，不清掉下一轮会整轮空转。
等待成本是固定的十分钟，而丢失的结论和卡住的下一轮是复利的。
