## 关键取证与 trade-off

### 1. 上一轮为什么「看起来像完成了」——实际什么都没交付

- `batch-105` 说明文件写完了「并入记录」「静态预检」「后续待办」三节 —— 但 **`## L2 批次闸` 一节里只剩 `<!--L2_SECTION-->` 占位符**；

- `last-l2-at` 被写了，但那是**调度者手工写的状态文件**，不代表 L2 跑过。

⇒ **L2 从未跑过**，`merge-ready` 只校验「工作区干净 + 有新提交」，从不跑测试 ——
**并入后的集成头状态从来没人验证过**（这正是组批协议要补的那层安全网）。

**本轮的取证顺序**（严格按 PIPELINE.md）：先 `sync.mjs`（414/0/51）→ 只读容量闸四条 → 节流闸（距上批 289 分钟 ≥ 100）→ 取闸 →

### 2. 缺陷 ①：解冲突时丢了对象分隔符 —— 静态预检查不到，只有 L2 能抓

`apps/web/src/lib/api-proxy.ts` 里 1.5.2.1 的 `channel/` 元素（12704–12709）与
13.2.2.2 的 `reporting/` 元素（12743–12747）**被并进了同一个对象字面量** ——
中间少了一组 `},` + `{`。

| 表现                                       | 机制                                                           |
| ------------------------------------------ | -------------------------------------------------------------- |
| `TS1117` at 12746                          | 一个字面量里两份 `prefix`/`env`/`fallback`/`pattern`（语法级） |
| `channel/service-task-status/alerts` → 404 | JS 重复键**取最后一个** ⇒ channel 那条白名单被**静默吞掉**     |

⚠️ 这和 PIPELINE.md 点名的「取错一侧会静默删掉别人已交付的路由」是**同一个事故形状**，
区别只在于本次丢的是**分隔符**，所以语法也坏了 ⇒ **typecheck 与 allowlist 测试同时抓到**。
**如果丢的是整段（语法仍合法），typecheck 会全绿而路由静默消失** —— 这才是真正危险的那个版本。

**为什么静态预检查不到**：协议里的静态预检只扫**迁移**（`ADD COLUMN` / `SET NOT NULL` / `CHECK`），
而这条破损在**前端共享文件**里。⇒ **前端共享累积文件没有任何静态闸**，只能靠 L2。

**上一轮那份「并入记录」里的校验结论要更正**（已在 batch-105 文件里留痕）：
「`(prefix, pattern)` 组合零重复」查的是**正则内容**，重复的是**对象键**本身 ⇒ 查不到；
「元素数 238 → 239（+1）」**连数字本身也是错的** ——
修复车道用 **TypeScript 编译器真实求值数组**实测：**修复前 247 → 修复后 248**。
**教训：校验元素数要用编译器求值，不要用文本计数猜；校验要覆盖对象键，不只是正则内容。**

### 3. 缺陷 ②：跨时钟取整抖动 —— 隔离复跑 3 次全绿 ⇒ 抖动不是回归

`ApprovalTodoIntegrationTest.超时判定用节点上配的时限…` 红在 `7199` vs `7200`。

**归属取证**：本批 4 条车道改动面 = reporting(29) + channel(8) + apps/web(21) + api-contracts(4) + 文档(5)，
**`backend/services/identity` 零改动**；该测试文件最后一次改动是 `b2ec6b97`（模块 1.1.1.3），早于本批。
**隔离复跑 3 次全绿** ⇒ 只在全量验证的高负载下偶发。

**根因**：dwell/overdue 在 **DB 侧**算（`V160__my_approval_inbox.sql` 的 `approval_dwell_seconds`），
`clock` 传的是 **PG 的 `now()`**，而夹具把 `node_entered_at` 写成 **JVM 墙钟**的 `now()-3h`
⇒ **两端分属两个钟域**。两钟差不足 1 秒时，`floor()` 把 10800.0 落成 10799 ⇒ overdue 7199。

**仓库既有先例**：`371246c6 fix(test): 异常订单队列的停留时长断言不再依赖「类加载那一刻」的基准时刻`
（1.1.1.2，已并入集成头）修的是同一族问题。其要义是「**在服务端判定所用的那个钟域里比**」，
并记了一条教训：「两个钟域各管一段时，只换一端反而制造新的跨钟域依赖」。

**分域判定（对本用例）**：本用例的**终点本来就在 DB 钟域**（生产代码传 PG 的 `now()`），
所以把**起点也换回 DB 钟域**即可两端同域 ⇒ 与先例不同，这里**两端一起换**是对的。

### 4. trade-off：**先派修复车道、后跑 L2**，而不是先派新车道

**本轮没有先派 13.1.2.2 / 13.2.2.1，而是先把 L2 跑到红、定位、修复、再复跑 L2。**
理由：

1. **push 的前提是 L2 绿**。batch-105 已经悬了两轮，再往集成头里加两条新车道，
   只会在破损的基线上叠更多代码 ⇒ 第 2 跑一旦红，**二分定位会被新车道搅浑**。
2. **协议明令「L2 不得与在途车道的 L1 并发跑」**（2026-10-19 实测：L2 与 4 条车道 L1 并发时
   PG 峰值 16、1364 例里 3 failures + 24 errors **全是假红**）。
   ⇒ 新车道与 L2 **不能并行**，只能串行；既然要串行，先跑完 L2 更划算。
3. **Maven fail-fast 的连带影响必须讲清**：第 1 跑在 identity（第 3/11 个模块）就停了，
   **catalog / warehouse / trade / channel / crm / reporting 六个模块的后端测试根本没跑到**
   ⇒ 第 1 跑**没有验证过本批 4 条车道自己的后端代码**。第 2 跑必须把这六个模块全跑到，
   才算真正对 batch-105 验收。

### 5. 修复车道用**合成 ID**，不覆盖已交付模块的车道历史

`lane.mjs` 没有「修复车道」命令（`init/status/plan/heartbeat/land/merge-ready/abandon/gc`）。
`adopt` 要求 ID 在台账里 ⇒ 用 `1.1.1.3` 会**覆盖那条已 merged 的车道记录**，且把 1.1.1.3 在台账里的
语义搅浑（本模块是**已交付**，不是「进行中」）。

⇒ 用**合成 ID**（`fix-batch-105-api-proxy-literal` / `fix-1.1.1.3-approval-todo-clock`）自建车道条目，
形状与 `lane.mjs plan` 写出的**逐字段一致**（含 `baseSha` 用 7 位短 sha —— `land` 比较的是
`sha.slice(0,7)`，存 40 位会让「没有新提交」这道闸永远失效）。

**这个做法安全的依据（已核对）**：`sync.mjs` 与 `lanes.json` **完全解耦**（`grep lanes` 零命中，
`sync.mjs` 只读台账 + 蓝图）；`plan` 只按台账选模块；`land`/`merge-ready`/`gc` 只认
`state.lanes[id]` 与 worktree/branch ⇒ 合成 ID 不惊动任何既有逻辑。

### 6. 修复车道**不写台账** ⇒ 本批台账数字不动

修复车道不对应新的 L4 模块（1.5.2.1 / 13.1.2.1 / 13.2.1.1 / 13.2.2.2 早已是「已交付」），
所以两条修复车道**不改台账任何一行**，只改代码/测试。⇒ 台账仍是 414/0/51。
