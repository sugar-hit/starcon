# 15.5.2.1 关怀与催办（阶段 D7，L3 锚点 15.5.2）

日期：2026-10-22 ｜ 分支 `feat/15-5-2-1` ｜ 基线 `integration/module-dev` @ `5636f458`
迁移版本：**V303**（本车道预分配；同批另三条车道用 V301 / V302 / V304）
落点服务：**crm**（`backend/services/crm/`，包 `com.starcon.crm`，端口 8086，DB 角色 `crm_app`）

## 决策摘要

### 1. 退订名单**只读不写**：唯一事实源是 15.3.2.2 的 `crm_customer_opt_out`

蓝图输入句写明「输入：……退订名单」，输出句写明「输出：……退订记录」。
本模块**不新建任何退订表**：15.3.2.2 的 `crm_customer_opt_out` 已经是唯一事实源，
两个事实源必然打架 —— 客户说了「不要再联系我」却仍被触达，是最伤信任的一类事故。

⇒ 退订闸**走 15.3.2.2 的同一条判定路径**（`CustomerContactService.optOutCheck`），
不另写一份 SQL：判定逻辑分叉一次，「哪些端点信哪一份」就变成要逐个审计的问题。
本模块**只读**它，**不写**它，**不撤销**它。

拦截的**输出**落在本模块自己的触达任务上（`status='BLOCKED'` + `block_code` + `block_reason`），
而不是另造一张「退订记录」表。

### 2. 加粗句「遵守频次上限与退订要求」= 服务端两道闸 + DB 一道物理闸

- **闸 1（退订）**：scope=`ALL` 一律排除；scope=`MARKETING` 排除**营销类触达**
  （关怀邮件 / 催评 —— 这两类带索取性质，正是「过度索要被投诉」的那一类）；
  发货通知 / 物流提醒 / 催付 / 售后进度通知是**服务性通知**，只有 `ALL` 才挡
  （与 V299 自己的营销豁免口径一致）。
- **闸 2（频次）**：该买家在该触达类型下的窗口内触达次数（**已发 + 已排期**）
  ≥ 规则上的 `frequency_limit` ⇒ 拒绝。
- **任一命中 ⇒ 拒绝并给出明确原因**：落成一条 `BLOCKED` 任务，
  原因写「客户已退订（ALL：……）」/「近 24 小时内该买家在【催评】下已触达 2 次……上限 2 次」。
  **不是静默跳过** —— 拦截本身也是一条要留痕的事实（我们想在什么时候给他发、被什么挡住了）。
- **DB 物理闸**：`guard_crm_care_reminder_task_opt_out` 让**非 BLOCKED** 的触达任务
  在退订生效后**根本落不了库**（豁免依据要真的拦得住，而不只是一条可读的事实）。

**静默时段刻意不是闸**：它的意思是「这段时间别发」，不是「不许排期」⇒
计划时刻**顺延**到静默结束，并在 `note` 里写明顺延了多少。

### 3. 加粗句「催付有合规边界」落成三层

1. **按平台单值配置**：`platform_code` 单值 + `UNIQUE (tenant_id, rule_code)`
   ⇒ 一个全局规则套不了所有平台，不同平台的催付话术与频次上限可以各配各的。
2. **平台白名单**（`SHOPIFY` / `EBAY` / `TIKTOK_SHOP` / `ALIBABA_1688`）：
   **表级 CHECK** 在规则表与任务表各挡一道 ⇒ 白名单外的平台**建不出催付规则**；
   服务层再给一句人话「该平台不支持催付」（400 且**一行都不写**）。
   两处白名单是同一份口径（`CareReminderService.PAYMENT_DEMAND_ALLOWED_PLATFORMS`），
   `CareReminderRulesTest` 钉住它 —— 它是**产品决策**，不是实现细节。
3. **催付只对未付款订单成立**：实查 trade 的 `sales_order` **没有 payment_status 列**
   （`GET /trade/sales-orders/list` 的 `paymentStatus` 恒为 null —— 那是 12 财务的缺口）。
   真正存在的支付状态**观察值**在 trade 的 `order_address_check`（V210）里，
   经 `GET /trade/order-address-payment-check/checks` 只读暴露 ⇒ 新增
   `OrderPaymentStatusPort` 读它（照抄既有端口纪律）。
   **「没量到」不等于「未付款」**：没有观察值的订单**不纳入**催付，并如实计数。

### 4. 催评只对已签收订单成立

目标集合 = **已签收订单**（channel `logistics-pickup-signoff/cases?status=DELIVERED`）
**∩** **订单事实**（trade `sales-orders/list`，用于取买家标识 ——
签收确认单不带买家维度，归因链路是「签收单 → 订单号 → 订单 → 买家」）。
**未签收不生成催评任务**，且生成结果里**如实报出未签收的条数**（不是静默跳过）。

### 5. 未交付的下游一律不编

- **12 财务（催付加速回款）未交付** ⇒ 只落催付任务与「已提醒回款」的意图，
  **不写财务单据 id、不编下游 id**；api-proxy 也**刻意不放行**任何财务单据路径。
- **平台侧发送接口未接入** ⇒ `transport` 恒 `MANUAL_HANDOFF`（**不重造发送**），
  运营在平台侧实际发出后回本服务登记结果与失败原因（失败**必带原因**）。
- **平台打开/点击回执未接入** ⇒ 自动采集端点**如实答「未接入」且不写数据**。
  这里刻意用 `Unavailable*Port` 同款写法**返回带原因的结论，而不是抛异常**：
  抛异常走 Spring 的 `sendError`，**响应体是空的、原因就丢了**，
  调用方只剩一句「保存失败」，那等于没答「未接入」。
- **15.5.1.1 自动回复未开发** ⇒ 不碰。

### 6. 统计口径服务端算，前端不做算术

触达总数 / 成功数 / 失败数 / 打开数 / 点击数 / 退订拦截数 / 频次拦截数
全部由 SQL 聚合得出（`BigDecimal` / `long`），页面**原样显示后端给的那串说明**，
不自己算打开率 / 点击率 —— 分子分母各取一份、两个页面各算一次，口径迟早会打架。

## 关键 trade-off

- **拦截码词表只留两档**（`OPT_OUT` / `FREQUENCY_LIMIT`），与那两道强制闸一一对应。
  「该平台不支持催付」**不在**拦截码里：它是**规则级**判定 ——
  平台不在白名单时那条催付规则根本建不出来，不存在「一条催付任务被平台挡住」
  这种自相矛盾的情况。词表里留一个永远打不出来的码，等于给后来人留一个假入口。
- **静默时段顺延而不是拒绝**：拒绝会让运营以为「这条规则坏了」，
  而顺延（并留痕）才是「这段时间别发」的本意。
- **`frequency_limit = 0` 不等于「不生成任务」**：它生成的是一条 `BLOCKED` 任务，
  原因写「这条规则不允许任何触达」—— 「什么都不做」与「明确拒绝并留痕」是两件事。
- **平台回执端点返回 200 而不是 409**：见第 5 条 —— 抛异常会让原因在响应体里消失。
- **api-proxy 新增一条独立的 `services[]` 元素**（锚点 = `crm/customer-contacts` 之后），
  **不**往既有 crm 分支的巨型 alternation 里并分支：那些是超长单行正则，
  多车道同时并进去 git 必然判冲突（结构性，retry 不会自愈）。
