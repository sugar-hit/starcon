# 集成分支合入主分支：改为每半小时走 Pull Request

**日期**：2026-10-21
**范围**：`tools/module-progress/` 下的合入协议与两个新工具 + 一个定时任务

## 做了什么

把「集成分支并入 main」这个定时任务从**每日一次、直推 `main`** 改成
**每半小时一次、走 Pull Request**：

- 定时任务 `fb70d589`（原「starcon 集成分支并入 main」，每日 00:00 直推）
  改为 **`*/30 * * * *`**，职责变为「开 PR → 审查并解决冲突 → 验证 → 等 CI → squash 合入」。
- 协议文件 `MAIN_MERGE_CRON_PROMPT.md` 按新流程重写，并新增**提交文本可读性规范**。
- 新增两个工具：`merge-summary.mjs`（功能增量摘要）、`ci-gate.mjs`（CI 基线相对闸）。

## 关键决策与 trade-off

### 1. 走 PR 而不是直推 main

用户明确要求「创建 MR」。这同时消掉了原来协议里「AGENTS.md 禁止直推 main，
本任务显式豁免」这条自相矛盾的规定 —— 现在 `main` 只经 PR 更新，禁令不需要豁免。

代价：合并多一道 CI 环节，且 CI 可能红。收益：`main` 上每轮只有**一条**可读提交，
不再是一串工程流水账。

### 2. 合并用 squash，且提交标题只讲功能

squash 合并后，`main` 的 `git log` 里每轮一条提交，标题是「这次交付了哪些功能」。
提交数、文件数、冲突解决机制、内部脚本名、工程决策理由一律不进标题与正文 ——
这是用户对「易读、专业、不暴露过多工程细节」的具体要求。

### 3. CI 闸必须**基线相对**，不能是「全绿」

**实测发现：`main` 的 CI 自 2026-10-14 起长期是红的**，最近一次 run 失败作业有
`Lint`（Prettier 格式债 337 个文件）、`Java 21 & PostgreSQL Integration`
（identity 1 例失败）、`Catalog Browser & Contract Tests`（端到端失败）。

如果把「CI 全绿」当合并前提，这个任务**永远合不进去**，等于没有闸。
所以判据改成：**PR 的失败不得比 `main` 基线更多** —— 失败作业集合必须是基线的子集，
且同名作业里不得出现基线没有的新失败用例。`ci-gate.mjs` 实现了这个判据，
明细取不出来时降级到作业粒度并要求汇报点名。

### 4. 「合入了什么功能」从台账增量出，不从提交信息出

集成分支一次能带进几十上百个提交，提交信息是工程视角的
（`docs(batch-28): 11.2.3.3 / 7.8.2.1 ...`）。直接读提交信息写 PR 描述，
必然写成「合了 N 个提交 / 改了 M 个文件」这种读者不关心的流水账。
功能进度台账记的是**功能**（模块 ID + 功能名 + 交付状态），是业务视角的真相源，
所以 `merge-summary.mjs` 从台账增量里出功能清单与候选标题。

### 5. 闸的持有范围收窄到「本地会改状态的动作」

原来闸贯穿整个合并过程。半小时节奏下，CI 要跑 20–40 分钟，
若等 CI 时还持闸，一轮就把闸占住，流水线整轮空转。
改成：**本地合并/验证/推分支持闸 → 放闸 → 等 CI（不持闸）→ 合并 PR 前再取一次短闸**。

### 6. 幂等：固定 PR 分支 + 无增量不动手

固定用 `chore/sync-module-dev` 一个分支，复用同一个 PR。
每轮先判断「`main` 相对集成分支有没有新内容」，没有就只读收工 ——
半小时一次意味着大多数轮次本来就无事可做。

### 7. `main` 是 squash 合入的 ⇒ 「一律求并」是错的

`main` 的每次更新都是 **squash 合并**，所以 `main` 的提交**不是**集成分支的祖先。
两个直接后果：

1. **增量不能看提交数**。`git rev-list --count upstream/main...upstream/integration/module-dev`
   报 142 个提交，**实际内容差异只有 83 个文件**。用提交数判断增量 ⇒ 每轮都以为有大增量
   ⇒ 每轮都开一个内容其实没变的 PR。判据改成**树差异**。
2. **冲突多半不是双向分叉，而是线性演进**。`main` 的文件版本来自集成分支的**某个较早提交**，
   于是「取一边」在多数情况下才是对的解法，而**无脑求并**会把 main 侧的旧内容重新塞回去。

由此新增 `merge-resolve.mjs`，逐个冲突文件判定：

- **祖先快照判定**：main 侧该文件的 blob 是否出现在集成分支该路径的历史里。
  是 ⇒ 线性演进，取集成分支侧；否 ⇒ main 有集成分支从未有过的内容，必须人工求并。
- **累积型文件三件套**（白名单这类只增不减的文件）：集合包含 / 有序子序列 / 零删除。
  三条同时成立 ⇒ 「取新侧」在结果上等同于完整求并。

实测本仓库当前 6 个冲突文件全部通过祖先快照判定；
`api-proxy.ts` 的三件套 73 → 97 条 pattern 全部成立。

### 8. 固定 worktree 路径是共享地，会被打断

协议原来规定合并用固定路径 `.worktrees/main-merge`。08:30 那轮正在这个 worktree 里
合并解冲突，被**另一个并发的、人工驱动的会话**（演练协议命令时用了同一个路径）
在收尾时 `git worktree remove --force` 一起删掉 —— 合并状态丢失。

改成 `.worktrees/main-merge-<时分秒>`，收尾**只删自己本轮建的那一个**。

⇒ **推广**：任何跨执行者共享的临时路径，都要带唯一后缀，
且收尾只删自己创建的那个。固定路径 + 「谁都能删」的组合 = 必然互相踩踏。

## 过程中踩到的两个真问题

1. **台账已超过 Node 的 1MB 默认缓冲**（`upstream/integration/module-dev` 上是 1,276,189 字节，
   而 `upstream/main~3` 是 1,034,003 字节 —— 刚好卡在阈值下面）。
   `execFileSync` 抛 `ENOBUFS`，而原来的错误处理把它吞成空表，
   于是「读不到 head」退化成「head 里没有新交付」。现在读失败**响亮抛错**，
   并且台账行数必须恒为 465，否则拒绝给出「无增量」的结论。

2. **模块 ID 的卷号不是前两位字符**。台账里是 `9.2.1.1`（不补零），按 `slice(0, 2)` 会切出 `'9.'`。
   卷文件是补零的（`09-*.md`），所以查卷名要按两位补零回查。
