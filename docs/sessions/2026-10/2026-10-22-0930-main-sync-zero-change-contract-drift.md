# 2026-10-22: 集成分支并入主分支的零变更复核与契约漂移结论

## 摘要

本轮把 `integration/module-dev` 并入 `main`（Pull Request 形态），逐项取证后确认
**合入后 `main` 一个字节都不会变** ⇒ **本轮不开同步 PR**，交付本篇会话记录。

树差异报 36 个文件、13.7 万行增删，看起来像一次大增量；逐文件核对后确认：

- **24 个是「`main` 有、集成分支没有」**（历史会话记录、进度看板工具产物、1 篇 backlog），合入动作**不改变**它们。
- **12 个是两侧都有但字节不同**（5 个 OpenAPI 契约文件、5 个契约类型文件、协议文件、`.gitignore`）。
- **「集成分支有、`main` 没有」的新增文件数 = 0。**

解掉唯一那处冲突后，落地树哈希与 `main` 的树哈希**完全相同**（`8096891c`）。

相对上一轮零变更复核，本轮多产出三条可复用的结论：契约字节差异**可判定为纯序列化漂移**、
协议文件的冲突**取 `main` 侧零丢失**、以及集成侧的冲突面**已从 3 个文件收缩到 1 个文件**。

## 决策 / 结论

### 1. 零变更的判据仍是落地树哈希，本轮再次实测成立

- 树差异：36 个文件，`+137636 / −142937`；`git rev-list --left-right --count` 报 29 / 464。
  提交数是虚的（`main` 是 squash 合入的），文件数也是虚的（双向差异）。
- **解完冲突后**的落地树 = `8096891c6197861eb5adbc96073d6cb300c29bb6`，
  与 `git rev-parse upstream/main^{tree}` **完全相同**；
  `git diff upstream/main` 与 `git diff --cached upstream/main` **都为空**。
- ⚠️ **预演与落地不是一回事**：`git merge-tree --write-tree` 本轮报 `00940b7a`，
  与 `main` 树不相等 —— 但那是因为**冲突标记还没解**，`00940b7a` 是「把冲突标记写进文件后的树」。
  ⇒ **不能用预演 OID 不等来判断「有变更」**，必须解完冲突再比落地树。

### 2. 契约文件的字节差异是纯序列化漂移，语义差集双向为空

本轮把「契约要不要并入」从「肉眼比 diff」升级为**可机械执行的判据**：

| 契约文件    | 导出类型名集合 | 导出类型名差集（双向） | OpenAPI `paths` | `components.schemas` | 归一化后深度相等 |
| ----------- | -------------- | ---------------------- | --------------- | -------------------- | ---------------- |
| `catalog`   | 863            | 空                     | 494             | 863                  | ✅               |
| `channel`   | 1348           | 空                     | 710             | 1348                 | ✅               |
| `crm`       | 76             | 空                     | 44              | 76                   | ✅               |
| `trade`     | 1717           | 空                     | 789             | 1717                 | ✅               |
| `warehouse` | 1077           | 空                     | 518             | 1077                 | ✅               |

⇒ 5 个 `*.openapi.json` 解析后**逐层深度相等**（键序与数字格式归一化后），
5 个 `contracts/*.ts` 的导出类型名集合**双向差集为空**。
**13.7 万行的字节差异里没有一行是语义变更。**
（上一轮曾在 `minSimilarity` 上留过 `int` / `float` 的类型差异，本轮已消失 —— 主分支前进后两侧彻底对齐。）

⇒ **契约文件判「取一边会不会丢内容」的唯一可靠裁判是语义等价**；
字节不同、blob 不同、diff 巨大，这三件事**都不构成「集成分支有新内容」**。

### 3. 协议文件的冲突取 `main` 侧，零丢失

该文件是版本化的执行协议，`main` 侧被修正过、集成侧没有这些修正 ⇒ 典型线性演进。
用行级集合差集确认（`git show` 两侧各自 `sort -u` 后 `comm`）：

| 维度           | `main` 侧 | 集成侧 |
| -------------- | --------- | ------ |
| 总行数         | 787       | 621    |
| 去重后行数     | 503       | 381    |
| 共有行         | 375       | 375    |
| **该侧独有行** | **128**   | **6**  |

集成侧独有的 **6 行**逐条看过，**全部是旧措辞**（第 3 节那句 echo 的旧写法、
以及 3.1 决策表里「没有新内容 / 有新增内容」的旧行），
在 `main` 侧都存在对应的新版形态 ⇒ **取 `main` 侧零丢失**，不是「必须两侧都留」。

### 4. 集成侧的冲突面已从 3 个文件收缩到 1 个文件

集成侧同步任务在 08:19 记录的冲突墙是「3 文件 15 区」。本轮重新取证，**只剩 1 个文件**：

| 文件                                                              | 08:19 记录                                | 本轮实测（两侧 blob）   | 结论               |
| ----------------------------------------------------------------- | ----------------------------------------- | ----------------------- | ------------------ |
| `apps/web/src/lib/api-proxy.ts`                                   | `main` 侧 `7f844ce6` vs 集成侧 `9325e4d3` | 两侧**同为** `9325e4d3` | 冲突已消失         |
| `docs/backlog/2026-10-13-flaky-integration-tests-l2-false-red.md` | `main` 侧 `26fb4553` vs 集成侧 `d13bd140` | 两侧**同为** `d13bd140` | 冲突已消失         |
| `tools/module-progress/MAIN_MERGE_CRON_PROMPT.md`                 | 真双向                                    | 仍是唯一冲突文件        | 取 `main` 侧即可解 |

⇒ **该任务下一轮不必再按 3 文件 15 区准备**，只剩协议文件一处，且解法已在上面给出。

## 关键 trade-off / 讨论

- **为什么本轮不按「有差异」开同步 PR？** 因为它会是空 PR。合入后 `main` 一个字节都不变，
  开 PR 只会给 `main` 添一条无内容提交。⇒ 零变更轮次的产出放在**会话记录**上，
  放在真正改变判据的地方（协议）—— 这与前两轮的做法一致。

- **为什么不把契约差异顺手「整理」掉？** 契约是 codegen 产物（仓库明令不可手改），
  字节漂移由生成器决定。本轮只**判定**它无语义变更，不去改它。

- **为什么不顺手把集成侧的冲突也解掉？** 集成分支归开发流水线那个任务所有，
  本任务对它是**只读**的。本轮只把解法与取证结论写进记录，由那个任务取用。
