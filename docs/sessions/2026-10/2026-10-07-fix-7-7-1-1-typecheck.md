# 2026-10-07 · 修复 7.7.1.1 货主与所有权前端类型错误

## 背景

`integration/module-dev` 并入 7 条新车道后，后端全绿（`./mvnw verify` BUILD SUCCESS，
23 个迁移 V1→V74 干净应用），但 7.7.1.1 与 7.8.1.1 两条车道的前端编译不过。
本轮只负责 **7.7.1.1「货主与所有权」**，工作区 `.worktrees/fix-7.7.1.1`，
分支 `fix/7-7-1-1-typecheck`。7.8.1.1 的 `allocation-policy-*` 不在本轮范围内。

## 决策摘要

本车道 26 处类型错误归为 5 类，根因和处理如下。

### 1. `superseding` 不可见（9 处）

**根因**：`superseding` 是主组件 `StockOwnershipWorkspace` 的 `useState`，而用到它的
`useEffect` / `submit` / 按钮文案在 `RuleEditor` 这个 props 子组件里；`RuleEditor` 的形参
只解构了 `onRetire` 等回调，漏了解构 `superseding`（它的 prop 类型本来就已经声明了）。

**处理**：在 `RuleEditor` 形参解构里补上 `superseding`。既有 prop 类型已存在，不需要新增类型。

### 2. `onRetire` 不可见（1 处）

**根因**：作废回调只以**内联 prop** 的形式写在 `RuleEditor` 的 `extra={...}` 里，
主组件作用域里并不存在这个绑定，而下方货权档列表的「作废」按钮又要调用它。

**处理**：把内联实现提取成主组件的具名函数 `doRetire`（与既有的 `doReassign` /
`doToggleStatus` 同一风格、同样是 `return` 之后的函数声明），`onRetire={doRetire}` 传下去，
列表侧改为 `doRetire(rule.id)`。行为等价，两处共用一份实现。

### 3. `variant="primary"` 不存在（2 处）

**根因**：`packages/ui` 的 Button 没有 `primary` 变体，契约是
`default | secondary | outline | ghost | link | brand | destructive | success`。

**处理**：改为 `outline`。依据是**同文件内既有写法** —— 本文件其余十来个按钮
（刷新 / 重新加载 / 换版 / 作废 / 改判 / 启用停用）全部是 `variant="outline"`，
保存与提交这类按钮在同一区块里也用 `outline`。**没有动 `packages/ui`**，
那是设计系统的公共契约，新增变体会影响所有车道。

### 4. `exactOptionalPropertyTypes` 违规（11 处）

**根因**：`filterParams` 这个 `useMemo` 永远把三个筛选键物化出来，空值时值是 `undefined`
（`warehouseFilter || undefined`）。而下游签名一律是 `?:` 形如 `{ warehouseId?: string }`。
在 `exactOptionalPropertyTypes` 下「键存在但值为 undefined」与「键不存在」不是一回事。

**处理**：在**唯一的源头** `filterParams` 改成条件展开（`...(x ? { k: x } : {})`），
一次性解决 111/112/113/230/335 五处；`ScopeFilter` 三个下拉的类型统一成 `?: string`，
并用「先把旧键摘掉再条件展开」的方式处理清空 —— 直接 `{ ...filter, ...(v ? {k:v} : {}) }`
会让清空下拉后旧值残留，这个行为坑一并避开了。风格对齐
`components/inventory/completeness-score-workspace.tsx:66` 的既有条件展开写法。

### 5. 契约类型 `OwnerRefType` / `StockOwnerKind` 不存在（2 处 + 测试 3 处）

**根因**：后端 `StockOwnershipModels.java` 里这两个**确实是两个不同的枚举**
（`StockOwnerKind` 在 :51、`OwnerRefType` 在 :75），但 codegen 只把枚举**内联**成
`StockOwnerRow` 上的字面量联合，不生成具名类型别名，所以 `catalog.ts` 里找不到这两个名字。

**处理**：**不改 Java、不重新生成契约**。改成从契约行类型反推别名：

```ts
export type StockOwnerKind = NonNullable<StockOwnerRow>['ownerKind'];
export type OwnerRefType = NonNullable<StockOwnerRow>['ownerRefType'];
```

理由：AGENTS.md 要求「前后端类型不同源，OpenAPI 契约是唯一共享面」。从契约反推既保持
契约为唯一来源，也不用在前端复制一份手写枚举 —— 手写枚举才是真正会漂移的东西。
**绝对没有手改 `packages/api-contracts/src/catalog.ts`。**

`stock-ownership-model.test.ts` 130/131/132 的根因是 `scopePriority` 声明成
`Record<string, number>`，在 `noUncheckedIndexedAccess` 下索引结果带 `| undefined`。
`scopePriority` 全仓只有这一个测试消费，改成 `as const`（对齐
`warehouse/goods-receipt-model.ts:131` 的既有写法）后键是已知字面量键、索引结果就是 `number`，
**三行断言无需改动**，比较的是真实数字而不是可选值。

## 关键 trade-off

- **条件展开 vs. 拓宽签名**：`?:` 加 `| undefined` 也是合法 TS，改动更小，
  但它把「显式 undefined」固化进所有下游签名，掩盖了「这个键到底存不存在」的语义，
  且与仓库既有条件展开风格不一致。选了条件展开 + 在源头修一次。
  代价是 `ScopeFilter` 三个下拉要多写「摘掉旧键」的两行。
- **从契约反推类型 vs. 改 Java 补 DTO**：补 Java 会改动 OpenAPI spec 并重新生成契约，
  波及面远超本车道；反推别名是 0 副作用且同样以契约为唯一来源。
- **`outline` 而非 `brand`/`default`**：按「同文件既有写法」取证，不引入新语义。

## 目录纠正（重要）

中途调度器指出：最初的 3 处改动落在了**主工作区** `integration/module-dev` 而非本车道 worktree。
处理：导出 patch → `git apply` 到 `.worktrees/fix-7.7.1.1` → 主工作区 `git checkout --` 还原。
恢复时主工作区又出现 `stock-ownership-model.ts` 被改（另一写者正在同一车道上作业，
采用了「拓宽 `?:` 签名」的不同解法），**未予还原** —— 那不是本车道产物，
贸然 checkout 会毁掉别人在途的改动。

另外发现 patch 导出存在竞态：主工作区在导出时仍有写者在改同一文件，
`git diff` 快照只显示 3 处，实际导出 5 个 hunk，多出的 2 个属于那位写者。
其中 `ScopeFilter` 类型那处已被本轮自己的改动覆盖，`doReassign` 签名拓宽那处
既非本轮所需、也已移除，**最终提交只含本车道自己的改动**。
