## 决策摘要

接手时车道里有 5 个未跟踪文件（迁移 + 服务层 + 模型 + 控制器 + 集成测试），全部来自前一位
worker，但**那份迁移从未被执行过一次，后端也从未编译通过**。实际接手后第一件事是重跑构建拿
准确错误，结论与交接说明里的预期**完全不同**，见下节。

### 最重要的一条：Java 与 SQL 是两套互不相干的设计

交接说明给的 16 个编译错误是**并发写入时的假象** —— 重跑后 `default-compile` 一次通过，
16 个错误一个都不存在。真正的问题是另一件事：

迁移被重写过（578 行版本取代了 713 行版本），而 **Java 三件仍停留在被重写掉的那一版设计**。
两边连不到一起：

| Java 期望 | 磁盘上的迁移 |
| --- | --- |
| `sales_order.source` | `order_source` |
| `customer_party_id` / `customer_name` 在订单头 | 在 `sales_order_party_snapshot` |
| `total_amount` / `other_amount` / `charge_tax_amount` | `grand_total_amount`；后两者不存在 |
| `order_charge_allocation` 分摊表 | **表不存在** |
| `order_line_component` 组件表 | **表不存在** |
| `order_status_history` + `status_domain` | `sales_order_status_history` + `event_type` |
| PaymentMethod：CARD/WIRE/PAYPAL/… | PREPAID/COD/BANK_TRANSFER/CREDIT_TERM/… |
| Status：含 APPROVED / CANCELLED | 只允许 DRAFT / SUBMITTED |

**取舍：保留 578 行迁移，按它重写 Java。** 依据有三条：

1. 迁移是台账证据引用的对象，且逐条对齐了蓝图硬要求（来源词表预先含全部平台来源、
   快照纪律、部分唯一索引），注释密度高且已经过审；
2. Java 侧对 `order_charge_allocation` / `order_line_component` 的引用是**指向不存在的表**，
   保留它等于凭空多出两张表和一套分摊模型；
3. 迁移的 CHECK 值域（MANUAL + 六个平台来源）比 Java 枚举（MANUAL + PLATFORM）更完整，
   正是「来源是一个字段」最硬的证据。

代价是 Java 三件几乎整体重写（models / service / controller）。

## 关键 trade-off

### 1. 端点前缀 `/trade/sales-orders` 而不是 `/trade/orders`

`TradeTenancyIntegrationTest` 断言 2 **显式预留**了 `/trade/orders`（断言 GET 与 POST 都必须
404，且注释写明「第一条 9.x 端点车道落地后要升级这条断言」）。用了 `/trade/orders` 会直接打红
一条已通过的测试，而那个文件属于别的模块。`/trade/sales-orders` 也与既有 `/trade/processing`
一致。**契约：后端命名空间按服务走，前端路由 `/orders`。**

### 2. 本模块刻意没有取消动作

草稿的处置方式是「不提交」—— 它从未进过审单队列，不需要作废。取消 / 作废属于 9.2 的驳回动作；
在审单还没交付时先造一个 `CANCELLED`，9.2 落地时会与它的驳回语义打架（同一个终态两个来源）。

### 3. 状态机只到 SUBMITTED

9.2 审单未交付。审单结论由它按「加值迁移」扩展，本表不需要为它 ALTER 一次。

### 4. 「没有分摊明细表」是选择不是遗漏

`order_charge.charge_kind`（ORDER / LINE）只是**层级标记**，不带金额。v2 README 提过
「分摊之和等于头金额，保留舍入差额」，但 9.1.2.2 的蓝图职责句只要求「费用是表单的一部分」。
把分摊金额摊进行里会让「这一行到底买了多少钱」出现两个答案（单价 × 数量 vs 含分摊的净额）。
真要做行级分摊时另开 `order_charge_allocation` 子表。

## 交接线索的逐条结论

前一位 worker 留了四条待核查线索（读的是已被重写的旧版本）。逐条对照**当前磁盘上的 578 行**核实：

| # | 线索 | 结论 |
| --- | --- | --- |
| 1 | `guard_sales_order_charge_allocation` 挂在 `order_charge` 上却解引用 `NEW.charge_id`，每次写费用都炸 | **不成立**。当前版本没有这个函数、没有 `charge_id`、没有分摊表。**但残留**：第 6 节注释引用了一个并不存在的「7.5 延迟约束触发器」和并不存在的分摊明细列 → 已改成如实描述 `charge_kind` 的真实含义。 |
| 2 | `sales_order_line` 上的延迟触发器导致「同一事务建行 + 提交」必然报错，submit 必须独立事务 | **不成立（结论反了）**。`sales_order_line` 上**没有**延迟触发器；两个 DEFERRABLE 触发器都在 `sales_order` 上。DEFERRABLE INITIALLY DEFERRED 正是让「先插头 → 写行/地址/费用 → 提交」成立的原因——当场算会把「还没写完」误判成「不完整」。submit 仍是独立事务，理由是**提交后行/地址/费用被冻结**，与建单同事务会让刚建的单在确认前就被锁死。 |
| 3 | `guard_sales_order_state` 在 DB 层无条件拒绝 `APPROVED`，9.2 要 `DROP TRIGGER` 才能用 | **不成立**。当前版本没有这个函数，也没有 `APPROVED` 值。状态 CHECK 只有 `('DRAFT','SUBMITTED')`；9.2 按 AGENTS.md 的 R6「加值」纪律扩展。确有一步 `ALTER ... DROP/ADD CONSTRAINT`，但那是正常流程，不是「必须 DROP TRIGGER」的地雷。 |
| 4 | `GRANT ... TO starcon_app` 与 V1 的 `REVOKE ALL ON ALL TABLES FROM starcon_app` 矛盾 | **成立，但是既有车道的问题，不是本车道引入的**。V97、V98 都做了同样的 `GRANT ... TO starcon_app`。V1 的 REVOKE 只作用于 V1 时刻已存在的表（只有 `trade_tenancy_probe`），后续每个迁移都把写权限授回了这个被 V1 注释定义为「跨服务只读」的角色。**按 V97/V98 先例照做**（单改 V99 会让三条迁移不一致，更糟），把发现留给专门车道统一处理。 |

## 实际修掉的缺陷

### 迁移（此前从未被执行过）

1. **客户快照表建在订单头之前却对 `sales_order` 有外键** → Flyway 直接失败
   （`relation "sales_order" does not exist`）。把订单头提到第 1 节。
2. **索引建在 `sales_order` 上但 `customer_party_id` 在客户快照表上** → 建索引就报列不存在。
3. **`guard_sales_order_totals` 把 4 个值 `SELECT ... INTO` 3 个变量** ——
   PL/pgSQL 编译期不报错，提交时运行期才炸；`v_discount` / `v_tax` 被赋值两次；
   `grand_total_amount` 根本没被核对。改为六项全部独立复算。
4. **头部缺 `other_amount` 列** → `PACKAGING` / `OTHER` 类费用无处安放。补列。
5. **注释引用了一个并不存在的 `line_amount_matches` CHECK** → 补上真 CHECK
   （行小计 = 单价 × 数量，DB 侧独立复算）。
6. **注释引用了一个并不存在的「7.5 延迟约束触发器」与分摊明细列** → 改成如实描述。

### 由集成测试当场抓出来的（写测试的价值）

7. **外部订单号用普通 UNIQUE 时，空号会撞车**。`external_order_no` 是 `NOT NULL DEFAULT ''`，
   而 PostgreSQL 的普通唯一约束把 `''` 视为相等——一个租户完全可以有任意多张没填客户参考号的单，
   第二张会撞上第一张。**改成部分唯一索引** `WHERE external_order_no <> ''`。
   手册那条「空号参与唯一性要用表达式唯一索引处理」在当前实现里正好命中。
   迁移第 3 节的注释原本**声称**空串不参与唯一性并指向一个不存在的 CHECK——是测试证伪的。

### api-proxy 白名单

8. **第一版 pattern 漏了裸列表路径**。写成 `sales-orders\/(?:...)` 强制要求一个斜杠，
   而列表端点就是裸的 `trade/sales-orders` → 集成测试当场抓到 404。改成整个分组可选。

### 契约平铺地雷（自己踩了一次）

9. **下游缺口记录原本叫 `DownstreamGap`，覆盖了已交付模块的同名类型**。
   全仓契约被 codegen 合并进**一个扁平文件**，同名 key 后者覆盖前者且**不报冲突**。
   它的形状是 `moduleId/moduleName/service/available/ownerModule/effect`，
   被我覆盖后 `processing-order-workspace` 三处 typecheck 报「属性不存在」。
   改名 `SalesOrderDownstreamGap` 后旧形状原样还原。
   **与 CRM 那 40 多个 `Trade*` 是同一类地雷，教训一致：跨模块共享的类型名必须带自己的模块前缀。**

## 写入所有权结论

本模块是 `sales_order` 的**第一个写入所有者**（此前只存在于 `db/schemas/v3/` 设计稿）。
9.1.1.1 订单列表 / 9.1.1.2 订单详情是**读投影**，本车道不替它们建表、也不由它们写。
**V99 只新建七张表，不 ALTER 任何既有表**——跨车道 DDL 回归面 = 0。

**「来源 = MANUAL 是字段不是表」怎么体现**：
只有一张 `sales_order`；`order_source` 一列的 CHECK 词表**连同 MANUAL 一起预先钉住**
`PLATFORM/AMAZON/SHOPIFY/EBAY/TIKTOK_SHOP/ALIBABA_1688`；D5 落地时直接写同一张表，
不需要 ALTER 改 CHECK，也不需要另建一套流程——这就是蓝图「避免两套流程」的实现形式。
集成测试逐条钉住：不存在 `manual_sales_order` / `platform_sales_order` 表；CHECK 含全部平台来源；
请求体带 `orderSource` 被 400 拒（应用开了 `fail-on-unknown-properties`）。

**外部单号唯一约束怎么带来源维**：
部分唯一索引 `(tenant_id, order_source, external_order_no) WHERE external_order_no <> ''`。
带 `order_source` 是必须的（Amazon 的 123 与 Shopify 的 123 是两张毫不相干的单）；
`WHERE` 子句同样必须（否则多张没填参考号的单互相撞车，见上文缺陷 7）。
测试从 `pg_index` 断言索引列顺序与 `pg_get_expr(indpred)` 的谓词。

**快照怎么保证不被后续变更改写**：
行携带 `sku_code/sku_name/spec_snapshot/sku_mapping_version` 快照列 + 逐属性快照表；
服务层**不回查 catalog / crm**（回查就会让「后来改了参数的商品」改写历史行）。
地址是独立快照行，**不建指向 3.6.3.1 活地址的外键**（跨服务本就禁 FK），测试从
`information_schema` 断言该表没有任何指向活地址的列。
提交后由触发器冻结——测试直连 SQL 改已提交单的地址被 DB 挡下。
