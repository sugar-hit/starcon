# 12.1.1.3 坏账与核销（阶段 D6，L3 锚点 12.1.1）

> 车道：`feat/12-1-1-3` · worktree：`integration/.worktrees/12.1.1.3` · 基线：`integration/module-dev` 的 `a70ea6f1`
> 日期：2026-10-24

## 决策摘要

**做什么**：在 finance 服务里落成蓝图 12-finance.md 的 12.1.1.3「坏账与核销」——
核销申请（申请单）+ 依据材料（可多项）+ 审批（审批人 ≠ 提交人、意见必填）+ 执行核销 + 审计留痕。

**四条硬约束怎么落的**（蓝图里那两句加粗句是本模块的骨架）：

| 蓝图加粗句 | 落法 |
| --- | --- |
| 「核销是**财务终审动作**，需要完整依据链」 | 依据材料是**独立的一层**（不是单据上的备注字段）；提交审批时**零依据的申请进不了审批**（服务层 400 + DB 守卫各拒一次）；审批意见必填、审批人 ≠ 提交人（同样两层各拒一次）；**没有「一键批量核销」的端点**（蓝图另一句加粗句） |
| 「**不允许批量一键核销无审批**」 | 本模块**不提供任何批量核销端点**；状态机只能一张一张走；能力声明里「批量一键核销」这一行 `available=false` 并写明原因；测试断言「批量形状返回 4xx **且没有任何一笔被核销**」 |
| 「保留核销依据与审批」 | 依据与审批都进 **append-only 事件流**（`finance_bad_debt_event`，运行角色 UPDATE/DELETE 已收回）；依据表本身的 DELETE 权限也收回 |
| 输出里的「**会计处理**」 | 下游 12.5.2.1 未交付 ⇒ **不可产生**：`accounting_status` 恒为 `PENDING_FINANCE`、`accounting_ref` 由 CHECK 钉死恒为空串、`accounting_owner_module` 恒为 `12.5.2.1`。**绝不填 0、绝不造凭证**（直连 SQL 写凭证号被 DB 拒） |

## 关键 trade-off

### ① 核销路径：**「作废 + 新单」**，不写 `settled_amount`

**选「作废 + 新单」，不选「直接写行级 settled_amount」。**

- **理由**：V338 的注释原文写死「只放行 settled_amount（核销金额）—— 那是 **12.2.1.2 的写入所有权**」。
  本模块走作废 + 新单 ⇒ `settled_amount` 的写者在本仓恒为 12.2.1.2 一个，
  **本批 12.1.1.3 与 12.2.1.2 两条车道在核销金额上不撞同一列**。
- **怎么做的**：作废与建单**都走 12.1.1.1 自己的能力**
  （`ReceivableService.voidReceivable` / `ReceivableService.create`）——
  它的冻结守卫、它的 VOIDED/CREATED 留痕、它的应收确认政策校验全部照旧生效，
  本模块**不自己往 12.1.1.1 的表里插一行**，也不在它那两张表上加触发器 / 改 GRANT。
- **与 12.2.1.2 的交互关系**（按任务书要求写明）：
  - 本模块**不写** `finance_receivable_line.settled_amount`（一个字节都不写）；
  - **已部分回款的应收（`settled_amount > 0`）本模块不受理** ——
    冲减「已核销」那部分属 12.2.1.2 核销的**冲销（红冲）**范围，
    而本模块写那一列会与 12.2.1.2 抢写权、并把「已收回应收」的口径污染成「已收回应收 + 已坏账」；
  - 能力声明里这一条 `available=false`，归属模块写明 `12.2.1.2`。
- **核销的账务效果**：应收账上减少的正好是核销金额 ——
  作废把整张单移出账簿，承接单把**仍然收得回**的那部分以一张干净的新单继续挂着。

### ② 部分核销的承接单到期日

12.1.1.1 的建单端点不允许到期日早于确认日 ⇒ 原单已逾期时承接单到期日只能取今天。
本模块**如实标注**（`replacement_due_date_adjusted` 布尔列 + 页面上的提示），
不静默改账龄归属。测试覆盖两条分支（未逾期 ⇒ 沿用原单到期日；已逾期 ⇒ 取今天并标注）。

### ③ 依据材料的「移除」是**软移除**，端点走 POST 而不是 DELETE

- finance 的 API 出口 `apps/web/src/app/api/finance/[...path]/route.ts` 里
  **刻意不导出 DELETE**（12.1.1.1 留下的成文约定：应收单是凭据，错了只能作废不能删）。
  本模块**不越界改那个共享文件** ⇒ 移除动作改成 `POST /{id}/evidence/{evidenceId}/remove`。
- 移除是 `status='REMOVED'`（与 12.1.1.1 的催收任务「取消走 status='CANCELLED'」同一手法），
  **物理删除在 DB 层就做不到**（运行角色对依据表的 DELETE 权限收回），且已移除的依据**不可复活**。

### ④ 跨模块引用只留 uuid + 快照，不建外键

任务书明令「零 FK 指向别的模块的表」⇒ `finance_bad_debt_case` 对 `finance_receivable`
只有 `receivable_id`（uuid）+ 一组**快照列**（单号 / 币种 / 总额 / 已核销额 / 未核销余额 / 对象 / 店铺 / 到期日）。
快照是「核销**当时**的账」—— 依据链要能自证，不能靠事后去查别人表里的当前值。

### ⑤ 上游 11.4.1.1 纠纷：经 trade 的**授权 HTTP API** 读

`TradeDisputePort` 读 `GET /trade/platform-disputes/{id}`（trade 服务，端口 8085），
转发调用方自己的 bearer（租户仍由 trade 侧按已认证成员关系解析）——
**不跨库 SQL / 跨库 FK / 跨库视图**。读到的单号 / 状态 / 金额以快照落库。
**争议损失确认要求上游纠纷已是「我方败诉」（RESOLVED_LOST）**：未出裁决的纠纷不能核销；
上游读不到时整体失败（503 / 404），**绝不装作「上游没有纠纷」**。
