## 关键取证：29 个冲突全是排版差异，且 main 侧是规范态

`merge-resolve.mjs` 把 29 个文件全部判成「并入（人工）」，依据是
「main 侧的文件版本不在集成分支的历史里」。**该依据在本轮不成立** ——
main 是 squash 合入的，合入时全仓被 Prettier 重排过，
所以 main 的 blob 天然不会出现在集成分支的历史里
（实测 29 个冲突文件的 main 侧 blob 在集成分支历史中 0 命中）。
这是该工具在纯排版场景的固有误报。

改用**字节级 Prettier 归一化**取证（两侧各跑一遍同配置的格式化，再逐字节比对）：

| 计数器 | 含义                                | 实测      |
| ------ | ----------------------------------- | --------- |
| A      | 两侧规范化后逐字节相同              | **29/29** |
| B      | 集成侧规范化结果 == main 侧原始字节 | **29/29** |
| C      | main 侧规范化结果 == 集成侧原始字节 | **0/29**  |

三条合起来说明：**内容完全等价（A），main 侧就是规范态（B），集成侧不是（C）。**
⇒ 取 **main 侧**：语义零损失，且不给仓库新增格式债。
反之取集成侧会让 `format:check` 多出 29 个未格式化文件，直接加重 `Lint` 作业的存量失败。

**独立交叉验证**：并行的另一实例在第 39 轮纪要里记录了完全相同的分类
（A=29/29、B=29/29、C=0/29、取 main 侧）。两个独立实例结论一致。
