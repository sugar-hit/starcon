## 决策摘要

### 1. 基线对齐是快进，不是合并

`git merge integration/module-dev --no-commit` 报 **Fast-forward**：`225ba19` 已是 `be2e109` 的祖先。
因此本车道**不需要** merge commit，HEAD 直接等于集成头，无冲突。
验：`git merge-base --is-ancestor integration/module-dev HEAD` 返回 0，`git status` 干净。

> 教训写在这里给下一条车道：先跑 `git merge-base --is-ancestor` 再决定要不要 `--no-commit`。
> 本车道不会触发任务书里警告的「MERGE_HEAD 被清掉」坑，因为压根没有 merge。

### 2. 冻结语义：快照，不是引用（蓝图那句加粗是验收项）

落点：**trade 服务**（与 6.4.1.1 同车道同库，前端 /purchase/processing，后端 /trade/processing）。

两张新表：

| 表                             | 作用                 | 关键列                                                                                                                                                                                                                 |
| ------------------------------ | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `processing_bom_snapshot`      | 冻结头（一单一快照） | `explosion_run_id` / `bom_version_no` / `output_quantity` / `as_of` / `max_depth` / `reached_depth` / `snapshot_status` / `line_count` / `frozen_by` / `frozen_at`                                                     |
| `processing_bom_snapshot_line` | 展开树明细           | `depth` / `path` / `sku_id` / `component_id` / `source_version_id`+`source_version_no`+`source_bom_code` / `unit_quantity` / `scrap_rate` / `required_quantity` / `available` / `in_transit` / `gap` / 子 BOM 判定四列 |

**为什么不会被后续 BOM 修改影响**：读快照时**不 join catalog、不 join 当前 BOM**。
每一列都是展开那一刻的**值**。集成测试 `snapshotSurvivesBomChange` 把 catalog 侧的
组件用量、损耗率、可用量、在途全改掉之后，逐行断言七列原封不动，且 `bom_version_no` 仍是 v1。

**唯一一次跨服务调用是 R4 的时刻查询，且只用于生成漂移提示**，绝不参与计算快照里的任何一行。

### 3. 与 6.4.1.1 是互补，不是重复（无冲突）

读 V97 后确认：6.4.1.1 在建单时冻结的是**单层** R7 三元组到 `processing_order_component`
（问「要领哪些料」，随仓库出库逐行推进 `issued_quantity`）。
本模块冻结的是**多层**展开树（问「这批料当时按哪棵树、哪一版算的」）。
蓝图把上游写成 **3.5.2.2 展开**而不是 3.5.2.1，正说明这一层不是重复：
成品→半成品 SA→面料/拉链时，单层清单答不出「这 3 个 SA 的面料按哪一版算的」，
而加工周期长达数周 —— 这正是蓝图点名要消灭的「实物与系统不符」。

**因此不 ALTER 任何 V97 表、不加指向 `processing_order` 的 CHECK / 触发器**：
跨车道 DDL 回归面 = **0**。唯一的跨表依赖是复合外键 + 两处**只读**触发器查询。
实测：trade 全量 85 例全绿，其中 6.4.1.1 的 27 例未回归。

### 4. R1–R7 口径逐字沿用，不另立一套

展开由 catalog 3.5.2.2 真算，trade 经 `BomExplosionPort` 原样搬运，不重算、不取整。

- **R6（损耗率是百分数不是比率）**：`scrap_rate NUMERIC(7,4)` + `CHECK 0<=x<=100`，
  与 V25/V26 同精度同上界。服务层 `scrap()` **只做刻度对齐，绝不除以 100**。
  测试断言 `5.0000` 而非 `0.05`，并额外断言 `> 1`（防止有人「顺手」比率化）。
- **R7**：`required_quantity NUMERIC(19,6)`，6 位小数**不取整**。
- **E1（逐层结转）**：深层 required 按**父行缺口**驱动，不是按父行需求。
  这就是**为什么必须同时冻结 available / in_transit / gap** ——
  只冻 required 答不出「这一层为什么是这个数」。测试用 SA 的
  required=31.5、gap=24.5，断言面料是 `24.5 × 0.5 = 12.25` 而不是 `15.75`。
- **E4（截断必须显形）**：`snapshot_status`/`truncated` 落库，TRUNCATED 页面显红。
- **R4**：`as_of` 随快照冻结（事后重算会得到另一个答案）。

### 关键取舍

- **POST 而不是 PUT 冻结**：`PUT` 的语义是「把这份资源改成这样」，与「冻结之后永不可改」相反。
- **冻结幂等**：已冻结过返回既有那份（`alreadyFrozen=true`）而不是报错；重试不该让运营以为没冻上。
  并发下靠 `UNIQUE(tenant_id,order_id)` + `DuplicateKeyException` 兜。
- **剥掉 `UNIQUE(tenant_id,explosion_run_id)`**：初版加了，跑测试时发现我的 catalog stub
  返回恒定 run id 会撞。复查后确认 catalog 每次调用都新建 run，同一 run 冻两次本来就不会发生；
  而将来若支持「拿一次已算好的展开结果直接冻到另一张单」，这条约束会挡掉合法场景却换不来新保证。
  **主动放宽的是约束，不是断言。**倒排查询由按 run 的索引承担。

### 过程中被证伪的三处（都不是靠放宽断言解决的）

1. **`plpgsql` 的 `RAISE EXCEPTION` 不接受 `||` 拼接** —— 格式串必须是字面量。
   改成单行后迁移才能跑。V97 本来就是单行，我一开始按排版折行了。
2. **stub 的截断判定用 `rindex('(?:')` 取组是错的** —— 新加的 `bom-binding(?:\/lines)?`
   自带嵌套，rindex 会命中最里层、只数出 1 个分支，**一个假绿**。
   改成配对括号提取；且 fixture 特意包含嵌套形状，让这个坑在改文件之前就先被自测抓住。
3. **我断言 `orders/{uuid}` 应 404 是错的** —— 核对 OpenAPI 后发现它是 6.4.1.1 的**真实**端点
   （`GET /orders/{orderId}` 详情）。按纪律报告而不偷偷改松：改正方向是把它挪进正向集合，
   理由写在测试注释里。

### 两个环境问题（都不是本车道代码导致，已举证）

1. **catalog `ZombieCandidateIntegrationTest.最后维护时刻走timestamptz往返` 偶发失败**（1ms 漂移
   `.660Z` vs `.661Z`）。该测试的 `backdate()` 与断言各自调一次 `now()`，会跨毫秒边界。
   本车道 **catalog 零改动**；单跑该用例 **5/5 通过**；完整重跑 `./mvnw verify` 全绿。
   是既有 flaky 测试，未修（不碰别的模块的测试文件）。
2. **`NEXT_TELEMETRY_DISABLED=1 pnpm --filter @starcon/web build` 失败**：
   `next/font` 拉不到 Google Fonts（`Failed to fetch Inter`，`ECONNRESET`），
   失败点在 `src/app/layout.tsx`（本车道未改）。
   举证：把我的改动**全部 stash** 后，同一 worktree 仍然同样失败；
   而主工作区（未改代码）连续两次构建成功。`next.config.js` 两边 `diff` 完全一致。
   结论：本机到 `fonts.googleapis.com` 的链路在 worktree 里不可达，与本车道代码无关。

## 契约

`python3 tools/codegen/catalog-contracts.py --spec-dir backend/target/openapi`
→ `catalog.ts` +5 类型、`trade.openapi.json` +409 行，**全部为新增**，无手改。

顺带记录一个**既有**契约缺口（未修，只在本车道模型里写明并在前端防御）：
Spring 对**记录组件类型的引用**不发射 `nullable`，所以
`BomBinding.snapshot` 在契约里是裸 `$ref`；而服务在「还没冻结」时返回 `null`。
6.4.1.1 的 `inboundRequest` 是同一形状。前端因此按「可能为 null」处理
（`?? null` + 空态分支），不依赖契约的单取值。

## 跨车道回归结论

- 本迁移**不 ALTER 任何既有表**：没有 ADD COLUMN、没有 SET NOT NULL、
  没有既有表的触发器被新约束覆盖。
- 唯一跨表依赖：`processing_bom_snapshot.order_id → processing_order(tenant_id,id)`（复合外键 + CASCADE）
  与两处只读触发器查询。
- 对 catalog 的 V25/V26 表只存逻辑 ID，不建跨库 FK/视图/JOIN。
- 实测：6.4.1.1 的 27 例、9.3.2.2 的 32 例、trade 租户 4 例全部未回归。
