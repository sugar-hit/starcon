# 5.3.2.2 价格规则（阶段 D6，L3 锚点 5.3.2）

> 会话日期：2026-10-21 · 车道：feat/5-3-2-2 · 状态：**已交付**（待并入集成分支）

## 决策摘要

1. **🔴 蓝图加粗句落成服务层的四道闸，而不是页面上的提示。**
   蓝图写的是「自动调价必须先"建议"再"执行"，高风险规则（降价超过 X%）需人工确认，
   避免错误规则批量改价造成损失」。本模块因此：
   - 只产出**建议调价**（`pricing_rule_suggestion`），**永不写价格** —— 改价是 5.4.1.1 调价单的写入所有权，
     价目表 5.1.1.2 未交付（本仓无 `price_list` 表）⇒ 当前价只读 5.5.2.1 的价格观测台账；
   - 建议状态机 `PENDING_CONFIRMATION / READY / CONFIRMED / REJECTED`：「执行」= 放行给下游；
     已放行 / 已确认 / 已驳回的建议**不可改判**（只追加事实，改判历史等于把留痕洗掉），驳回必须写原因；
   - **自动放行**只在三条同时成立时发生：降价幅度 ≤ 规则上的 `max_auto_price_drop_rate`
     **且** 5.3.1.1 复核得了毛利（`decision_ready`）**且** 是价格动作。
     ⇒ 降价超阈值、成本不完整、暂停促销 / 下架三类，一律进人工确认；
   - 毛利只能来自 5.3.1.1 的真实测算（不重写任何扣减公式）；成本不完整 ⇒ 毛利率为 `null`
     （不是 0），且该建议**不自动放行**。

2. **五类触发条件各有真实数据来源；取不到就「不判定」，不判定 ≠ 没超阈值。**
   | 触发条件 | 数据来源 | 取不到时 |
   | --- | --- | --- |
   | 库存低于阈值 | 7 库存（warehouse `POST /warehouse/inventory/availability`，catalog 既有 `InventoryAvailabilityPort`） | 记未命中 + 写明「取不到」，**不**当成 0 |
   | 库龄超期 | 7.6.1.1 库龄呆滞（warehouse `GET /warehouse/inventory/aging/slow-moving`）—— **新建** `InventoryAgingPort` | 同上 |
   | 成本上涨 | 5.2.1.1 `sku_cost_revision` 版本历史 | 只有一版 ⇒ 不判定；两版快照必须**完整**，否则不判定 |
   | 竞品降价 | 5.5.2.1 价格观测台账相邻两次 `platform_price` 观测 | 只有一次观测 ⇒ 不判定 |
   | 毛利低于下限 | 5.3.1.1 在当前价下的真实毛利率 | 成本不完整 ⇒ **不判定**（不是判定成「没低于下限」） |

3. **「竞品降价」的可测口径如实标注，不编竞品价。**
   本仓**没有**竞品价采集模块（2.x 卷里没有采集竞品价的模块，5.3.2.1 也把竞品价定成「人工登记」）。
   本模块**不建**任何竞品价表来假装上游已交付；它用**平台在售价（`platform_price`）的观测下降幅度**作可测口径，
   并在能力声明里写明「那是我们这条 listing 在平台上的在售价的下降，**不是竞品价**」+ ownerModule 指向未交付的竞品价模块。

4. **优先级语义定死为「先命中者优先」。**
   数字小者优先（与本仓既有约定一致：`supplier_quote` 的 1 = 首选、`exchange_rate_source` 按 priority 升序）。
   同一 SKU 上只有**优先级最高**的那条命中规则产出建议调价，其余命中记录标 `superseded` 并点名覆盖者
   —— 否则两条规则会对同一个 SKU 给出两个互相矛盾的价。生效时段 `effective_from`（含）~ `effective_to`
   （不含，空 = 长期有效），评估只跑 enabled 且落在时段内、币种与本次评估一致的规则。

5. **跨服务只读取数，遵守模块边界纪律。**
   库存与库龄都在 warehouse 的库里 ⇒ 新建 `InventoryAgingPort`（仿 `CostBasisPort` + `CostBasisConfiguration`
   的 Http / Unwired 双实现 + `@Value("${WAREHOUSE_URL:}")` 装配，透传调用方 `Authorization` 头、
   租户由 warehouse 从已认证成员关系解析；**不**发明 `X-Tenant-Id` 之类的旁路）。
   库龄端点显式请求 `NORMAL / SLOW_MOVING / OBSOLETE` 三档全量 —— warehouse 的呆滞清单默认只返回
   `status <> 'NORMAL'` 的行，而本规则的阈值可能比 warehouse 的滞销线更短。

6. **零外键 + 触发器 guard；四表职责不重叠。**
   `pricing_rule` / `pricing_rule_scope` / `pricing_rule_hit` / `pricing_rule_suggestion`；
   引用校验一律用触发器（避开 batch-37 的「加 FOREIGN KEY 打破既有测试 TRUNCATE」的坑）；
   `tenant_id NOT NULL` + ENABLE/FORCE RLS isolation，命中记录与建议调价再加 `data_scope` 跟随 sku。

7. **契约模型类型全部带 `PricingRule` 前缀。**
   起因：catalog 服务里**已有**别的模块定义了 `RuleInput` / `ScopeView` / `CategoryOption` / `BrandOption` /
   `CapabilityItem`。SpringDoc 的 schema 名取简单类名 ⇒ 同名会**互相顶掉**，实测本模块的 `RuleInput`
   把另一个模块的 `RuleInput` 从契约里挤掉了。改名后重新生成契约：**0 条路径删除、0 个既有 DTO 改动**。

## 关键 trade-off

| 决策 | 取舍 |
| --- | --- |
| 「竞品降价」用平台在售价降幅，而不是等竞品价模块 | 上游没有可读端点；等下去本模块交付不了。代价是口径必须显式标成「市场价观测」而不是竞品价（能力声明里写明），竞品价落地后由上游接管 |
| 成本上涨要求两版快照都完整 | 部分成本算出来的涨幅是假的。代价是上游单据晚到时规则会「不判定」而不是「误判」—— 宁可漏报不可错报 |
| 成本不完整的建议也不自动放行 | 自动放行的前提是「复核得了毛利」。代价是成本补齐前建议全部停在人工队列，运营要手工放行 |
| 非价格动作（暂停促销 / 下架）也一律人工确认 | 蓝图只提了降价超阈值，但规则写错一次就是一批商品被误伤。代价是这类规则无法全自动跑 |
| 命中记录连「未命中」也落库 | 台账会变长。代价换来的是「为什么这条规则没动我的商品」有答案 —— 运营最常问的就是这句 |
