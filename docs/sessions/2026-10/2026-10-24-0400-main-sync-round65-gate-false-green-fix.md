# 2026-10-24: main 同步第 65 轮 —— 修好闸工具的假绿灯，独立复核三个「明细不可比」作业

## 摘要

本轮**没有合入任何内容**，PR #65 的闸门结论仍是**阻塞**。

本轮做完了三件事：

1. **独立复核了闸工具判为「明细不可比」的三个作业**，逐个下钻到文件级/用例级，
   确认它们相对 `main` 基线**没有劣化** —— 只有 Java 作业多出一条新增失败用例。
2. **修好了闸工具自身的假绿灯缺陷**：run 还在跑时它会输出「可以合并」。
   这是决定「能否合进 `main`」的闸门本身，工具侧的修法本轮落地。
3. **确认了阻塞缺陷至今无人认领的机制性原因**：派活链路的候选集只来自台账，
   而两个出问题的模块在台账里都是「已交付」⇒ 永远不进候选集。

## 决策 / 结论

1. **本轮不合 PR #65**。闸工具在 run 收尾后给出「阻塞」：
   新增失败用例 1 条（`PlatformFlagIntegrationTest.公告生效期按值写回且窗外不展示`）。
2. **本轮不刷新同步分支**。集成分支相对同步分支头的提交数为 **0** ⇒ 没有新交付可取。
3. **修闸工具，但不修那两条失败用例**。前者是放行闸本身的判据缺陷（属本任务职责），
   后者是集成分支交付内容的所有物（属集成侧职责）。
4. **三个「明细不可比」的作业自己下钻，不按默认放行处理**。
5. **不在同步分支上动业务代码**，只改闸门工具与文档。

## 关键 trade-off

- **为什么修闸工具不算越界**：它不是业务代码，而是「本任务能否合进 `main`」的判据本身。
  它的假绿灯会直接导致带新增失败的 PR 进 `main`，而 `main` 基线本身是红的 ⇒ 这类假绿灯
  不会被「基线也红」兜住。修它属于**加固放行闸**，不是开发业务功能。
- **为什么不顺手修那两条失败用例**：它们是集成分支交付内容的所有物。
  在同步分支上打补丁会让两边分叉，且源分支后续修复时还要再解一次冲突；
  更关键的是，那等于自己把闸门改绿。
- **为什么本轮花力气下钻三个「明细不可比」的作业**：闸工具在明细取不出来时**按作业粒度放行**。
  只比到作业粒度时，「持平」是默认结果而非证据 —— 那三个作业恰好是 Lint / Security / Catalog，
  每一个都可能藏着新增失败。
- **为什么把「无人认领」这件事查到底**：连续四轮阻塞，缺陷的 backlog 条目已经写好，
  但**没人会去做**。查清原因是派活链路只读台账、不读 backlog，
  而这两个模块在台账里是「已交付」⇒ 这不是「还没排到」，是「永远不会排到」。

### ④ 闸工具的假绿灯：源码级根因与修复

根因在 `tools/module-progress/ci-gate.mjs`：

- `failingJobs()` 只数 `conclusion === 'failure'` 的作业；
  **在飞作业的 `conclusion` 是 `null`**，被默认归入「非失败」。
- 于是「PR 的失败集合 ⊆ 基线的失败集合」这条判据**空洞地成立** ⇒ 输出「可以合并」。
- 而 `prRun()` **不校验 run 是否收尾**，`baselineRun()` 还会用 `?? runs[0]` 兜底 ——
  在 `main` 上一个收尾 run 都没有时，会把**在飞 run** 当基线（失败集合被低估 ⇒ 同样的假绿灯）。

工具侧已修（详见
[`2026-10-24-ci-gate-in-progress-run-false-green.md`](../backlog/2026-10/2026-10-24-ci-gate-in-progress-run-false-green.md)）：

1. 新增 `runIsSettled(run)`，未收尾的 run ⇒ 抛错 ⇒ 退出码 2（「状态取不到」）。
2. 基线选取不再兜底取在飞 run。
3. 判据从 `conclusion !== null` 改为 `status === 'completed'`。
4. 被取消（`cancelled`）的 run 一律拒绝当判据。
5. 显式按 `createdAt` 倒序取最新 run。
6. 输出补上 run 的 `status` / `conclusion` / `head_sha`。

回归测试补在 `ci-gate.itest.mjs`，**26 条断言全绿**。其中一条是**反向锁定假绿灯形态**的：
断言「在飞作业被当成非失败时，`compareRuns` 确实会给出不阻塞」——
把「为什么必须在取 run 处拦住」写成可执行证据，而不是只写结论。

实测对照：

| 场景                                 | 修复前             | 修复后               |
| ------------------------------------ | ------------------ | -------------------- |
| run 还在跑（全部作业 `in_progress`） | 「可以合并」（错） | 退出码 2，状态取不到 |
| run 已收尾且失败                     | 阻塞               | 阻塞（判定不变）     |

⚠️ 调用侧纪律仍保留：**拿到「可以合并」后，执行合并前先确认 run 收尾** ——
工具已经不会再给假绿灯，但纪律是最后一道防线。

### ⑤ 阻塞缺陷「永远不会被自动认领」的机制性原因

派活链路的候选集来源只有一处：`lane.mjs` 的 `pickModules()` 读台账，
只挑状态为 `未开发` / `进行中` 的模块。而：

| 模块     | 名称           | 台账状态 | 能否进候选集 |
| -------- | -------------- | -------- | ------------ |
| 17.7.2.1 | 平台参数与开关 | 已交付   | **不能**     |
| 17.7.1.2 | 用量统计       | 已交付   | **不能**     |

全仓搜索确认：`tools/` 下**没有任何代码读 `docs/backlog/`**，
`PIPELINE_CRON_PROMPT.md` / `PIPELINE.md` / `PIPELINE-MULTI.md` 也**不读它**。

⇒ 这两条缺陷虽然已经有可跟踪的 backlog 条目，但**没有任何自动链路会把它们排成车道**。
解除阻塞需要**有人显式派一条修复车道**（像流水线此前给财务那条派
`fix/12-1-1-1-due-date-timezone-assertion` 那样），这一步**超出本任务范围** ——
本任务只做「合入」，不做开发，也不派车道。
