## 决策摘要

1. **收款单**按蓝图 12-finance.md 12.2.1.1 落地：登记与跟踪资金收入，输出「收款单 + 未核销余额」。
   三张新表：`finance_receipt`（单头）/ `finance_receipt_allocation`（预留核销关系）/ `finance_receipt_event`（留痕）。
2. **没有明细行**（与 12.1.1.1 的应收单不同）：一次到账流水**本身就是一笔资金事实**，
   金额是原子的、可直接记账的。为它编一条「明细行」只是为了凑结构，那是**假明细**。
   「一笔收款对应哪几笔应收」改由 `finance_receipt_allocation` 表达。
3. **未核销余额是生成列**（`unsettled_amount` = `amount − settled_amount`），没有第二个写入口。
   核销金额的唯一写入口是 `settled_amount`，属 **12.2.1.2（未交付）** ——
   本模块**不写它、也不开放写端点**，所以未核销余额**恒等于收款金额**（口径，不是缺陷）。
4. **「预留」≠「核销」**：蓝图加粗句「一笔收款可核销多笔应收（合并回款）」由预留关系承载，
   但预留**不减少**未核销余额。预收（还没有对应应收的资金）由 `advance_flag` 单列，
   预收与预留**互斥**（DB 层守卫）。页面**不提供**任何「标记已核销」的入口。
5. **到账流水导入是真的**：CSV（按 RFC 4180 处理引号）与 JSON 都能解析 → 真实入库 + 幂等
   （幂等键 = 来源系统 + 来源流水号）。文件级错误整体失败（一条不导入），行级错误只跳过那一行并逐条说明。

## 关键 trade-off

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 明细行 | **不做** | 一次到账 = 一笔资金事实；编明细是假数据。合并回款由 allocation 表表达。 |
| 资金账户 | **受管引用恒为 NULL + 自由文本标识** | 12.7.1.1 未交付 ⇒ 没有受管账户可引用（填 0 / 假 id 会被读成「进了某个已登记的账户」）。人能填的只是一段自由文本，页面明确写它**不是**受管资金账户。 |
| 结算单号 | **恒为 NULL（DB CHECK 钉死）** | 12.3.1.1 未交付 ⇒ 词表保留 `PLATFORM_SETTLEMENT` 但服务层拒绝建单并写明归属模块；上游交付后 DROP 那条 CHECK 即可接上，不改结构。 |
| 核销 | **只登记与跟踪，不实现** | 12.2.1.2 未交付。造一个「手工标记已核销」的端点会让界面以为核销可用 —— 明确不做。 |
| 导入的行级错误 | **跳过该行 + 逐条 warning** | 文件级错误整体失败（半个文件入库比完全失败危险）；行级错误吞掉的话「导入 0 条」会被读成「文件是空的」。 |
| 到账时间无偏移 | **拒收该行** | `Timestamp.valueOf(LocalDateTime)` 在东八区静默偏 −28800s ⇒ 到账时间错 8 小时就是错账。 |
| 页面路由 | **`/finance/receipts`**（子路由） | 与 12.1.1.1 的 `/finance` **并列**而非混在一起：两者各有各的单据号前缀与未核销口径。 |

## 撤回记录（调度者裁决，2026-10-23）

**撤回对象**：`apps/web/src/app/finance/page.tsx` —— 恢复成基线 `8a5b91be` 原样，
**一字未改**（`git diff 8a5b91be -- apps/web/src/app/finance/page.tsx` 为空）。

**撤回前的改动**：加了 `import Link` + 一段 javadoc + 把 `return <ReceivableWorkspace />`
包进 `<div>` 并挂一个指向 `/finance/receipts` 的链接。

**为什么撤回**（调度者裁决，不是口味问题）：

1. **本仓的惯例**是同服务多模块各走各的路由、**没有中心索引页**：
   `apps/web/src/app/warehouse/` 下 12+ 个模块页面（`receipts` / `pick-tasks` / `outbound` / `parcels` …）
   **全部只能靠 URL 直接访问**，`warehouse/page.tsx` 只是个 `DomainPlaceholder`，并不给它们做导航。
   ⇒ 「模块页面只靠 URL 可达」**就是本仓的既定形态**，不是缺陷。
2. **同批就有反例**：11.2.3.2 车道交付 `/aftersales/return-dispositions` 时，
   **没有**去改 `apps/web/src/app/aftersales/page.tsx`（那是 11.1 售后单模块的页面）。
   同一条批次里两种做法并存是不一致的。
3. **纪律**：`不要动别的模块的前端页面`。`/finance` 是 12.1.1.1 交付的页面，
   当时的改动动了它的渲染结构（包 `<div>`）与它的 javadoc，属于跨模块改动。
4. **最实际的理由：会造成并入冲突。** `apps/web/src/app/finance/page.tsx`
   **不在** merge-union 驱动器的覆盖范围内（`.gitattributes` 只给 `packages/api-contracts/src/**`
   与 `module-progress.md` 配了驱动），所以它走普通 git merge；而**同批 12.1.2.1（应付单管理）
   车道也在改同一个文件的同一段**（它的 javadoc 与 `return` 块，改法是「一个 `<nav>` 两个链接」）
   ⇒ 下一轮并入**必然冲突**，该车道会被标 `conflict`、整个模块交付被卡住一轮。

**撤回后的可发现性**：`/finance/receipts` 页面**全部保留**（路由页、workspace、model、
allowlist 测试一个都不动），它与 warehouse 下那 12 个页面一样，**走 URL 直接访问**。

**api-proxy 的插入锚点保持不动**：`receipts` 条目仍在 `services[]` 数组末尾（`receivables` 之后）。
三条 finance 条目的 `prefix` 都是 `finance/` 但首 token 互不相同（`receivables` / `receipts` /
`receivable-aging`），三个正则两两不相交 ⇒ `services[]` 的遍历顺序不影响正确性
（`resolve()` 只取 `{base: FINANCE_URL}`，同一前缀同一个后端），git 能干净求并。

**撤回后的验证**：
- `git diff 8a5b91be -- apps/web/src/app/finance/page.tsx` → 空（与基线逐字相同）
- `pnpm vitest run apps/web/src/app/api` → **211 文件 / 1202 例全绿**（全量 allowlist 回归）
- `pnpm typecheck` → 3 successful
- 新增测试 `pnpm vitest run <receipt-model.test.ts> <receipts-allowlist.test.ts>` → **19 例全绿**
