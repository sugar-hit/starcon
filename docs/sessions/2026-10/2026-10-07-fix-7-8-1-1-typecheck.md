# 7.8.1.1 分配策略配置 · 前端类型修复

## 决策摘要

车道 7.8.1.1「分配策略配置」的后端已并入 `integration/module-dev` 且 `./mvnw verify` 全绿，
但前端 `@starcon/web` 在 `allocation-policy-*` 三个文件上报 3 处类型错误，无法编译。
本会话在 worktree `/Users/tommy/Project/starcon/.worktrees/fix-7.8.1.1`
（分支 `fix/7-8-1-1-typecheck`，基线 `ae36a62`）只做类型修复，不动后端、不动契约。

三处错误的真实根因与处理：

1. **`allocation-policy-model.ts(284) TS2304: Cannot find name 'AllocationOutcome'`**
   根因不是「漏写 import」，而是**契约里根本没有这个类型**。codegen 把 Java 的
   `AllocationPolicyModels.AllocationOutcome` 枚举**内联**成了 `AllocationLine.outcome`
   上的字符串联合（`"OK" | "CAP_REACHED" | "DEMAND_EXHAUSTED" | "NO_SALES" | "DISABLED"`），
   枚举不单独生成 TS 类型；同批的 `AllocationScopeType` / `AllocationMethod` /
   `AllocationBufferMode` 同样 0 命中。原文末尾那句 `export type { AllocationOutcome };`
   是个**无绑定的悬空 re-export**（既没 import 也没本地定义），TS 报的就是它。
   处理：改为从契约反推 `export type AllocationOutcome = AllocationLine['outcome'];`。
   不手写字符串联合——手写会和后端漂移，枚举加值时前端不会报错；从契约取则自动跟随。

2. **`allocation-policy-workspace.tsx(111) TS2532`**
   `skuList[0].id` 开了 `noUncheckedIndexedAccess` 后索引访问可能为 undefined。
   改为 `skuList[0]?.id ?? ''`，**没有用 `!` 断言**。

3. **`allocation-policy-workspace.tsx(778) TS2379: exactOptionalPropertyTypes`**
   `referenceLabel: shopLabel.trim() || undefined` 显式传 `undefined`，
   而目标形参是 `referenceLabel?: string`（开了 `exactOptionalPropertyTypes` 后不接受）。
   改为条件展开 `...(shopLabel.trim() ? { referenceLabel: shopLabel.trim() } : {})`，
   与 `apps/web/src/lib/api.ts:47` 的既有写法一致。语义不变：空串时该字段**不出现**而非传 undefined。

## 关键 trade-off

- **不补 Java、不重新生成契约。** 契约缺的不是「DTO 没写」，而是 codegen 对枚举的展开方式。
  补 Java DTO 会引入一个后端并不需要的类型，反而制造第二个真相源。前端按契约反推是正确方向。
- **`AllocationOutcome` 反推而非手写联合。** 代价是它只等于「当前这份契约的 outcome 取值」，
  收益是后端枚举变更后重新生成契约即自动跟随，不会静默失配。
- **不碰 `apps/web/src/lib/api-proxy.ts`。** 白名单由调度器并集处理，改它会和后续并入冲突。

   `expect(notNull(null)).toBeNull()` 断言失败：`notNull` 是**类型谓词**（`v is T`，返回 boolean），
   运行时对 `null` 返回 `false` 而非 `null`。测试按「归一化函数」写的，实现是「类型守卫」，
   两者语义不同。这是本车道自己的账，建议由 7.8.1.1 车道 owner 定夺：
   要么把断言改成 `expect(notNull(null)).toBe(false)`，要么给归一化需求另起一个函数名。
   本次**未擅自改**，因为它超出「修 3 处类型错误」的范围，且改断言会掩盖真实的语义分歧。
