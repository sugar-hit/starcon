# 8.3.2.2 波次与合并拣货 · 交付记录

## 决策摘要

- **命名空间 `/warehouse/pick-waves`（顶层）**，与 8.3.2.1 的 `pick-tasks` 同一理由：
  一个波次横跨多张出库单，它不属于任何一张出库单，也不属于任何一张拣货任务。
  挂成 `outbound-orders/{id}/waves` 会让契约以为波次从属于某一张单 ——
  而八张单聚成一波时任取一张都代表不了这一波。
- **权限码复用 `warehouse.inventory.read` / `.update`**，不新起 `warehouse.picking.*`。
  identity 只注册了 warehouse 的两个页面资源，用没注册的码会让连 OWNER 都 403。
- **库区是推导出来的，不是配置的**：仓库里没有 `zone` 列，库区 = 取货库位沿
  `warehouse_location.parent_id` 上行到**顶层根节点**（V105 的注释把顶层节点称作「区」）。
  时段按**仓本地**小时窗口 `[start, end)` 判，时区取 `warehouse.timezone`。
- **迁移 V113 建四张表、零 ALTER**：`pick_wave_rule` / `pick_wave` / `pick_wave_task` /
  `pick_wave_event`。V110 的六张表一个字都没改。

## 关键 trade-off

### 1. 波次进度**不做冗余列**（与 V110 刻意不同）

V110 把 `pick_task` 的合计做成列，由 refresh 触发器从**本模块自有**的明细表重算 ——
安全，因为明细与单头同属一个写入所有者。

波次的明细是 `pick_wave_task`，而它的进度住在 **`pick_task`（V110 的表，8.3.2.1 的唯一
写入所有者）**。在本表挂「工单变了就刷波次」的触发器，等于去 ALTER 别人的表，
也会让 8.3.2.1 以后改自己的表时踩到一条它不认识的外部依赖。

所以这里**一个冗余进度列都不建**：`orderCount` / `taskCount` / `plannedLineCount` /
`plannedQuantity` / `pickedLineCount` / `pickedQuantity` 全部在查询时由
`pick_wave_task ⋈ pick_task` 一次聚合算出。「永远算得对」比「算得快而且大部分时候对」值钱。

DB 级仍然要挡的那一条用 BEFORE 守卫直接**回表读当前行**：
`guard_pick_wave_status_fn` 要求**全部成员工单已终态**才允许 `COMPLETED`。
这是「合并不改订单粒度」在 DB 层的落点 —— 绕开服务层直连 SQL 也过不去。

### 2. 「同键只能有一个未完波次」是合并二字的全部含义

`pick_wave_open_key` 部分唯一索引（同租户同仓同库区同承运渠道）+ `pick_wave_task_active`
（一张工单只能在一个未完波次里）。理由不是洁癖：两个拣货员同时在 A 区按同一承运商口径
拣货必然互相踩，而这件事在任何 CHECK 里都看不出来。

**代价**：订单数上限撞顶后，剩下的出库单要等这个波次收工才能开下一波。所以
`candidates` 接口必须报「还有 N 张在等上一波收工」，否则看板上只剩一个解释不通的空白。

### 3. 跨区任务没有单一库区

一条拣货任务的拣货段横跨多个区时，`zone_id` 为 null、`crossZone=true`，
**只能进「库区不限」的规则** —— 绝不硬塞进某一个区，那会让「按库区合并」这个口径失真。

### 4. 候选查询刻意不用 `WITH RECURSIVE`

库位树只有六层（V105 的 `guard_warehouse_location_tree` 限死），所以用了六次自连接 +
`coalesce` 从最深往上取根。这个上界是**由数据库守卫保证的**，不是猜测。

### 5. 踩到并修掉的三个真 bug（都留了注释当纪念）

- **`c.*` 在 jOOQ 的 PlainSQL 里没有列名**：读的时候报
  `Field "zone_code" is not contained in row type`。改成逐列列举。
- **注释里的 `?` 会被 jOOQ 当成占位符计数**：SQL 文本块里的 `--` 注释写了
  「`?` 占位符会数错」，结果那个 `?` 本身被算成了第 8 个标记。**SQL 注释里不能出现 `?`**。
- **守卫的跃迁判据写成了「回表读当前行 status 再和 OLD.status 比」**，而回表读到的就是
  OLD 本身 —— 那个判断恒为假，`PLANNED → COMPLETED` 这种非法跃迁会被放行，
  直到下面「全部成员工单终态」那一条才拦下来，报出来的原因还完全不是用户做的那一步。
  跃迁判据必须用 `OLD.status` / `NEW.status` 这一对行内值。

## 后续待办

- **8.3.3.1 复核扫描**：波次完成只把「这一组拣货任务都拣完了」这件事交出去，
  出库单各自进「待复核」。复核与打包仍按订单逐张做，本模块不替它判通过与否。
- **`StockOwnershipIntegrationTest` 疑似既有时序 flake**：`货权档优先级是sku大于法人大于仓库大于兜底`
  会偶发失败（`order by scope 优先级, effective_from desc` 本身是确定的，
  但规则插入用 DB 侧 `now()`、resolve 用 JVM 侧 `now()`，时钟回拨会让最新那条规则
  落在「未来」而被 `effective_from <= moment` 滤掉）。单独跑 40 例全绿；
  排除本车道测试类时全模块 1281 例全绿；带上本车道测试类出现过一次。
  **不是本模块引入的数据冲突**，但建议后续把它钉成不依赖跨时钟的写法。
- 波次**不写** `outbound_order_event`（那张表的唯一写入所有者是 8.3.1.1，
  且它的 `event_type` CHECK 没有本模块的取值）。
