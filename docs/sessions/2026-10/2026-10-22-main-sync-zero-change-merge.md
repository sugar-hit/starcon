# 2026-10-22: 集成分支并入 main —— 零变更合并的判据修正

## 摘要

本轮把 `integration/module-dev` 并入 `main`，逐项取证后确认：**合入后 `main` 一个字节都不会变**，
因此**本轮没有开同步 PR**。真正产出的不是一次合并，而是**修正了「有没有新内容」的判据** ——
原协议用「树差异是否为空」决定开不开 PR，本轮实测证明这个判据会给出假阳性。

取证过程：树差异报 31 个文件、12 万行增删，看起来像一次大增量；
但逐文件核对后发现，**这 31 个文件全部是 `main` 侧独有的**（会话记录、看板工具等），
集成分支侧并没有任何 `main` 缺的内容。落地树哈希与 `main` 的树哈希**完全相同**，
真合并后 `git diff upstream/main HEAD` 为空。

## 决策 / 结论

1. **「有没有新内容」的最终判据是落地树哈希，不是树差异。**
   树差异是双向的，既含「集成分支有、`main` 没有」，也含「`main` 有、集成分支没有」。
   后一部分不该被合入动作改变 —— 真合并时 git 会自动保留 `main` 侧。
   ⇒ 树差异只用来提示「值得看一眼」；**落地树哈希 == `main` 树哈希 ⇒ 零变更，不开 PR**。

2. **零变更的判定必须做两次**：`merge-tree --write-tree` 的预演结果，
   以及真合并后 worktree 里的 `git write-tree`。两者都等于 `git rev-parse upstream/main^{tree}` 才算数。

3. **本轮不开同步 PR。** 落地树与 `main` 相同 ⇒ 同步 PR 会是空 PR，
   只会给 `main` 添一条无内容提交。本轮改为提交协议修正与会话记录。

4. **契约文件的字节差异不是「集成分支有新内容」。**
   本轮 8 个契约文件的 blob 在两侧不同，但逐键核对后：导出的类型名集合完全相同、
   `paths` 集合完全相同、递归到叶子键后只有 `minSimilarity` 的 `maximum`/`minimum`
   存在 `int` 与 `float` 的类型差异（值相等）。**集合差集双向为空** ⇒ 语义等价。
   合并驱动在 base 侧取值后恰好产出与 `main` 侧相同的字节，属预期行为，不是丢内容。

5. **`api-proxy.ts` 本轮两侧 blob 完全相同**（`7f844ce6`）——
   上一轮记录的「5 文件冲突面」在本轮已随 `main` 前进而消失。
   `api-proxy.ts` 未出现在两侧差异清单里（清单里的 4 条是**会话文档文件名**含该词，不是源码本体）。

## 关键 trade-off / 讨论

- **为什么不按原判据开一个「同步进度」PR？** 因为它会是空 PR。
  上一轮的历史里，零内容轮次也开过 `chore: 同步集成分支最新进度` 这类 PR 并带上会话文档 ——
  那种 PR 至少还带一份新文档；本轮若照做，等于给 `main` 添一条什么也没带的提交。
  本轮选择把产出放在**协议修正**上，那是对下一轮真正有价值的。

- **为什么用「落地树哈希」而不是「祖先快照可达性」？**
  本轮两侧的契约 blob 互相都不可达（是并行演进出的不同字节序，不是祖先快照），
  祖先快照判据在这里给不出答案。而**语义等价**（集合差集双向为空）能给出答案。
  ⇒ 契约文件判「取一边会不会丢内容」时，唯一可靠的裁判是语义等价。

- **合并驱动的参与与否用对照实验证明**：把 `merge.contract-union.driver` 指向坏路径后，
  `merge-tree` 退出码变为 1 并列出 40 条契约冲突 ⇒ 证明驱动确实参与了计算。
  但**两组的落地树 OID 完全相同** ⇒ 单看 OID 区分不出「真干净」与「驱动没跑」，
  这也是「最终以落地树哈希为准」这条判据必须独立验证的原因。
