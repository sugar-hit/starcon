前几任形成了「早提交、多提交」的纪律，本轮沿用。

**第三任的半截改动是什么**：它把三处错误消息断言从「读 HTTP 响应体」改成
「在服务层 `assertThrows(ResponseStatusException.class, …)` 后断言 `e.getReason()`」。
这个方向**是对的**（本仓约定如此，见下面第 5 条），但它改到一半被打断，
留下一个**编译不过**的文件：`tenants.run(tenant, () -> service.deleteMapping(id))`
把 `void` 方法塞给了 `Supplier<T>`（类型推断上下界冲突）。
本轮先把它改通，再顺着它的思路把剩下两处补齐。

## 决策摘要

交付**从其它 ERP 迁移历史数据**的完整通道（platform 服务，端口 8089）：
映射配置（外部字段 → 内部模型）→ **试运行预览** → 正式迁移 → **失败回滚** → 核对报告。

蓝图原文（卷 18 → 18.1.3 → 18.1.3.2）：
「职责：支持从其他 ERP 迁移历史数据：映射配置（外部字段 → 内部模型）、试运行预览、正式迁移、
失败回滚与核对报告。输入：源数据文件；字段映射配置。输出：迁移任务 + 迁移核对报告
（成功/失败/跳过数量与原因）。关系：上游 = 18.1.3.1；下游 = 各业务域。
**历史数据迁移必须支持试运行**，直接正式跑会产生大量脏数据难以回退。」

**最关键的一条设计决定**是「下游 = 各业务域」怎么落地 —— 答案见下面第 1 条 trade-off。

## 关键 trade-off

### 1. 🔴 只迁**有真实 create/delete 对**的域（catalog 商品 SPU / SKU）

「下游 = 各业务域」听起来是七个域，实际上**只有 catalog 商品域**能接：
判据不是「有没有文件型导入作业」，而是**有没有 create/delete 对** ——
只有这样「失败回滚」才可能是**真的**。

catalog 侧真实存在的写入 / 删除对（已逐个 grep 确认）：

```
POST   /catalog/products                              → 建 SPU
DELETE /catalog/products/{id}?version=                 → 删 SPU（要求 DRAFT 且名下无 SKU）
POST   /catalog/products/{id}/skus                    → 建 SKU（version 是**父 SPU 的**版本号）
DELETE /catalog/products/{id}/skus/{sid}?version=      → 删 SKU（version 也是**父 SPU 的**版本号）
```

⇒ 回滚是**真去目标库删**（按逐行记下的 `upstream_id`），不是把状态改成「已回滚」。

**订单 / 库存 / 凭证**三格**如实标 `available=false`** 并写明缺什么、归谁：
订单要走占库存 / 信用校验 / 平台回传，库存是由单据推导出来的余量，
凭证是会计事实（导一份凭证等于凭空记账，试算平衡表会与银行流水对不上）。
强行迁移会绕过属主服务的校验链，把账实关系写坏。

### 2. 🔴 「试运行」不是「加个开关」

蓝图那句加粗句在三个地方落地：

- **服务层**：`Mode.DRY_RUN` 走**只读**分支 —— 解析源文件、逐行校验、查目标库判重，
  **一个写端点都不调**；
- **数据层**：触发器 `guard_platform_migration_row_success` 兜底 ——
  试运行的行**不许带 `upstream_id`**（带了 ⇒ 目标库里真的多了一条记录 ⇒ 试运行不是试运行），
  正式迁移里「迁成」的行**必须**有 `upstream_id`（没有 ⇒ 回滚不回去，那条「成功」是骗人的）；
- **页面层**：发起面板把「试运行」与「正式迁移」摆成**两个并列选项，默认落在试运行** ——
  默认值会让「直接正式跑」变成一次误点。

### 3. 🔴 回滚与迁移是**两条独立的状态机**

一次迁移「成功」之后仍可以被回滚，那时 `status` 仍是 `SUCCEEDED`、
`rollback_status` 变成 `SUCCEEDED`。把两者揉进一个字段就会丢掉
「迁移本身成功过」这个事实 ⇒ 两列分开，回滚的前提（已跑完 / 未回滚过 / 非试运行）
由**数据库触发器**钉死，应用层绕不过去。

逐行结论也分两列（`rollback_status` / `rollback_message`）：
「迁成了什么」与「删掉了什么」不揉在一起。

### 4. 🔴 每一行一个独立事务

一行迁成之后它的「上游记录 id」**立刻落库** —— 中途挂掉时，已经迁进去的记录
**回滚得掉**。整批塞进一笔事务的话，崩掉会把「迁了哪些」一起抹掉，
而目标库里的记录还在，我们却已经不知道它们是谁了 ——
那正是蓝图说的「直接正式跑会产生大量脏数据难以回退」。

### 5. 错误消息**在服务层断言**（本仓约定）

MockMvc 里 `ResponseStatusException` 的响应体是**空的**（状态码对，body 没有），
断言响应体等于断言一个空串。第三任的判断是对的，本轮**保留并补齐**：
三处 400 / 409 都在服务层 `assertThrows` 后断言 `e.getReason()`。

### 6. 🔴 契约类型必须**带模块前缀**

`DataMigrationTargets.Field` ⇒ `DataMigrationTargets.DataMigrationTargetField`。
springdoc 用 record 的**简单名**当 schema 名，而这份契约是从 `packages/api-contracts`
的**桶文件**导出的（全局可见）—— 叫 `Field` 的话，桶文件里就多一个谁都能 import 的
`Field`，一个没有模块前缀的通用名，与别的模块的同名类型迟早撞车。
（本次实测九个服务里只有 platform 有 `Field`，所以 codegen 的**跨服务重名闸没拦住它** ——
它拦的是跨服务重名，不是「名字太通用」。）

### 7. api-proxy.ts 只做**纯增量**

`apps/web/src/lib/api-proxy.ts` 是多条车道共用的**累积型**白名单。
新条目是**独立的一条 `services[]` 元素**，插在**数组最开头**（本文件第一个元素之前），
与同批另一条车道（18.2.3.1，插在数组末尾）相距 10000 行以上 ⇒ 并入时 git 能干净求并。
首 token `data-migration` 对既有 **9 条** `prefix: 'platform/'` 正则
（webhooks / deliveries / io / text / apps / finance-software / api-catalog /
call-monitor / payment-funds）实测**零命中** ⇒ 不需要改动那九条里的任何一个字符。

⚠️ `io`（18.1.3.1 导入导出任务）与本模块**不是一件事**：
那边管「把本系统的数据导出去 / 把文件导进来」，
这边管「把**别的 ERP 的历史数据**迁进本系统的业务库」—— 方向、状态机、回滚语义都不同。

## 本轮修掉的三个真 bug（不是把断言改松）

1. **回滚报告印的是原始码，不是人话**。`rollbackLabel()` 用的是**任务级**枚举
   `RollbackStatus`（未回滚 / 回滚中 / 已回滚 / 回滚失败），而逐行结论里存的是**行级**枚举
   `RowRollbackStatus`（未回滚 / **已删除** / 未删除）⇒ 报告的「回滚结论」列印出 `DELETED`
   而不是「已删除」。审计的人分不清「已删除」和「未删除」的区别 ——
   而那正是这份报告的全部意义。⇒ 新增 `rowRollbackLabel()`，逐行两处改用它。
2. **回滚报告的 CSV 列宽不一致**。摘要行固定补齐成 10 列，而回滚报告的表头与明细是 6 列
   ⇒ 摘要块与明细块错位，在 Excel 里像两张表拼在一起。⇒ `summary()` 增加宽度参数。
3. **建映射时只点名第一个缺掉的必填字段** ⇒ 运营要来回提交四五次才知道还缺什么。
   ⇒ 一次把所有缺掉的必填字段都列出来。

另修两个**测试侧的真问题**（不是把断言改松）：

4. **轮询回滚状态的循环每轮读两次状态** —— 两次之间状态可能从「未回滚」翻到「回滚中」，
   于是「不是回滚中」与「不是未回滚」同时成立 ⇒ 循环**提前退出**，而回滚其实还在跑，
   报告文件也就还没写出来（后面那个断言拿到 404）。⇒ 抽出 `waitForRollbackTerminal()`，
   每轮只读一次。
5. **reset() 与后台执行器抢锁形成死锁** —— 迁移与回滚都是异步的，上一条用例的执行器还在跑时
   就 TRUNCATE，会与执行器持有的读锁形成死锁（TRUNCATE 要 ACCESS EXCLUSIVE，
   执行器要 ACCESS SHARE），表现为「随机一条用例报 deadlock detected」。
   而「同一租户已有迁移在跑时发起新的迁移返回 409」那条用例**故意**留了一个永远跑不完的
   PENDING 任务，于是每条用例的 reset() 都要等满超时。
   ⇒ 新增 `awaitQuiescent()`（清库前等后台执行器停下）+ `settle()`（每条用例结束时把故意
   留在非终态的任务收成终态）。**整条用例链从 86 秒降到 6.1 秒。**

## 关键 trade-off / 讨论（其余）

- **「查不清」不等于「不存在」**：目标库查询被截断时**跳过**这一行并写明原因，
  绝不把「可能已存在」的记录再迁一遍（那会造出重复主数据）。
  catalog 的 `GET /catalog/products?q=` 是模糊匹配且上限 200 条 ⇒ 命中上限就判「查不清」。
- **源文件缺必填列 ⇒ 整个任务失败**（不是「每一行都失败」）：根因在**文件结构**，
  逐行报错会让人去查数据，其实该查表头。
- **映射是冻结的契约**：迁移任务把**创建那一刻的映射快照**冻进 `mapping_snapshot` ——
  审计要回答的是「**当时**按什么映射迁的」，事后再读「用户当下的映射」是答非所问。
- **落库的 SPU / SKU 一律是草稿**：catalog 的新建规则要求先存草稿、补齐 SKU 再提交待上架。
  外部系统里的「在售」直接写进去会被 catalog 拒 —— 迁移不绕过这条规则。
- **属性值不在本模块范围内**：属性是 SPU 级的定义（catalog 的属性字典），
  迁移属性值要先重建属性字典再逐 SKU 覆写 —— 那是另一件事，本模块**不假装做了**。
- **目标模型与字段清单只有一份代码**（`DataMigrationTargets`）：映射校验、迁移执行、
  页面上的「目标模型」下拉**共用**它。两处各写一份字段名 ⇒ 迟早对不上，
  而对不上的后果是「页面说能迁，跑起来报未知字段」。
- **异步执行是进程内执行器，任务表里不存凭据**：迁移要经目标服务的授权端点写数据，
  而目标库按已认证成员关系解析租户 ⇒ 需要调用方的会话。
  存 bearer = 把 secret 落库 ⇒ 只让它在内存里活到这次执行结束。
  进程重启后卡住的任务被如实标「执行中断」而**不自动重试**（没有凭据就写不进目标库）。
- **超限就报错，不偷偷截断**：单次上限 10 MB / 20000 行，超过就让任务失败并说明怎么拆 ——
  偷偷只迁一部分会让迁进来的数据**看起来是完整的，而它不是**。

## 后续待办

- **属性值迁移**（catalog 3.1.3 的属性字典）：本模块的 SKU 迁移只覆盖编码 / 名称 / 条码 /
  单位 / 所属商品五个字段。要迁属性值，需要先重建属性字典再逐 SKU 覆写 ——
  归属写在 `capabilities()` 的 `gaps` 里。
- **订单 / 库存 / 凭证的历史补录**：需要**属主服务**各自提供面向迁移的写入端点
  （且必须配套删除端点，否则回滚是假的）。本模块的端口层照抄 catalog 那一支即可。
- **映射配置的可视化编辑**：当前前端的新建映射按目标模型的字段清单**逐字生成**外部列名
  （用字段的中文名当列名），真实使用时要改源文件表头或改这份映射的列名 ——
  「外部列名 ↔ 源文件表头」的可视化映射界面尚未做。
- **回滚粒度**：当前回滚是**整任务**回滚（删掉这次迁移建出来的全部记录）。
  「只回滚其中几行」需要逐行的目标库删除与并发保护，尚未实现。
