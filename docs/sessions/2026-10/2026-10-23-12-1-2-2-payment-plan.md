# 2026-10-23: 12.1.2.2 付款计划

## 摘要

交付蓝图 **12.1.2.2 付款计划**（卷 12 财务核算，L3 锚点 12.1.2 应付）。迁移 `V343__finance_payment_plan.sql`
在 finance 服务里新建**七张表**（零 ALTER 零 DROP 既有表，不碰 V338 应收族 / V340 应付族 / V341 收款族），
后端 18 个端点挂在 `/finance/payment-plans`（jOOQ 显式 SQL），前端真实工作区在 `/finance/payment-plans`。
蓝图那句加粗句「**付款计划与资金预测联动**」的落法是：资金需求预测**不是一张静态表**，而是每次查询时按
(币种 × 到期窗口) 对付款计划（流出）与 12.1.1.1 应收单的未核销余额（流入）**实时聚合**出来的 ⇒ 计划一改，
预测当场跟着变。

## 决策 / 结论

### 1. 三种付款条件是三种算法，不是一个 type 字段上的三行取值

蓝图写「按付款条件（**账期、里程碑、到期日**）生成付款计划」。照抄上游到期日就能糊过去，但那不是这一格的意思：

| 条件 | 条件日（`condition_date`）怎么来 | 一张应付 → 几条计划 |
| --- | --- | --- |
| `DUE_DATE` 到期日 | 直接取 12.1.2.1 的 `finance_payable.due_date` | 1 条 |
| `TERM` 账期 | 起算基准日（确认日 / 到期日）+ **租户自己配的账期规则**的天数 | 1 条 |
| `MILESTONE` 里程碑 | 每个里程碑自己的触发日（相对确认日的偏移或绝对日） | **N 条**（按比例拆金额） |

- **账期规则（`finance_payment_term_rule`）刻意不预置任何一行**：预置一条「30 天账期」等于替用户把资金政策定了。
  没有可用规则 ⇒ 排不出计划，服务层把原因说清楚（不是含糊的「参数错误」）。
- 规则选谁：**最具体优先**（指定供应商 + 指定币种 > 指定供应商 > 指定币种 > 全局），确定性排序。
- **里程碑比例之和必须为 1**，且这条**跨行**约束**只由服务层对着整份配置校验**，不做 DB 触发器 ——
  一套里程碑是**整体替换**写入的（先删旧、再插新），逐行 AFTER 触发器会把「只插了第一期、比例和 = 0.3」
  这个中间态打掉，那样就只可能「一套一套慢慢加」，永远加不到 100%。
  （与 12.1.1.2 的账龄区间「连续覆盖」同一手法：DB 兜单行，服务层兜跨行。）

### 2. 「批量安排付款」的边界（12.2.2.1 未交付）

本模块交付的是**计划与安排**（把应付排进某个付款窗口 / 批次），**不是**执行付款。边界写在**数据层**而不是注释里：

- `finance_payment_plan.execution_available` 与 `finance_payment_batch.execution_available` 都是
  `CHECK(... = false)`：**表级 CHECK 只允许这一个取值** ⇒ 表里根本写不出「已付款」。
- `execution_owner_module` 恒为 `'12.2.2.1'`：归属写在数据上（参照 trade 的 `PENDING_FINANCE` 写法）。
- 表里**没有** `paid_at` / `executed_at` / `payment_no` 这类列 —— 集成测试直接断言列不存在。
- 一批 = **一个币种**：跨币种的批次会让「这批要付多少钱」变成一个没有意义的数字。

### 3. 「到期提醒」的边界（1.3 未交付）

- 提醒**记录**归本模块：真实的提醒条目、**真实的到期判定**（UPCOMING / DUE / OVERDUE，按计划付款日与基准日比较
  算出来）、**真实的处理状态**（PENDING / ACKNOWLEDGED / DISMISSED，`acknowledged_at` + `acknowledged_by`
  记下谁在什么时候确认的）。
- 但**不推送**：`push_status` 恒为 `'NOT_PUSHED'`、`push_owner_module` 恒为 `'1.3'`（表级 CHECK）。
  **没有** `sent_at`、**没有**「已发送」这个取值、**没有**假的通知计数 ——
  集成测试直接断言 `information_schema.columns` 里**没有** `sent_at` / `pushed_at` / `notified_at` / `delivered_at`。
- 扫描语义（三条都写了断言）：
  - 计划变了（日期 / 金额 / 类型）⇒ 提醒改回「待处理」；
  - **已经人工确认过的不会被重置**；
  - **人手动忽略过的不会被扫回来**（用「系统收起」与「人忽略」两种 `dismiss_reason` 区分）；
  - 计划取消 ⇒ 提醒**当场失效**（DB 触发器 `guard_finance_payment_reminder_on_cancel` 做这件事）。

### 4. 「计划日」与「条件日」是两个列

`condition_date`（按条件算出来的日子）与 `planned_paid_date`（排进资金计划的那一天）**故意分开**：
条件日落在付款窗口之外时，计划日被压到窗口边界，界面据此显示「条件日 X → 计划日 Y」。
`clamped` 是**生成列**（`condition_date <> planned_paid_date`）⇒ 「这两件事不一样」不可能被改错。
两个日期都保留 ⇒ 「为什么这笔钱提前 / 延后付」答得出来。

### 5. 同一张在册应付不会被排两次

两个**部分唯一索引**在数据层挡着（非里程碑：每张应付最多一条在册计划；里程碑：每个里程碑最多一条）。
取消（`CANCELLED`）的计划不在索引里 ⇒ 取消后可以重新排。
**换条件必须先取消旧计划**：计划的付款条件与依据在建出来之后就冻结（DB 触发器），
换条件 = 取消旧的 + 生成新的 ⇒ 不会有「改了一半的条件」。

### 6. 资金需求预测：实时聚合，不是静态表

- 流出 = `finance_payment_plan`（PLANNED / SCHEDULED）的计划付款日与计划金额。
- 流入 = 12.1.1.1 `finance_receivable` 的未核销余额（`amount - settled_amount`）与到期日 —— **只读**，
  不写、不改结构、不加触发器（同一服务内的引用，jOOQ 显式 SQL）。
- 净额 = 流入 − 流出，负数即「这个窗口净流出」⇒ 现金流断裂风险。
- **绝不跨币种相加**：流入与流出都按币种分开比。

## 关键 trade-off

| 选择 | 备选 | 为什么选这个 |
| --- | --- | --- |
| 条件日与计划日**两个列** + 生成列 `clamped` | 只留一个日期 | 压进付款窗口是真实的资金决策；只留一个日期就答不出「为什么改了」。生成列保证两者不漂移 |
| 里程碑比例和的校验放**服务层** | DB 触发器逐行校验 | 整套替换的中间态会被触发器打掉，等于「永远加不到 100%」 |
| 预测**实时聚合** | 建一张预测快照表 | 蓝图加粗句要求「联动」；快照表需要同步动作，计划改了预测不会当场变 |
| 提醒一条计划一条（`UNIQUE(tenant_id, plan_id)`） | 每次推送一条历史 | 推送通道未交付，没有「推送历史」这个事实；提醒是**当前状态**。系统收起用 `dismiss_reason` 区分人忽略 |
| `execution_available` 写死 `CHECK(... = false)` | 普通列 + 应用层不写 | 「已付款」这个状态在**数据层**就不存在，比「应用层不写」强 |
| 一批 = 一个币种 | 一批跨币种 | 跨币种的批次金额没有意义（USD + EUR 不是任何一个金额） |

## 踩过的坑（留给下一条车道）

1. **DELETE 触发器里 `NEW` 是 NULL 记录，读它的字段会直接报错**（`record "new" is null`）。
   `guard_finance_payment_batch_amount` 必须按 `TG_OP` 分支取 id，**不能**写
   `COALESCE(NEW.batch_id, OLD.batch_id)`。
   （V340 的 `guard_finance_payable_amount` 有同样的写法，但它的 DELETE 路径没人走过。）
2. **「按供应商筛选」会让汇总查询炸成 SQL 错误**：筛选条件里有 `pa.*` 的列 ⇒ 计数查询与汇总查询
   都必须带上同样的 `JOIN finance_payable`。集成测试专门加了一条「按供应商筛选时汇总也跟着筛」来钉它。
3. **`options()` 里的供应商列在应付表上，不在计划表上** —— `finance_payment_plan` 没有 `counterparty_ref`。
4. **批次金额由 DB 触发器派生 ⇒ 必须在计划全部落库之后再读批次**，否则读到的是「刚建出来、还没挂计划」的空批次。
5. **提醒表的行没有 `plan_no` / `payable_no` / `counterparty_name`** —— 映射必须走带 JOIN 的取法，
   直接 `select *` 出来的行没有这些列（jOOQ 会抛 `Field "plan_no" is not contained in row type`）。
6. **`prettier --write` 会把别的车道那几行 `pattern:` + 正则并成一行** —— 本仓的 `api-proxy.ts`
   在 HEAD 就不是 prettier-clean 的。**共享白名单里既有条目一个字不许改** ⇒ 改完要把那几行还原。
