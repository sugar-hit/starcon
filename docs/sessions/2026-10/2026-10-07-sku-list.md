# 3.1.2.1 SKU 列表（D1–D2）

## 做了什么

交付能力蓝图 3.1.2.1「SKU 列表」：全租户 SKU 明细 + 多维筛选 + 批量操作 + 导出。
L3 = 3.1 商品主数据，锚点路由 `/products/sku`。

开工前 `sku` 表已存在（V1）并已纳入 V1 末尾的强制 RLS 循环，所以本轮只写 `V5` 增量迁移：
**没有**新加 catalog 自有的规格/名称列——`variant_signature` 与条码都已存在。

蓝图职责逐条对应：

| 蓝图要求                          | 落地                                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| SKU 编码 / 商品名 / 条码 / 状态   | `sku` 既有列，列表直读                                                                                     |
| 规格                              | 从 `attribute_definition.variant_axis` + `attribute_value` + `attribute_value_item` 解析，不落冗余字符串列 |
| 库存（在仓/在途/可售）            | 属 07（阶段 D3）→ `SkuProjectionPort`，未接入                                                              |
| 成本 / 采购价                     | 属 06 采购 → 同上                                                                                          |
| 售价                              | 属 05（阶段 D5）→ 同上                                                                                     |
| 在售平台                          | 属 04 刊登 → 同上                                                                                          |
| 多维筛选                          | SPU、分类、状态、关键字、条码、规格关键字、排序白名单                                                      |
| 库存/价格区间、是否缺货、是否在售 | 依赖未接入投影 → 显式 422，不静默退化                                                                      |
| 批量停售 / 批量改状态             | `POST /catalog/skus/batch`，支持预览（dryRun）与执行                                                       |
| 批量分配 / 批量生成刊登           | 依赖 04 刊登 → 显式 422，说明归属服务                                                                      |
| 导出                              | `GET /catalog/skus/export`，分批读取 + 流式写出                                                            |
| 批量操作任务                      | `sku_batch_operation` + `sku_batch_operation_item` 落库留痕                                                |

## 关键 trade-off

### 1. 库存/售价/成本一个都不落库

蓝图把 SKU 列表定为「仓储、采购、财务共用的事实入口」，并明写「库存数以 07 为准，售价以 05 为准」。
**结论：这四个数字在 catalog 一列都不建。** 一旦落库，catalog 就成了第二个事实来源，
和蓝图直接冲突，而且没有任何机制能保证两边不漂移。

沿用 3.1.1.3 建立的 `LifecycleProjectionPort` 范式：`SkuProjectionPort` + `UnwiredSkuProjectionPort`
（`supportedFields()` 返回空、一律 `available=false`）+ `SkuField` 枚举带 `ownerNote()` 说明归哪个服务、
哪个阶段。07/05/06/04 落地后替换那个 Bean 即可，列表与筛选逻辑不用改。

**列表列与筛选条件的处置不同，这点是刻意的：**

- **列**照常返回，但 `available=false` 时 `value`/`text` 传 `null`——**不传 0**。
  前端 `projectionText()` 渲染成「未接入」。缺失数据不是 0，画成 0 会让运营以为真的断货了。
- **筛选条件**直接 422。静默忽略更危险：用户以为在按缺货筛选，看到的却是没筛过的全量数据，
  而且「查不到」和「没在筛」看起来一模一样。

`GET /catalog/skus/capabilities` 把可用性做成运行时事实返回，前端据此禁用控件——接入与否是后端事实，
编进前端就会漂移。

### 2. 真分页，不是内存切片

`LIMIT/OFFSET` 下推到 PostgreSQL。排序键末尾**恒定追加 `id` 决胜列**：
`updated_at` 有大量相同值，不加决胜列翻页会在边界上错位或漏行。排序字段走白名单，
输入只能挑列、改不了 SQL 结构。

### 3. 导出分批 + 流式，每批一个租户事务

租户上下文是事务级 GUC（`app.current_tenant`）。`StreamingResponseBody` 在 servlet 异步线程上跑，
拿不到 controller 那个事务的连接——所以**按批重新 `access.run(...)` 绑定租户**，而不是共用一个长事务
（共用会丢掉绑定，等于没有 RLS）。每批 1000 行，读进 JVM 立刻写出，峰值内存与结果集大小无关。
上限 50 000 行，超限报错让操作人收窄条件，不悄悄截断。

### 4. 批量明细只为可见的 SKU 落库

`sku_batch_operation_item` 的 `data_scope` 策略要求对应 SKU 对当前租户可见。
用别人的 SKU ID 发起批量时，那条明细**连写入都不允许**——写一条指向看不见的 SKU 的行，
等于把别人的 ID 存进自己的表。越权的那些只在响应里回一条 `SKIPPED`，
`requested_count` 与 `matched_count` 的差额已经如实记录了这件事。

执行时逐条 CAS（`update ... where id=? and status=?`），并发的另一批操作改掉状态就不覆盖；
失败条目退回 `SKIPPED`，`applied_count` 以最终落库为准。

### 5. 顺带修了代理层的 CSV 透传

`apps/web/src/lib/api-proxy.ts` 原来对**所有**上游响应做 `JSON.parse` 再重新序列化。
CSV 导出走这条路会解析失败变成 503，即使解析成功下载到的也是一串引号转义的文本。
现在 `text/csv` 原样透传（连 `Content-Disposition` 一起）。

判断条件收窄到 `contentType.includes('text/csv')`：先试过更宽的 `!includes('application/json')`，
结果测试里 `new Response('{}')` 这种没有 content-type 的桩响应也被判成非 JSON，
把登录 token 的剥离逻辑绕过去了——条件必须只认 CSV。

**这个 bug 此前也让 17.5.3.1 的审计导出不可用**，本轮一并修好。

## 过程中踩到的三个非显然问题

**`sql.fetch(sql, list)` 会把整个 List 当成一个参数绑定**，报
`Type class java.util.ArrayList is not supported in dialect POSTGRES`。必须 `.toArray()`。

**jOOQ 纯文本语句无法为 `OffsetDateTime` 推断类型**，`occurred_at` 要显式 `?::timestamptz`，
否则报 `column "occurred_at" is of type timestamp with time zone but expression is of type character varying`。
与 `LifecycleService` 里已有的写法一致。

**测试里 `String status(UUID)` 会遮蔽 MockMvc 静态导入的 `status()`**，导致整片
`.andExpect(status().isOk())` 编译失败。改名为 `skuStatus`。

租户隔离三条断言在 `skuListIsTenantIsolatedAndHeaderForgeryIsIgnored` 里实跑真实 PostgreSQL 16：
两租户互不可见（含拿对方 SPU ID 查列表得到空页、拿对方 SKU ID 批量操作全部跳过）、
伪造 `X-Tenant-Id` 无效（读接口与写接口都试了）、连接池压到 1 后交替租户请求五轮不串租户。

另外 `everyNewTableHasForcedRls` 断言 `sku` 与三张新表都 `relrowsecurity + relforcerowsecurity`，
运行时角色非 superuser、非 bypassrls，且 `sku.tenant_id` 仍是 `NOT NULL`。
