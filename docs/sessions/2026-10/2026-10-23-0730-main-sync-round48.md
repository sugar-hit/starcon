# 2026-10-23: 集成分支并入 main（第 48 轮）—— 55 个冲突全是排版差异，净变化 1 篇纪要

## 摘要

本轮把 `integration/module-dev` 通过 Pull Request #60 合入 `main`，squash 合并，合并提交 `d7a5181b`。

合并形态是「真合并 + 55 个 `add/add` 冲突」（33 个 TS/TSX + 22 篇会话纪要）。
起手判定工具把 55 个文件全部标成「并入（人工）」，但该判据在 squash 合入的仓库里会系统性误报，
因此本轮没有直接采信，而是用两条互相独立的取证重新判定。

**核心结论：这 55 个冲突全部是排版差异，不存在任何内容分歧；而且 `main` 侧已经是仓库规范排版、集成分支侧不是。**
据此，合并结果取集成分支侧后再按仓库规范归一化，最终 55 个文件与 `main` 上的版本**逐字节相同**，
净变化只剩 1 篇新纪要。既没有丢内容，也没有引入任何新的格式债。

## 决策 / 结论

1. **不采信「main 侧的 blob 是否在集成分支历史里」这个判据**。
   在 squash 合入的仓库里，`main` 侧文件的 blob 天然不在集成分支的历史中（它是上一次 squash 的解冲突产物），
   所以这个判据会把线性演进误判成真分叉。本轮改用**内容超集**判据。

2. **55 个冲突全部取集成分支侧 + 按仓库规范归一化**，依据是三条互相印证的取证：

   - **Prettier API 归一化**：用仓库自身的 prettier（3.9.9 + `.prettierrc` + tailwind 插件）分别归一化两侧的 blob，
     **55 / 55 个文件归一化后逐字节相同** ⇒ 差异只在排版。
     用 API 而不是 `--stdin-filepath` 通道，是因为 stdin 通道对被忽略路径会「原样透传」，
     会让「两侧都没被处理」伪装成「两侧相同」的假绿。
   - **AST 指纹（不依赖 prettier）**：33 个 TS/TSX 的节点序列逐位相同；
     另外 22 篇纪要的差异只落在空行与一个空引用标记上，规范化后多重集相同。
   - **阴性对照**：向 `main` 侧注入 4 类真实语义改动（改字符串字面量、新增导出常量、改数字字面量、改标题文字），
     **10 / 10 全部被检出** ⇒ 上一条检查确实有区分力，不是空转。

3. **合并结果与 `main` 只差 1 个文件**：新增 `docs/sessions/2026-10/2026-10-23-batch-71-dispatch-compliance-plans-platform-flags.md`；
   后端、契约产物、工具链脚本、功能台账**逐字节不变**。
   用文件清单做集合差集验证过：`main` 有而合并结果没有的文件为 **0 个**。

4. **本轮的核心事实：集成分支上这 56 个文件是「未格式化」状态，`main` 上是「已格式化」状态。**
   所以直接取集成分支侧会让 `format:check` 的失败文件数比 `main` 基线多出 56 个 ⇒ 违反闸的判据。
   把合并结果按规范归一化之后，这 56 个文件全部合规，且 55 个与 `main` 逐字节相同。

5. **没有跑本地全量 L2**：合并结果的树与 `main` 的差异只有一个 `docs/` 下的 markdown 文件，
   后端与前端代码逐字节未变，重跑全量没有信息增量；且本地全量属发热高峰，全量闸由 CI 的远端 runner 承担。
