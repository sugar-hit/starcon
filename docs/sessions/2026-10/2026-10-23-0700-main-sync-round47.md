# 2026-10-23: 集成分支并入 main（第 47 轮）—— 排版差异归零，冲突取 main 侧

## 摘要

本轮把 `integration/module-dev` 通过 Pull Request 合入 `main`。起手时发现上一轮的同步 PR #58
在本会话开始前 15 秒才被合入 `main`（squash 合并，合并后的树与 PR 头逐字节相同），
集成头在其后只推进了一个提交，内容是一篇会话纪要。

合并形态为「真合并 + 55 个 add/add 冲突」。本轮的核心取证结论是：**这 55 个冲突全部是排版差异，
不存在任何内容分歧，而且 main 侧已经是仓库规范排版、集成侧不是。**
据此 55 个冲突全部取 main 侧，合并结果等于「main 的内容 + 1 篇新纪要」，
既没有丢失任何内容，也没有引入任何新的格式债。

## 决策 / 结论

1. **55 个冲突全部取 main 侧**（与上一轮取集成分支侧的方向相反），依据是两条互相独立的取证：
   - **规范化取证**：用仓库自身的 prettier（3.9.9 + 仓库 `.prettierrc` + tailwind 插件）
     分别归一化两侧的 blob。main 侧 **55 个文件里 0 个发生变化**，集成侧 **55 个文件全部发生变化**，
     归一化之后两侧逐字节相同 ⇒ 差异只在排版，且 main 侧就是规范形态。
   - **AST 指纹（不依赖 prettier）**：33 个 TS/TSX 文件的节点序列里有 23 个逐位相同；
     另外 10 个文件的**节点数完全相同**，差异只在 Tailwind 类名字符串的**顺序**上，
     类集合逐项比对 14/14 相同 ⇒ 没有一个类被增删。
2. **取 main 侧在结果上等同于完整求并**：既然规范化之后两侧内容逐字节相同，
   那么「取 main 侧」得到的就是「两侧的并集按规范排版之后的结果」，不可能丢内容。
3. **合并结果与 main 只差一个文件**：新增
   `docs/sessions/2026-10/2026-10-23-0650-main-sync-round44-conflict-verification.md`；
   契约产物、工具链脚本、功能台账**逐字节不变**。
4. **没有跑本地全量 L2**：合并结果的树与 main 的差异只有一个 `docs/` 下的 markdown 文件，
   后端与前端的代码逐字节未变，重跑全量没有信息增量；且本地全量属发热高峰，
   全量闸由 CI 的远端 runner 承担。
5. **闸工具的「阻塞」结论本轮是假阻塞**：它把 main 最近一次 run 当基线，却不检查该 run 的作业是否收完。
   本轮被选中的基线 run **仍在进行中、6 个作业全在跑**，于是被读成「基线没有失败作业」，
   虚报出「新增 4 个失败作业」。改用 main 当前 tip 对应的 run（作业全部收完）后，
   基线的失败作业集合与 PR 的失败作业集合**完全相同**，零新增失败。

## 关键 trade-off / 讨论

- **本轮取 main 侧、上一轮取集成分支侧，方向相反不是随意切换。**
  上一轮取集成分支侧之后，把 55 个文件在合并结果里格式化掉了，于是 main 侧成了规范排版；
  本轮集成侧仍然是车道写完未格式化的原始排版。判据始终是同一条：
  「规范化之后两侧是否逐字节相同，以及哪一侧已经是规范形态」。
- **取证方法的两个坑本轮都显式避开了**：一是 blob 抽到仓库内被 gitignore 的目录时，
  prettier 会静默跳过全部文件，归一化变成空操作，必须显式传 `--ignore-path=/dev/null`；
  二是必须配一个对照实验证明归一化通道是活的，否则「归一化后相同」可能是两边都没被处理的假绿。
  本轮对照实验输出与输入不同，通道确认可用。
- **闸工具的结论不能直接采信。** 本轮闸工具输出「阻塞」，但那是基线选取缺陷造成的假阻塞。
  基线相对的判据本身仍然正确，只是必须自己核对基线 run 的作业是否全部收完。
