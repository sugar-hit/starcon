# 9.1.1.1 订单列表（全渠道统一订单列表读投影）

- 日期：2026-10-11
- 车道：`feat/9-1-1-1`（worktree `.worktrees/9.1.1.1`），基线 `b696e02`
- 主责服务：trade · 端点 `/trade/sales-orders/list` · 前端 `/orders`（tab 壳）

## 决策摘要

**本模块是读投影，不是写入者。** sales_order 及六张子表的写入所有权属于 9.1.2.2
（手工单）与将来的 9.1.2.1（平台同步）。本车道一行 INSERT/UPDATE/DELETE 都没有，
不改任何既有表的结构，不建任何占位表。

### 蓝图九个维度：三个可得、六个不存在

| 维度 | 结论 | ownerModule |
| --- | --- | --- |
| 订单号 / 下单时间 / 总金额+币种 / 买家 / SKU 行数 | ✅ 可得、可筛、可排 | — |
| 平台店铺 | ❌ available=false | 2 平台同步 |
| **支付状态** | ❌ available=false（**只有 payment_method = 付款方式**，语义是「约定」不是「实收」） | 12 财务 |
| **履约状态** | ❌ available=false（`status` CHECK 只有 `('DRAFT','SUBMITTED')`，**完全没有履约概念**） | 9.3 履约 |
| 发货仓 | ❌ available=false（无履约请求关联） | 9.3.3.1 |
| 平台状态 / 售后状态 | ❌ available=false | 9.1.2.1 / 11 售后 |

**两条语义造假的红线**：绝不拿 `status` 冒充履约状态，绝不拿 `payment_method` 冒充支付状态。
响应里 `documentStatus` 与 `fulfillmentStatus` 是两个不同字段，后者恒为 `null`。
前端表格两列分开显示，`—` + tooltip 写明归属，而不是留空白（空白会被读成「这单没填」）。

**不提供**那六个维度的筛选参数与排序项 —— 一个永远筛不出东西的下拉框比没有更糟。
排序只给 ORDERED_AT / AMOUNT 四个真维度。

### 批量操作：四条全部 available=false

审单（9.2 未交付）、备注（写 `sales_order.note`，**写入所有者是 9.1.2.2，本模块不抢写**）、
取消（9.1.1.3 未交付）、发催付（15 客服侧未交付）。**本模块不提供任何写端点**。
导出同样报 available=false：缺六个关键维度时导出的 CSV 比不提供更危险。

### 汇总条

订单数与金额可算，金额**按币种分开报**（USD 与 EUR 加起来不是任何金额）。
**「待处理数」报 null + ownerModule=9.2** —— 口径由 9.2 定义，刻意不拿「DRAFT 算待处理」
自造替代口径却在界面上宣称它就是待处理数。

### 迁移结论

`V100__trade_sales_order_list_projection.sql`：**只加两条 CREATE INDEX，零新建表、零 ALTER 既有表**。
与 8.3.1.2 出库单详情「纯读投影」的先例同一形态，**跨车道 DDL 回归面 = 0**。

- `sales_order_by_amount(tenant_id, grand_total_amount, id)` —— 金额排序/区间筛选
- `sales_order_line_by_sku(tenant_id, sku_id, order_id)` —— 「这个 SKU 出现在哪些订单」反向查询
  （原 `sales_order_line_by_order` 的 lead 列是 `order_id`，走不上）

### 关键 trade-off

**端点取 `/trade/sales-orders/list` 而不是覆盖裸路径。** 裸 `GET /trade/sales-orders`
与 `/capabilities` **已被 9.1.2.2 占用**（已交付、有测试、有前端页面在用），
而 `/trade/orders` 被 `TradeTenancyIntegrationTest` 断言 2 显式预留（该文件属别的模块）。
故取并列子路径，集成测试正向断言 9.1.2.2 的两个端点原样可用。

**`/orders` 改为 tab 壳而非合并。** 蓝图系统树里 9.1.1 与 9.1.2 是并列 L4 却共用同一 URL，
一个 URL 不能有两个页面。做成 tab 而非合并，因为两者**读写边界不同**（列表只读、手工单是写入所有者），
合并会让「哪个 tab 能改数据」变得不明显。

**用户数据范围 SELF 收窄到本人经手过的订单**（`sales_order_status_history.actor_id`），
`actorId` 与 `selfOnly` 均取自已认证身份，不接受请求参数。
订单无部门维度，DEPARTMENT 退化为 SELF（退化方向刻意取更严一侧）。
刻意**不**给 sales_order 加 owner 列 —— 写入所有权属 9.1.2.2，读投影不改别人的表结构。

## 踩坑记录

1. **命名扫描必须逐个精确比对**。本次 9 个 `SalesOrderList*` 名字在改动前于扁平契约里
   全部 0 命中（`SalesOrderList` 前缀整体空闲）。刻意避开已被 9.1.2.2 占用的
   `SalesOrderPage` / `SalesOrderRow`。
2. **写脚本改一万多字符的正则前必须先自测**，且自测要抓**脚本自身**的假绿。
   本次自测当场抓出：最外层 `(?:` 包裹导致只看到 1 条分支（而不是 3 条）——
   若不自测，`main()` 会以为只有一条分支并报「3→1 条」也算成功。
   最终实现用配对深度剥离外层组（不用 `rindex`）。
3. **RLS 会让测试里的裸 `sql.execute` 静默失效**（无租户上下文 → 改动 0 行）。
   症状是「时间筛选失效」看起来像筛选写错了。夹具 SQL 必须包在 `access.run(...)` 里，
   并断言受影响行数。
4. **proxy 白名单按路径登记、不区分方法**（既有约定）。曾想断言「POST 到只读路径返回 404」，
   实测得到 503 —— 那是在把 proxy 的设计约定当缺陷断言。改为断言真正该守的性质：
   **白名单里不存在任何批量操作的写路径**。后端侧的写端点缺失由集成测试守。
5. **`Badge` 用 `tone` 不是 `variant`**（codegen 出来的 BigDecimal 在 TS 侧是 `number`）。
