# 10.5.1.3 关税与税费 —— 车道交付

日期：2026-10-08　车道：`feat/10-5-1-3`　worktree：`.worktrees/10.5.1.3`
基线：集成头 `integration/module-dev` @ `c14d757`（已含 10.5.1.1 报关单 V85）

## 决策摘要

### 1. 「估算与实缴差异要记录」是本模块的硬约束，钉进 DB 而不是只靠服务层

蓝图关系段原文加粗：「**税费估算与实际缴纳差异要记录**，长期差异大说明 HS 归类或税率配置有误」。

只存最终一个数的话，差异永远无法被回答，「HS 归类错了」这个结论就没有证据。所以分三张表：
`duty_tax_estimate`（按税率表算出的「应该有」）→ `duty_tax_payment`（海关实收，append-only）
→ `duty_tax_variance`（差额 + 归因 + 复核痕迹，append-only）。

关键取舍：**归因建在差异那一刻**，由缴款请求携带，不提供事后改归因的端点。
差异记录是 append-only 的（已归因的差异是纠错闭环的证据），要重新判定就再录一笔缴款对账出新的快照 ——
纠错过程本身就是证据链。

**「有实缴却没有差异记录」由延迟约束触发器 `duty_payment_has_variance` 拒收**（23514），
绕过服务层直接写 SQL 同样被挡（集成测试有 raw SQL 用例）。
所以「先存实缴、差异以后再补」在本模块**做不到** —— 这正是蓝图要的效果。

### 2. 差异是「逐次对账的快照」，不是「最终差额」

实缴逐次发生（补缴、退汇），差异也逐次对出来：第 1 次缴款留下「对到第 1 次为止差多少」，
第 2 次再留一条新的。`UNIQUE(tenant_id, estimate_id, tax_kind, payment_sequence)` 保证
同一笔缴款不会被对账两次（双记差异），而汇总口径只取**最新一次**快照，不把多次实缴累加。

### 3. 0% 税率合法，「没匹配到税率」不合法

第一版我在税率表上写了 `CHECK(ad_valorem_rate>0 OR specific_rate_per_unit>0)`，
理由是「配了但没填的税率行算出来恒为 0 且无人察觉」。**在真实 PG 上试插一条 0% VAT 才发现这是错的**：
0% 是真实且常见的合法配置（英国零税率商品、免税供货），禁掉它等于表达不了最常见的合法税率。

改法：撤掉那条 CHECK，把风险挪到**锁定**这一动作上 ——
`guard_duty_estimate_lock_completeness` 拒绝带 `NO_MATCH` 关税行、无 HS 码行、
或未配目的国增值税税率行的锁定。
理由：0 率本身合法，「没配税率」才不合法；把关卡放在「要作为报价依据发出去」这一步比禁税率更准确。

### 4. 税率按生效期检索，明细行抄下当时税率

税则会变，用代码常量记税率等于「改了税率就改了历史」。所以税率表带 `effective_from/effective_to`，
匹配时取（目的国 + 适用范围 + HS **最长前缀** + 当日生效）那条，
并把命中的税率值**抄进估算明细行**（`duty_ad_valorem_rate` + `duty_rate_prefix`）。
集成测试断言：改税率表之后历史明细行仍写着旧税率。

### 5. 增值税/GST 是**国别**税率，不是 HS 税率

真实税则里关税按 HS 细分、增值税按国征收。硬把国别增值税绑到某个 HS 码上，
结果是「换一个 HS 码就换了一个增值税率」—— 凭空造出来的税率。
所以 `duty_tax_rate` 有 `rate_scope`（COUNTRY/HS）且 CHECK 保证与 `hs_code_prefix` 自洽。
匹配：关税走 `rate_scope='HS'` + 最长前缀；增值税先试 VAT 再试 GST 的国别行。

### 6. 逐行算税，不合并成一个总税率

不同 HS 编码税率不同，合并算出来的「总关税」既无法归因也无法纠错。
蓝图那句「差异大说明 HS 归类或税率配置有误」要能落到**具体哪一行**，就必须是逐行的。
运费/保险/完税价按申报货值比例分摊，**最后一行吃余数**，保证「逐行分摊合计 = 单头金额」精确成立
（差一分钱也会让明细与单头对不上，而对不上的明细没人敢拿来报价）。

### 7. 金额口径：统一 HALF_UP 到分，两处一致

Java `setScale(2, HALF_UP)` 与 DB `round(x,2)` 表达同一口径，延迟约束在提交时复核。
集成测试专门断言 `0.505 → 0.51`（不是银行家舍入的 `0.50`）与负数 `-0.505 → -0.51`。

## 过程中修掉的三个真实缺陷

1. **DEFERRABLE 约束触发器用 `NEW` 会拿到事件发生那一刻的旧值**（最隐蔽的一个）。
   服务层写法是「先 INSERT 头（合计先落 0）→ 写明细 → UPDATE 头回填合计」，
   于是同一事务里既触发 INSERT 事件又触发 UPDATE 事件；延迟到提交时，
   INSERT 那一次仍拿着合计=0 的旧 `NEW` 去核对已经算完的明细，于是**每次必报**
   「单头 ≠ 明细合计」。解法是回表读当前行（V85 的 `customs_rate_snapshot` 用的就是同一办法）。
2. **实缴 append-only 有两道防线，我只测到了一道**：授权层 `REVOKE UPDATE, DELETE`
   对 `warehouse_app` 生效（测试连的就是 `warehouse_app`，所以先被权限拒掉），
   触发器层要换成超级用户直连才触得到。现在两条都断言 —— 只测一条的话，
   将来有人撤掉 REVOKE（或撤掉触发器）时另一条就没有回归保护。
3. **前端 `recalculate` 动作原本会调 `lock`**：动作分支里 `else` 兜底成了锁定。
   是白名单测试「源码里真实调用点被放行」那条用例逼出来的（`/recalculate` 没被抽到）。

## 上游依赖（10.5.1.1 报关单）

- 本迁移**不 ALTER 任何既有表**，只对 `customs_declaration(_line)` 建**复合外键**（同服务），
  跨车道回归面 = 0。
- 遵守 V85 已裁决的语义：`submitted_at` 是历史痕迹，打上就永不消失 ——
  所以「已报关 / 未报关」的判据必须看 `submitted_at` 而不是 `status`。
- 夹具**走真实的上游服务**（`CustomsDeclarationService`）建报关单，不手写 SQL 抄状态机：
  V85 把「人工复核闸」「三单据齐备才能提交」「放行要结果回执」都钉在 DB 触发器里，
  手写 SQL 会绕过这些纪律，夹具就变成一个上游并不存在的世界。
