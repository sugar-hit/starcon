## 摘要

蓝图 18.3.3.1「自动审批」：自动化审批场景（自动通过低风险小额单据、自动驳回明显不合规单据、
金额分层路由审批人、超时自动升级），输入 = 审批规则配置 + 单据风险信号，
输出 = 自动审批结果 + 决策依据记录。

本车道交付的是 platform 服务里的 **「自动审批决策层」**：规则配置、风险信号码表、
判定引擎、**只追加**的决策台账（结论 + 依据快照）、超时升级的扫描与执行。

本车道经历**一次会话掐断**（前一任 `net::ERR_CONNECTION_CLOSED`，只做勘察、0 commit），
交接说明在 `HANDOFF-18.3.3.1.md`（调度者代写，已复核上游表名与端点清单）。
本次沿用其取证结论，**没有**重头勘察。

## 🔴 核心边界结论（决定实现形态的那一条）

**问：上游 17.4（identity 服务）是否暴露「程序化通过 / 驳回」的通道？**

**答：没有。** 本车道**亲自读代码**确认（不是推测）：

| 上游端点 | 形状 | 能否程序化调用 |
| --- | --- | --- |
| `POST /identity/approval-instances` | `X-Internal-Key` + 已认证会话 → 建一条 PENDING 实例，按金额分层分支选起始节点 | ✅ **能**（唯一的程序化通道） |
| `POST /identity/my-approvals/{id}/decide` | 绑定调用者自己的会话；`actor_membership_id` **恒为调用者**；取单条件是 `MINE`（指派 / 节点指定人 / 节点角色） | ❌ 不能 |
| `POST /identity/my-approvals/{id}/transfer` | 同上（`batch` 也是逐条走同一个 `apply()`） | ❌ 不能 |

补充取证：identity 侧**没有** service account 概念（`session_access(?)` 只认 bearer 会话），
`INTERNAL_KEY` 只出现在「建单」与「平台运维」两类端点上，**没有**任何按内部密钥做审批决策的路径。

⇒ **实现形态定为「判定 + 记录 + 经授权端口转交」**：

- **自动通过 / 自动驳回** ⇒ **不建上游实例**。没有单子需要人审，也就没有待办 ——
  这与上游自己「免审 EXEMPT」的语义一致（上游的 EXEMPT 规则同样不建实例）。
  结论与依据落在本模块**自己的**决策台账里，供下游各业务系统取用。
- **必须走人工** ⇒ 经 `IdentityApprovalPort` 调上游 intake，**真的**把单子送进人工审批。
  建单之后那张单的状态**只由 identity 管**，本模块只留一个引用（`upstream_instance_id` 等）。
- **本模块不在 platform 侧另起一套审批状态机**：不复制 `approval_instance` /
  `approval_instance_action`，不在本服务里造第二套 `PENDING / APPROVED / REJECTED` 实例状态机。
  本模块拥有的是**「自动审批决策」**这一层事实。

## 决策 / trade-off

1. **「自动审批只处理明确安全的场景」落成三条可执行判定 + 逐条落库**：
   `SMALL_AMOUNT`（小额）、`SUPPLIER_VERIFIED`（供应商已验证，**不可配置**）、
   `NO_RISK_SIGNAL`（一条风险信号都没有）。缺一条 ⇒ 走人工。
   「供应商已验证」做成**硬条件**而不是开关：它是蓝图加粗句里的三个条件之一，
   做成可关的开关等于给「关掉内控底线」留了一个口子。
2. **自动驳回只对确定性违规**：金额与币种不成对、金额为负、金额越硬上限、
   命中**登记过的** `VIOLATION` 信号。主观风险（`RISK`）**绝不**驳回，只走人工。
   🔴 **信号的性质由租户码表决定，不由调用方自称**：调用方只报**码**，
   码表里查不到 ⇒ 按 `RISK` 从严 ⇒ 「编一个码就能把单子驳掉」这件事在本模块里不可能发生。
3. **信号码表按租户建、不预置**：蓝图把「单据风险信号」列为本模块的**输入**，
   而「必填缺失 / 黑名单命中」这两类确定性违规是**业务事实**（本模块无从自己判断），
   由业务系统以信号的形式报上来、性质由租户码表判定 ⇒ 与蓝图口径一致。
   系统零预置行（与 18.2.3.1 同纪律）；本模块自己额外判定的是**金额类**的不合规。
4. **金额分层路由读上游，不另造区间语义**：上游 `approval_flow_amount_branch` 是现成的分层结构，
   本模块经授权端口读 `GET /identity/approval-flows/{id}`，
   **区间口径与上游逐字同款**：`[min_amount, max_amount)` 左闭右开、多条命中按 `priority desc, id` 取第一条。
   ⚠️ 与上游的差异只有一处且是**故意的**：上游建单时按**提交时的金额**选**起始节点**；
   本模块记录的是**判定当时**命中的那一档（决策依据的一部分）。
   金额比较一律 `BigDecimal.compareTo`（`equals` 会把 `100` 与 `100.00` 判成不等）。
5. **超时判定只有一个时钟基准**：用**上游算出来的停留秒数**（identity 的 `approval_dwell_seconds`，
   DB 钟域）与规则里的 `timeout_hours` 比较 —— 两者同钟域，比较才有意义。
   本模块自己的落库时刻取**注入的 `Clock`**（可被测试钉死）。
   没有 `Timestamp.valueOf(LocalDateTime.now())`（会静默偏 −28800s），没有 sleep。
   ⚠️ 上游的 `approval_flow_escalation` **只定义规则、不实现定时器**（其注释逐字写着
   「本模块只定义它，不实现任何会去看它并放行的定时器」）⇒ **「超时自动升级」正是本车道的活**，
   不是重复实现。
6. **「执行升级」以发起人自己的身份在上游完成**：上游的审批动作只认**当前审批人自己的会话**，
   所以执行时转发的是**发起人的** bearer，本模块**不冒充**任何人。
   发起人不是当前审批人时上游会如实拒绝，那个拒绝被**原样记进台账**（`status=FAILED` +
   `execution_detail` 写清「这条待办不在当前用户的待办里」）—— 「谁有权放行」正是内控底线。
7. **升级目标只在唯一解时才解析**：转交通道只接受**具体成员**。
   目标为 `USER` ⇒ 直接用；目标为 `ROLE` 且该角色下**恰好一名**在职成员 ⇒ 用他；
   角色下有多名在职成员 / 目标是 `POSITION`（上游岗位字典不携带成员绑定）⇒
   **如实拒绝并写明该由谁来做**，不做「替租户挑一个人」的判断。
8. **提交上游失败也留决策**（`executionState=SUBMIT_FAILED` + 原因）：
   「这张单必须走人工」与「上游那次提交成功没有」是两件事，混在一起会让台账说谎。
   决策台账是**只追加**的（触发器钉死 UPDATE / DELETE），依据记的是**当时**的规则与信号**快照**。
9. **权限码分「配置」与「判定」两个**：`platform.auto_approval.read / .create / .update / .decide`。
   能改规则的人不一定有权让规则替他放行单据 —— 这两个码分开，「改规则」才不等于「批量放行」。
   只授 OWNER。
10. **本端口自带 HTTP 客户端**，不改共用工具 `PlatformUpstreamClient`：
    它只提供「读」与「空体 POST」两种形状，而本端口需要「带请求体 + 额外请求头（内部密钥）的 POST」
    与「动作类调用的 4xx 不抛异常」两种新形状 —— 改共用工具会把别的模块的写入面卷进来。

### 修掉的三个真缺陷（写测试时暴露的，不是写测试时凑出来的）

- 🔴 **PostgreSQL 里一条失败语句会毒化整个事务**（后续语句全报 `25P02`）：
  升级台账原来「插完再捕获唯一冲突」，重复扫描时事务已被毒化 ⇒ 409。
  改用 `ON CONFLICT (tenant_id, upstream_instance_id, node_key, timeout_hours) DO NOTHING`。
- 🔴 **Jackson 默认把 JSON 数字读成 `double`** ⇒ 快照里的金额 `1000.000000` 变成 `1000.0`（标度丢了）。
  快照改用专用 mapper（`USE_BIG_DECIMAL_FOR_FLOATS`）。
- 🔴 **timestamptz 回读按会话时区渲染** ⇒ 断言改比**时刻**而不是文本
  （这是 18.2.3.1 车道踩过的同一个坑：不把会话时区当成被测值）。

## 后续待办

1. **上游若要支持「服务间程序化审批」，需在 identity 侧新增一条程序化决策端点** ——
   本车道不碰 identity 的端点（模块边界纪律），只能在授权端口这一层做转交。
   在那之前，「自动审批」能替人做的只有**判定与留痕**，真正的审批动作仍由人按。
2. **「超时升级」的转交目标解析**目前只支持 `USER` 与「角色下恰好一名在职成员」；
   多成员角色与岗位目标会**如实拒绝**。若上游将来支持「按角色/岗位转交」，本模块可直接接上。
3. **本模块的调度**：`POST /escalations/scan` 是**手动触发**的扫描端点。
   「定时器」本身由部署侧调度（本仓没有统一的调度框架），本模块提供的是**扫描 + 判定 + 执行**这三段。
4. **18.3.3 的另外两格**（18.3.3.2 等）不在本车道范围内。
