# 2026-10-24: 16.3.2.1 VAT/IOSS（channel 服务）

> 车道：`feat/16-3-2-1`（worktree `.worktrees/16.3.2.1`），基线 `integration/module-dev` @ `1c73d1e`。
> 迁移版本号：**V365**（`V365__vat_ioss.sql`），与同批车道（V364 / 其它预分配号）互不撞号。
> 落点：`backend/services/channel/`（卷 16「合规与风控」的后端主责服务 = `channel + identity`，取列表第一项）。

## 摘要

蓝图原文：「管理 VAT 与 IOSS 制度：适用店铺与商品、申报周期、税率适用、IOSS 订单识别与代收代缴统计、
与财务申报数据的对接。输入：IOSS 配置；订单税务数据；12.6.1.2 申报底稿。输出：IOSS 订单清单与金额统计；申报状态。
关系：上游 = 12.6.1.1 税率、9 订单；下游 = 12.6.1.2。**IOSS 订单与一般 VAT 订单必须区分统计**，
混在一起申报是最常见的错误。」

本模块交付三样东西：**IOSS 登记与适用范围**（店铺 / 商品）、**申报周期与申报状态**（真实流转）、
**IOSS 订单识别 + 代收代缴统计**（按 IOSS / 非 IOSS 分档、按币种分组）。

## 决策 / 结论

### 1. 🔴 「必须区分统计」落成**数据列**，不是页面上的颜色

蓝图那句加粗是硬要求。做法：`vat_ioss_order.filing_scope` 是一列受控枚举
（`IOSS` / `GENERAL_VAT` / `OUT_OF_SCOPE` / `UNRESOLVED`），**每一张订单行都有一个取值**；
统计一律 `group by filing_scope, currency` ⇒ **取数层面**就是分开的。

trade-off：**第四档 `UNRESOLVED` 是刻意加的**。蓝图只说「区分 IOSS 与一般 VAT」，
但「没有收货国家 / 买家类型没采到 / 汇率读不到折不出免征门槛」这三类**判不了** ——
把它们塞进 IOSS 或一般 VAT 都是**假结论**，而且「IOSS 少算了」看起来像「本来就没有」。
⇒ 独立成档，**不并进任何一档**，但**必须**出现在清单与汇总里。

### 2. 🔴 方向澄清：12.6.1.2 是**下游**，不是上游

蓝图写「输入：…；12.6.1.2 申报底稿」，同时写「下游 = 12.6.1.2」。
⇒ 方向上**本模块在上游**：本模块输出的「IOSS 订单清单与金额统计」是 12.6.1.2 的**输入**。
12.6.1.2 在同批另一条车道开发（V364），集成头里**没有**。

处理：按「**读不到 ⇒ 如实显示『读不到申报底稿』**」落地 ——
统计结果里 `filingDraftAvailable=false` + `filingDraftOwnerModule='12.6.1.2'` + 影响说明，
能力声明里逐条列 `available=false`。**不编造**它的底稿，**不停工**。

### 3. 税率读不到 ⇒ 税率为 `null`，**绝不退化成 0%**

`tax_rate` 列允许为 NULL，但 **NULL 的含义是「读不到」**，另有 `tax_rate_source`
（`FINANCE` / `UNAVAILABLE`）把这件事写进数据本身。

trade-off：**税率不参与分档判定**。分档回答「这单该不该走 IOSS」，税率回答「适用多少税率」，
两件事。税率读不到时订单照样归档（分档照常），只是 `tax_rate` 留空 + 页面显示「读不到（不是 0%，也不是免税）」。
理由：把「读不到税率」做成「判不了」会让税率服务一抖动，整个 IOSS 归档就停摆。

### 4. 免征门槛带币种 ⇒ 需要折算 ⇒ 汇率读不到就**判不了**

IOSS 免征线是 **150 EUR**，而订单可以是任意币种 ⇒ 门槛比较必须折算。
折算走 catalog 的**授权只读端口** `GET /catalog/exchange-rates/latest`（按订单日期取）。
汇率读不到 ⇒ 该单判 `UNRESOLVED / THRESHOLD_UNRESOLVED`，**不许拿猜的汇率把单子归档进 IOSS**
（那等于凭空造一份申报数据）。

trade-off：**汇率只用于门槛比较，绝不进任何金额合计**。统计永远按币种分组
（EUR + USD 不是钱）。所以「IOSS 的钱」在不同币种下是**几行**，不是一个数。

### 5. 订单口径：trade 的**平台单投影**（`platform_order`）

9 订单的事实在 trade 服务（跨服务 ⇒ 只能经授权 HTTP API 读）。要判 IOSS 需要同时有
**店铺**（判「适用店铺」）与 **收货国家 / 买家类型 / 行明细**（判欧盟 B2C / 非应税消费品 / 货值），
而这两组字段分处 trade 的两个端点 ⇒ `TradeOrderPort` 读两个端点。

**已知边界**：trade 的**手工单**（`sales_order` 无平台投影）**没有店铺归属**，
判不了「适用店铺」⇒ **不在本模块口径内**。这条写进了能力声明与页面，不是隐藏缺口。

### 6. 辖区码表**只读**，不写死欧盟 27 国清单

辖区（`EU-DE` / `EU-FR` …）直接读 16.3.1.1 已交付的全局码表
`tax_registration_jurisdiction`（**同库只读**），本模块**不写** `tax_registration_record`、
**不另建**辖区表。`vat_ioss_filing_cycle` / `vat_filing_period` 的 `jurisdiction_code`
由 DB 触发器钉死必须落在那张表里 ⇒ **不留自由文本**。

### 7. 申报状态三档，**只能前进**

`DRAFT 待提交` → `DRAFTED 已出底稿` → `CONFIRMED 已确认`，DB 触发器钉死（不许回退、不许跳过）。

**刻意没有「已向税务机构提交」状态**：本系统只保证数据完整可核，**不代用户向税务机构提交申报**
—— 那个动作由用户在税务机构门户完成。本仓任何模块都无权声称「已申报」。

### 8. 登记号与生效时刻**不可回改**

就地改 IOSS 登记号 = 把当初申报时用的号偷偷换掉。DB 触发器拒（服务层也先拒一次，给出可读原因）。
想换号 = 关闭当前登记（写 `effective_to`）+ 另登记一条；**已关闭的登记内容冻结**。

### 9. 🔴 api-proxy 自检脚本抓到一个真 bug（差点静默 404）

本车道新增的 `services[]` 元素插在**数组末尾**，而 `resolve()` 是**首个命中即返回** ——
只要前面任何一条 `channel/` 的巨型 alternation 吃掉了 `vat-ioss/...`，浏览器里就是静默 404，
而 typecheck / lint / vitest **全绿**。

为此写了 `.tmp/check-api-proxy.mjs`（把全文件 214 条正则逐条抽出实测）。
**它当场抓到本车道的正则多了一个 `)`** —— 那条正则根本编译不过，浏览器里 17 个形状**全部 404**。
这类 bug 正是「改了 api-proxy 就必须跑全量 allowlist 回归」的原因。

修完后再测：17 个正向形状全部放行、16 个负向形状全部 404、既有 channel 模块入口零误伤。

### 10. 契约：纯新增，零漂移

`python3 tools/codegen/catalog-contracts.py --spec-dir backend/target/openapi`
⇒ channel **纯新增 17 条路径与 26 个 DTO、零删除、零改字段**；
既有 939 条路径与 1787 个 schema **逐字节零漂移**（用 `json.load` 逐个比对验证，不是看 diff 行数）；
其余 6 个服务的契约**零漂移**（`git status` 只有 channel 两个文件）。
