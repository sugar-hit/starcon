## 决策 / 结论

1. **本轮不合 PR #65**（`chore/sync-module-dev` → `main`）。闸工具结论「阻塞」。
2. **本轮刷新同步分支**。上一轮不刷新的理由是「台账未变 ⇒ 无新功能交付」；本轮台账新增 4 项能力，
   该理由不成立 ⇒ 刷新。
3. **58 个冲突的解法分两类，都带证据**：
   - 57 个文件：两侧经格式化归一化后**逐字节相同**（纯排版差异：表格填充、函数签名折行、中文折行），
     且 main 侧原样即合规 ⇒ **取 main 侧**。取集成侧等于新增 57 个未格式化文件 = 自造排版债。
     （这一条与「冲突文件默认取集成分支侧」的直觉相反，理由见下。）
   - `api-proxy.ts`：main 侧 blob 出现在集成侧分支历史里（线性演进），且累积型三件套全成立
     （集合包含 ✓ / 有序子序列 ✓ / 零删除 ✓，条目 176 → 209）⇒ **取集成侧**，再用格式化归一化保持合规。
4. **平台授权判定类的注释排版已修正**：该文件是集成侧新交付的内容，其 Javadoc 被硬折行，
   不满足仓库自己的 Java 格式化规则 ⇒ 构建在第一个模块就中断。已换成合规版本，
   并逐字节验证「去掉注释与空白后代码完全相同」（1747 字符 vs 1747 字符）。
5. **新增失败用例的归属不变**：集成侧交付内容自带，解除条件是集成侧车道修掉该用例，本任务不做本地测试改写。

## 关键 trade-off

- **为什么不无脑取集成侧**：本仓库的 `main` 是 squash 合入的，绝大多数冲突不是双向分叉而是
  「main 侧 = 集成分支的旧快照」。但**排版型冲突是反过来的**：本轮 57 个冲突里，集成侧才是未格式化的一方。
  判据不能靠默认直觉，必须逐文件拿证据。
- **为什么不直接合上**：闸门的判据是「失败不得比基线更多」，不是「基线也红就放行」。
  本轮 PR 的失败用例集合严格包含基线集合且多出一条 ⇒ 不合。
- **为什么把平台授权类的排版问题顺手修掉**：不修的话，Java 作业在格式化阶段就中断，
  **一个测试都跑不到**，闸工具拿不到用例级明细 ⇒ 下一轮会看到「明细不可比」而误判为持平，
  放行一个构建已断的 PR。修好之后失败形状回到基线可比的样子，闸门判断才有效。
- **为什么不在本地跑全量 L2**：本轮增量只有「合并动作 + 冲突解法 + 注释排版」，
  集成侧推分支前已跑过自己的全量；真正的全量闸在远端 CI。且本地只有 JDK 25，
  仓库固定的 JDK 21 工具链跑不了格式化器（见下）。

## 本轮关键取证

### ① 冲突解法逐个带证据（独立复核，不复用工具的计数口径）

| 类别                              | 文件数 | 证据                                                         | 解法       |
| --------------------------------- | ------ | ------------------------------------------------------------ | ---------- |
| 纯排版差异（前端组件 / 会话纪要） | 57     | 归一化后两侧逐字节相同；main 侧原样合规、集成侧不合规        | 取 main 侧 |
| 白名单累积型                      | 1      | main 侧 blob 在集成侧历史内；累积型三件套全成立（176 → 209） | 取集成侧   |

  并配**阴性对照**：篡改集成侧一侧后集合包含立即不成立 ⇒ 检测器有效。
- 归一化后两侧 pattern 集合逐条一致（209 = 209），合并结果**逐字节等于**「集成侧原文经格式化归一化」。

### ⑤ 本地格式化检查的结果**不可信**，已用对照实验排除

本地用固定 JDK 21 的 Maven 镜像跑格式化检查，报出 identity 60 / catalog 151 / channel 513 等
上千个文件「需要修改」；但 CI 对同一份代码只报出**一个**文件。
对照实验：把**上一轮 PR 头**（CI 里格式化检查通过）用同样方式跑，本地报出**完全相同**的计数
⇒ 本地判定口径与 CI 不一致，**本地数字不作为证据**。
⇒ 只有 CI 自报的清单是可信的。本地那次跑只用于**复现失败点**（两边的失败模块与文件逐项吻合）。

### ⑥ 联动风险：新财务能力的集成测试在本轮 CI 里没有跑过

Java 作业在 `identity` 模块因 2 个已知用例失败而中断，reactor 把 `catalog`/`channel`/`warehouse`/
`trade`/`crm`/`finance` 全部 SKIPPED ⇒ 本轮 4 项新财务能力（坏账与核销、付款计划、核销、结算单管理）
的集成测试**在 CI 里一次都没跑**。这是把闸门判据落到基线相对之外的另一层风险，
解除条件：平台开关的精度缺陷修掉后，Java 作业才能跑完整条 reactor，财务模块的测试才会有 CI 证据。

### ⑦ 并发与漂移检查

- 起手闸空闲，中途取闸两次（合并前、合并前刷新），推送后放闸；本轮结束时闸为空闲。
- 集成分支在轮中持续推进（`d2ade98b` → `ccc62410` → `3a2eb791` → `ac0b1509` → `d7d58550`），
  每轮裁决前重新 fetch，且**一律用 `upstream/<branch>` 判定**，不拿本地分支指针当远端事实。
