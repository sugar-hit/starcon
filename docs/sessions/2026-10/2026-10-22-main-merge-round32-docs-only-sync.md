## 摘要

把集成分支最新的一批内容合进主分支。集成头本轮新增的只有会话纪要与车道并入预演结论，
**功能进度台账与主分支逐字节相同**（已交付 316 · 进行中 0 · 未开发 149，共 465 条 L4 记录），
因此这是一次纯文档同步，不涉及任何功能交付。合入过程有一处 add/add 冲突（文档副本），
按行级差集取证后取集成分支侧；该文件在集成分支侧的表格列宽不是规范形态，
落地前按规范形态格式化，格式闸失败文件数相对基线零增长。

## 决策 / 结论

1. **冲突取边靠行级差集取证，不靠 diff 行数**。
   冲突文件两侧行数差 74 行、diff 显示 170 行变更（122 增 / 48 删），但归一化后 main 侧的独有内容行为 **0 行**
   （main 侧“独有”的 8 行**全部**是 Markdown 表格分隔线，是列宽差异的噪声，没有一行是实质内容）。
   ⇒ 集成分支侧是 main 侧的**严格超集**，取集成分支侧零丢失。
   判定工具给的是「并入（人工）」，但那只是「不能机械取一边」的保守警报，不是「必须两侧都留」的判决。

2. **交付轮必须先格式化再推**。
   本轮是交付轮（带进 3 个文档），集成分支侧那份纪要的表格列宽不是规范形态，
   直接推会让格式闸的失败文件数比基线多 1 个 ⇒ 属于「比基线更多的失败」⇒ 协议硬禁令不许合。
   格式化前后做过归一化比对：**语义零差异**，纯列宽变化。
   ⚠️ 反过来说：**零变更轮不要顺手修格式债** —— 修完下一轮三方合并会自动撤回，白吵一遍。

3. **闸工具只比作业粒度时，必须人工补明细**。
   闸工具对 Lint / Security Scan / 端到端 / Java 四个作业只比了作业粒度，标为「明细不可比」。
   逐个补完明细后，四个作业与基线**逐项持平**：

   | 作业          | 补的明细                       | 结论                                                                                                                    |
   | ------------- | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
   | Lint          | 失败文件集合双向差集           | 两侧同为 619 个文件，差集**双向为空**；本轮 3 个文件**都不在**失败集合里                                                |
   | Security Scan | 审计严重度分布 + advisory 条目 | 两侧同为 `1 low \| 7 moderate \| 2 high`；`pnpm-lock.yaml` 在两侧 blob 逐字节相同                                       |
   | 端到端        | 失败根因链（bean 创建失败链）  | 8 行签名逐字节相同（`localCredentialDocumentStorage` → `brandCredentialService` → `brandCredentialController`）         |
   | Java 21       | 逐测试类计数 + 失败用例名      | 两侧同为 `Tests run: 270, Failures: 1`；同一例 `ApprovalRecordIntegrationTest` 的同一方法；断言里的时间戳归一化后无差异 |

4. **「工作区里的协议文件可能是旧版」**。
   本机主工作区常驻集成分支，那份任务书落后主分支几百行（含契约产物必须拆两个 PR 的次序约束）。
   ⇒ 协议要从远端 ref 读，动手前先比 blob。

5. **worktree 路径做格式取证会被静默跳过**。
   `prettier --check` 对被 gitignore 的路径**既不报错也不判失败**，直接放行
   ⇒ 在 worktree 里做格式取证，拿到的「合规」是假象，那个文件从未被检查过。
   ⇒ 判格式前先 `--file-info` 看 `ignored` 字段，非 false 则该次判定无效。

## 关键 trade-off / 讨论

- **取集成分支侧 vs 人工求并**：判定工具标「并入（人工）」时，取一边有可能静默丢掉另一侧的独有内容。
  本轮用「归一化后的行级差集」证明集成分支侧是严格超集，因此取一边是零丢失的。
  ⚠️ 这个结论只对本次这一个文件成立，下一轮必须重新取证。

- **格式化 vs 不动格式**：不动格式会让格式闸失败数上涨 1（协议硬禁令），
  动了格式会让下一轮三方合并产生 add/add 冲突。
  取「动了并保留规范形态」是正解 —— 判据工具对 add/add 不会自动取一边，
  所以规范形态会被稳定保留下来，不会被下一轮撤回。
