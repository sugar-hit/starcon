# 2026-10-23 04:14 集成分支并入 main（第 41 轮 · 零净变更复核）

## 摘要

第 41 轮同步：`integration/module-dev` → `main`。

**结果：零净变更，本轮没有开同步 PR。**
两分支的树差异非空（34 个文件），但解完冲突后**合并结果的落地树哈希与 `main` 的树哈希逐字节相同**
（两侧都是 `baec9b55`），落地的 Pull Request 文件差异为空。

本轮的实际产出是**核验结论**：确认主分支相对集成分支**没有待合入的新交付**，
并确认冲突面的 29 个文件全部是排版差异、内容完全等价。

## 决策 / 结论

### 1. 「有没有新内容」以落地树哈希为准，本轮结论为零净变更

- `upstream/main` tip = `26370073`（树 `baec9b55`），`upstream/integration/module-dev` tip = `d29f804f`（树 `35ea3ce2`）。
- 两侧树差异报 **34 个文件**（412 增 / 1024 删），看上去像一次实增量。
- 但逐文件核对后，这 34 个文件的差异**全部不是内容差异**：

| 类别                     | 文件数 | 核对结论                                                               |
| ------------------------ | ------ | ---------------------------------------------------------------------- |
| 两侧都存在，差异只在排版 | 29     | 经格式归一化后**逐字节相同**（A=29）；主分支侧已是规范态（B=29 / C=0） |
| 只在主分支侧存在         | 5      | 主分支独有内容，合并动作不改变它                                       |

- 冲突面 **29 个文件全部是 add/add**（相对共同祖先，两侧各自新增同一批文件）。
- 在专用 worktree 里真实合并、解完 29 个冲突后 `git write-tree` = `baec9b55…`，
  与 `git rev-parse upstream/main^{tree}` **完全相同**。

⇒ **主分支没有任何集成分支尚未包含的内容。** 判定依据是落地树哈希，不是树差异：
树差异是双向的，既含「集成分支有、主分支没有」，也含「主分支有、集成分支没有」，
后一部分不该被合入动作改变。

⚠️ `merge-resolve.mjs` 把这 29 个文件**全部**判成「并入（人工）」——
它比对的是文件的原始字节，规范化过的字节必然对不上原始内容 ⇒ **该工具在纯排版场景会全量误报**，
它的结论必须与格式归一化取证**交叉验证**后才能采信。

### 2. 冲突解法：取主分支侧，零内容丢失、不增加格式债

三个计数器合起来说明：**内容完全等价（A），主分支侧就是规范态（B），集成侧不是（C）。**

- 取主分支侧 ⇒ 语义零损失，且不给仓库新增格式债。
- 反之取集成侧会让 `format:check` 多出 29 个未格式化文件，直接加重 `Lint` 作业的存量失败。

本轮 `api-proxy.ts` **不在冲突面内**（白名单在两侧逐字节相同），
后端业务代码与迁移脚本**亦不在冲突面内**。

### 3. 后端与契约产物完全未受影响

- `backend/` 整树 **2060 个文件**逐个 blob 比对，两侧**完全相同**，零差异。
- 迁移脚本集两侧 **321 个文件**，文件名集合差集**为空**。
- `packages/api-contracts`、`packages/sdk` 契约产物**零差异**。

⇒ 本轮合入动作**不可能**引入后端回归或契约漂移，
因此无须跑本地全量 L2（协议第 5.1 节的例外条件均不成立）。

### 4. 台账两侧逐字节未变

- 台账「已交付」两侧同为 **332** ⇒ 集成分支没有新增交付，主分支也不落后。
- 台账与功能蓝图一致性自检**通过**。

### 5. 冲突面专项验证全绿

## 关键 trade-off / 讨论

- **为什么不开一个「同步进度」的 PR？** 因为它会是**空 PR** ——
  落地树与主分支相同，文件差异为空，只会给主分支添一条什么也没带的提交。
  零变更轮的产出应当放在**核验结论**上，而不是一条无内容的同步提交。
- **为什么不跑本地全量 L2？** 冲突解法**未触碰后端业务代码或迁移脚本**
  （后端整树两侧逐字节相同），且定向验证全绿
  ⇒ 按协议走定向级别，全量闸交给远端 CI。
- **为什么保留主分支侧独有的 5 份纪要？** 它们只存在于主分支、共同祖先里也没有
  ⇒ 单边新增，合并时自动保留，不构成冲突，也不该被合入动作改变。
- **本轮的取证成本为什么值得付？** 树差异报 34 个文件、1024 处删除，
  单看统计数字会误判成「有大增量要合」⇒ 必须逐文件核对到字节级才能定性。
