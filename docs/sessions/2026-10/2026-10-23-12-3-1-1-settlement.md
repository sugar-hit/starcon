## 决策摘要

蓝图原文（`docs/product/capability-blueprint/12-finance.md` 第 170–176 行）：

> ### 12.3.1.1 结算单管理
>
> - **职责**：管理平台结算单：结算周期、店铺、平台账单汇总（销售额、退款、佣金、FBA 费用、广告费、赔付、其他调整）、结算金额、到账状态。
> - **输入**：平台结算报告同步（2 同步）；人工上传账单；结算周期配置。
> - **输出**：结算单 + 汇总项 + 明细行 + 与我方账的差额。
> - **关系**：上游 = 2 渠道与店铺；下游 = 12.3.2.1 对账、12.2.1.1 收款、13 利润。**平台账单是财务事实的重要外部来源，需保留原始文件与解析版本。**

本车道落地要点：

1. **「结算金额必须由明细项求和得出」钉在 DB 层，做成三段派生链。**
   明细行 →（语句级触发器）→ 汇总项 →（同一个触发器）→ 结算金额。
   `guard_finance_settlement_summary_derived` 与 `guard_finance_settlement_amount_derived`
   用 `pg_trigger_depth()` 判别「派生写入」与「直接写入」，把「服务层/直连 SQL 手填总额」这条后门**拒掉**。
   ⚠️ 为什么结算金额是普通列而不是 `GENERATED ALWAYS AS`：PG 的生成列**只能引用同一行的其它列**，
   而汇总项在**子表**里 ⇒ 生成列这条路走不通，只能用触发器 + 守卫。
2. **符号约定统一归一（跨境结算单最容易算错的一格）。**
   退款/佣金/FBA 费用/广告费在各家账单里有的写负数、有的写正数（绝对值）。
   本模块固定一套符号（销售额/赔付为正、四类费用为负、其他调整按账单原样），
   解析阶段归一，明细行**同时**留 `raw_amount`（账单里写的那个数）与 `amount`（归一后的贡献），
   两个数都在库里，原始文件原文也在库里 ⇒ 任何时候都能逐行对回账单。
3. **原始文件与解析版本是两张表而不是一张。**
   `finance_settlement_source_file` 一行 = **一次解析**（原文 + sha256 指纹 + `parse_version` + 告警），
   结算单通过 `source_file_id` 指向**具体哪一次解析** ⇒ 可追溯到「哪个文件的哪个版本的哪一次解析」。
   同一份账单重解析时版本号**递增**，旧结算单置为 SUPERSEDED 但**不删**（留痕）。
   ⇒ 幂等键因此用**部分唯一索引**（`WHERE status <> 'SUPERSEDED'`）而不是表级 UNIQUE ——
   表级会让「重新解析」永远做不成。
4. **平台结算报告自动同步不可用，归属模块 卷 02 同步。**
   全仓 grep 过：`backend/services/channel` **没有**任何结算报告 / 结算周期端点
   （`SyncController` 只有通用同步游标 / 批次 / 失败重放这类**同步设施**，它不产出平台结算账单）。
   ⇒ DB 词表保留 `PLATFORM_SYNC`，服务层拒绝用它建单并写明归属模块，能力声明里如实写
   「平台结算报告自动同步不可用，归属模块 卷 02 同步」。**绝不造一份「同步来的」假账单顶替它。**
   人工上传账单这条路径**是真的能用的**（CSV 按 RFC 4180 处理引号 + JSON，两级错误分层 + 幂等）。
5. **差额是真的算出来的，不是存下来的快照。**
   平台侧结算金额 vs 我方应收（同店铺、同结算周期、同币种、**只算已确认的**应收，按来源分组），
   差额 = 平台结算金额 − 我方应收未核销余额。
   ⚠️ **不做「金额相同即匹配」**（卷 12 硬约束）：收款侧**只**按
   `finance_receipt.settlement_no = 结算单号` 关联 ⇒ 12.2.1.1 放开那条 CHECK 之前这一侧恒为 0。
   12.3.2.1 自动对账任务与 13 利润未交付 ⇒ 只算差额，不实现匹配、不产出利润。
6. **上游的店铺是真的从 channel 读的。**
   `ChannelShopPort` 打 `GET /channel/shops`（2.3.1.1），转发**调用方自己的** bearer
   （租户由 channel 侧按已认证成员关系解析，隔离是两道）。取不到就**显式失败** 503，
   绝不返回空集合冒充「上游没有店铺」。跨服务**只走授权 HTTP API**，不直连对方库、不建跨库 FK / 视图。
7. **结算事实登记后不可改。**
   店铺/周期/币种/来源/原始文件版本/预计到账全部冻结（`guard_finance_settlement_frozen`），
   合法变化只有三种：登记到账、作废、被新版本取代；到账时间一旦登记**不可抹掉**。
   明细行 **append-only**（运行角色 UPDATE/DELETE 已收回）—— 账单是外部事实，
   改账单等于改写外部凭据，正确做法是重新解析建新单。
8. **时间不许静默偏 8 小时。**
   `expected_at` / `arrived_at` / `parsed_at` 全是 timestamptz，一律 OffsetDateTime + `?::timestamptz`；
   `nowUtc()` **截断到微秒**（PG 的 timestamptz 精度就是微秒，不截断则写回值与读回值差最后一位 ⇒ 断言会 flaky）。
   写时间的测试**断言写回的值逐位相等**（含 `+08:00` 偏移不被换掉）。
9. **结算周期配置是本模块自己的输入，不是上游的。**
   蓝图输入里写着「结算周期配置」⇒ 一家店一份（`UNIQUE(tenant_id, shop_id)`），
   预计到账时间 = 结算周期结束日 + 到账滞后天数（该日 00:00:00Z）。

## 关键 trade-off

| 决策点                                                     | 取舍                             | 理由                                                                                                                             |
| ---------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 汇总项与结算金额：子表 + 触发器 vs 单头七列 + 生成列        | **子表 + 触发器**                | 生成列不能跨表聚合（PG 限制）⇒ 只能触发器；换来的是「类别可扩展 + 每类别笔数 + 汇总项是蓝图点名的可查实体」 |
| 派生写入 vs 直接写入怎么区分                               | **`pg_trigger_depth()`**         | 直接写汇总项/结算金额在 DB 层拒掉（报错里直接写明「由派生维护」），服务层与直连 SQL 都绕不过               |
| 结算报告幂等键：表级 UNIQUE vs 部分唯一索引                 | **部分唯一索引**                 | 表级会让「同一份账单重新解析」永远做不成（旧单挡路）⇒ 只约束在册的那一张，被取代的旧单不占用这个键      |
| 结算金额列：普通列 + 守卫 vs 生成列                         | **普通列 + 守卫**                | 生成列引用不了子表；守卫保证「手填总额」进不来                                                                  |
| 收款侧差额怎么关联                                         | **只按 `settlement_no`**         | 卷 12 硬约束「不允许金额相同即匹配」；上游放开 CHECK 后这条读路径**自动**就有数据，不用改本模块          |
| 店铺主数据：本地冗余 vs 实时读 channel                       | **建单时读上游 + 冗余快照**       | 结算单要能独立可查（不能因为 channel 挂了就查不到历史结算）；快照在创建时从上游核验，不是手填              |
| 平台结算报告同步：造一条假同步 vs 留归属标记                 | **留归属标记**                   | 上游没有端点 ⇒ 假同步是编事实；人工上传路径真能用，所以能力是真的有，只是自动那一半没有               |
| 前端路由：`/finance/settlement` vs `/finance/settlements`   | **`/finance/settlement`**        | 首 token 与同批其它车道互不相同；`packages/ui/src/lib/task-pages.ts` 一字未碰（本页**未预登记** ⇒ 不触碰「implemented 必须等于真实路由页面是否存在」那条不变式） |
