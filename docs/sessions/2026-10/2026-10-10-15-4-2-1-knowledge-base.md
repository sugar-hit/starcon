### 2. 与 11.4.2.2 的边界：判定为「两个不同模块」，不复用

任务书给了一张对照表；读完两边迁移原文后**确认该判断成立**，并补上了任务书没给的一条理由。

| | 11.4.2.2（catalog V100，已交付） | 15.4.2.1（本车道，crm V99） |
|---|---|---|
| 服务 / 库 | catalog / starcon_catalog（8082） | **crm / starcon_crm（8086，本次新建）** |
| 命名空间 | `/catalog/kb` | `/crm/knowledge` |
| 页面 | `/aftersales/knowledge` | `/crm/knowledge` |
| 组织维度 | 平台规则版本 | **店铺 × 类目 × 语言**（三者全 NOT NULL） |
| 版本机制 | 平台政策条目的多版本 + 命中统计 | **半开生效区间 [from, to)** |
| 改版响应 | 规则被接替 → 自动生成 `kb_review_task` | 一条 `review-due` **查询**列出待复核条目 |

补上的关键理由：**读者不同**。11.4.2.2 的读者是处理客诉的售后客服（工单上下文），
15.4.2.1 的读者是应答**所有**买家消息的客服。
合并成一张表只能加一个 `source` 列把两套口径混在一张表里，
而两者的生效区间根本不同步 —— 「同一家店同一类目同一种语言，售后口径与客服口径分别是什么」
这个问题在合并后无法回答。

落地纪律：六张 `kb_*` 表**未改动一个字节**，端点**未进入** `/catalog/kb`。

### 4. 生效区间：逐字沿用 V23 / V25 / V95 的 R1–R5，不另立一套

先读了 V25（`bom_version`）与 V95（`customs_destination_version`）的迁移原文再动手。
沿用部分：半开区间 `[from, to)`、`tstzrange(from,to,'[)')` 判重叠、
**重叠一律拒绝不做自动裁决**、只有已发布版本参与判定、当前生效版本确定性查询、
已发布版本只能向前关闭到仍在未来的时刻。

四个触发器（CHECK 可被 `NOT VALID` 或迁移脚本绕过，触发器不行）：
`guard_crm_knowledge_version_published`（逐列不可变 + R5 向前关闭）、
`refuse_crm_knowledge_version_published_delete`、
`guard_crm_knowledge_version_interval`（区间重叠）、
`refuse_crm_knowledge_reference_mutation`（引用只追加）。

**三个组织维度为什么全 NOT NULL**（而不是「类目可空 = 全店通用」）：
一旦允许 `category_id` 为空，「这家店这个类目该答哪一条」就有**两个**答案
（一条全店通用 + 一条类目专属），而生效区间按档案分组判定，两条档案之间没有共同分组键，
重叠检查根本覆盖不到它们。「一处改、处处生效」请用版本接替，不要引入第二种归属。

### 5. 「平台改版 → 定位过期条目」落成一条真查询

判据：给定平台 P 与新政策生效时刻 T，返回

> **当前生效**那一版 `effective_from < T` **且** `effective_to IS NULL`（至今仍无接替版本）的条目

即「内容还停留在改版前的政策口径下，而且从来没人改过」。

「开放区间」是必要条件：已被接替的版本已退出历史舞台，**不是**过期内容，列出来只会让运营去复核一批早已不生效的答案。

**不用**「最后更新时间 > 改版时刻」这种更宽松的判据 —— 改备注/改标题会刷新 `updated_at`，
与答法正文是否按新政策重写毫无关系；用它会让只改过备注的条目冒充「已按新政策复核过」。
为此建了部分索引 `crm_knowledge_version_open_ended (tenant_id, effective_from, entry_id) WHERE status='PUBLISHED' AND effective_to IS NULL`。
判定口径原文（`criterion`）随响应返回，页面能自证它按什么查的。

### 6. 引用记录：真实落库，只追加

引用指向**具体版本**而不是档案 —— 15.1.1.2 发出的消息引用的是某一版答法，
档案后来出了 v2 也不能让那条历史消息看起来引用过 v2。
`referenced_by` 取服务端 `Access.userId()`，`referenced_at` 取服务端 `now()`，**都不接受客户端传值**。
只追加由 `refuse_crm_knowledge_reference_mutation`（BEFORE UPDATE OR DELETE）钉死：
删掉一条引用等于把「没人用过」这个答案**做出来**，而「多少条知识根本没人用」恰恰是运营最该先看到的数。
前端因此**刻意不提供删除引用入口**。

### 7. 踩到并修掉的三个真问题

**（a）DTO 与 11.4.2.2 完全同名，codegen 会互相覆盖。**
本模块 DTO 原名 `KnowledgeEntry` / `KnowledgeEntryDetail` / `KnowledgeVersion` /
`KnowledgeReference` / `KnowledgeScope` / `KnowledgeCapabilities`，
与 11.4.2.2 的 catalog kb **一字不差同名**。
而 `tools/codegen/catalog-contracts.py` 把五个服务的 schema **合并进同一个**
`packages/api-contracts/src/catalog.ts`，按字母序遍历、后写覆盖先写
—— 生成后 11.4.2.2 的类型被打掉，`catalog/knowledge-workspace.tsx` 报 30+ 个 TS 错误。
**修法：本模块全部 DTO 加 `Crm` 前缀**（`CrmKnowledgeEntry` / `CrmKnowledgeEntryDetail` / …）。
复验：11.4.2.2 的 `KnowledgeEntryDetail` 恢复原形、本模块并存，`pnpm typecheck` 全绿。

> 教训：**新增服务时 DTO 必须带服务前缀**，`catalog.ts` 是扁平的共享命名空间。

**（b）白名单正则里 `versions/{id}` 的动作后缀写成了可选。**
初版 `versions\/[0-9a-f-]+(?:\/(?:publish|close|references))?` 里的 `?` 让裸的
`crm/knowledge/versions/{id}` 也通过（后端根本没有这个端点），反向用例直接抓到（503 而非 404）。
修法：后缀改为必需。

**（c）白名单脚本第一版自己造假绿。**
第一版用「整条 entry 的正则」做匹配，结果**漏掉 3 / 6 条**（凡是在 `pattern:` 之后还带注释的 entry 全部匹配失败），
却照样打印成功；改成按 `prefix:` 切分后又踩了第二个坑 ——
「`pattern:` 之后第一个 `/.../` 」会匹配到注释行的 `//`，把 catalog 的 200 分支抽成 1 分支。
最终版改为**逐行扫描、跳过 `//` / `*` / 空白行**才取到真正的正则字面量。

**脚本自测（按任务书要求，先证明它会对已知正确的输入报错）**：
- 去掉某条 entry 的 `pattern:` → 脚本报 `FATAL: entries without a pattern literal: ['trade/']`，exit 2；
- 故意从 catalog 分支删掉一条 → 比较器报 `catalog/: 分支数 200 -> 199 (丢了 1 条)`，`SELFTEST PASS`。

## 关键 trade-off

- **不复用 kb_\***：宁可多一套表，也不把两个 bounded context 的口径混进一张表。
  代价是两个模块都要各自维护「知识」这一概念；收益是任一个单独演进都不影响另一个。
- **DTO 加 `Crm` 前缀**：牺牲一点可读性，换 11.4.2.2 的契约不被本车道打掉。
  这是被 codegen 的合并语义逼出来的，不是洁癖。
- **三个维度全 NOT NULL**：牺牲「全店通用一条」的省事写法，换「一个格子一个答案」的结构性保证。
- **`review-due` 用 SQL 而不是页面积累**：牺牲「改个备注就算复核过」的宽松，换不产生假绿。
