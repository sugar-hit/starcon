# 2026-10-07 · 3.9.1.2 SKU 合并

> 车道 `3.9.1.2`，分支 `feat/3-9-1-2`，基线 `integration/module-dev`（6bf8912）。
> 上游 3.9.1.1 重复 SKU 识别（V36 + DuplicateDetectionController）已在集成头。

## 决策摘要

**执行入口挂在候选，不挂在决定，也不接受手输一对 SKU。**
蓝图把执行合并写在 3.9.1.2、把「确认合并/保留决定」写在 3.9.1.1 的输出里。落地时
`SkuMergeService` 只读 `sku_duplicate_decision` 的 MERGE 决定，不重新判断「像不像」，
入口是候选 ID。手输两个 SKU 绕开决定登记，等于跳过「谁在什么时候凭什么判的合并」
这段可回溯链路。

**`expected_version` 是执行的判据，不是请求体字段。**
它读 3.9.1.1 登记决定那一刻快照的 `sku.version` 与此刻真实值比对，对不上就 409。
让客户端再传一遍等于多一个「传 0 就能跳过检查」的入口。并发保护改用
`update sku ... where version=<读取时的值>` 的行数断言 + V41 的 `UNIQUE(tenant_id,decision_id)`。

**引用策略落成一张表，不写成 if 分支。**
catalog 里有 29 张表带 `sku_id`。逐张 if 会让「这张表到底搬不搬」这个最重要的决定
淹没在代码流里，而它恰恰是审计时最需要一眼看清的东西。`SkuMergeRules.RefPolicy`
把 `{维度, 表, 指向 SKU 的列, 冲突键, 动作}` 写在一起，全量计数与执行迁移共用同一段
SQL 拼接 —— 「预演报 N 行、执行动 N 行」因此是结构上保证的。

**新增两类维度而不是只搬 V36 数过的那九类。**
V36 的九类是「合并合不合得动」的体检口径。执行时还必须搬 `sku_unit_conversion`
（活的换算表，合并后主记录少一个换算档会让 06 建采购单按错比例算数量）、
`sku_translation`、`bundle_sku`、`bom.output_sku_id` —— 漏掉任何一类都是真实数据损失。

**`sku_unit_conversion_snapshot` 刻意不搬。**
它与 `sku_unit_conversion` 只差一个词：前者是采购单/入库单的**行冻结快照**，
钉在 `document_ref+line_no` 上；后者是活的换算规则。搬走前者等于说
「当初那单用的换算比例是按合并后的 SKU 算的」—— 而它当初不是。

**不加 `'MERGED'` 状态枚举值。**
V1 的 `sku.status` 是四值域，3.1.1.3 的 `sku_status_event` 也按这四值记账。
加第五个值要同时改 CHECK、事件表与所有按状态过滤的下游，属于跨模块状态域扩张。
本模块要表达的是「它被合并了」而不是「它有第五种状态」：状态落 `INACTIVE`
（主记录自然不再被刊登/列表选中），合并事实由 `merged_into_sku_id` 表达。
SPU 侧对应 3.1.1.3 生命周期的终态 `DISCONTINUED`。

**合并链保持一层。**
两端任一已被合并就不再允许参与下一次归并。链一旦成环或多跳，
「当前有效归属」就不再唯一，而那是所有下游查询的前提。

## 关键 trade-off

| 决定                                    | 取舍                                                                                                                                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 冲突行**留在**被合并记录上，不删        | 主记录已有同值条码/包装/安全属性时，删掉被合并记录那一行等于让「这两条曾经撞过码」查无对证；代价是被合并记录上仍挂着引用，但它是保留的、可回查的                          |
| BOM / 套装组件**用量相加**              | 同一版本里同时挂着两条重复 SKU 时，「每 1 个成品需要这个组件多少」只能有一个答案，取和而不是二选一；这是本模块唯一会改数值的动作，测试按 BigDecimal 精确断言读回值        |
| 素材引用冲突**按去重删**                | 与其它维度相反：冲突行与主记录那条引用完全相同，删掉不丢任何信息                                                                                                          |
| `attribute_value` 跨 SPU **整维度拒迁** | 它的外键是 `(tenant_id,spu_id,sku_id) → sku`，硬改指会指向「主商品的 SKU + 源商品的属性定义」这样一个不存在的组合。宁可显式报 blocked，也不要造出一行改指后语义错乱的数据 |
| 跨 SPU 时源商品上**剩余的 SKU 不搬**    | 搬它们要逐条判断是不是同一个商品，而登记的决定只覆盖「这一对 SKU」。报告里显式报出这个数，而不是让运营以为整个源商品已经空了                                              |
| 加 `blocked` 独立列而不是从计数反推     | 反推（「有冲突且没搬动」）会把「这一维度全部撞了唯一约束」误报成「整维度被拒」，两者在页面上的处置完全不同                                                                |

## 踩到的坑（都写进注释了）

1. **V7 的 `sync_primary_barcode` 触发器会 `update sku set version=version+1`。**
   所以「登记决定之后再补条码」是一次真实改动，会让 `expected_version` 比对失败 ——
   那正是本模块该拦的东西。夹具按真实业务顺序排：先备齐引用，再登记决定。
2. **`bom_explosion_run` 的列叫 `output_sku_id`，不是 `sku_id`**；
   `bom` 同理。写死 `sku_id` 会让这两个维度**静默统计成 0** —— 报告上显示
   「这一类没有引用」而实际上有，比报错危险得多。
3. **`sku_duplicate_candidate` / `sku_duplicate_decision` 没有 `sku_id`**，
   它们记的是「这一对」（`left/right`、`primary/secondary`）。
4. **`?::timestamptz` 放在 values 的最后一个位置时 jOOQ 绑定会错位一格**
   （PG 报「cannot cast type uuid to timestamp」）。把 cast 放在中间位置即稳定。
5. **本仓库的 jOOQ 没有 `DSLContext.fetchCount(String, Object...)`**，
   用 `fetchOne(...).get(0, Integer.class)`（与 3.9.1.1 同一写法）。
6. **jOOQ 的 `get(String, Class)` 是泛型方法**，`cond ? null : row.get(c, UUID.class)`
   会把 null 那一支推成 Long；先取到有类型的局部变量再进构造器。
7. **api-proxy 的 `sku-merges` 段不能写成 `(?:\/(?:overview|by-candidate|by-sku)?(?:\/[0-9a-f-]+)?)?`**
   —— 那个形状要求 `/word/id`，于是裸 `/id` 匹配不上而 `by-candidate`（无 id）反而放行。
   正确写法是四个并列分支，其中 by-candidate / by-sku **必须**带 id 段。
8. **`StatCard` 不接 `hint`、`SectionCard` 的动作插槽叫 `extra`**（不叫 `actions`）。
