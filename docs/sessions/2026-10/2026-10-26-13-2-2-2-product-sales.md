# 2026-10-26: 13.2.2.2 SKU/SPU/Listing（reporting 服务，V389）

## 摘要

交付 **13.2.2.2 SKU/SPU/Listing**：按商品维度拆解销量 —— SKU / SPU / Listing 三层，
支持 SPU 汇总（多平台多 SKU 合并看）与变体销量分布，输出商品销量报表 + 层级钻取。

主责服务 `reporting`（卷 13 的唯一归属服务），迁移 **V389**，
路由 `/analytics/sales/products`。

## 开工前的依赖自检（10 分钟闸）

逐个端点核对了三条上游的**请求参数与响应字段形状**，结论是**三层链路齐备**：

| 层 | 上游端点 | 拿到的字段 |
| --- | --- | --- |
| SKU → SPU | `GET /catalog/skus`（3.1.2.1） | `id` / `code` / `spuId` / `spuCode` / `spuName` / `variantSignature` |
| Listing → SKU | `GET /channel/listings`（4.1.1.1） | `id` / `platformCode` / `shopCode` / `externalItemId` / `mappingStatus` / **`internalSkuIds`** |
| 订单与明细 | `GET /trade/sales-orders/list` + `/detail/{id}`（9.1.1.1） | 订单：`id` / `orderNo` / `currency` / `submittedAt`；明细：`skuCode` / `quantity` / `lineAmount` |

🔴 **两个被拦下来、没去猜的地方**：

1. **Listing 层拿不到的是「归属」，不是「层级」** —— channel 的 Listing **有**内部 SKU 挂载关系，
   但 trade 的订单明细**只带 SKU 码、不带平台商品 id** ⇒ 同一款内部 SKU 挂在多个 Listing 上时，
   它的销量**无法唯一归属**到某个 Listing。处理办法见下面「决策 3」。
2. **订单明细逐单取有硬上限**（既有 `ReportingTradePort.MAX_DETAIL_FETCHES = 50`）——
   销量与 SKU 下钻只存在于明细里，必须逐单取。触到上限**如实报「已截断」**，不悄悄少算。

## 决策 / 结论

1. **🔴 SPU 是跨平台经营的基本单位 ⇒ SPU 层真的合并，且合并口径由服务端算。**
   SPU 层的一行 = 名下**所有平台、所有 SKU** 的销量之和，不按平台拆；
   行上还写明「合并了 N 个 SKU × M 个平台 × K 个平台商品」。
   前端**绝不自己把 SKU 相加** —— 前端算一遍就会引入浮点误差，且界面会和服务端的数对不上。

2. **🔴 口径唯一：另起一张商品维度口径表，DB 触发器把「口径不成立」挡在数据层。**
   `reporting_product_metric_definition` 是商品维度的指标口径唯一表：
   CHECK 钉死「派生型必须写全分子分母 / 非派生型不许写」，触发器拒绝引用未登记的分子分母。
   6 个指标（3 个流量型 + 3 个派生型）只写引用不写公式，查询 SQL 里无任何硬编码公式。

3. **🔴 Listing 层的销量归属：可唯一归属才归，归不了就单列，绝不摊。**
   一款内部 SKU 只挂在一个 Listing 上 ⇒ 它的销量归到那个 Listing；
   挂在多个（或零个）⇒ **归不了**，这部分销量**不摊给任何 Listing**（摊给谁都是造假），
   单列成「无法唯一归属」并在能力声明里写清原因。
   ⇒ 用户看到的是「这个 Listing 的销量不完整 + 为什么」，不是「这个 Listing 没卖出去」。

4. **🔴 三层维度的口径靠三列扩展表达，而不是为每层各立一套指标码。**
   `numerator_dimension_type` / `denominator_dimension_type`（分子分母取自哪一层）
   + `currency_scope`（SAME 同币种 / ANY 允许跨币种合计）。
   变体销量占比是全模块唯一**跨层**口径（分子 SKU 层 / 分母 SPU 层）：
   不声明这两层，引擎会把「SPU 销量 ÷ SPU 销量」算成 100% —— 那是个**看起来对、其实没意义**的数；
   声明了分子层，该指标就**只在 SKU 层出现**（SPU 层干脆不列这一列，而不是报一个假指标）。

5. **🔴 绝不跨币种直接相加，但件数可以跨币种合计。**
   金额按币种分别报；**只有件数与单数**（与货币无关）给一个跨币种合计，
   它的币种显示为**空串**（= 与币种无关，不是「币种未知」）。
   DB 层 CHECK 钉死「`currency_aware = true ⇒ currency_scope = 'SAME'`」⇒
   这条红线在**数据层**就绕不过去。

6. **🔴 件数走 `quantity` 列（numeric(19,6)），金额走 `value` 列（numeric(24,4)）。**
   件数塞进 4 位小数会丢精度（trade 的订单行数量是 6 位小数）⇒ 引擎按指标的 `unit` 选列。

7. **另起五张表，不 ALTER 13.1.1.1 的任何一张表。**
   13.1.1.1 的 `reporting_metric_fact` 维度键是 uuid（shop_id）**没有商品维度**，
   `reporting_drilldown_fact` 的 `scope_type` 枚举只有 (COMPANY, LEGAL_ENTITY, SHOP) ——
   在 reporting 零 ALTER 既有表的纪律下，只能另起一组表（两边互不干扰）。

8. **只读跨服务调用**：转发调用方自己的 bearer、**不传租户号**，上游按已认证成员关系解析租户并强制 RLS。
   上游读不到一律 503（`ReportingUpstreamClient` 把故障翻成「读不到」而不是「没有数据」）。
   本模块**另起 `ReportingProductSalesPort`**（catalog SKU + channel Listing 两条新上游），
   **复用**既有的 `ReportingTradePort`（订单与明细它已经有了）——
   与 13.1.1.2 的 `ReportingStoreComparisonPort` 同一套路：**每个模块一个自己的端口**，
   不去改共享端口（并行车道会同时改它 ⇒ 合并冲突）。

## 关键 trade-off / 讨论

- **🔴 变体占比的分母跨层 ⇒ 引擎要能「沿父链向上找那一层」。**
  SKU 的父是 SPU（`reporting_product_dimension.parent_dimension_id`），
  所以「分子在 SKU 层、分母在 SPU 层」可以解析成「本行」与「本行的祖先」。
  找不到祖先（SPU 层算变体占比）⇒ **该指标在这一层干脆不出现**，而不是报「不可比」。

- **🔴 构成明细用「订单号 + 行序号」做幂等键。**
  同一张订单里同一款 SKU 出现两行时（不同规格 / 不同促销），只按订单号去重会把两行合并成一个数
  —— 那就丢了明细。行序号取自订单明细数组的下标（上游的 `OrderLineRow` 没有行号字段）。

- **🔴 下钻默认看「销量」那一组构成明细。**
  每个订单行同时落了「销量」与「成交金额」两条构成明细（度量不同）。
  不指定指标就返回两组 ⇒ 同一行订单出现两遍 —— 那是重复，不是信息。
  ⇒ 端点在没给 `metricCode` 时默认用 `PRODUCT_SALES_QUANTITY`，并在响应里说明看的是哪个指标。

- **🔴 事实行按「维度 + 指标 + 日 + 币种」聚合一行，而不是每个订单行一行。**
  订单数必须**按订单去重**（一张订单里同一款 SKU 出现两行只算一单）⇒ 内存里按
  (维度, 指标, 日, 币种) 聚合 + 订单号集合，订单数取集合大小。
  刷新时先**按窗口删干净再重写** —— 上游改了「SKU 挂在哪个 Listing 上」之后，
  陈旧的行留在表里会被一起求和 ⇒ 销量翻倍。投影可重建 ⇒ 按窗口重建是安全的。

- **🔴 时间字段按瞬间往返，不用 `Timestamp.valueOf(LocalDateTime)`。**
  构成明细带 `occurred_at timestamptz`（下单时刻），绑定用 `?::timestamptz` + `OffsetDateTime`。
  测试断言**写回的值**：夹具里 SO-3 的下单时刻是 `2026-10-02T01:00+08:00`，
  读回来必须是**同一个瞬间**（`2026-10-01T17:00Z`）—— 有人用 `Timestamp.valueOf` 就会静默偏 −28800s。

- **🔴 分桶日按所用时区，并把这个时区记进行里。**
  同一条 SO-3 在 UTC 下落在 10-01，在 `Asia/Shanghai` 下落在 10-02。
  事实行的 `timezone` 列记的是「算这个 bucket_date 时用的那个时区」——
  写死 `'UTC'` 会让「跨时区汇总必须显示所用时区」这条口径失真。

- **🔴 能力声明逐条写出「确实拿不到」的部分**（先例 13.4.2.2 的做法）：
  Listing 层归属边界 / 订单行没有平台与店铺维度 / SPU 自身没有平台维度 /
  Listing 的价格库存评分属 4.5.1.1 / 手工单与平台单两套口径 / 退货量不在本模块 /
  变体的进一步细分要读 3 商品的属性定义 / 订单明细 50 张上限。

- **假上游起的是真的 HTTP 服务**（catalog + channel + trade 三个路径各自一个 `HttpServer`），
  驱动**真实的拉取与投影路径** —— 端口写错路径或字段名会在这一层就暴露。
  ⚠️ 踩过的坑：夹具里的下单时刻带 `+08:00` 偏移，`Instant.parse` **只认 `Z` 形式** ⇒
  假上游抛异常 ⇒ 连接被掐断 ⇒ 客户端看到的是「上游不可达」而不是「这一单不在窗口里」。
  假上游的日期解析必须同时认得两种形式。

- **多租户测试的假上游按 bearer 分租户**（A 只给自己的 SKU、B 只给自己的 SKU）。
  否则「B 看不见 A」只能靠「B 什么都没有」证明，证明不了「B 只看得见自己的」。
  连接池固定 **1 条连接** —— 池大于 1 时「没串」可能只是碰巧换了条干净连接。

- **写权限必须在同一个 grant 里同时命中对应的 `.read`**，否则刷新端点直接 403。
  测试夹具漏了 `reporting.projection.read` 就撞上了这条。

- **api-proxy 只做纯新增**（一条独立的 `services[]` 元素、零删除、既有条目一字未改不重排），
  插入锚点选在**数组末尾**（同批其它车道锚在数组最前面那一段，相距 10000 行以上，
  并入时 git 能干净求并）。只放行 7 条真实路径，刻意不放行
  `reporting/product-sales/{uuid}`、`/breakdown`、`{uuid}/variants`。
  ⚠️ `apps/web/src/lib/api-proxy.ts` **整体本来就不是 prettier-clean 的**（其它车道留下的
  `pattern:` 折行漂移，共 6 处）—— **不能整文件重排**（会碰别人的行、且制造合并冲突），
  本车道只保证**自己那一段** prettier-clean。

- **台账只手工改 13.2.2.2 那一行**（该文件在 `.prettierignore` 里），
  其余行一律没动 ⇒ 并行车道不会被我改到。

## 后续待办

1. **Listing 层的销量归属要等上游补齐「订单 → 平台商品」的链路。**
   trade 的订单明细只带 SKU 码；一旦订单行带上平台商品 id（或平台单带 listing 引用），
   同一款 SKU 挂在多个 Listing 上的那部分销量就能**真的**分摊，
   刷新服务改一处即可，**不需要改表结构**。
2. **SPU 自身的平台维度仍不可得** —— catalog 只给 SKU → SPU 的归属，
   SPU 覆盖哪些平台是**间接**从 Listing 绑定表推出来的（且受归属边界限制）。
   若 catalog 后续提供 SPU 的平台清单，档案表多一列即可。
3. **变体的进一步细分要看 3 商品的属性定义** —— 本模块按 catalog 的 `variant_signature` 分组，
   同一签名内的更细规格（颜色 / 尺码）不再拆。当前上游没有面向本模块的只读端点。
4. **订单明细 50 张上限** —— 一次刷新最多取 50 张单的明细，触到上限报「已截断」。
   大租户需要更宽的窗口时，得等 trade 提供「按 SKU 聚合的销量」只读端点。
5. **退货量不在本模块** —— 「销量」是**成交**口径，不是净销量。
   退货是 13.4 利润分析（13.4.2.2 费用差异）的事。
6. **下游（6 补货 / 5 定价）尚未接入** —— 蓝图关系句点名的下游归各自模块；
   本模块的 SPU 汇总正是为它们准备的「跨平台经营的基本单位」。
