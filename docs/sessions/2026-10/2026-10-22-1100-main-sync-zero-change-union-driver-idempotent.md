# 2026-10-22 11:00：集成分支并入主分支的零变更复核与契约并合驱动幂等结论

## 摘要

本轮把 `integration/module-dev` 并入 `main`（Pull Request 形态），逐项取证后确认
**合入后 `main` 一个字节都不会变** ⇒ **本轮不开功能同步 PR**，交付本篇会话记录。

相对上一轮（09:30）的零变更复核，本轮多产出一条可复用结论：
**契约并合驱动（`contract-union`）在当前两侧内容上是一个稳定不动点** ——
它对「`main` 侧漂移后的字节」与「集成分支侧原始字节」求并的结果，
与 `main` 侧已有字节**逐字节相同**。这解释了为什么零变更轮次能稳定收敛，
也意味着**后续轮次不必再对契约文件做人工裁决**。

## 决策 / 结论

### 1. 零变更判据仍是落地树哈希，本轮实测成立

- 树差异：37 个文件，`+137636 / −143046`；`git rev-list --left-right --count` 报 30 / 464。
  提交数是虚的（`main` 是 squash 合入的），文件数也是虚的（双向差异）。
- **解完冲突后**的落地树 = `eca743b45d32a30ddc228c46e67d1dca65d66d99`，
  与 `git rev-parse upstream/main^{tree}` **完全相同**；
  `git diff upstream/main --stat` 为空，工作区 `git status --porcelain` 为空。
- ⚠️ **`git diff --quiet` 的「有新增内容」是误导**：它只回答「两侧字节是否相同」，
  不回答「合入后 `main` 会不会变」。本轮 37 个文件里，
  **「集成分支有、`main` 没有」的新增文件数 = 0**，
  全部差异是「`main` 有、集成分支没有」（历史会话记录、进度看板工具产物）
  或「两侧都有但字节不同」（契约文件、协议文件、`.gitignore`）。

### 2. 契约并合驱动是不动点，这是本轮的新结论

上一轮已证明契约文件的字节差异**是纯序列化漂移、语义等价**。本轮再进一步，
直接检验驱动本身的幂等性：

| 检验项                        | 方法                                                   | 结果                                  |
| ----------------------------- | ------------------------------------------------------ | ------------------------------------- |
| 驱动求并结果 vs `main` 侧字节 | 以真实三方输入跑驱动，产物与 `main` 侧逐字节比对       | **完全相同**（`channel.ts` 校验通过） |
| 落地树内契约 blob vs `main`   | `git rev-parse :<file>` vs `git rev-parse main:<file>` | 同一 blob                             |
| 驱动是否报冲突键              | 检查驱动输出中的 `CONFLICT_KEYS`                       | 未出现                                |
| 驱动是否走行级兜底            | 检查驱动输出中的「走了行级兜底并集」                   | 未出现                                |

⇒ **契约文件在本轮不需要人工裁决**。上一轮结论「契约文件的唯一裁判是语义等价」仍然成立，
本轮补上了更强的一层：**语义等价 + 驱动幂等 ⇒ 驱动输出必然落在 `main` 侧既有字节上**，
于是「驱动跑过」与「落地树不变」是同一件事的两种说法。

⚠️ 判据的适用范围：以上结论建立在**两侧契约键集合完全相同**的前提下。
若集成分支新增了键（新的接口路径 / 新的类型名），驱动会正常求并并产生真实增量，
届时落地树必然不同于 `main` 树 —— 那就是真的「有新增内容」，应当正常开 PR。

### 3. 协议文件的冲突取 `main` 侧，零丢失（与上一轮一致）

该文件是版本化的执行协议，`main` 侧被修正过、集成侧没有这些修正 ⇒ 典型线性演进。
用行级集合差集确认（两侧各自归一化后 `sort -u` 再 `comm`）：

| 维度           | `main` 侧 | 集成侧 |
| -------------- | --------- | ------ |
| 去重后行数     | 501       | 381    |
| **该侧独有行** | **124**   | **4**  |

集成侧独有的 **4 行**逐条看过，**全部是旧措辞**（第 3 节那句 echo 的旧写法、
3.1 决策表里「没有新内容 / 有新增内容」的两行、以及一行表格分隔线），
在 `main` 侧都存在对应的新版形态 ⇒ **取 `main` 侧零丢失**。

### 4. 集成分支侧没有新提交可合

集成分支 HEAD（08:22）**早于** `main` 最后一次内容 squash（09:03），
⇒ 集成分支自 `main` 上次同步以来**没有新增交付**。
`main` 此后的三个提交（09:19 / 09:31 / 09:58）都只是本任务自己的会话记录与协议修正。

### 5. 冲突面仍然只有 1 个文件

本轮实测：冲突文件 = `tools/module-progress/MAIN_MERGE_CRON_PROMPT.md`（唯一）。
`apps/web/src/lib/api-proxy.ts` 与 backlog 文件两侧已完全一致，不再进入冲突面。
契约文件全部由并合驱动自动求和，未留冲突。

### 6. 闸工具的「可以合并」不能单独作为放行依据，本轮差点漏掉一个新失败

闸工具对代码风格检查、安全审计、浏览器端到端用例这三个作业**只能比对作业粒度**
（它自己也标注了「明细不可比的作业」），因此
**它报「可以合并」时，并不代表作业内部没有多出失败**。

本轮第一次流水线跑完后，闸工具结论是「可以合并，新增失败作业：无，新增失败用例：无」，
但**代码风格检查的失败文件数是 601，比基线多 1** ——
多出来的正是本轮自己新增的那篇会话记录（它没有被格式化工具判为合规）。

补做的明细比对（三项都必须做，缺一不可）：

| 作业             | 比对方法                                       | 结果                                             |
| ---------------- | ---------------------------------------------- | ------------------------------------------------ |
| 代码风格检查     | 比对失败**文件集合**，不只比数量               | 首次跑出 601 vs 基线 600，差集就是本轮新增文件   |
| 安全审计         | 比对漏洞数量与严重度分布，并核对依赖锁文件字节 | 两侧均为 10 项、严重度分布一致，锁文件 blob 相同 |
| 浏览器端到端用例 | 比对异常类型集合与根因链路                     | 两侧集合与根因链路完全一致                       |

⇒ 处置：把本轮新增文件用格式化工具修好，改写提交并强推，**等新的流水线跑完**后再判一次。
新的这一轮代码风格检查回到 **600 个文件**，与基线持平，本轮新增文件已不在失败列表里。

⚠️ **判「持平」不能只看作业粒度** ——
一个在 PR 侧和基线侧都失败的作业会被报成「持平」，
哪怕 PR 往这个作业里新增了一个失败文件，闸工具也完全看不见。
