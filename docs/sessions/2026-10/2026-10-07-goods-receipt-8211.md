## 关键 trade-off

- **入账用 V1 已有的 `kind='RECEIPT'`，不新增 kind。**
  V1 的 `inventory_transaction.kind` CHECK 里本来就有 `'RECEIPT'` 且此前无人写入，是留好的空位。
  加新 kind 要改 V1 那条 CHECK 约束面 —— 那是 7.1.2.1 台账、7.1.1.1 总览等一堆既有模块共同依赖的表，
  一条 CHECK 变更会让并行车道上所有既有回归一起冒烟。用既有 kind 是零迁移风险的唯一选项，也确实语义正确。
- **本迁移只插不改库存表。** 不动 `inventory_entry` / `stock_bucket` / `inventory_balance` 的任何列、约束或触发器，
  所以**不存在跨车道 DDL 回归面**（brief 第 8 条点名的风险）。写入一律带符号增量
  （`on_hand += qty`），不是覆盖式写回 —— 覆盖式会把收货期间并行发生的出库 / 预占 / 盘点调整整段抹掉。
- **拒收量不写分录、不进库存。** 它从没进过 `inventory_balance`，所以 8.2.1.2 接手的是索赔与改判，
  而不是「把它从库存里删掉」。
- **全单拒收时不开 `RECEIPT` 事务。** 一条没有任何 `inventory_entry` 的 `inventory_transaction`
  会让台账出现一笔查无下文的空交易，而 `CHECK(on_hand_delta<>0)` 又保证 entry 侧无法作陪。
  那比不记更糟：它让「这批完全没入库」看起来像是记了账。
- **超收必须留痕由 DB 钉死**（延迟约束触发器 `guard_receipt_line_overage`）：
  实收 + 拒收 > 预期 ⟹ 必须存在一条 `OVER_RECEIPT` 差异记录。少收与拒收天然留痕，超收不钉死就会变成凭空多出来的货。

## 踩过的坑

1. `inventory_lot` 的列是 `lot_code` / `expires_on`（不是 `code` / `expiry_date`），且 `sku_id NOT NULL`。
2. 夹具建 `IN_TRANSIT` 状态的调拨单时，V61 的 `guard_transfer_order_state` 要求同时带 `confirmed_at` 与 `shipped_at`；
   且 `guard_transfer_line_conservation` 要求一条 `IN_TRANSIT` 在途腿存在，否则夹具自己就对不上账。
3. `INSERT ... SELECT ?,?,(select nextval(...)::text ...)` 会让 PG 报
   `INSERT has more target columns than expressions` —— 完全指不到真因。改成序号与日期分两步取（与 7.5.1.1 同纪律）。
4. `exactOptionalPropertyTypes` 下不能写 `warehouseId: undefined`，只能 `delete` 键。
5. `StatCard` 没有 `hint` prop，是 `comparisonLabel`；`Modal` 用 `open` + `onOpenChange` 而不是 `onClose`。
6. `InventoryLedgerRow` 没有 `id` / `skuCode`，主键是 `transactionId`。
7. `deriveStatus` 判「是不是草稿」必须用**实收笔数**而不是实收量 —— 整单拒收时实收量是 0，
   但那确实是一次真实到货动作；用实收量判会让单据退回草稿，而 `guard_receipt_event_state` 明确禁止。
