# 2026-10-22: 集成分支并入主分支（契约并合不动点 + 格式闸陷阱）

## 摘要

「集成分支 `integration/module-dev` → 主分支 `main`」同步任务的第 27 轮。

本轮**功能增量为零**（两侧台账 blob 逐字节相同，摘要工具报「本次没有新的功能交付或推进」），
但树差异非空：集成分支侧多了 3 份文档记录（2 份同步排查记录 + 1 份待办条目）。
真实合并形态为**真合并有冲突**，冲突面只有 1 个文件（协议文件本身）。

本轮有两处**可复用的取证经验**，已在下方单列：
一是「从集成分支带过来的 `.md` 文件必须先过格式校验，否则会静默抬高格式闸的失败文件数」；
二是「闸工具只比作业粒度，必须补失败文件集合 / 审计分布 / 根因链的明细比较」。

## 决策 / 结论

1. **功能增量判定用三条独立证据**，不看提交数、不看树差异空不空：

   | 证据                 | 本轮结果                                                                               |
   | -------------------- | -------------------------------------------------------------------------------------- |
   | 台账 blob 逐字节相同 | `9b715163…` 两侧一致 ⇒ 已交付 316 / 进行中 0 / 未开发 149                              |
   | 摘要工具             | 「本次没有新的功能交付或推进」                                                         |
   | 源/目标代码树无差异  | `backend/`、`apps/` 一字未改，只有 `docs/`、`tools/`、`packages/api-contracts/` 有差异 |

2. **冲突面只有协议文件一个，且是「main 侧更新」的线性演进**（不是真分叉）。
   判定用**归一化行级双向差集**（保留换行、只压行内空白）：

   | 侧     | 行数 | 独有行数 |
   | ------ | ---- | -------- |
   | base   | 349  | —        |
   | `main` | 808  | 135      |
   | 集成侧 | 621  | 4        |

   集成侧仅有的 4 行**逐条都是被 `main` 新版措辞替换掉的旧行**
   （旧判据「无新内容 / 有新增内容」被新判据「落地树 == / != `main` 树」替换，外加旧表格列宽）。
   ⇒ 取 `main` 侧**零丢失**，不是「无脑求并」。

3. **契约并合驱动确认是稳定不动点**：用真实三方输入（base / `main` 侧字节 / 集成分支侧字节）
   跑驱动，**沉默即按键求并成功**，产物与 `main` 侧已有的字节**逐字节相同**。
   ⇒ 契约文件的字节差异是纯序列化漂移，**不是**新交付；台账求并后行数恒为 **465**、模块 ID 无重复。

4. ⚠️ **格式闸陷阱（本轮实测踩中，已在推 PR 前修掉）**：
   `prettier --check` 覆盖 `**/*.{ts,tsx,js,jsx,json,md,yaml,yml}`，
   而 `.prettierignore` **只**排除了 `packages/api-contracts/`、`packages/sdk/` 与台账文件
   ⇒ **新进来的 `.md` 必须自己满足格式规范**。

   本轮从集成分支带过来的 3 个 `.md` **全部不合规**，直接推上去会让格式闸的失败文件数
   从基线 **619 变成 622**，把一个「持平」轮次变成「新增失败」的假阻塞。
   修法：`prettier --write` → `git commit --amend` → 强推 → **等新的 run 跑完**再判闸。

5. ⚠️ **闸工具只比作业粒度，必须补明细比较**。本轮闸工具报「结论：可以合并」，
   但同时点名 3 个作业「明细不可比」。补做明细比较后**四项全部逐条持平**：

   | 作业                             | 基线（`main` run `39728333099`）                             | PR 侧（run `39729232476`）                 | 判定 |
   | -------------------------------- | ------------------------------------------------------------ | ------------------------------------------ | ---- |
   | Lint                             | 619 个失败文件                                               | 619 个失败文件，双向差集**均为空**         | 持平 |
   | Security Scan                    | 10 条（1 low / 7 moderate / 2 high）                         | 同上；`pnpm-lock.yaml` blob 两侧逐字节相同 | 持平 |
   | Java 21 & PostgreSQL Integration | `ApprovalRecordIntegrationTest` 1 例失败（9/270 跑，1 失败） | 同测试类、同测试方法、同计数               | 持平 |
   | Catalog Browser & Contract Tests | `AccessDeniedException` → `BeanCreationException` 链 ×2      | 同根因链 ×2                                | 持平 |

   ⇒ 「闸工具说可以合」**不等于**可以合，必须补这一层。

6. ⚠️ **基线 run 必须在跑完时取**：`main` 的最近一次 run 在本轮判闸时**仍是 `in_progress`**，
   闸工具不检查这一点 ⇒ 未出结论的作业会被读成「基线没有失败」⇒ PR 侧同样的失败被算成新增失败
   ⇒ **假阻塞**。本轮等基线 run 跑完（结论 `failure`）后才取闸。

7. ⚠️ **`gh pr merge --delete-branch` 在本地分支被 worktree 占用时会漏删远端分支**：
   合并本身**成功**，但远端 `chore/sync-module-dev` 残留 ⇒ 收尾需补 `git push upstream --delete`。

8. **本轮合并净效果**：真合并（squash），相对 `main` 只落 **3 个文档文件**，
   契约与台账字节不变，业务代码零改动。

## 关键 trade-off / 讨论

1. **冲突解决取「一边」还是「求并」**：协议文件的 4 个冲突区，`main` 侧全部是集成侧的**超集**
   （多出整节「落地树哈希」判定、新版表格、新版并发提示、闸工具基线提示）。
   求并会把 `main` 的旧措辞重新塞回去，制造「该被替换的旧内容又活了」的状态
   ⇒ 取 `main` 侧，且**带证据**（归一化行级双向差集 + 逐条核对 4 行独有行）。

2. **要不要为纯文档记录单开一个 PR**：功能增量为零，但树差异非空 ⇒ 按协议仍该合。
   本轮把同步记录与待办条目一次带进 `main`，未单独为「零功能变更」再开一次 PR
   —— 避免同一轮内出现两个内容高度重叠的 PR。

3. **本地全量 L2 要不要跑**：冲突解法只动了一个 Markdown 协议文件，
   **未触碰后端业务代码与迁移脚本** ⇒ 不触发「必须本地跑全量」的条件，
   定向验证（静态预检 / 台账完整性 / 台账同步自检）已足够，全量闸交给 CI。

## 后续待办

1. **集成分支侧新增 `.md` 必须在进入集成分支前过格式校验**，
   否则每一轮同步都会抬高格式闸的失败文件数 ⇒ 建议在流水线侧加一道 `prettier --check`。
2. **冲突面三处仍未收敛**（本轮反向同步任务已连续三轮记录）：
   接口放行规则、契约漂移待办、协议文件三处被两侧各自改写，
   `origin/main` 不推进时冲突面稳定同墙。收敛点在内容侧，不在同步任务侧。
3. **待办条目 `docs/backlog/2026-10-22-merge-abort-fails-on-merge-union-ledger-file.md`**
   （P0）：并合驱动改写台账后 `git merge --abort` 退出码 128 且 `MERGE_HEAD` 残留堵死流水线，
   待用户拍板改协议还是改驱动。
