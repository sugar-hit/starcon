⚠️ **教训（可复用，且与 round 107 已记过的那条同源）**：
`lane.mjs status` 的「已交付数」与 `sync.mjs` 的输出**都读本地台账**。

判定「本地是不是落后」的最小充分命令仍然是：

```bash

git rev-list --left-right --count upstream/integration/module-dev...HEAD   # 期望 0 0
```

**本轮开工第一件事就该跑这条**，而不是先信 `sync.mjs` 的数字。

## 四、本轮为什么零派发 / 零回收 / 不跑 L2

**不是**闸门拦截 —— 本机这套的闸门全绿（温度无降频、PG 容器 0、load 3.58/4.33/4.69、
running 0 / 配额 6）。真正的理由是**归属权**：

- 本机的两个 cron 任务与真正在跑的那套**指向同一个 GitHub 远端、同样的车道分支名、
  同样的 `feat/<id>` 命名空间**。本机若照常派发，会在同一条远端分支上**双写**：
  撞 Flyway 版本号、撞 `lanes.json`、以及 push 被 non-fast-forward 拒。
  协议对此的取舍写得很清楚：「**宁可挡住一轮，也不能双派发**」。
- 08:00 那一格已经由**真正在跑的那套**占位（round 128 于 06:20 记明「2 条 ready 车道留给下一轮」，
  下一格 07:00/08:00 会回收它们）。

⇒ 本会话的定位是**取证与修复**，不是第 N 个调度者。**不取闸、不 `plan`、不派发、
不 `merge-ready`、不跑 L2**（L2 是发热高峰，且本机检出在修复前还是陈旧的）。
