## 决策摘要

### 1. 上一 worker 的代码**编译不过** —— 接手第一件事是让它能编译

`.worktrees/4.1.2.1/backend` 里 `./mvnw -pl services/channel -am compile` 直接红：

| # | 症状 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | `MappingCapabilityDimension` 构造器参数不匹配 | `capabilities()` 里 `mapping_version` 维度少传一个参数（6 个字段的 record 只给了 5 个） | 补 `ownerModule=""` |
| 2 | `LinkedHashSet` 赋给 `List<String>` 不兼容 | `codeTokens` / `barcodeValues` 声明类型写成了 `List` | 声明改成 `Set<String>` |
| 3 | `RestClient.uri(...)` 找不到重载 | 端口用了 `UnaryOperator<UriBuilder>`，Spring 只有 `Function<UriBuilder, URI>` | 换成 `Function<…>` |

**结论**：上一 worker 写完代码**一次都没编译过**。这批文件的**设计**（模型 / 服务 / 迁移的骨架与蓝图逐条对应、注释密度与本仓风格一致）是可用的，所以**不推倒重来**，而是逐个修到能编译、能跑、能被测试钉住。

### 2. 迁移 V176 里有一个**别名写错**，会让整个 channel 服务起不来

`data_scope` 策略（`listing_mapping_version` 那条）写的是：

```sql
EXISTS(SELECT 1 FROM listing m JOIN listing l ON l.tenant_id=m.tenant_id AND l.id=m.listing_id …)
```

`m` 指的是 `listing`，而 `m.listing_id` 这一列**不存在** ⇒ Flyway 直接失败：

```
SQL State: 42703  Message: ERROR: column m.listing_id does not exist
```

改成 `FROM listing_mapping m JOIN listing l …` 即可。**教训**：RLS 策略里的别名不是笔误级的小事 —— 它让整个服务的上下文加载失败，表现为「所有 channel 用例一起红」，很容易被误判成环境问题。

### 3. 🔴 表级 `UNIQUE(tenant_id, listing_variant_id)` 让「解除后重新建立映射」永远写不进去

原设计的语义是「解除 = 置 `status='REMOVED'`，行留着当历史」。但表级唯一约束**不区分 status**，被解除的那行会一直占着 `(tenant_id, listing_variant_id)` ⇒ 变体一旦被解除，**再也无法映射**（插入撞唯一约束），而重新映射是运营的日常动作。

处置：表级 `UNIQUE` 换成**部分唯一索引**

```sql
CREATE UNIQUE INDEX listing_mapping_active_variant
  ON listing_mapping(tenant_id, listing_variant_id) WHERE status='ACTIVE';
```

它精确表达「一个平台变体**同时**只能有一条生效映射」，而历史行可以并列。

### 4. 🔴 基数相关的 CHECK 无条件生效 ⇒ **解除一套装映射必然写不进去**

`CHECK((relation_type='ONE_TO_MANY') = (mapping_status='BUNDLE'))` 这类约束假定「基数 ⇔ 状态」恒成立。但解除映射时 `mapping_status` 变成 `UNMAPPED`、`relation_type` 仍是 `ONE_TO_MANY`（它如实记录「这条曾经是什么」）⇒ 约束恒假 ⇒ **解除动作直接撞约束**。

处置：把基数相关的三条 CHECK 与守卫触发器的对应分支**限定在 `status='ACTIVE'`**。语义上也更对：**已解除的行没有「现在的映射」，只有历史**。

### 5. 详情端点不能走列表分页

原 `load()` 是「取第一页 200 条 → 在内存里找那一条」⇒ 映射条数超过 200 时，一条**完全合法**的映射会因为「排在第 201 位」而答 422。抽出 `MAPPING_FROM` / `MAPPING_COLUMNS` 常量，列表与详情共用同一条 SQL，详情直接 `and m.id = ?::uuid`。

### 6. 乐观锁用了 `Integer !=`（引用比较）

`current != request.expectedVersionNo()` 比较的是 `Integer` 引用。版本号 ≤ 127 时落在 Integer 缓存里、碰巧能工作，**超过 127 就把每一次正常请求都判成冲突**。改成 `equals`。

### 7. 补生效时间早于当前版本 ⇒ 500（撞部分唯一索引）

`effectiveFrom` 早于当前版本的 `effective_from` 时，「关闭上一版」的 UPDATE 匹配不到任何行（旧版闭不掉），随后的 INSERT 就撞上「至多一个当前生效版本」的部分唯一索引 ⇒ 用户看到一条看不懂的 500。改成 422 并说清楚：「补生效只能落在当前版本之后」。

### 8. 确认候选时**只写版本不更新映射行** ⇒ 两个来源给出两个 SKU

候选确认走的是 `appendVersion`（写 `listing_mapping_version`），但**没有**更新 `listing_mapping` 行。变体已有映射时，`listing_mapping.internal_sku_id` 仍指旧 SKU，而当前生效版本指新 SKU ⇒ **列表读映射行、订单解析读版本，两个来源给出不同答案**。改成同步更新映射行（改动本身留痕在版本历史里，`changeSource=BATCH_CONFIRMED`）。

### 9. 候选规则里 `row.code()` 为 null ⇒ NPE，一批推荐全毁

catalog 返回的脏行（code 为 null）会让 `row.code().equals(token)` 抛 NPE，整批候选直接失败。改成 null-safe。

## 关键 trade-off

- **候选表与映射表物理分离**（蓝图「标题相似度推荐但需人工确认」）：`listing_mapping_candidate` 与 `listing_mapping` 是两张表，候选在人工 CONFIRMED 之前**一个字节的映射行都不写**；DB CHECK 再钉一道 `rule<>'TITLE_SIMILARITY' OR requires_confirmation`。否决走另一条路（只记 `REJECTED`），平台变体保持未映射 ⇒ 订单行继续进待映射。
- **`/resolve` 只有两态**：`RESOLVED` / `PENDING_MAPPING`，**没有第三种「疑似匹配」**。加一个 `guessed` 字段就已经在给「猜」开门了 —— 哪怕候选表里躺着 1.0 分的相似度候选，没经人工确认就不是映射（测试里专门钉了这一条）。
- **候选集只来自 catalog 授权 HTTP API**（`GET /catalog/skus`），转发的是**调用方自己的 bearer** ⇒ 租户隔离是**两道**（channel 侧 RLS + catalog 侧 RLS），不是「本服务替对方决定租户」。catalog 读不到时**显式 503**，不返回空集合冒充「这个租户一个 SKU 都没有」。
- **标题相似度由 PostgreSQL `pg_trgm similarity()` 真算**，分数可在库里复算（测试直接拿库里的 `similarity()` 值与响应里的 `score` 对比）。前端**不把分数换算成百分比**再四舍五入 —— 那会把「当时算出来的那个数」变成另一个数，复核时对不上账。
- **候选行里的 code/name 是「推荐当时的展示快照」**，不参与匹配计算（匹配永远重查 catalog）。这样「快照过期」最坏只是显示旧值，**不会让匹配结果随时间漂移**。
- **未交付段不冒充**：①「按版本回溯受影响订单」（4.1.2.2）需要 09 订单的真实来源，本仓没有 ⇒ `affected_orders` 维度 `available=false` + ownerModule + 影响，**不返回空数组**；②「未映射清单回流 02 映射缺失队列」（2.4.2.3）未交付 ⇒ 端点返回 `backflowDelivered=false` + 说明，**清单本身给全**；③ 套装组件逐条明细归 4.1.2.3 ⇒ **不建组件表**（那会抢下一个模块的写入所有权）；④ 手工填的 `internalSkuId` **没有跨服务存在性强校验**（跨服务不建 FK），这条缺口在 capabilities 里显式说出来。
- **分支基线前移到当前集成头**：接手时集成头在我工作期间合入了 4.1.1.2（`V175`）与 4.2.1.2（`V177`），而 `api-proxy.ts` 的插入锚点附近**已经被别人占了三个位置**。不前移的话，我这条车道并入时会在同一处撞冲突 ⇒ 接手后第一件事是 `git merge --ff-only integration/module-dev`（本车道尚无 commit，前移是纯快进），再重新导出契约、重新生成，**并入时的 diff 相对新集成头是干净的**。
