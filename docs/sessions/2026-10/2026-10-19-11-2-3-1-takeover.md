# 11.2.3.1 质检与判定 — 接管会话

- **日期**：2026-10-19
- **车道**：`11.2.3.1`，分支 `feat/11-2-3-1`，worktree `.worktrees/11.2.3.1`
- **性质**：**接管**（上一轮调度会话 09:25:55 因 Token Plan 用量上限暴毙，worker 被中途掐断）

## 决策摘要

1. **上一个 worker 的 6 个文件整体保留，逐个评审后只改了两处真缺陷**，没有推倒重来。
   迁移 V179（1069 行）、三件套 Java（3134 行）、两个测试类（1450 行）质量明显高于平均：
   硬规则写在 DB 触发器里而不是只写在服务层、残值公式可人手算复核、
   跨表一致性由触发器在写入时刻真查（刻意不加 FK 以免产生跨车道 DDL 依赖），
   这些判断全部**直接采用**。

2. **修掉上一个 worker 留下的 L1 红**（它暴毙前没来得及看到结果）：
   `连接池归还后不串租户` 报 `质检单不存在或不属于当前租户：null`。
   病因在测试夹具：`seed()` **刻意不开质检单**（待检队列断言要的是「还没开单」的那批货），
   于是 `Fixture.inspectionId` 恒为 `null`；而那个用例把刚用 `open(...)` 开出来的
   `ia` / `ib` 丢在一边，转头去读 `fa.inspectionId`。**不是生产缺陷**。
   处理：5 处引用改用 `ia` / `ib`，并把 record 里那个恒 `null` 的字段**删掉** ——
   留着一个恒 null 的字段只会被再次误用，而症状（报 null id）离病因很远。

3. **发现并修掉一个会波及已交付模块的契约撞名（本车道最值得记的一条）**：
   `FulfillmentQualityModels` 里 9.x 已交付的 `QualityEventRow`（字段
   `seq/kind/summary/orderId/alertId`）与本模块留痕 record **同名**。
   两个 record 同在 `com.starcon.trade` 一个包里，**Java 侧互不冲突**，
   但 OpenAPI 契约**按简单名拍平**，codegen 让后者覆盖前者**且不报冲突** ——
   `fulfillment-quality-workspace.tsx` 当场编译失败。
   上一个 worker 只核过与 `ReturnReceipt*` 零重叠，漏了这条。
   处理：本模块留痕类型改名 **`ReturnQualityEventRow`**，沿用该文件既有的
   `ReturnQuality*` 前缀避让约定。**已交付模块的类型名不能由新车道重定义。**

4. **契约撞名的通用判据固化下来**：不是比「新类型名 vs 旧类型名」有没有重名
   （那是 888 个存量名字的交集，没信号），而是看
   `git diff` 里 **`^-export type` 的删除行** —— 那是「某个既有定义被改写」的
   唯一直接证据。本次该列表为空，即零既有定义被动过。

## 关键 trade-off

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 继承代码 vs 重写 | **保留 + 定点修** | 重写 5653 行已验证代码的期望收益远低于「把好代码改坏」的风险 |
| 类目真值 | **租户自维护映射表**，不跨服务读 catalog | AGENTS.md 模块边界纪律禁止跨服务 SQL / 视图 / FK |
| 残值口径 | **公式算 + DB 触发器重算比对**，传输层无残值字段 | 残值是财务数据；可填的金额等于把损耗口径交给每个调用方自己编 |
| 判定规则落点 | **服务层 + DB 触发器各判一次** | 只判一次的话，绕过服务层直连 SQL 就能把「缺配件」判成可再销售 |
| 模板停用 | **POST `/retire` 而不是 DELETE** | 停用是口径变更；真删掉会让「这张单当初按什么口径判的」永远答不出来 |
| L1 收窄 | 只跑 `ReturnQuality*` | 全量是调度器在集成头上每批一次的事 |
| codegen 带出的 channel 漂移 | **revert** | 不是本车道的文件，基线有端点没重生成契约属存量漂移 |
