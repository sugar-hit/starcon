## 摘要

10.4.1.2 的集成测试 `InTransitTrackingIntegrationTest` 里，`节点_时间往返` 用例把「改期后的新 ETA」
写死成绝对时刻 `2026-12-01T08:00+08:00`；而同一张跟踪记录里当前存着的 ETA 是 `eta(ETA_ONT)`
（= `eta(40)`），它**跟着墙钟的小时数走**。于是当 UTC+8 墙钟小时数 ≥ 08 时，写死的新 ETA
**早于**当前 ETA，被领域规则「新的预计到港不许早于当前 ETA」当场拒掉。

本轮把新 ETA 改为**与记录里实际存着的当前 ETA 同源推导**（从跟踪行读回 `effectiveEta()` 再 +1 天），
并注入**可钉死的测试时钟**、新增一条**永久回归用例**把 07 / 09 / 23 三个小时基准各跑一遍
⇒ 墙钟无关这件事从此是**确定性、可复现**的，而不是「等下一个 09 点再炸一次」。

**只改测试**：领域规则、DB 约束、迁移、服务代码、前端、契约**一行未动**。

---

## 决策 / 结论

### 1. 根因：断言的一边来自 `now()`，另一边是写死的绝对时刻

链路（逐段核实）：

| 段                            | 事实                                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| 夹具 `eta(int daysFromNow)`   | `OffsetDateTime.now(+08:00).plusDays(n)`，**只截断分/秒/纳秒 ⇒ 保留当前小时数**                  |
| `shipmentReq()`               | 用 `eta(etaDays)` 填 `expectedArriveAt`                                                          |
| 建跟踪（服务层 + DB 触发器）  | `expected_arrive_at` 被抄进 `original_eta`（触发器 `guard_first_mile_tracking_shipment` 同逻辑） |
| 领域规则比较用的 `currentEta` | `revised_eta ?? original_eta`                                                                    |
| `ETA_ONT`                     | `40` ⇒ 基线 ETA = `2026-12-01T{墙钟小时数}:00+08:00`                                             |
| 写死的新 ETA                  | `2026-12-01T08:00+08:00`                                                                         |

⇒ 墙钟 07 点时写死值恰好晚于基线（碰巧绿）；**09 点一过就是「往前调 ETA」**，被
`InTransitTrackingService.recordEvent` 当场拒（`InTransitTrackingService.java:1058-1063`）。

DB 层还有一条同纪律的 CHECK：`kind <> 'ETA_REVISED' OR (eta_before IS NOT NULL AND eta_after IS NOT NULL AND eta_after >= eta_before)`。

### 2. 领域规则**是对的，不改**

「新的预计到港不许早于当前 ETA」是业务纪律：往前调会让「已经晚了几天」算成负数。
DB 层的 CHECK 也在钉同一条纪律。**要让步的是测试，不是规则。**

### 3. 同源推导 = 从跟踪行**读回** `effectiveEta()` 再 `+1` 天

没有重新调用 `eta(40)`（那样仍会与记录里真实存着的值漂移），
而是**直接用领域规则比较用的那个值**当基准：

```java
var currentEta = head.effectiveEta();   // 记录里此刻真正存着的当前 ETA
var newEta = currentEta.plusDays(1);     // 构造上保证严格晚于 currentEta
```

好处：新 ETA 的基准**就是**规则比较的基准 ⇒ 无论墙钟几点都恒成立。
`改期(...)` 助手接受调用方传进来的 `TrackingRow`（`节点_时间往返` 第 713 行已经查过 detail），
**不新增查询**。

### 4. 注入可钉死的测试时钟（沿用 trade 模块既有约定）

按调度者允许的例外保留：照 `trade` 模块 `DropshipTrackingIntegrationTest` / `DropshipConfigIntegrationTest`
的写法，把 `now()` 抽成可替换的 `clockSource`（默认 `WALL_CLOCK`），并在 `@AfterEach` 里还原。

**为什么值得留下**：该缺陷的成因正是「墙钟小时数决定成败」。只有时钟可钉死，
「墙钟无关」才能变成**一条每次都跑的断言**，而不是一次性脚本。

### 5. 新增**永久回归用例**，不只修一个用例

`改期基准_与墙钟小时数无关`（07 / 09 / 23 三个基准）逐个断言：
当前 ETA **正好**是 `eta(ETA_ONT)`、新 ETA **精确等于**「当前 ETA + 1 天」、且严格晚于当前 ETA、
`revised_eta` / `effective_ta` 都写回新值。基准日取真实「今天」只换小时 —— 既不跨天翻转，
也不把 ETA 推到过去而改变预警档位。

### 6. 断言只加不减

`节点_时间往返` 的**原有断言一条未删、一条未放宽**（`revisedEta`/`effectiveEta` 等于 `newEta`、
`sourceSystem` = FORWARDER、`referenceId` = FF-BOOK-77、位置时间往返等全部原样保留）；
新增的只有 `currentEta` 非 null 前置断言与新回归用例。**没有 `@Disabled`、没有 `assumeTrue`、没有把
`isEqualTo` 换成宽松比较。**

### 7. 台账：跑 `sync.mjs` 重新生成，而不是手工改生成部分

`module-progress.md` 的「状态」「证据」两列是人工维护、脚本按模块 ID 继承。
本轮把 10.4.1.2 的证据列从「**18 例全绿**」改为「**19 例全绿**」并补上本轮修复说明，
**状态列保持「已交付」未动**，然后跑 `node tools/module-progress/sync.mjs` 让生成部分回到规范形态。

> ⚠️ 顺带发现（**本车道修的**）：集成头 HEAD 上的台账与蓝图**本来就不一致**
> （`sync.mjs --check` 在**本轮改动之前**就已经红）。逐行比对（465 行）确认：

## 关键 trade-off

| 选项                                                 | 取舍                                                              | 结论     |
| ---------------------------------------------------- | ----------------------------------------------------------------- | -------- |
| 放宽领域规则 / 允许新 ETA 早于当前 ETA               | 直接让用例绿，但破坏业务纪律，且 DB CHECK 仍会拦 ⇒ 治标不治本     | **否决** |
| 把写死的绝对时刻改成另一个绝对时刻（换个点「对齐」） | 只是把地雷推到下一个小时点                                        | **否决** |
| 把写死值改成 `eta(40).plusDays(1)`                   | 仍是**重新计算**，与记录里真实存着的值可能漂移（跨小时/跨天边界） | 否决     |
| **从跟踪行读回 `effectiveEta()` 再 +1 天**           | 基准 = 规则比较的基准，构造上恒成立                               | **采纳** |
| 一次性脚本验证 + 不留回归用例                        | 改动最小，但「墙钟无关」没有断言保护 ⇒ 有人写回绝对时刻还会再炸   | 否决     |
| **注入时钟 + 永久回归用例（07/09/23 三基准）**       | 每跑一次就验一次三档                                              | **采纳** |

### 墙钟无关的验证

**① 常驻回归用例（已在 commit 内，每次 L1 都跑）**
`改期基准_与墙钟小时数无关` 把测试时钟钉在 **07 / 09 / 23** 三个小时基准上，
逐个走「建单 → 建跟踪 → 改期」，断言改期被接受、且新 ETA **精确等于**「当前 ETA + 1 天」。
⇒ 三个基准同时成立，且**不依赖当天几点**。

**② 整类用例的三个小时基准（临时插桩，验证后已回退）**
把整类的墙钟临时改成可被 `-Dstarcon.test.hour` 钉住，分别跑 H=7 / 9 / 23：

| 墙钟基准   | 结果                                                      |
| ---------- | --------------------------------------------------------- |
| **H = 7**  | `Tests run: 19, Failures: 0, Errors: 0` / `BUILD SUCCESS` |
| **H = 9**  | `Tests run: 19, Failures: 0, Errors: 0` / `BUILD SUCCESS` |
| **H = 23** | `Tests run: 19, Failures: 0, Errors: 0` / `BUILD SUCCESS` |

**③ 负对照（同样三档 + 旧的写死值 `2026-12-01T08:00+08:00`）** —— 证明三档都会被抓：

| 墙钟基准 | 结果                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------- |
| H = 7    | `Failures: 1`（新回归用例抓出）                                                                     |
| H = 9    | `Failures: 1, Errors: 1`：`新的预计到港 2026-12-01T08:00+08:00 早于当前 ETA 2026-12-01T09:00+08:00` |
| H = 23   | 同样红（基线 23:00）                                                                                |

**④ 反证「红」的来源真实存在** —— 把 `改期(...)` 的 `newEta` 临时改回写死值后 L1 即红，
错误正是上面那条领域规则；恢复后即绿。⇒ 领域规则是红的来源、本修复是它转绿的原因。

> 上述 ② ③ ④ 的插桩（`starcon.test.hour` 系统属性、`defaultClockSource` 钩子）**已全部移除**；
> 移除后文件与修复版**逐字节一致**（diff 退出 0），`grep -c TEMP-PROOF` = 0。

**⑤ 格式**：`spotless:check` 在本地默认 JDK 25 下会因 google-java-format 1.22.0 的
`NoSuchMethodError` 崩溃（环境问题，与本改动无关）；改用 **JDK 21**（与 CI 一致）后，
`spotless:check` 只报 `PendingInspectionIntegrationTest.java`（**别的车道的既存违规，本车道未触碰**），
**本文件零违规**（清缓存重跑确认，非缓存假象）。

### 同形文件排查（亲自复核，非转述）

判据：**断言的一边来自 `now()`、另一边是硬编码**才算雷；「文件里有没有硬编码日期」不算。

| 文件                                                                | 结论                                                                                                                                                                                             |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `warehouse/FirstMileShipmentIntegrationTest.java:66-67`             | `ETA = 2026-11-20T09:45+08:00` 是**确定性 fixture**：depart 与 ETA 用同一个值，断言都拿它自己比；`now()` 只出现在 INSERT 的 `created_at` 与 confirm 请求里，**不与该固定 ETA 比较** ⇒ **不需改** |
| `channel/LogisticsTransitIntegrationTest.java:154-157`              | `WINDOW_FROM/WINDOW_TO/INSIDE_WINDOW/OUTSIDE_WINDOW` 是**确定性窗口 fixture**，全部只与彼此比较；文件注释明写「本测试不用 now() 去喂一个会被断言的分片键」⇒ **不需改**                           |
| `FirstMileShipmentService` / `InventoryInTransitService` 的领域规则 | 只有**相对**校验（「预计到港不能早于计划开船」「预计到达不能早于发出时间」），**没有**「ETA 必须晚于 now()」⇒ 上述未来日期 fixture 今天不会炸                                                    |

> ⚠️ 记录一条**将来会变成雷**的风险（今天不改）：上述两个文件里的固定日期之所以今天安全，
> 是因为**目前**没有「ETA 必须晚于 now()」这类规则。若将来引入这类规则，
> 那些 fixture 会集体变红 ⇒ 届时应改为注入时钟，而不是回头改日期。
