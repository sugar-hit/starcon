# 14.2.2.2 自动规则（阶段 D7，L3 锚点 14.2.2 预算）

- **日期**：2026-10-21
- **车道**：`feat/14-2-2-2`（worktree `integration/.worktrees/14.2.2.2`）
- **蓝图原文**（`docs/product/capability-blueprint/14-ads-and-growth.md` 150-154 行）：
  > 职责：自动化规则：按条件自动调整预算/竞价/启停（ACOS 超标降价、ROAS 达标加预算、消耗完毕暂停、花费无转化停投），支持规则优先级、单次调整上限与总上限、试运行模式。
  > 输入：规则定义；实时广告表现；上下限保护参数。
  > 输出：规则命中记录 + 调整执行记录 + 效果回溯。
  > 关系：上游 = 14.3 报表；下游 = 平台广告 API。**自动规则必须有上限与试运行**——没有上限的自动调价一次异常就能烧掉大量预算。

## 决策摘要

### 1. 与 14.1.1.1 活动列表**零耦合**（本批最容易做错的地方）

14.1.1.1 是**同批并行**的另一条车道，它的广告活动与活动表现表在同批才落地，本 worktree 里看不到它的迁移。
所以本模块**不读它的表、不建跨车道 FK、不假设表名存在**：

- 规则通过**外部引用**（平台 + 店铺 + 外部活动 id / 外部关键词 id）定位广告对象；
- 广告表现数据由**本模块自己的 `ad_rule_metric` 表**承载，经一个**显式的指标登记写入口**落库；
- 合并时两边互不依赖。

代价：界面上显示不出活动名称与分组，运营要自己认外部 id。这条代价在 capabilities 的 `campaign_catalog` 维度里显式声明（available=false + ownerModule + 影响），**不用空列表或 0 冒充「这一项没有数据」**。

### 2. 🔴 蓝图加粗句「必须有上限与试运行」= 执行路径上的**三道闸 + 一个一等的模式**

不是「有这两个字段」就算落实了，而是：

- **单次上限**：金额上限（必填 > 0）与比例上限（0 = 不启用）**取更严的**生效。超限 ⇒ **拒绝并留痕**（`outcome=REJECTED` / `cap_check=SINGLE_CAP_EXCEEDED`），**绝不静默截断** —— 截断会让人以为「规则按预期工作」，而实际上调了另一个数。执行记录里 `after_value` 仍是「本来会变成多少」、`applied_delta` 为空，测试直接断言这一点。
- **总上限**：窗口内累计**金额** + 累计**次数** + 窗口小时数，全部必填 > 0。超限同样拒绝并留痕，窗口内已用额度落在记录上可复算。
- **上下限保护**：`min/max_budget`、`min/max_bid`，越界拒绝并留痕。
- **试运行**：规则自带 `dry_run`（**默认 true**，新建规则一律先试运行）**且**运行带 `run_mode`，**取更严的那个** ⇒ 一次「APPLY」的运行**不能**把一条开着试运行的规则推成真实执行。试运行照常匹配、照常产生命中记录与「本来会变成多少」，但**不产生实际调整、不产生待下发动作**；执行记录里 `outcome=DRY_RUN` 与 `outcome=APPLIED` 分得开。

DB 层兜底：上限与试运行是**必填列**（CHECK 保证「一条没有上限的规则」建不出来），另有**延迟约束触发器**保证「启用的规则至少有一个条件」（绕服务层写 SQL 同样被拒）。

### 3. 优先级真的参与判定，落选的**照样留痕**

同一目标（平台 + 店铺 + 层级 + 外部活动 id + 外部关键词 id）上多条规则同时命中时**按 priority 升序取一条**（数字小 = 优先高），落选的那几条写 `matched=true` / `selected=false` + 「为什么没选它」。
**不做多条规则叠加** —— 叠加会让上限判定失去意义（每条都以为自己只动了一点）。

### 4. 命中 / 执行 / 回溯**三样分开落库**

- `ad_rule_hit`：**每一次评估都留**（命中与未命中都留），未命中写清「哪条条件不满足 / 为什么不���比」—— 这是运营调规则时唯一的依据；
- `ad_rule_execution`：动作 + 幅度 + 前后值 + **逐项闸门结论**（单次上限 / 总上限 / 上下限各一行），被拒绝的调整也留；
- `ad_rule_effect`：执行前后的 ACOS / ROAS / 花费 / 销售额 + 结论。

「执行后还没有更新的指标数据」是一个**合法且必须被看见**的答案（`INSUFFICIENT_DATA`），不能拿 0 冒充「没变化」；数据到齐后**必须能重算**（所以 `INSUFFICIENT_DATA` 的行会被再次回溯覆盖，确定结论的行不会）。

### 5. 比率不可比 ≠ 0；「没有数据」≠「没同步到」

- ACOS = 花费 / 归因销售额，ROAS = 归因销售额 / 花费，**都是 GENERATED 列**（服务层写不进去，绕过服务层也编不出与原始量对不上的比率）。
- **分母为 0、或归因销售额为 0 ⇒ 一律 NULL（不可比）而不是 0**。归因销售额为 0 时 ROAS 也给 NULL：数值上它是 0，但那说明这一轮根本没有可比的投放，用 0 冒充会让「暂停中 / 没同步到」看起来像「效率极高」。
- `ad_rule_metric.metrics_as_of` 必填 + 规则行上的 `latest_metrics_as_of` / `metrics_stale` ⇒ 界面上「没有数据（还没登记）」与「没同步到（最新数据已超出评估窗口）」**分开显示**。

### 6. 下游平台下发**不实现**，但边界要显式

下游 = 平台广告 API，本模块**不实现**平台侧真实下发：调整只落成 `ad_rule_dispatch`（`dispatch_status=PENDING`，载荷按平台适配器要什么放什么、**不猜平台字段名**）。界面上写「**待下发**」而不是「已生效」。
本模块**唯一**能改变待下发队列的动作是 `POST /dispatches/{id}/cancel`（撤销）—— **刻意不提供**「标记已下发」这种假动作。

## 关键 trade-off

- **规则条件是 AND 语义的多行表，而不是一个「条件类型」枚举列**。代价是求值逻辑多一层；收益是「花费无转化停投」（花费 > 50 且 转化 ≤ 0）与「消耗完毕暂停」（花费 ≥ 1000）走**同一套结构**，不用在代码里开特例。
- **条件阈值分两列**（`threshold_value` 比率/计数 NUMERIC(19,6)、`threshold_amount` 金额 NUMERIC(19,4)），不合并成一列。代价是请求模型多一个字段；收益是「0.35 到底是 35% 还是 0.35 元」这种无法分辨的记录在 DB 层被 CHECK 拒 —— 而这正是自动调预算最容易出的错。
- **单次上限拆成金额 + 比例两列并取更严者**，而不是只留一个。代价是表单多一个字段；收益是「相对当前值降 10%」这种规则在预算很小时不会因为固定金额上限而永远动不了。
- **规则不做删除**：撤下走 `status=ARCHIVED`。代价是列表里会积累归档规则；收益是「规则曾经这么配过」这件事可查 —— 自动调预算的审计链不能被删掉。
- **指标登记是显式写入口**而不是自动同步。代价是运营/上游要先把数据送进来；收益是「没有数据」与「没同步到」能分得开（上游 14.3 报表未交付，这是唯一诚实的做法）。
- **契约只保留 channel 的两个文件**：codegen 会把集成头上 **trade 契约的既有漂移**（6.6.2.2 转量产那批 DTO 未再生物）一起改掉，本车道**刻意不越界改它**并已还原 —— 那是集成头批次级的事。

## 修掉的两个自己引入的真 bug

1. **总上限按带符号的 `applied_delta` 累加** ⇒ 降价的负数会互相抵消，「降了 0.2 又加了 0.2」被算成「累计 0」，**总上限形同虚设**。改成 `sum(abs(applied_delta))`。这是测试 `totalCapExceededIsRejected` 逼出来的。
2. **`insert into ad_rule` 多写一列** ⇒ PG 报 `INSERT has more target columns than expressions`；顺带发现 update 分支的 SET 子句写成了裸列名（`set rule_code, rule_name, …`）。改成**列清单 → 占位符 / 赋值子句 / 绑定值三处都由同一份清单派生**，杜绝手写两遍对不上。
