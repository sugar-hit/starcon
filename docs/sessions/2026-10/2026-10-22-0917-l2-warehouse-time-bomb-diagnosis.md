## 二、根因推导（可复核）

```java
// backend/services/warehouse/src/test/java/.../InTransitTrackingIntegrationTest.java
static final int ETA_ONT = 40, ETA_WATCH = 5, ETA_WARNING = 2, ETA_OVERDUE = -2;   // :65

/** ETA：相对现在的天数。 */
static OffsetDateTime eta(int daysFromNow) {                                        // :313
  return OffsetDateTime.now(ZoneOffset.ofHours(8))
      .plusDays(daysFromNow)
      .withMinute(0).withSecond(0).withNano(0);
}

// 失败用例里：
var shipmentId = dispatched(a, ETA_ONT, "100");   // → 当前 ETA = eta(40) = now+40d
var newEta = OffsetDateTime.of(2026, 12, 1, 8, 0, 0, 0, ZoneOffset.ofHours(8));      // :717 硬编码
```

领域规则（`InTransitTrackingService.java:1060`）拒绝对「ETA 往前调」：

```java
if (currentEta != null && r.etaAfter().isBefore(currentEta)) {
  throw new IllegalArgumentException("新的预计到港 " + r.etaAfter()
      + " 早于当前 ETA " + currentEta + "：把 ETA 往前调会让「已经晚了几天」算成负数…");
}
```

⇒ 测试用**硬编码绝对时刻**（`2026-12-01T08:00+08:00`）去改期，
而被改的基准 ETA 是 **`now + 40 天`（保留当前时刻）**。
两者只要 `now + 40d ≥ 2026-12-01 08:00` 就��倒挂。

### 临界时刻

```
now + 40d ≥ 2026-12-01T08:00+08:00   ⇔   now ≥ 2026-10-22T08:00+08:00
```

| batch-61（绿，commit `da1f96f9`） | 2026-10-22 **07:06** 起 | 2026-12-01 07:06 | 08:00 仍在未来 ⇒ **绿** |
| batch-62（本轮） | 2026-10-22 08:45 起，warehouse 模块段 **08:54–08:57** | 2026-12-01 08:54 | 08:00 已过去 ⇒ **红** |

**绿批次离红线只差 54 分钟。** 这不是「上一批绿、这批红」的竞态，
而是**同一天内定时到期的墙钟地雷**。

## 三、修法建议（只改测试，**不要动领域规则**）

领域规则「ETA 不能往前调」是**正确的业务规则**（往前调会让「已经晚了几天」算成负数），
错的是**测试写死了绝对时刻**。

- 把 `newEta` 从硬编码改成**相对量**，例如 `eta(ETA_ONT).plusDays(1)`，
  或把 shipment 的基准 ETA 固定成一个绝对时刻，让两者不再依赖墙钟。
- 断言要跟着改成「相对基准 ETA 往后推」，不要断言绝对日期。

**同形硬编码绝对日期的姊妹文件，建议一并扫一遍**（同仓同类地雷）：

- `backend/services/warehouse/src/test/java/com/starcon/warehouse/FirstMileShipmentIntegrationTest.java`
- `backend/services/channel/src/test/java/com/starcon/channel/LogisticsTransitIntegrationTest.java`
