## 决策摘要

1. **核销落地在四张新表**上：`finance_write_off`（核销记录单头）/
   `finance_write_off_allocation`（核销 ↔ **应收明细行** 的分配关系）/
   `finance_write_off_event`（留痕追加式）/ `finance_advance_ledger`（**预收挂账账**）。
   **零 ALTER 零 DROP 既有表、零新触发器挂上游表、零改上游 GRANT** —— V338/V341 已经把
   「12.2.1.2 的写入所有权」留在了两列上，本模块只去用它们。
2. **写入所有权只有两列**：`finance_receivable_line.settled_amount`（V338 原文：
   「只放行 settled_amount（核销金额）—— 那是 12.2.1.2 的写入所有权」）与
   `finance_receipt.settled_amount`（V341 原文：「核销金额的唯一写入口是 settled_amount」）。
   **不写应收单头** —— 单头的已核销金额与状态由 V338 自己的派生触发器
   `guard_finance_receivable_amount` 带出来 ⇒ 核销状态只有一个出处，
   「单头说已核销、明细还说未核销」在数据层写不出来。
3. **核销必须精确到明细行**：分配关系上 `SETTLEMENT` **必须**带 `receivable_line_id`，
   且由 DB 守卫校验它**确实属于**所写的应收单。分配金额小于该行未核销余额 ⇒ **部分核销**；
   一张核销单多条分配 ⇒ **合并核销**。
4. **自动匹配是「金额 + 订单号 + 日期」三者组合**，不是「金额相同即匹配」
   （卷 12 对 12.3.2.3 写死的同一条纪律）。金额条件有两档：
   该订单下未核销余额**合计** = 目标金额（合并核销），或某条明细行的未核销余额恰好等于它（单行）。
   命中原因逐条写进结果供人工复核；命中 0 条整体 400，**绝不硬凑**。
5. **预收挂账不减未核销余额**：12.2.1.1（V341）的口径是「预收 ⊂ 未核销余额」
   （带 `advance_flag` 的收款单其 `unsettled_amount` 仍全额留在未核销余额里），
   本模块与它同口径 —— 挂账只是把一部分未核销的钱**分类**成预收（记进 `finance_advance_ledger`），
   并把它**专用**起来（核销按「未核销余额 − 未释放挂账额」封顶，要动用先显式释放）。
   预收余额 = 本模块挂账 + 12.2.1.1 预收标记收款单的未核销余额，**两段口径互不重复计数**。
6. **下游 13 利润不可用就说不可用**：reporting 服务不在集成头里 ⇒「回款口径」当前不可产生。
   能力声明 `available=false` 且 `ownerModule='13'`，**绝不造利润数据、绝不用假报表顶替**。

## 关键 trade-off

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 核销金额落在哪 | **明细行 `settled_amount` + 收款单 `settled_amount`** | 这两列是 V338/V341 写死留给 12.2.1.2 的唯一入口。**不写单头**：单头由上游派生触发器带出，避免「两个写入口」。 |
| 上游表能不能改 | **零 ALTER、零新触发器、零改 GRANT** | 任务书明令；且上游守卫（冻结 / 派生 / CHECK / 事件流追加式）已足够 —— 我的职责是让它们**继续成立**，不是绕开或改写它们。 |
| 撤销怎么退 | **退明细行的 `settled_amount`，让上游派生触发器把单头带回来** | V338 的行冻结守卫只冻「金额/数量/单价/描述/订单号…」这些账目事实，`settled_amount` 被**显式放行**。 |
| 整单核销后能不能撤销 | **不能，如实拒绝并说清替代路径** | V338 写死「已核销（SETTLED）是终态：整单冻结，一行都不许改」。绕开守卫 = 给账目留后门；替代路径是「作废 + 新单」（红冲），属 12.1.1.3 的域。**这是上游纪律，不是本模块的缺口。** |
| 预收挂账动不动收款单 | **不动**（预收 ⊂ 未核销余额） | 与 V341 同口径；两段预收口径（挂账 / 预收标记）因此互不重复计数。 |
| 挂着的预收能不能直接拿去核销 | **不能，要先显式释放** | 挂着 = 专用。直接花掉会让「预收余额 > 未核销余额」这种自相矛盾的数字出现。显式释放留痕。 |
| 自动匹配的金额条件 | **订单下合计 或 单行恰好相等** | 只用「单行相等」就做不了合并核销（300 的钱对 100+200 两条行）；只用「合计相等」又做不了部分核销。两档都要求订单号与日期同时成立 ⇒ 金额相同永远不构成匹配。 |
| 单头三个金额 | **由分配明细派生** | 与 V338 同手法：「单头 300、明细合计 280」这种漂移在数据层写不出来。 |
| 「核销记录必须有分配明细」 | **延迟约束触发器**（DEFERRABLE INITIALLY DEFERRED） | 单头先落库、分配后落库（分配要外键指向单头），非延迟触发器在单头插入的瞬间看不到分配明细，会误判。⚠️ 延迟触发器**必须回表读当前值**：用行镜像会把一笔正常核销判成「合计不一致」（派生回写发生在行镜像之后）。 |

## 踩到的坑（值得留给下一个人）

1. **jOOQ 读 `timestamptz` 返回的是本机时区的 `OffsetDateTime`。**
   自动匹配的日期条件在 SQL 侧用 `(confirmed_at at time zone 'UTC')::date`（UTC 日期），
   服务层却直接 `toLocalDate()`（本机日期）—— 东八区差**一天**，
   自动匹配**静默失配**（不报错，只是永远没命中）。已统一用
   `atZoneSameInstant(ZoneOffset.UTC).toLocalDate()`。
   ⚠️ 这与「`Timestamp.valueOf(LocalDateTime)` 静默偏 −28800s」是同一族坑。
2. **延迟约束触发器不能信行镜像。** 见上表最后一行：第一次提交时就炸，
   原因是它拿到了单头插入那一刻的 `total_amount = 0`。
3. **`List.toList()` 不存在**（那是 `Stream.toList()`）；jOOQ 的 `fetch()` 返回 `List`，
   `.map(...)` 之后要 `new ArrayList<>(...)` 才能再包一层。
