## 缺陷一：14:20 轮把「正在写」误判成「已崩」，重复派发导致双写

14:00 轮我派发的三条车道，到 14:20 时 worktree 里已有 4450 / 2389 / 4221 行未提交代码、
但 `git log integration/module-dev..HEAD` 全空。14:20 轮据此判定
「Worker 写完前几层后耗尽回合被回收」，于是对同样三条车道 `redispatched:1` 重派。

**这个判据是错的。** 未提交代码正是一个活着的 worker 的正常形态；而车道有
`heartbeatAt` 与 `stale` 字段（本轮实测三条车道 `stale=false`），完全可以用来判活。
结果是同一时刻 **6 个 worker 写 3 个 worktree，每个 worktree 两个 writer**：

| worktree | 14:00 轮 worker | 14:20 轮 worker |
| --- | --- | --- |
| 3.6.1.1 | `mvs_14c6b458`（已完成） | `mvs_5bf41c01` |
| 3.7.2.1 | `mvs_41e6d821`（进行中） | `mvs_6d32e65f` |
| 3.8.1.1 | `mvs_dbefb609`（进行中） | `mvs_8733aa9d` |

处置：我只能停自己派的那两个（`bg_41653414`、`bg_6152fac9`），留下 14:20 轮那一份，
恢复「每个 worktree 单写」。停之前先确认磁盘状态可交接：3.7.2.1 已有的 16 个改动文件
被 14:20 轮 worker 审计、补完并以 `2187a02` 落地；3.8.1.1 的 11 个未跟踪文件仍在推进。
停掉两个 worker 没有丢任何代码。

> **根因在编排器不在任务书**：`lane.mjs` 需要一条「lane 处于 running 且
> `stale=false` 时不得重派」的硬规则。现在它把「无提交」当回收信号，
> 而 worker 按设计就是**全部写完才 commit**（一个 atomic 改动一个 commit），
> 所以「无提交」在任务存活期间是常态而非异常。

## 缺陷二：并集驱动对台账是「追加」而不是「按键求并」

`merge-ready` 并入两条车道时打出两次告警：

```
merge-union: 走了行级兜底并集，请人工确认这个文件改对了
```

复核发现台账从 **465 行涨到 467 行**，3.6.1.1 与 3.7.2.1 各出现两次，
同一模块 ID 出现互相矛盾的状态：

```
| 3.6.1.1 | … | 已交付 | V27__party_profile.sql（…） |
| 3.7.2.1 | … | 未开发 | — |
| 3.8.1.1 | … | 未开发 | — |
| 3.6.1.1 | … | 未开发 | — |     ← 重复且过期
| 3.7.2.1 | … | 已交付 | V28__…  |
```

**第二次伤害来自修复动作**：`sync.mjs` 重建后行数正确（465、0 重复），
但它按**最后一条**取值，3.6.1.1 恰好落在旧的「未开发」副本上 ——
一个代码已完整并入集成头的模块，台账被改回未开发。

处置：从合并提交 `b56c62d` 取回权威行（连同完整证据）还原，再跑 `sync.mjs` 重算计数。
`c8b6787` 是这次修复的提交。

**契约侧没有中招**（这点值得记下来）：`catalog.openapi.json` 358 schema / 358 `$ref` /
**0 悬空引用**，Party 10 个 + PhysicalSafety 5 个 DTO 都在，
`catalog.ts` 每个类型各导出恰好一次，`OpenApiContractTest` 在集成头 BUILD SUCCESS。
说明按「类型名 / OpenAPI 路径」求并的那条路径是对的，**出问题的是台账那条按「模块 ID 行」求并的路径** ——
它退化成了整段追加。

## 并发定级：瓶颈是 CPU，不是内存 —— 维持 6，不要提到 8

派发瞬间与三条车道同时进入 `./mvnw verify` 的高峰期，两次实测：

| 时刻 | load avg | Docker 内存 |
| --- | --- | --- |
| 14:01 派发后 | 2.28 / 1.77 / 1.69 | ≈1.30 GB / 11.67 GB |
| **14:27 峰值** | **8.25 / 5.73 / 3.71** | **1.48 GB / 11.67 GB** |
| 14:31 收尾 | 2.59 / 4.88 / 4.03 | 1.27 GB / 11.67 GB |

峰值时 `Virtualization.framework`（Testcontainers VM）单独占 **374% CPU**，
另有 java 114%、node 88%、Docker Desktop Helper 87%。
`memory_pressure` 显示系统空闲内存 **43%**，无换页压力（pageouts 仅 3178）。

结论与预期相反：**Docker 那 11.7GB 从来不是瓶颈（用了不到 13%），10 核才是**。
3 条车道已经把 load 打到 8.25，提到 8 条只会让构建互相踩、把每模块工时拉长而不会提高吞吐。
**维持全局 6 条。**

## 附带发现：临时文件落在主工作区根目录

主工作区根目录出现未跟踪文件 `.tmp-check-party-test.java`（44KB，
PartyIntegrationTest 的临时副本，时间戳 14:31 —— 在 14:20 轮那个
3.6.1.1 worker 做完「改坏→跑测试→还原」反向验证之后生成）。
`.gitignore` 第 18 行只忽略 `.tmp/` 目录，匹配不到根目录的 `.tmp-` 前缀文件。

**没有删除它**：那是另一个 worker 正在用的还原备份，删掉会打断它的流程。
但这是个真实的纪律违反 —— 车道任务书第 9 条要求临时产物写 `<WORKTREE>/.tmp/`。
任何 `git add -A` 都会把它带进版本库。**下一轮开工前必须清掉。**
