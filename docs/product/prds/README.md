# 产品需求文档（PRD）

PRD 描述一个可独立交付、可验收的产品增量。系统全貌与能力归属见
[`capability-blueprint/`](../capability-blueprint/README.md)，技术边界与不可逆决策见
[`architecture/`](../../architecture/overview.md) 和 [`decisions/`](../../decisions/README.md)。PRD 不重复数据库字段、服务拆分或页面视觉稿。

## 需求索引

| PRD                                                | 状态      | 范围                                     |
| -------------------------------------------------- | --------- | ---------------------------------------- |
| [IAM](iam.md)                                      | In Review | 登录、租户切换、组织管理及待验收安全要求 |
| [订单、库存与出库](order-inventory-fulfillment.md) | Draft     | D3–D4 自营仓手工订单与实物售后闭环提案   |

审查发现与后续立项见 [业务设计审查](../../backlog/2026-09-30-business-design-review.md)。状态只表示需求成熟度，不表示功能已部署。

实施顺序与逐功能进度见 [Sprint 计划](../sprints/README.md)。当前用户已授权开发；PRD 状态仍独立记录需求评审与发布验收。

## 文档状态

每份 PRD 在标题下声明以下元数据：

| 字段     | 说明                                                                           |
| -------- | ------------------------------------------------------------------------------ |
| 状态     | `Draft` / `In Review` / `Approved` / `In Delivery` / `Released` / `Superseded` |
| 负责人   | 对需求取舍和验收结论负责的人或角色；未知时写 `待指定`                          |
| 目标版本 | 明确版本、里程碑或 `待排期`，不得用“本轮”                                      |
| 最后更新 | `YYYY-MM-DD`                                                                   |
| 关联蓝图 | 对应 L3/L4 编号                                                                |
| 关联决策 | 约束本需求的 ADR；没有则写 `无`                                                |

只有负责人确认后才能从 `In Review` 进入 `Approved`。开发完成不自动等于 `Released`，还需满足验收标准与发布门槛。

## 必备结构

1. **摘要**：一句话说明给谁解决什么问题，以及本期交付结果。
2. **背景与问题**：现状、证据、影响；事实与假设分开写。
3. **目标与非目标**：3–5 条可验证目标，以及明确不解决什么。
4. **用户与权限**：Persona、使用场景、前置权限和数据范围。
5. **范围**：按业务能力列 in scope / out of scope；不按文件或接口列任务。
6. **关键流程**：主流程、替代流程、失败/恢复流程；跨服务未知结果必须有用户可理解的状态。
7. **业务规则与状态**：不变量、状态转换、权限、幂等、时间与金额口径。
8. **功能需求**：使用稳定编号 `FR-01`；每项说明触发、行为、结果。
9. **验收标准**：使用 `AC-01`，写成可观察结果，并关联相应 FR。
10. **度量与护栏**：基线、目标值、观察窗口、数据来源、不能恶化的指标。
11. **依赖与风险**：外部依赖、合规/安全风险、缓解措施和责任方。
12. **发布与回滚**：迁移、灰度、兼容、回滚条件；无发布风险时也要明确写出。
13. **开放问题**：只保留会影响范围或行为的未决项，注明负责人和决策期限。

## 需求写作规则

- 蓝图的“职责 / 输入 / 输出 / 关系”是**设计完整性门槛**，不是 PRD 验收标准。验收标准必须能从用户界面、API 结果、业务事实或审计记录观察。
- 区分“当前已实现”“本期承诺”“后续候选”。目标态能力不能写成当前行为。
- 使用稳定业务名词；同一对象不得同时称“企业、组织、租户”而不定义差异。
- 所有业务数据需求都要说明租户边界、角色动作和数据范围；客户端传入的租户标识不构成授权。
- 涉及金额必须声明币种、精度、汇率时点和舍入方；涉及时间必须声明业务时区和截止规则。
- 自动操作必须声明幂等语义、重复触发结果和人工恢复入口。
- 不在 PRD 内写开发任务、类名、表名、临时 mock 或未经承诺的具体技术实现。

## 验收标准示例

不合格：`支持租户切换`。

合格：`AC-04（FR-03）：当用户在无未保存修改时切换到另一个有效成员租户，系统卸载原租户页面与缓存，进入目标租户工作台；随后在目标租户上下文访问仅属于原租户的对象被拒绝且不泄露对象是否存在，且审计记录包含操作者、源租户、目标租户和时间。`

## 评审清单

- [ ] 问题、目标、范围和非目标彼此一致
- [ ] 主流程、失败流程、空状态和恢复路径齐全
- [ ] 每项 FR 至少有一项可测试 AC，且无孤立 AC
- [ ] 权限、租户隔离、审计和敏感数据处理已说明
- [ ] 上下游业务事实、所有者和失败责任明确
- [ ] 指标有基线、目标、窗口和数据来源，或明确标为“发布前补齐”
- [ ] 当前能力、本期承诺和未来方向没有混写
- [ ] 开放问题有负责人和决策期限
- [ ] 与蓝图、ADR、代码现状没有已知冲突

## 文件命名与变更

- 新文件命名：`<ticket>-<feature-slug>.md`；没有 ticket 时先用稳定功能名，取得 ticket 后再重命名。
- 需求发生重大方向变化时，在原 PRD 标记 `Superseded` 并链接替代文档，不静默改写历史承诺。
- 文案澄清、验收补充和范围收敛可原地更新，并维护“最后更新”。
