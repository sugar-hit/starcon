## 1. 设计输入：三类来源如何合成

starcon 的功能不是拍脑袋列的，而是三份材料交叉验证后的交集与并集。

### 1.1 来源 A — 网店后台（平台侧 Admin）

Amazon Seller Central、Shopify Admin、eBay/Temu/TikTok Shop 后台等。它们定义了**"一个商品/订单在平台上长什么样、有哪些状态、平台允许什么操作"**。starcon 必须能完整承载平台的字段与状态机，否则同步必然丢数据。

采纳：Listing 编辑器、变体树、图片/视频与 A+ 内容、订单状态机、库存同步语义、广告体系、评价与站内信、账号健康指标、结算报告。

### 1.2 来源 B — ERP 后台（企业侧，这是本蓝图的核心）

领星 ERP、店小秘、马帮、易仓、赛盒、通途，以及金蝶/用友/SAP/Odoo 这类通用 ERP。ERP 的本质不是"网上开店"，而是**把企业的进销存、业财、供应链、组织权限做成一个可审计的事实系统**。

采纳：主数据（商品/往来单位/仓库/科目）、单据流（采购→销售→退货）、库存账与预占、成本核算与利润、应收应付与总账、批次序列号、盘点与调拨、多仓多货权、审批与操作日志、报表体系、组织与权限。

> **ERP 与网店后台的根本区别**：网店后台以"平台页面"为中心（一个列表页 = 一个功能）；ERP 以"单据与账"为中心（一张单据的生命周期 = 一个功能）。starcon 必须两者都做——**页面沿用网店后台的操作习惯，数据模型沿用 ERP 的事实纪律**。本蓝图每个模块都按这条线写。

### 1.3 来源 C — 跨境电商行业专属需求

这是 starcon 区别于通用 ERP 的地方，也是最容易被漏掉的部分：

| 行业特性 | 具体要求 | 落在哪个系统 |
|---|---|---|
| 多平台多店铺多站点 | 一个 SPU 在 40+ 平台有 1000+ listing，映射要版本化 | 02 渠道与店铺、04 刊登与内容 |
| 平台为库存真相来源之一 | FBA 库存是平台仓，不是自有 SKU；与本地库存要分账 | 07 库存核算、10 物流与头程 |
| 全托管 / 半托管 / 自发货并存 | 三种模式的货权、结算、履约责任完全不同 | 09 订单、12 财务、13 利润 |
| 头程与尾程分离 | 采购→国内仓→头程→海外仓→平台仓→买家，5 段物流各自计费 | 10 物流与头程 |
| 报关清关 | HS 编码、原产地、申报价值、关税，直接影响利润与合规 | 16 合规与风控、10 物流与头程 |
| 多币种与延迟结算 | 下单币种 ≠ 收款币种 ≠ 记账币种；平台延迟结算需单列 | 12 财务、05 定价 |
| VAT / IOSS / EPR / 销售税 | 欧盟、英国、日本、美国各辖区规则不同 | 16 合规与风控 |
| 成本口径不统一 | 先进先出/移动加权/批次成本，卖家各自选择 | 12 财务、13 利润 |
| 广告是利润的一等公民 | ACOS/ROAS/TACOS 必须能与 SKU 利润打通 | 14 广告与增长、13 利润 |
| 平台合规红线 | 跟卖、侵权、违禁词、关联封号、ODR 超标 | 16 合规与风控 |
| 达人 / 社媒带货 | TikTok 达人建联、样品、佣金、归因 | 14 广告与增长、15 客户与客服 |
| 旺季峰值 | 大促单量涨 10 倍不能靠加班解决，靠规则与批量 | 09 订单、08 仓储作业 |

## 2. 四级目录约定

本蓝图统一使用**四级**功能目录，这是最小的可设计粒度：

| 级别 | 名称 | 定义 | 判定标准 |
|---|---|---|---|
| **L1** | **系统** | 一级业务系统 / 业务域 | 有独立的业务目标、数据主责方和团队归属 |
| **L2** | **功能** | 系统内的业务能力域 | 有明确的一组职责边界，英文可作为模块路径一级 |
| **L3** | **子功能** | 可独立授权的操作域 | 对应 ADR-0005 里的一张页面资源表，可单独配角色 CRUD |
| **L4** | **模块** | **最小设计单元**：一个页面或一个能力 | 有确定的输入和输出，可被跳转、引用、被任务触发 |

路径写法与前端路由一一对应：

```
L1 系统  07 库存核算
  L2 功能 7.2 库存预占
    L3 子功能 7.2.1 预占需求管理
      L4 模块 7.2.1.1 预占需求列表  →  /inventory/reservation
```

**L4 是设计单元，L3 是权限单元，L2 是导航单元，L1 是归属单元。** 四者不要混用：例如"库存调整单"是一个 L4 模块，它挂在 L3"库存变动"下；不能因为它出现在两个页面就升格为 L2。

## 3. L4 模块的写法：四项必写

本蓝图**每一个 L4 模块**都必须写清四件事，缺一不可。这四问就是验收标准：

| 字段 | 含义 | 反面（不允许出现） |
|---|---|---|
| **职责** | 该模块**完成什么功能**，写到可判断"做完了没有"的程度 | "管理商品"这种同义反复 |
| **输入** | 接受什么输入：用户操作、导入文件、上游系统的数据、事件 | 只写"用户输入" |
| **输出** | 提供什么输出：页面呈现、产生的业务事实、发出的事件、对下游的指令 | 只写"展示数据" |
| **关系** | 与其他系统、功能、页面的关系：上游是谁、下游是谁、共享什么数据 | 孤立描述 |

**关系记法**（全套统一，便于交叉检索）：

```
上游 <系统·功能>  →  本模块  →  下游 <系统·功能>
共享数据：<数据对象>            触发：<事件或人工动作>
```

四问之外的补充约束：

- **输入要区分人工/导入/上游事件三类**，自动触发的模块必须写明幂等键
- **输出要区分"页面输出"和"业务事实"**，只有后者才进事件总线
- **涉及金额/数量的模块必须写明币种、精度、舍入责任方**
- **涉及跨服务调用的必须写明超时与未知结果的处理**（查证后重试，不能当作失败）

## 5. 业务形态适配：铺货型 vs 品牌化

跨境电商公司不是一种。**铺货型**与**品牌化**的资金结构、库存模型、风险点几乎相反，一套"都能用"的系统等于两套都别扭。本节说明 starcon 如何用同一套模型容纳两种形态。

### 5.1 两种形态的本质差异

| 维度 | 铺货型（无货源 / 多店铺货） | 品牌化（DTC / 品牌出海） |
|---|---|---|
| 货在哪 | **供应商仓**，甚至买完才发 | 自有工厂 + 国内仓 + 海外仓 + 平台仓 |
| 货权 | 常为**代发/寄售**，货主是供应商 | 自有为主，部分供应商寄售/VMI |
| SKU 量级 | 数千到数万，生命周期极短 | 数百到数千，生命周期长、迭代制 |
| 核心动作 | **采集 → 铺货 → 开单 → 发货** | **开发 → 打样 → 备货 → 品牌 → 复购** |
| 毛利结构 | 低毛利、高周转，薄利多销 | 毛利较高但被退货、广告、头程、关税侵蚀 |
| 最大风险 | **账号关联封店**、漏单、批量操作出错 | **断货/积压**、退货率、现金流、合规（VAT/EPR/侵权） |
| 关键度量 | 上新效率、订单处理时效、店铺健康 | 库存周转、毛利率、复购率、LTV/CAC |

### 5.2 系统对两种形态的取舍矩阵

图例：**● 核心**（缺了做不了这门生意）· **○ 重要**（规模化后必需）· **△ 可选**（特定模式才需要）

| 系统 | 铺货型 | 品牌化 | 说明 |
|---|---|---|---|
| 01 工作台与门户 | ○ | ○ | 两者都要；铺货型更依赖"异常订单"与"系统健康" |
| 02 渠道与店铺 | ● | ● | 共同命脉；铺货型多店铺多平台，品牌化多站点多渠道 |
| 03 商品主数据 | ○ | ● | 铺货型重采集去重与批量，品牌化重属性/报关/开发源数据 |
| 04 刊登与内容 | ● | ○ | 铺货型命门（采集/铺货/搬家），品牌化更重品牌内容与 A+ |
| 05 定价与价目 | ○ | ● | 铺货型追价即可，品牌化必须算到岸成本与利润底线 |
| 06 采购与供应 | △ | ● | 铺货型常无采购（代发/寄售），品牌化是命脉；**6.6 产品开发仅品牌化** |
| 07 库存核算 | △ | ● | 铺货型多数不持货，**7.7 货权/寄售/VMI 与 7.8 分摊在此放大** |
| 08 仓储作业 | △ | ● | 铺货型常不自建仓，多用三方仓/平台仓 |
| 09 订单履约 | ● | ● | 共同核心；**9.6 代发仅铺货型，9.7 B2B 仅品牌化/工贸** |
| 10 物流与头程 | ○ | ● | 铺货型重尾程效率，品牌化重头程/报关/关税/逆向物流 |
| 11 售后与退货 | ○ | ● | 品牌化退货率高，**10.7 逆向物流在此放大** |
| 12 财务核算 | ○ | ● | 铺货型够用即可（结算+对账+利润），品牌化需总账/多账簿/税务 |
| 13 利润与经营分析 | ○ | ● | 两者都要；品牌化维度更细（按经营模式分组） |
| 14 广告与增长 | ○ | ● | 铺货型多为平台自动广告，品牌化重达人/促销/归因 |
| 15 客户与客服 | ○ | ● | 铺货型以效率为主，**15.6 会员与复购主要服务品牌化 DTC** |
| 16 合规与风控 | ● | ● | 铺货型重防关联与侵权，品牌化重 VAT/EPR/认证/品牌保护 |
| 17 组织权限与系统设置 | ○ | ● | 品牌化团队与多主体更复杂（**17.6 多账簿仅品牌化/工贸**） |
| 18 集成开放与智能自动化 | ○ | ● | 铺货型重批量规则自动化，品牌化重集成与 AI |

### 5.3 因此的设计后果（已落到模块）

1. **07.7 货权与经营模式**：把"货是谁的"从租户维度拆出为 `stock_owner` 维度，否则代发/寄售客户无法建模（实体目录 §8 原把寄售列为未决项，此处给出显式方案）。
2. **07.8 多平台可售量分摊**：多店铺共享一池库存是铺货型刚需，缺了必然超卖或店铺"饥饿"。
3. **09.6 代发履约**：代发不产生库存分录，只有代发单与差价结算——**不能套用"采购→入库→发货"主链路**。
4. **09.7 B2B 与渠道销售**：账期方向与零售相反（先发货后收款），资金计划需分开。
5. **06.6 产品开发与打样 + 03.9 主数据治理**：品牌化的上游（开发源数据）与长期维护（SKU 上万后的治理）。
6. **10.7 逆向物流**：跨境退货三去向（转卖/退运/弃置）对品牌化利润影响巨大。
7. **15.6 会员与复购运营**：品牌化 DTC 留存能力，独立站/会员体系与平台订单分开处理。
8. **12.5 能力分级**（见 §5.4）：总账/多账簿对多数跨境卖家是过度设计，标记为按需启用。

### 5.4 能力分级（避免 460+ 模块成为实施灾难）

| 级别 | 含义 | 启用方式 |
|---|---|---|
| **P0 基础** | 没有它这门生意跑不起来（订单、库存账、店铺授权、商品、财务结算） | 默认开启 |
| **P1 常用** | 规模化后的效率与管控需要（分仓拆单、批次效期、成本核算、利润报表、审批） | 按租户开通 |
| **P2 高级** | 特定模式或大卖才需要（总账/多账簿、BOM/委外加工、寄售/VMI、总成本分摊、AI 预测、开放 API） | 按模块开通 |
| **P3 形态专属** | 只服务某一形态（6.6 产品开发=品牌化；9.6 代发=铺货型；9.7 B2B=工贸；15.6 会员=品牌化 DTC） | 按经营形态开通 |

**关键原则**：P3 模块**不因未启用而产生实现负担**——它们共用同一套底层模型（订单、库存、成本），只是额外的策略分支。这是在"一套系统"与"两种生意"之间取平衡的方式。

## 6. 通用横切规则（每个模块默认遵守）

这些规则不逐模块重复写，但每个 L4 模块的实现必须满足：

| 规则 | 内容 | 出处 |
|---|---|---|
| 多租户 | 所有业务表 `tenant_id NOT NULL` + DB 层 RLS；租户来自已认证成员关系，**不信任 `X-Tenant-Id` 头** | [ADR-0002](../../decisions/0002-multi-tenancy-strategy.md) |
| 子租户 | 子租户是独立数据边界，父子不自动赋权 | [ADR-0005](../../decisions/0005-tenant-hierarchy-and-page-rbac.md) |
| 页面权限 | L3 子功能 = 一张 `page_resource`，按角色配 CRUD | ADR-0005 |
| 数据范围 | 角色分配必须同时限定法人/店铺/仓库/部门，操作与范围同一分配 | ADR-0005 |
| 金额 | `BigDecimal` + `NUMERIC`，禁浮点；币种、精度、舍入责任方必须显式 | 实体目录 §5 |
| 数量 | `NUMERIC(19,6)`，单位换算在单据上冻结快照 | 实体目录 §5 |
| 时间 | 业务时间与系统时间分开存；跨时区用 IANA 时区 + 业务日期 | 实体目录 §3.9 |
| 状态机 | 状态用 enum + 显式转换规则；**有值不等于可转换** | AGENTS.md 代码风格 |
| 幂等 | 外部事件按 `event_id` 去重；主动操作带幂等键 | 实体目录 §6 |
| 未知结果 | 调外部平台超时先**查证**再重试，禁止当作失败 | 实体目录 §6 |
| 审计 | 关键动作写 `audit_event`，脱敏，不记密码/完整客户地址 | 实体目录 §4 |
| 冻结快照 | 订单行冻结商品、价格、汇率、映射版本、单位换算 | 实体目录 §3.6 |
| 可逆性 | 已发生的流水只冲销不覆盖；已过账凭证不改只红冲 | 实体目录 §5 |

## 7. 与现有前端 IA 的关系

现有 [`nav-config.ts`](../../../packages/ui/src/lib/nav-config.ts) 是 **4 个职能 Tab（开发/运营/物流/仓储）× 15 个 Domain**。本蓝图的 18 个系统是**功能归属维度**，两者不是同一层东西：

- 现有 Tab = **角色视图**（切 Tab 换的是"我是哪种岗位"）
- 本蓝图系统 = **功能归属**（回答"这功能归谁设计、归谁供数"）

**目标态 UI 沿用现有 Tab 结构不变**，18 系统映射进 4 个 Tab：

| 现有 Tab | 归属系统 |
|---|---|
| 开发 | 03 商品主数据、04 刊登与内容、05 定价与价目、06 采购与供应 |
| 运营 | 09 订单履约、11 售后与退货、15 客户与客服、13 利润与经营分析、12 财务中心、14 广告与增长 |
| 物流 | 10 物流与头程 |
| 仓储 | 08 仓储作业、07 库存核算 |
| 跨 Tab（顶部固定） | 01 工作台与门户、02 渠道与店铺、16 合规与风控、17 组织权限与系统设置、18 集成开放与智能自动化 |

需要在现有 Domain 上**新增**的入口（当前 15 个 Domain 未覆盖）：

| 新增入口 | 挂载 Domain | 原因 |
|---|---|---|
| 平台账号 / 店铺中心 | `/channels` | 现有无入口，是所有同步的前置条件 |
| 广告中心 | `/ads` | 广告费用是利润的一等组成，不能只做利润中心的子页 |
| 站内信与评价 | `/crm` 下的 `messages` | 客服高频操作，独立入口 |
| 报关清关 | `/logistics` 下的 `customs` | 影响利润与合规，不可埋在物流设置里 |
| 成本核算 / 计价模型 | `/finance` 下的 `costing` | 利润口径的唯一入口 |
| 审批中心 | `/settings` 下的 `approvals` | 单据流转的横向能力 |

## 10. 本蓝图的边界

**不做**：具体 UI 布局与视觉（见 [`docs/design/visual-spec.md`](../../design/visual-spec.md)）、数据库物理字段（见 [`db/schemas/v2/`](../../../db/schemas/v2/README.md)）、平台 API 具体字段映射（按平台逐个写实施文档）。

**会变**：系统划分可以合并或拆分，L3/L4 可以增删，但 §2 的四级约定和 §3 的四问格式**不可放宽**——放宽后文档就退化成功能清单，失去验收价值。

**已实现范围**：以 [`docs/operations/catalog-local-development.md`](../../operations/catalog-local-development.md) 为准，当前仅 identity 与 catalog 真实运行。本蓝图其余部分为目标设计。
