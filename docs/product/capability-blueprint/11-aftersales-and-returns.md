# 11 售后与退货系统

> **定位**：把"出了问题"变成"有据可查地解决"。退货是实物流，退款是资金流，两者必须分开又必须能对上。
> **后端归属**：`trade` 拥有售后单据；退货实收与质检在 `warehouse`；退款执行在 `finance`。
> **前端入口**：`/aftersales`

## 边界

**做**：售后申请与授权、退货物流与实收、退货质检与处置、换货、仅退款/部分退款、平台纠纷与索赔、客诉工单、客户信誉与退货率分析。

**不做**：不直接增加可售库存（退货必须质检合格才转可售）、不自行确认退款已执行（12 财务执行并回报）。

**关键约束**：
- **退货 ≠ 退款**：退货是货回来，退款是钱出去；可以只退款不退货、退货不退款
- 一个 `return` **不直接触发增加可售库存**
- 退货实收与授权行要做**分配关联**，部分退货不超原数量
- 累计退款不能超过可退余额，失败释放占用

## 功能职责（L2）

| 功能 | 职责 | 主责服务 |
|---|---|---|
| **11.1 售后受理** | 受理平台与内部售后请求，判定售后期与条件、分配责任人，并做原因分类与商品问题归因 | trade |
| **11.2 退货管理** | 授权退货、下发退货指引、登记实收并分配到授权行，再经质检决定转可售/残次/报废 | trade + warehouse |
| **11.3 退款与换货** | 发起并跟踪退款（可部分）、执行换货并建立原单与新单关联；资金执行交 12 财务 | trade → finance |
| **11.4 平台纠纷与客诉** | 管理平台纠纷举证申诉与非售后类客诉工单与知识库 | trade + support |
| **11.5 售后分析** | 分析退货率（与销售额同口径）与质量成本，输出供应商与流程改进依据 | trade + reporting 投影 |

## 详细设计

### 11.1.1.1 售后单列表

- **职责**：售后单主列表：售后号、关联订单、店铺、类型（退货退款/仅退款/换货/补发/维修）、金额、原因、状态、时效（平台要求回复/处理时限）、责任人，支持多维筛选与批量处理。
- **输入**：筛选条件（类型、状态、原因、店铺、时效、金额）；用户数据范围。
- **输出**：列表 + 时效预警标记；批量操作（授权、备注、转工单）。
- **关系**：上游 = 9 订单、15 客服、平台消息；下游 = 11.1.1.2 详情、11.2/11.3。**平台时效倒计时必须显眼**：超时会直接影响账号绩效与资金冻结。

### 11.1.1.2 售后单详情

- **职责**：单售后全景：原订单信息、申请内容与买家诉求、商品行与数量、沟通记录、附件与凭证、处置流程状态、退款与退货关联、平台侧状态、责任判定。
- **输入**：`aftersales_id`；聚合子资源。
- **输出**：详情 + 操作入口 + 时间线。
- **关系**：上游 = 11.1.1.1；下游 = 11.2 退货、11.3 退款、11.4 纠纷。**详情页要把"买家说了什么"和"我们做了什么"按时间线对齐**，这是纠纷举证的基础。

### 11.1.1.3 售后受理

- **职责**：受理平台或内部发起的售后请求：判定是否在售后期内、是否符合条件、指定责任人与处理方案、设置回复时限。
- **输入**：售后申请（平台消息/买家消息/内部录入）；售后政策配置（期限、条件、必退情形）。
- **输出**：售后单（待处理）；政策判定结果；责任人分配。
- **关系**：上游 = 15 客户与客服、2 平台消息；下游 = 11.2/11.3。**必退情形（平台强制、收到即退）要自动判定**，人工不能为了业绩拖着不退导致平台判责。

### 11.1.2.1 原因分类

- **职责**：维护售后原因分类树（质量问题、描述不符、尺寸不符、物流损坏、买家原因、误购、欺诈退货），支持多选与平台原因码映射，驱动后续的质量归因分析。
- **输入**：原因分类维护；平台原因码映射（2.1.2.1）。
- **输出**：原因分类记录；报表用统一口径。
- **关系**：上游 = 2 平台映射；下游 = 11.5.2 质量分析、6 采购（供应商索赔）。**原因口径不统一会让退货率分析失真**——必须强制选择分类而不是留自由文本。

### 11.1.2.2 商品问题归因

- **职责**：把质量问题归因到具体环节（生产、运输、仓储、描述），支持批次追溯与照片比对，形成对供应商或流程的改进建议。
- **输入**：售后原因、批次信息、退回实物照片、质检结论。
- **输出**：归因结论 + 批次质量标记。
- **关系**：上游 = 7.3.1.1 批次、11.2.3.1；下游 = 6.4.2.2 索赔、6.1.1.3 评级。**批次归因是"同一个批次退回来 10 件"和"10 个批次各退 1 件"的区别**，前者是供应商责任，后者可能是运输或买家因素。

### 11.2.1.1 退货授权单

- **职责**：审批退货申请：确认可退数量（原订单行已退/已发数量约束）、退货地址、买家回寄物流、目标处理方式；部分退货需说明理由。
- **输入**：退货申请；原订单行可退量校验；审批决定。
- **输出**：退货授权单（授权/部分授权/拒绝）+ 拒绝理由。
- **关系**：上游 = 11.1.1.2；下游 = 11.2.1.2 退货指令。**授权不等于已收到**——授权后货可能在路上或根本没寄回，需要超时未寄自动关闭（实体目录 trade 段）。

### 11.2.1.2 退货指令下发

- **职责**：向买家发出退货指引（地址、要求、时限），生成退货标签，跟踪买家回寄物流。
- **输入**：退货授权；退货地址（3.6.3 或平台 RMA 地址）；渠道选择。
- **输出**：退货指令 + 标签文件 + 回寄物流轨迹跟踪。
- **关系**：上游 = 11.2.1.1；下游 = 10 物流（退货运单）、15 客服（通知买家）。**多数平台退货由买家寄回**，本系统只负责指引与跟踪，不控制实物。

### 11.2.2.1 退货入库

- **职责**：登记退回实物：扫码核对 SKU 与序列号、清点数量、拍照留证、判定外包装与商品状态。
- **输入**：退货实收登记（SKU、数量、批次/序列号、照片）；退货授权单。
- **输出**：退货实收记录 + 关联授权行分配；待检库存入库分录（**不是可售**）。
- **关系**：上游 = 11.2.1.2；下游 = 11.2.2.2、11.2.3.1。**退回商品默认进待检状态**，这是硬规则——直接进可售会把残次品当新品卖出去。

### 11.2.2.2 实收分配

- **职责**：把实收退货分配到对应的退货授权行与原订单行，处理实收多于授权（按实际退回）、少收、超期退回等情况。
- **输入**：实收记录；授权行可收量；分配操作。
- **输出**：分配记录 + 超收/少收说明；订单行已退数量更新。
- **关系**：上游 = 11.2.2.1；下游 = 9 订单（已退数量）、11.2.3.3。**按收货事件去重分配**，同一批退货不重复记已收数量。

### 11.2.3.1 质检与判定

- **职责**：退回商品质检：外观、功能、配件完整性、是否可再销售；给出可再销售/残次/报废判定与残值估算。
- **输入**：待检退货；质检模板（按类目）；质检结果。
- **输出**：质检结论 + 残值金额 + 质量状态指令。
- **关系**：上游 = 11.2.2.1；下游 = 11.2.3.2、12 财务（残值处理）。**可再销售判定要保守**：包装破损但商品完好可判可再销售，缺少配件则应判残次。

### 11.2.3.2 转可售/残次/报废

- **职责**：按质检结论把退货转入对应状态：可再销售转可售库存、残次转残次库存（可用于清仓）、报废则核销并计入损耗。
- **输入**：质检结论；处置决定；`expected_version`。
- **输出**：库存状态变更分录；可售量更新；报废损耗记录。
- **关系**：上游 = 11.2.3.1；下游 = 7.1.1.3 可用量、5.4 调价（残次品清仓）、12 财务（损耗）。**报废是不可逆的**，需审批与原因，不能由客服随手处理。

### 11.2.3.3 供应商索赔

- **职责**：对质量原因退货向供应商发起索赔：关联批次与责任判定、索赔金额、协商记录、赔付与冲减应付处理。
- **输入**：质检结论与责任判定；索赔金额；协商记录。
- **输出**：索赔单 + 冲减应付或退款记录。
- **关系**：上游 = 11.1.2.2、11.2.3.1；下游 = 12 财务（冲减应付）、6.5.1 对账。**索赔不是自动到账**，系统只跟踪流程与金额，冲减应付需财务确认。

### 11.3.1.1 退款申请

- **职责**：发起退款：选择退款方式（原路/平台/余额）、金额（可部分）、原因，校验累计退款不超过可退余额，提交审批后交财务执行。
- **输入**：退款申请；可退余额校验（已退 + 在途）；审批规则。
- **输出**：退款申请单（待审/已批/执行中/成功/失败）+ 可退余额更新。
- **关系**：上游 = 11.1.1.2、11.2.1.1；下游 = 12.3 收付款执行。**可退余额校验必须在服务端做**——重复提交退款是资损事故的高发点。

### 11.3.1.2 退款状态

- **职责**：跟踪退款执行状态与平台同步状态，处理退款失败、外部超时（先查证交易再重试，禁止重复支付）、平台退款与系统退款不一致的差异。
- **输入**：12 财务的执行结果回报；平台侧退款查询。
- **输出**：退款状态 + 失败原因 + 重试/人工处理建议 + 差异清单。
- **关系**：上游 = 12 财务；下游 = 15 客服（通知买家）、9 订单（订单退款状态）。**外部退款超时不等于失败**，重复发起退款会造成实质资损。

### 11.3.2.1 换货授权

- **职责**：批准换货：确认可换数量与库存（要真实预占替换货）、生成新出库安排，保留原单追溯关系。
- **输入**：换货申请；替换商品选择；库存可用性；`expected_version`。
- **输出**：换货授权 + 新发货需求 + 替换货预占。
- **关系**：上游 = 11.1.1.2；下游 = 9.3.3.1 新出库、11.2 退回旧货。**换货必须同时预占替换货并等待旧货回寄**，否则会出现只发不收的损失。

### 11.3.2.2 换货新单

- **职责**：建立换货关联（原售后 ↔ 新销售单/发货单），跟踪换货闭环状态，防止重复换货。
- **输入**：换货授权；新单创建请求。
- **输出**：换货关联记录（`exchange_order_link`）+ 新单状态跟踪。
- **关系**：上游 = 11.3.2.1；下游 = 9 订单、8 出库。**换货新单不修改原出库事实**，原单保持完整可追溯。

### 11.4.1.1 纠纷列表

- **职责**：管理平台纠纷/争议（Amazon A-to-Z、eBay 争议、速卖通纠纷）：类型、金额、平台时限、举证要求、我方立场、结果记录。
- **输入**：平台纠纷事件/同步；责任判定；举证材料。
- **输出**：纠纷单 + 时效倒计时 + 举证清单。
- **关系**：上游 = 2 平台同步、15 客服；下游 = 11.4.1.2 申诉、12 财务（争议金额影响结算）。**平台纠纷有严格举证时限**，超期自动判败，是硬性时效要求。

### 11.4.1.2 证据与申诉

- **职责**：组织举证材料（物流签收、沟通记录、商品照片、检测报告）打包提交申诉，记录平台回复与结果。
- **输入**：举证材料；申诉文本（可用模板）；提交动作。
- **输出**：申诉提交记录 + 平台回复 + 结果（胜诉/败诉/部分）。
- **关系**：上游 = 11.4.1.1；下游 = 2 平台接口、16 合规（账号绩效）。**举证材料必须来自系统记录**（轨迹、沟通日志），临时拼凑的证据在申诉中往往不被采信。

### 11.4.2.1 工单管理

- **职责**：管理非售后类的客户服务工单：咨询、投诉、催单、平台政策咨询；支持分配、SLA 计时、转派、关闭与满意度评价。
- **输入**：工单创建（人工/来自消息/自动触发）；SLA 规则；分配规则。
- **输出**：工单（待处理/处理中/待买家/已关闭）+ SLA 达成统计。
- **关系**：上游 = 15 客户与客服；下游 = 各业务模块（需转单处理）。**工单与售后单要能互转**：咨询升级为投诉、投诉升级为纠纷，需要保留上下文。

### 11.4.2.2 知识库与话术

- **职责**：维护客服知识库与回复模板：常见问题标准答法、平台政策说明、退换货话术、多语言版本；记录使用效果。
- **输入**：模板与知识条目；多语言版本；使用统计。
- **输出**：话术库 + 客服一键引用；命中率统计。
- **关系**：上游 = 3.4.2.2 文案资产；下游 = 15 客服消息发送。**话术需与平台规则版本挂钩**，平台政策变化时能定位哪些话术需要更新。

### 11.5.1.1 退货分析

- **职责**：统计退货情况：退货率（按店铺/SKU/类目/原因/批次）、退货金额趋势、拒退率、处理时效、平均退款金额与原因分布。
- **输入**：售后与退货数据；销售数据。
- **输出**：退货分析报表 + 维度下钻 + 异常识别。
- **关系**：上游 = 11.1、11.2、11.3；下游 = 13 分析、6 采购（质量改进）。**退货率必须与销售额同口径比较**，只看绝对数会误判（退货率从 3% 升到 5% 严重，但绝对数可能没变）。

### 11.5.2.1 质量分析

- **职责**：质量问题专项分析：缺陷类型分布、批次质量趋势、供应商质量对比、缺陷照片聚类、支持开箱率与质量成本估算。
- **输入**：质检结论与退货原因；供应商与批次维度。
- **输出**：质量报表 + 责任分布 + 改进清单。
- **关系**：上游 = 11.1.2.2、11.2.3.1；下游 = 6.1.1.3 评级、13 分析。**质量成本（退货物流 + 损耗 + 差评影响）应量化**，否则改进动力不足。
