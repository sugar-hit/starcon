# 02 渠道与店铺系统

> **定位**：starcon 与外部电商平台之间的**唯一边界**。所有跨平台数据都从这里进、从这里出；其他系统不直接调平台 API。
> **后端归属**：`channel` 服务（唯一拥有 `platform` `marketplace` `channel_connection` `shop` `listing` `sync_cursor` `webhook_receipt` `platform_operation`）。
> **前端入口**：`/channels`

## 边界

**做**：平台目录与能力矩阵、OAuth 授权与凭据管理、店铺与站点档案、同步任务与游标、同步失败处理、平台回写任务、Webhook 接收。

**不做**：不直接写 `trade` 订单或 `warehouse` 库存。渠道只负责"把平台的事实如实接进来、把内部的动作如实发出去"，业务规则判定属于 trade/warehouse。

**关键约束**：

- 库里**不存明文 token**，只存密钥管理器引用
- Webhook **不信任请求中的租户标识**，由 `shop` 反查租户
- 同步失败必须可续传、可重放，**只有处理提交后才推进游标**
- 平台返回**未知结果**（超时）时先查证再重试，不当作失败

## 详细设计

### 2.1.1.1 平台目录

- **职责**：列出 starcon 支持的全部平台（Amazon、Shopify、eBay、TikTok Shop、Temu、Walmart、Shopee、Lazada、Mercado Libre、AliExpress、Wish、Etsy、Wayfair 等），标注每个平台的接入类型（官方 API / 第三方 ISV / 中介服务）与支持状态（可用/灰度/规划中）。
- **输入**：平台注册表（`platform`，全局码表，非租户数据）；用户租户。
- **输出**：平台卡片/列表（平台名、支持店铺模式、授权入口、支持的能力图标）；点击进入授权向导或连接列表。
- **关系**：上游 = 平台注册表（发布时随代码/配置更新）；下游 = 2.2.1.2 授权向导。**平台注册表是全局共享只读数据，不带 tenant_id**，但不可直接全表暴露给普通请求（见实体目录 §4）。

### 2.1.1.2 平台能力矩阵

- **职责**：一张表说明"哪个平台支持哪些能力"，避免用户建了流程才发现平台不支持。例如：是否支持多渠道配送、是否支持库存回写、是否支持自发退货单、是否支持面单打印、是否支持延迟结算对账。
- **输入**：平台注册表的 `capabilities` 声明；平台适配器代码中的实际实现状态。
- **输出**：能力矩阵（行=平台，列=能力，单元格=支持/不支持/受限+原因）；被引用于功能禁用提示。
- **关系**：上游 = 平台适配器；下游 = 09 订单、07 库存、10 物流、11 售后的**功能可用性判断**。共享数据：`platform.capabilities`。**这是跨系统的隐性依赖**：某平台不支持的能力，对应功能的按钮在别处也要禁用，而不是点了才报错。

### 2.1.1.3 站点与国家参数

- **职责**：维护平台-站点-国家-默认币种-默认时区-语言的映射，以及站点级特殊规则（是否需申报 VAT、默认海关编码、货币小数位）。
- **输入**：平台站点注册表；运营维护的站点参数（币种、时区、税号规则）。
- **输出**：站点参数查询接口；供 05 定价、12 财务、16 合规引用。
- **关系**：上游 = 平台注册表 + 运营配置；下游 = 05 定价（默认币种）、12 财务（本位币/汇率）、16 合规（申报要求）。**站点参数是全局码表，不随租户变化**；租户级覆盖在对应业务对象上做。

### 2.1.2.1 平台枚举映射

- **职责**：维护平台特有枚举到 starcon 内部枚举的映射（如平台订单状态 → 内部订单状态、平台退货原因码 → 内部原因分类、平台物流状态 → 内部轨迹状态）。
- **输入**：平台枚举定义；租户级自定义映射（如某租户要把"平台 A 的 canceled"归到内部"用户取消"）。
- **输出**：映射表；同步与解析时按"平台默认 + 租户覆盖"生效。
- **关系**：上游 = 平台适配器；下游 = 09 订单状态机、11 售后原因、10 轨迹状态。**映射缺失必须显式报"未映射"**，不能默认落到某个兜底状态——否则状态机被污染。

### 2.2.1.1 连接列表

- **职责**：展示租户下所有平台授权连接：平台、授权账号、店铺数、授权时间、到期时间、健康状态、最近同步时间。
- **输入**：用户请求 + 数据范围；`channel_connection` 记录。
- **输出**：连接列表与状态标签（正常/即将到期/已失效/被限流）；批量操作（重新授权、断开、暂停同步）。
- **关系**：上游 = 2.1.1.1 平台目录；下游 = 2.2.1.2 授权向导、2.4.1.1 同步任务。共享数据：`channel_connection`、`credential_ref`。**断开连接不删除历史数据**，历史订单仍可查。

### 2.2.1.2 授权向导

- **职责**：引导用户完成平台 OAuth 授权，全过程分步展示（选平台 → 选账号 → 授权跳转 → 回调校验 → 确认店铺范围 → 完成）。授权失败给出可执行的原因（凭据错、权限不足、店铺已被其他租户绑定）。
- **输入**：用户操作；平台 OAuth 跳转参数；回调携带的授权码/令牌；`idempotency_key`。
- **输出**：`channel_connection` + `credential_ref`（密钥管理器写入令牌）+ 自动创建/确认 `shop` 记录；跳转到 2.3 店铺配置。
- **关系**：上游 = 平台注册表；下游 = 2.3.1 店铺档案。**授权回调的租户由连接中的平台账号与授权码绑定关系确定，不采信请求头**；同一平台账号只能绑定一个租户，冲突时明确报错。

### 2.2.1.3 凭据引用管理

- **职责**：管理平台令牌的存储位置与轮换，只暴露"是否存在、有效期、权限范围"，绝不回显明文。
- **输入**：授权流程写入的令牌；轮换操作；`credential_ref`。
- **输出**：凭据元信息（类型、创建时间、到期、权限范围）；轮换任务记录。
- **关系**：上游 = 2.2.1.2；下游 = 全部平台 API 调用。**令牌明文只在内存中短暂存在并直接写密钥管理器**，数据库仅存引用；日志与审计事件中一律脱敏。

### 2.2.2.1 健康诊断

- **职责**：一屏判断"现在能不能正常同步"：连接状态、令牌剩余有效期、API 配额使用率、最近调用失败率、限流命中、字段级权限是否缺失。
- **输入**：API 调用的埋点指标；令牌元信息；平台配额查询结果。
- **输出**：诊断卡片（绿色正常/黄色限流/红色失效）+ 具体处置建议；一键执行重新授权或配额等待。
- **关系**：上游 = 2.4.1.2 运行日志；下游 = 2.2.1.2 授权向导。**这是跨境 ERP 最高频的运维入口**，缺失字段权限（如只读权限无法改库存）要能提前显性化。

### 2.2.2.2 重新授权提醒

- **职责**：令牌临近到期时提前提醒用户操作，避免同步突然中断导致订单漏抓。
- **输入**：令牌到期时间；提醒提前量配置（默认 7/3/1 天）。
- **输出**：提醒通知 → 1.3 工作台待办 + 1.3.1 站内通知；跳转重新授权。
- **关系**：上游 = 2.2.1.3；下游 = 01 通知。**部分平台（如 Shopee）令牌有效期短且需定期刷新**，提醒阈值需按平台差异化。

### 2.3.1.1 店铺列表

- **职责**：展示租户下全部店铺：所属平台、站点、法人、负责人、经营模式、启用站点数、商品数、近 7 日销售额。
- **输入**：用户请求 + 数据范围；`shop` + `shop_marketplace` + 业绩投影。
- **输出**：店铺列表/卡片；批量启用停用；跳转到 04 该店铺的刊登管理。
- **关系**：上游 = 2.2.1.2 授权；下游 = 04 刊登、09 订单、13 分析、17 数据范围。共享数据：`shop`、`legal_entity`（店铺绑定法人是财务记账与货权的前提）。

### 2.3.1.2 店铺详情

- **职责**：单店铺档案页：基本信息、启用站点、平台店铺 ID、关联库存策略、关联价格表、负责人、最近同步与异常概览。
- **输入**：店铺 ID；`shop` 投影的关联对象。
- **输出**：详情视图 + 各关联配置的快捷入口 + 变更历史。
- **关系**：上游 = 2.3.1.1；下游 = 05 价目、07 库存策略、17 权限。**店铺是权限与数据范围的关键维度之一**，删除店铺前必须检查是否仍被单据引用。

### 2.3.2.1 经营模式

- **职责**：标注店铺属于自发货（FBM）、全托管、半托管、海外仓模式或本土店，不同模式决定订单货权、成本构成、结算方式与可执行操作，直接影响 09/12/13 的计算口径。
- **输入**：用户在店铺详情的选择；平台可推断的默认模式。
- **输出**：店铺模式标记；供 09 订单履约策略、12 结算对账、13 利润报表按模式分组。
- **关系**：上游 = 2.3.1.2；下游 = 09 订单、12 财务、13 利润。**模式是成本核算的第一分叉点**，全托管与自发货的"利润"含义完全不同，必须在报表上明示分组。

### 2.3.2.2 负责人与数据范围

- **职责**：为店铺指定运营负责人，并把店铺绑定到 17 的角色数据范围上，实现"运营只能看到自己负责的店铺"。
- **输入**：负责人选择；数据范围配置（法人/店铺/仓库/部门）。
- **输出**：`role_assignment_scope` 记录；影响该成员在所有系统的可见范围。
- **关系**：上游 = 17 组织权限与系统设置；下游 = 全部系统的数据过滤。**店铺归属与权限范围是两件事**：负责人用于业绩归属与绩效，数据范围用于可见性，分别配置。

### 2.4.1.1 同步任务列表

- **职责**：展示全部同步任务（按连接+资源类型+站点），每条显示状态（待执行/执行中/成功/部分失败/失败）、最近运行时间、处理记录数、耗时、积压量。
- **输入**：任务注册表；调度器状态；`sync_run` 记录。
- **输出**：任务列表；手动触发同步；暂停/恢复；调整频率与优先级。
- **关系**：上游 = 2.2 连接、2.3 店铺；下游 = 2.4.1.2 运行日志、2.4.2.1 失败队列。**任务粒度为（连接, 站点, 资源类型）**，不允许整店一把梭——否则部分失败无法续传。

### 2.4.1.2 运行日志

- **职责**：单次同步运行的明细：拉取分页过程、写入/更新/跳过条数、耗时分布、警告与错误明细。
- **输入**：`sync_run` 与 `sync_failure`；用户选中某次运行。
- **输出**：运行时间线 + 分页进度 + 错误列表（可点开看原始载荷，已脱敏）。
- **关系**：上游 = 2.4.1.1；下游 = 2.4.2.2 人工重放。**日志保留期可配置**，超期只保留聚合统计。

### 2.4.1.3 断点续传

- **职责**：管理同步游标，支持查看/重置/回退游标，处理"漏了一小时数据"和"游标跑飞"两类事故。
- **输入**：用户对 `sync_cursor` 的调整操作（回退到指定时间、强制重置）；系统检测到的游标异常。
- **输出**：更新后的游标；重置后触发的时间窗补拉任务。
- **关系**：上游 = 2.4.1.1；下游 = 2.6.2.1 增量补拉。**游标只在处理提交后推进**；回退重拉必须幂等（按 `event_id`/外部单号去重），不允许产生重复订单。

### 2.4.2.1 失败队列

- **职责**：集中列出同步失败的记录（订单、商品、库存、结算各类型），支持按失败原因聚类（授权失效/字段解析失败/映射缺失/平台限流/网络异常）。
- **输入**：`sync_failure`；失败原因分类。
- **输出**：失败清单 + 原因分布图；跳转到 2.4.2.2 重放或 2.4.2.3 处理映射缺失。
- **关系**：上游 = 2.4.1.1；下游 = 2.4.2.2、2.2.2.1 健康诊断。**"授权失效"类失败要自动升级为工作台待办**，因为它会导致持续漏单。

### 2.4.2.2 人工重放

- **职责**：对失败记录手工触发重新处理，支持单条、批量、按失败原因批量重放。
- **输入**：用户选择失败记录；重放范围与参数。
- **输出**：重放任务 + 结果（成功/仍失败及新原因）。
- **关系**：上游 = 2.4.2.1；下游 = 对应同步处理器。**重放必须幂等**：重复处理同一条外部记录不产生第二张订单/第二次扣减。

### 2.4.2.3 映射缺失队列

- **职责**：平台商品已同步但未映射到内部 SKU 的记录，等待人工建立映射或创建新 SKU。
- **输入**：`listing_variant` 无映射的记录；`listing_mapping_version` 的错误状态。
- **输出**：待映射清单（平台商品、变体、店铺、价格）；操作入口：映射到已有 SKU / 新建 SKU / 标记忽略。
- **关系**：上游 = 04 刊登与内容、09 订单（缺映射订单也进此队列）；下游 = 04 映射管理。**不按名称猜 SKU**；映射建立后回填受影响订单，历史订单冻结当时映射版本。

### 2.5.1.1 回写任务列表

- **职责**：展示所有发往平台的写操作（上架、改价、改库存、回传物流、取消订单）：目标店铺/站点、幂等键、状态、平台请求 ID、尝试次数。
- **输入**：内部业务事件触发的回写请求；`platform_operation`。
- **输出**：任务列表与状态（待发/已发/成功/失败/结果未知）；批量重试。
- **关系**：上游 = 04 刊登、07 库存（库存回写）、09 订单（发货回传）、10 物流；下游 = 平台 API。**每个回写任务必须带业务幂等键**，避免重试造成平台侧重复上架或重复扣减。

### 2.5.1.2 未知结果核验

- **职责**：处理"请求已发出但没收到明确结果"的情况——先查询平台实际状态，再决定重发还是标记成功，避免重复下单、重复扣库存。
- **输入**：超时或网络中断的回写任务；平台查询接口。
- **输出**：核验结论（实际已成功/实际未执行/仍不确定）+ 后续动作建议。
- **关系**：上游 = 2.5.1.1；下游 = 平台查询 API、2.4 同步（拉回平台真实状态）。**这是跨境 ERP 最容易造成资损的地方**：不核验直接重试会导致平台重复发货或库存错扣。

### 2.5.2.1 常用回写操作

- **职责**：提供高频回写的快捷入口与批量操作（批量改库存、批量改价、批量下架、批量回传物流），支持按店铺与筛选条件批量执行。
- **输入**：用户勾选的记录范围；操作参数（库存数量/价格/物流单号）。
- **输出**：生成 N 条独立回写任务，逐条记录结果，部分失败不影响其余。
- **关系**：上游 = 04、07、09、10；下游 = 2.5.1.1。**批量操作不等于事务**：每条独立成败、部分失败要如实回报，不能因一条失败回滚全部（跨服务无全局事务）。

### 2.6.1.1 接收记录

- **职责**：记录平台推送的每条 webhook：签名校验结果、外部事件 ID、来源店铺、接收时间、处理状态。
- **输入**：平台 HTTP 回调（原始报文）；平台公钥/密钥验签。
- **输出**：接收记录 + 处理状态（已入库/重复/验签失败/处理中）。
- **关系**：上游 = 平台；下游 = 2.6.1.2 去重视图、对应业务服务。**先持久化再处理**：接收成功即落库返回 200，业务处理异步化，避免平台超时重推造成压力。

### 2.6.1.2 去重视图

- **职责**：以 `event_id` 为准识别重复推送，展示同一业务事件被平台重推的次数与处理结果，保证只处理一次。
- **输入**：重复的 webhook 接收记录。
- **输出**：去重命中记录 + 首次处理结果引用。
- **关系**：上游 = 2.6.1.1；下游 = 业务服务消费（按 `event_id` 去重）。**重复事件不产生第二条业务记录**，这是"重复 webhook 不产生重复订单"的实现基础。

### 2.6.2.1 增量补拉

- **职责**：webhook 漏推、平台故障恢复或发现时间窗缺口时，按增量接口主动补拉订单、商品、库存、结算等资源，填补缺失区间；支持按连接 + 站点 + 资源类型 + 时间窗发起，并识别平台接口的分页上限与限频。
- **输入**：补拉触发（漏推检测、游标回退、人工发起）；时间窗；平台增量接口返回；`idempotency_key`。
- **输出**：补拉任务与处理记录（拉取条数、新增/更新/去重条数、耗时、失败原因）；推进后的游标；缺口填补结果统计。
- **关系**：上游 = 2.4.1.3 断点续传、2.6.1.1 接收记录；下游 = 对应同步处理器（09 订单、04 刊登、12 结算）。**补拉必须幂等**——同一条外部记录被补拉多次不得产生第二张订单或第二次扣减；平台若只提供"最近 N 条"而非按时间增量，必须分段轮询并靠去重兜底，此时要在页面上标明"补拉可能延迟发现"。
